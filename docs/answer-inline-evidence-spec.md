# Agent 问答行内证据引用与 Markdown 渲染 Spec

日期：2026-10-30

状态：行内引用产品行为已确认；Markdown 渲染为用户追加需求，具体支持范围与技术方案为本 Spec 的实施建议。测试入口已由用户确认。本文仅形成仓库文档，不创建 GitHub Issue，不代表已实施。

## Problem Statement

当前聊天正文没有 Markdown 渲染，标题、列表、强调和表格等格式无法正常呈现。当前 Agent 答案以整段文字展示，末尾统一列出“核查原视频证据”按钮。用户无法确定某句话、某个判断或某段综合回答具体依据哪些原始观察证据。

当前生成结果只包含全文与证据集合，公开结果通过范围回执传递证据，后端再保存消息及引用。没有句子与证据的映射，不能靠前端调整按钮位置或依据证据列表顺序解决。

## Solution

由 Agent 生成有序 Markdown 源文本片段及其证据关联，随答案持久保存。前端将完整正文作为一个 Markdown 文档解析，在对应语义片段后显示可点击的引用编号。用户消息和助手消息共用正文渲染能力，输入框仍编辑原始 Markdown 文本。

示例：主角进入房间后看向窗外〔1〕，随后拿起桌上的信封〔2〕。他可能正在准备出门〔2〕〔3〕。

- 默认按可独立核验的语义片段关联证据，不机械要求每句话都有引用。
- 同一句涉及不同依据时分别标注；只有整段共同依据同一组证据时才在段尾统一标注。
- 同一处可引用多条证据，每条证据有独立按钮；同一答案内重复引用同一证据复用编号。
- 引用表示回答依据，不额外增加“事实”“推断”标签。原有表达中的不确定性措辞可以自然保留。
- 点击编号直接定位播放对应素材，沿用现有证据查看能力。
- 新答案使用行内引用；缺少映射的历史答案继续显示原有尾部按钮，不自动补造映射。

## User Stories

1. 作为阅读视频问答的用户，我希望在具体判断后看到引用，以便知道判断依据。
2. 作为阅读复合句的用户，我希望不同语义片段分别关联证据，以便不把一条证据误认为整句的依据。
3. 作为阅读综合结论的用户，我希望一处可以引用多条证据，以便核查完整依据。
4. 作为阅读段落的用户，我希望共用依据的整段只在末尾标注，以便保持阅读连贯。
5. 作为阅读答案的用户，我希望同一证据重复出现时编号一致，以便识别复用的依据。
6. 作为核查答案的用户，我希望点击任意编号直接打开对应原视频时间位置，以便快速回看。
7. 作为核查跨素材回答的用户，我希望引用打开其实际所属素材，以便不会在当前视频中跳错位置。
8. 作为阅读综合分析的用户，我希望引用说明依据而不强制增加事实或推断标签，以便保持自然表达。
9. 作为返回制作会话的用户，我希望刷新后引用位置和编号保持一致，以便继续核查。
10. 作为浏览历史消息的用户，我希望旧答案仍可通过原有按钮回看证据，以便保留已有能力。
11. 作为阅读证据不足回答的用户，我希望 Agent 如实说明无法确认而不伪造引用，以便了解回答边界。
12. 作为键盘操作的用户，我希望引用可聚焦并激活，且有可理解的名称，以便核查证据。
13. 作为阅读长答案的用户，我希望行内引用不会再在尾部重复堆叠，以便避免无意义重复。
14. 作为制作会话的用户，我希望剪辑草稿、方案版本等其他引用仍保持原有交互，以便继续视频制作。
15. 作为阅读聊天内容的用户，我希望标题、强调、列表、引用块和表格正常排版，以便理解长答案。
16. 作为输入消息的用户，我希望自己提交的 Markdown 也能渲染，以便清楚表达结构化问题。
17. 作为阅读代码或原文的用户，我希望行内代码和围栏代码块保留字面内容，以便避免符号被错误解释。
18. 作为核查结构化答案的用户，我希望列表项、表格单元格和加粗文字中的引用仍对应原句，以便格式变化不破坏证据关系。
19. 作为阅读历史聊天的用户，我希望历史正文也获得 Markdown 排版，同时保留旧证据按钮，以便无需重新生成答案。
20. 作为阅读外部内容的用户，我希望消息不能执行脚本或自动加载外部图片，以便安全地阅读模型和用户提供的文字。

## Implementation Decisions

### 1. 生成结构与唯一正文

建议使用有序答案片段，每个片段携带文字及零到多项证据 ID。一个片段对应连续 Markdown 源文本，其关联证据适用于该片段表达的语义内容；无须引用的过渡文字可以使用空列表。换行保留在片段文字中。

模型为新问答生成片段，不同时独立生成另一份全文。运行时按顺序原样拼接 Markdown 源文本形成现有 content，继续供聊天历史和模型上下文等消费者使用。编号由首次出现顺序确定，从 1 开始，作用域为单条答案；不由模型输出编号。

选择片段而非字符偏移，避免跨 Python、Java、JavaScript 的中文、emoji 字符计数差异；选择结构化关联而非模型生成的正文字符串标记，避免普通文本中的编号被错误识别为引用。Markdown 与引用共享完整文档解析过程，具体规则见下节。

### 2. 证据授权与边界校验

保留当前问答范围快照、已读工具回执、项目归属与分析版本约束。片段引用的证据必须属于该次执行成功读取且合法的证据；不能因展示需求放宽权限。

运行时从片段引用汇总去重后的证据集合，供现有回执链路使用。回执顺序不承担文本映射职责。片段到证据的关联必须显式传递，不能从集合排序恢复。

在模型输出和跨服务结果接收边界校验结构与证据关联。新格式中的缺失证据、越界证据或正文不一致必须显式拒绝，沿用现有错误处理路径，不静默删除引用，也不把错误新结果伪装成旧格式。内部不重复添加无依据的防御校验。

合法性校验只证明证据存在且允许引用，不证明该证据在语义上支持句子。

### 3. 公共结果、消息持久化与恢复

扩展 Agent 问答结果、worker 公共结果、Java 接收契约以及消息快照，使有序片段和证据关联完整到达浏览器。后端将证据关联解析为具有范围信息的 EVIDENCE 引用，前端不得自行猜测 scopeId。

建议为助手消息增加可空的结构化答案片段 JSON 数据，并由消息快照返回。历史行保持空值；不要通过重算全文生成历史映射。content 与片段由同一个已验证结果写入，同一事务中保存，消息完成后才对外发布。

遵守已接受的“持久接纳对话轮次并独立订阅公开事件”架构决策：数据库业务消息为恢复来源，checkpoint 不替代聊天历史。刷新、会话重开和事件触发的快照重载均读取持久化映射。

片段字段缺失或为空值表示历史格式；有效的新格式必须包含有序文本，即使全部片段都没有证据。这样可以区分“新答案没有证据”和“旧答案没有映射”。

实施时同步修改跨语言契约、结果校验、严格字段解析与相关测试样例；上线先具备新格式接收和读取能力，再启用新格式生成，避免运行中的旧任务丢失结果。新生产者不得把缺失片段作为常规输出。

### 4. 前端展示与播放

新格式将片段拼接为完整 Markdown 文档，在其语义片段边界显示〔1〕〔2〕等独立按钮。引用编号按照证据身份去重并在每条答案内按首次出现顺序稳定分配。证据身份包含范围和证据 ID。

不执行用户或模型提供的原始 HTML，不新增富文本编辑器。按钮支持键盘操作和可访问名称，例如“查看证据 1”。Markdown 的换行、链接和安全策略见下节。

新格式不再重复显示尾部 EVIDENCE 列表；非证据类型的引用继续沿用原有展示。历史格式改为 Markdown 正文加原有尾部证据按钮；只改变正文排版，不补造历史引用映射。

点击按钮复用现有 evidence context 查询及播放授权流程：语音证据定位开始时间，画面证据定位观察时刻。不开新证据面板，不新增片段自动停止播放规则。查询或播放失败沿用现有可见错误反馈，不跳转其他证据掩盖失败。

### 5. 作用范围

首版覆盖 Agent 视频问答最终答案及其历史展示，包括跨素材证据的综合回答。不扩展到剪辑草稿的片段依据、方案版本引用、预览结果或进度事件。

### 6. Markdown 支持范围及引用组合

首版支持标题、段落、加粗、斜体、删除线、有序／无序列表、嵌套列表、引用块、行内代码、围栏代码块、分隔线、普通链接与表格。以 CommonMark 基础语法加表格、删除线扩展作为目标范围；不把完整 GFM 功能集作为默认承诺。聊天中的普通单换行保留为可见换行，空行分段；此规则固定配置，避免新旧答案表现不同。

用户与助手的聊天正文，包括历史消息，统一使用同一 Markdown 渲染组件。没有 Markdown 语法的文字保持正常可读；历史文字中原本只是字面符号的 Markdown 可能被重新解释，这是本次渲染升级的明确取舍。制作草稿卡片和预览卡片保持原有专用组件，其作为聊天正文显示的介绍文字使用统一渲染器。

必须对整篇文档做一次解析，不能将各片段分别解析后拼接 HTML。选用能保留源位置或扩展 token 的解析器，将片段边界转换成内部引用节点，再由 Vue 渲染文字、允许的 Markdown 节点与引用按钮。内部引用节点来自结构化绑定；用户输入的〔1〕、模型写出的编号、链接文字均不能自行获得证据按钮能力。

片段可以跨 Markdown 行内样式边界，但携带证据的片段必须结束在可插入引用的可见文字边界：位于完整行内结构之后、行末换行或表格单元格分隔符之前。例如加粗结论的引用出现在闭合加粗标记之后；列表项和表格单元格中的引用必须留在该列表项或单元格内。引用不允许插入代码块、行内代码、链接地址或 Markdown 控制语法内部。模型需要为代码示例补充带引用的解释文字。无效引用边界在结果接收边界明确拒绝，不能悄悄把引用挪到整篇答案末尾。

解析器由前端实现时选定并锁定依赖版本；当前没有 Markdown 依赖，需新增解析依赖及锁文件更新。采用 Markdown token 到 Vue 节点的受控渲染，不直接注入未经清理的 HTML。普通原始 HTML 按文字显示；普通链接只允许 http、https、mailto 与页内锚点，拒绝脚本、data 与本地文件协议。外部链接新窗口打开时隔离 opener。图片语法仅显示替代文字，不自动发起图片请求。数学公式、Mermaid、语法高亮、任务列表交互和远程嵌入不在首版范围。

正文容器改为可承载块级结构的元素，避免在 p 内嵌套标题、列表或表格。为标题、段落、列表、引用块、表格和代码块提供聊天局部样式；代码和宽表格局部横向滚动，不能撑破聊天栏。不要对整个 Markdown 容器沿用纯文本 pre-wrap 样式。

### 7. 具体数据模型

以下是目标字段契约，不是现有已实现接口。字段名采用公开 JSON 的 camelCase；Python 内部沿用 snake_case。使用字段表表达模型，不引入持久化 Markdown AST。

| 层次／模型 | 字段 | 类型与约束 | 用途 |
| --- | --- | --- | --- |
| 模型输出 AnswerSegment | text | 非空字符串，允许换行及 Markdown 源语法 | 按顺序组成唯一正文 |
| 模型输出 AnswerSegment | evidenceIds | 证据 ID 列表，允许空列表，片段内不重复 | 该片段对应的已读证据 |
| ANSWER 动作 | answerSegments | 非空 AnswerSegment 列表 | 新生成问答的正文来源 |
| 运行时 outcome | content | 原样拼接全部 text，沿用现有全文长度上限 | 兼容既有正文消费者 |
| 运行时 outcome | evidence_ids | 从片段收集的去重集合 | 沿用证据合法性与回执处理 |
| 运行时 outcome | answer_segments | 保留原始片段及顺序 | 不因证据集合排序丢失关联 |
| 公共 RunResult | answerSegments | AnswerSegment 列表或 null | 新 ANSWER 必须提供；其他结果与兼容旧生产者可为空 |
| 公共 RunResult | content、scopeReceipts | 保留原字段及原约束 | content 必须与片段拼接一致，片段证据必须能由回执证明 |
| 持久消息 MessageSegment | text | 同一段 Markdown 源文本 | 保存显示原文 |
| 持久消息 MessageSegment | evidenceRefs | EvidenceRef 列表，可为空 | 后端完成范围绑定后存储 |
| EvidenceRef | type、id、scopeId | type 固定 EVIDENCE；id 与 scopeId 为合法 ID | 复用现有证据查看语义，身份为 scopeId + id |
| 消息快照 Message | answerSegments | MessageSegment 列表或 null | 浏览器恢复正文及引用位置 |
| 消息快照 Message | content、references | 保留现有字段 | references 仍保留去重证据及其他类型引用，避免破坏已有消费者 |
| 数据库 conversation_messages | answer_segments_json | 新增可空 JSONB 列，无默认空数组 | 旧记录为 NULL，新问答存储 MessageSegment 列表 |

正文总长沿用当前 16000 字符约束；不为每个片段创建独立消息或独立证据表。无需新增引用编号列，编号由每条消息内 evidenceRefs 首次出现顺序计算。没有证据的新答案使用至少一个 evidenceRefs 为空的片段；空列表不代表历史格式。

模型侧只返回证据 ID，范围身份由 Java 根据该次运行已验证的 scopeReceipts 绑定。当前一次运行绑定一个问答范围快照，不新增跨范围引用能力。原有 references 用于兼容读取；它与片段中的证据引用由同一结果派生，不能成为两份人工维护的数据。

不另增 contentFormat：本次约定聊天 content 统一按 Markdown 源文本解释；answerSegments 是否为 null 只区分引用映射能力，不区分 Markdown 支持。展示、复制源文和模型历史仍有原始 content 可用。

RunResult 目前 schemaVersion 为 1.0 且两端严格限制；实施建议保持该版本下的可空字段扩展，并同步升级消费者后再启用生产者。需要检查实际反序列化是否允许未知字段，不能宣称未升级的 Java 能接收新字段。若部署要求新旧服务长期混跑，则需另行设计版本协商，不在本次最小实现内。

### 8. 相比原实现的变更位置与规模

规模为相对估算：小＝局部字段／样式传递；中＝单模块行为及契约调整；大＝跨层闭环。不是代码行数或工期承诺。以下按职责和代码符号定位，避免将文档绑定到易变的文件行号。

| 改动位置／现有符号 | 原实现 | 目标变更 | 规模 |
| --- | --- | --- | --- |
| Agent prompts 与 Action | content 加整篇 evidence_ids | 指导生成 Markdown 片段及局部证据绑定，更新输出 schema | 中 |
| Agent check_result／运行时 outcome | 校验证据集合并返回全文 | 从片段派生全文和证据集合，保留绑定，复用已有证据校验 | 中 |
| Python conversation contracts／worker RunResult | content + scopeReceipts，证据集合排序 | 新增 answerSegments 并跨 worker 传递；排序仅用于回执 | 中 |
| Java AgentRunContracts.RunResult | 固定字段及结果形状校验 | 增加可空片段模型，校验正文一致性及绑定约束 | 中 |
| Java AgentRunResults | 将回执转为整篇 EVIDENCE references | 校验证据后逐片段绑定 scopeId，保存引用映射 | 中 |
| AgentRuns.append 及消息数据库迁移 | 写入 content、references_json | 增加可空 JSONB 数据及写入参数；其他消息生产者保持 null | 小至中 |
| ConversationController.snapshot | 查询并返回 content、references | 查询返回 answerSegments；空值序列化要兼容当前响应构造方式 | 小 |
| 消息公开事件／数据库事件触发器 | payload 带正文及 references，前端事件后重载快照 | 核对所有消息消费者；事件仍只作刷新通知时不必重复携带片段，禁止用不完整事件覆盖快照 | 小，取决于消费者核查 |
| ConversationPanel 的 Message／Citation 类型 | 无片段字段，Citation 未声明 scopeId | 增加片段和证据范围类型，沿用现有 inspect 播放流程 | 小 |
| ConversationPanel 正文与引用渲染 | p 中纯文本插值，尾部证据按钮 | 接入统一 Markdown 正文组件，按结构化关联插入按钮，旧消息保留尾部证据 | 中 |
| 新增正文渲染组件及依赖 | 无 Markdown 解析库 | 整篇解析、边界到引用节点转换、安全节点渲染、布局样式 | 中；前端主要工作量 |
| 聊天中历史草稿正文等文字入口 | 可能各自使用纯文本 p | 复用正文渲染器，专用草稿／预览组件不重写 | 小 |
| 现有端到端与边界契约测试 | 仅验证存在 references 或全文 | 验证句子映射、刷新、点击定位、Markdown 组合及非法输入 | 中 |

总体属于中等偏大的跨层改动：Markdown 单独看主要集中于前端，而可靠的行内证据引用必须贯穿生成、Python 公共契约、Java 校验、数据库和快照，不能仅改前端。预计新增一个正文组件、一项迁移，修改上述现有模块及对应测试；不新增服务、路由体系、消息队列或证据存储系统。实际文件数量与工期须以实施差异为准。

推进顺序按用户要求调整为：第一阶段独立交付聊天 Markdown 渲染；第二阶段贯通引用数据契约、保存和读取；第三阶段交付行内引用展示与播放；第四阶段启用 Agent 结构化生成并完成闭环验收。各阶段具体门槛见下文。

## Testing Decisions

已确认的测试入口：优先复用现有制作会话端到端入口，以用户可观察行为验证“结果接收、持久化、快照读取、展示、点击播放”。用户已确认采用此方案，仅对非法证据绑定补充必要的边界契约测试。

现有测试先例包括 conversation 生命周期浏览器测试、conversations 问答测试、vision 证据测试，以及 Python conversation contracts、worker、Java executor 测试。选择当前有效执行链路扩展，不把历史退役入口作为验收依据。

自动化以受控模型输出和已有素材证据复用为主。只对非法证据绑定、正文不一致和非法引用位置补充必要边界契约测试；Markdown 安全与排版行为优先在同一浏览器测试入口验证。不得仅使用 HTML 快照代替实际点击及播放定位验证。仅在高层测试难以明确覆盖非法输入拒绝时补充契约断言，不为编号循环或组件内部实现单独构造测试体系。

| 验收场景 | 外部可观察结果 |
| --- | --- |
| 两个语义片段使用不同证据 | 各自后方出现正确编号，点击分别定位对应证据 |
| 一个结论使用多条证据 | 每条证据可独立点击，均能打开正确素材位置 |
| 后文再次引用已有证据 | 编号复用，不按回执列表顺序变化 |
| 整段共同依据相同证据 | 引用在段尾，未在每句重复添加 |
| 中文、emoji、重复句子与换行 | 文本完整，关联位置不因字符计数或字符串匹配漂移 |
| 保存后刷新或重开会话 | 正文、关联、编号及播放位置保持一致 |
| 历史答案没有结构化映射 | Markdown 正文正常显示，仍显示原有尾部按钮且可使用 |
| 新格式中没有可引用证据 | 正文正常显示，没有伪造编号或空按钮 |
| 引用未读、错误范围或其他项目证据 | 结果明确拒绝，不发布错误关联的成功答案 |
| 结果全文与片段文字不一致 | 边界拒绝，不保存两份不一致正文 |
| 剪辑草稿等其他类型引用 | 原有展示和交互不受影响 |
| 键盘核查与窄屏阅读 | 引用可聚焦激活，文字和按钮不遮挡 |
| Markdown 基础排版 | 用户与助手的标题、强调、列表、引用块、链接、代码及表格正常显示 |
| 跨片段 Markdown | 以整篇解析保持列表、强调和表格完整，不出现逐段解析造成的破碎结构 |
| 列表项、表格单元格中的引用 | 引用保留在对应项／单元格内，点击定位正确 |
| 引用边界进入代码或链接地址 | 边界拒绝，不静默移动引用；普通代码中的编号保持字面文字 |
| 原始 HTML、危险链接及外部图片 | 不执行脚本、不允许危险协议、不自动加载图片 |
| 普通文本中的〔1〕 | 不被识别成可操作的证据按钮 |
| 宽表格和长代码块 | 局部滚动，聊天栏无横向溢出 |
| 新旧消息并存并刷新 | 所有正文 Markdown 排版稳定，新旧证据交互各自保持 |

语义验收使用已有分析素材，抽查单证据事实、多证据综合回答和证据不足回答。逐项核对引用是否支持对应文字，尤其不能把只支持半句话的证据挂到整段末尾。真实模型验收与确定性自动化结果分别记录，不把结构校验通过宣称为语义正确。

涉及数据库时验证新迁移及旧消息读取；跨语言契约需验证双方解析及现有结果幂等处理。前端运行相关浏览器回归、类型检查和构建。只为当前影响范围增加验证，不运行无关模块测试。

完成条件：上述适用场景通过，实际问答样例关联正确，历史兼容保持可用，并记录通过、失败与未运行项。

## Phased Delivery Plan

### 推进原则与依赖

“可独立验收”指每个阶段在已完成的前置阶段上，可以用确定输入验证本阶段结果，不必等待下一阶段或依赖真实模型随机输出；不表示四个阶段彼此没有依赖。第一阶段可单独上线；第二、三阶段为兼容性增量；第四阶段才正式启用新答案生成。

| 阶段 | 可交付结果 | 前置条件 | 主要验收入口 | 相对规模 |
| --- | --- | --- | --- | --- |
| 1 | 用户与助手聊天正文支持 Markdown | 现有聊天接口 | 现有浏览器会话测试 | 中，前端为主 |
| 2 | 引用片段能验证、保存并原样恢复 | 阶段 1 通过；技术上不依赖其数据结构 | 现有结果接收与消息快照集成入口 | 中，Python／Java／数据库 |
| 3 | 片段显示为可点击的行内引用 | 阶段 1 的渲染器及阶段 2 的数据契约 | 浏览器会话与播放测试 | 中，前端为主 |
| 4 | Agent 自主生成正确绑定并完成闭环 | 阶段 2、3 均通过 | 受控模型端到端与真实问答样例 | 中，生成链路与联合验收 |

阶段内先完成最小行为，再验证直接受影响链路。每阶段记录最终代码对应的检查命令、结果、样例及未运行项；有失败就修正并重验受影响部分，不能拿上一阶段结果代替最终状态。不得为验收新增生产测试路由、独立模拟服务或新测试框架。

### 阶段 1：聊天正文 Markdown 渲染

**目标与交付**：仅使用现有 content 和 references，让新旧用户消息、助手消息获得统一 Markdown 排版。这个阶段完成后，用户已能直接使用 Markdown，证据按钮仍放在尾部。

实施范围：

1. 选择并锁定支持目标语法及源位置／token 扩展的解析依赖；此时仅实现 Markdown 正文，不提前实现证据节点抽象。
2. 新增统一正文渲染组件，整篇解析 content，接入现有聊天正文及历史草稿的正文入口。
3. 按本 Spec 实现标题、强调、列表、引用块、链接、表格、代码和换行规则，以及原始 HTML、链接协议和外部图片限制。
4. 调整容器和局部样式，保障窄屏、宽表格及长代码块可读；保留尾部证据按钮、草稿卡片和预览交互。

**独立验收输入**：在现有浏览器测试中提供覆盖目标 Markdown 语法的新旧用户／助手消息；另提供含真实可查看证据的旧格式消息。使用现有会话发送接口验证用户提交的 Markdown 源文不会在保存时被改写。

**验收门槛**：

- 所有目标语法正确排版，普通文本和中文换行正常；代码中的 Markdown 符号保持字面内容。
- 原始 HTML 不执行；危险链接不可导航；图片不触发外部请求。
- 刷新后正文一致，旧证据按钮仍能定位原视频，非证据卡片仍可操作。
- 桌面及窄屏均无聊天栏溢出；键盘能访问普通链接和现有证据按钮。
- 相关浏览器测试、前端类型检查及构建通过。

**阶段边界**：不修改模型提示词、跨服务结果、数据库或引用映射；不要求 Agent 此时稳定生成 Markdown。未实现行内证据不阻碍本阶段完成。已有接口直接支持部署；若需撤回，仅恢复旧前端渲染，不涉及数据回退。

### 阶段 2：引用数据契约、持久化与快照

**目标与交付**：受控的新格式问答结果可通过正式接收链路保存，并从消息快照完整读回；旧生产者及旧消息仍可用。此阶段不启用真实 Agent 的新生成格式。

实施范围：

1. 在 Python 公共契约及 worker 映射中加入可空 answerSegments，在 Java 接收契约中加入对应模型。
2. 按目标模型将证据 ID 解析成带 scopeId 的引用，验证正文一致性、已读范围、项目与分析版本等既有约束。
3. 增加可空 JSONB 列，调整消息写入与快照读取；结果和片段在同一事务落库。
4. 核查事件消费者，确保事件触发快照恢复后不会丢失片段；保留原 content 与 references。
5. 在外部结果边界验证 Markdown 引用位置是否合法，覆盖代码、链接和控制语法内部的非法位置。只为此约束使用必要的解析能力，不复制整套前端渲染。双方以相同输入样例验证边界解释一致。

**独立验收输入**：通过现有 worker／结果接收集成入口投递受控结果，使用该测试执行实际持有的合法工具回执；不能直接往消息表插入数据来代替验证结果接收链路。

**验收门槛**：

- 多片段、多证据、重复证据和无证据结果保存后，快照返回的文字、顺序及范围身份正确。
- 原 references 与片段引用一致；重复提交结果沿用现有幂等行为，不新增重复消息。
- 未读、跨项目、错误范围证据，以及正文不一致和非法引用边界被明确拒绝；不产生半条成功消息。
- 从迁移前数据库升级后，旧消息保持 NULL，旧结果缺少新增字段仍可按兼容路径接收。
- Python／Java 相关契约与集成检查、迁移验证通过；第一阶段页面仍可正常读取新旧快照。

**阶段边界**：页面暂可继续展示全文和尾部引用；测试不依赖行内按钮或真实模型。部署顺序为迁移及新消费者先就绪，再允许发送新字段，保持旧生产者工作。生产者启用前可暂停推进，无须删除新列。

### 阶段 3：Markdown 中的行内引用与播放

**目标与交付**：阶段 2 的结构化消息在页面形成准确、稳定、可点击的行内证据引用。仍不要求真实 Agent 生成该格式。

实施范围：

1. 扩展前端消息和证据类型，使用阶段 1 的整篇 Markdown 解析过程，将结构化片段边界映射到引用节点。
2. 在同一答案内按首次出现顺序编号，重复证据复用编号，多证据分别可点；隐藏新格式重复的尾部证据按钮。
3. 复用 inspect 与现有播放链路，保持旧消息尾部按钮及其他类型引用行为。
4. 补齐列表项、表格单元格、加粗文字、跨片段样式及键盘交互的组合场景。

**独立验收输入**：复用第二阶段的受控结果，经真实接收、持久化和快照读取后在浏览器展示；样式组合可另用现有浏览器 fixture 扩充。至少一条主路径必须真正调用证据查看并验证播放器素材及定位时间，不能只断言按钮存在。

**验收门槛**：

- 单句、多证据、段尾及重复证据引用位置和编号正确；回执排序不影响显示。
- 引用留在对应列表项或表格单元格中；整篇 Markdown 结构未因片段切分而破坏。
- 中文、emoji、重复句子和跨片段强调不造成错位；普通〔1〕不会变成证据按钮。
- 点击各编号打开正确素材及时间；刷新／重开会话后关联与编号保持一致。
- 新旧消息并存、无证据新消息、非证据引用均表现正确。
- 相关浏览器回归、前端类型检查及构建通过，第一阶段 Markdown 场景继续通过。

**阶段边界**：不使用真实模型质量作为本阶段完成条件。若暂停推进，旧 Agent 仍生成旧格式，用户继续使用 Markdown 和尾部证据按钮；受控新消息已经能正确显示。

### 阶段 4：Agent 生成接入与完整验收

**目标与交付**：真实视频问答从生成开始具有语义片段与证据绑定，通过正式执行链路保存、展示并可回看，完成本 Spec 的产品目标。

实施范围：

1. 更新 Action 与提示词，让新 ANSWER 输出 Markdown 片段及已读证据 ID；明确句子／段落引用和合法 Markdown 边界规则。
2. 调整结果节点，从片段派生全文及证据集合，保留对应关系并传给已就绪的 worker 契约；沿用现有错误处理和必要修正流程。
3. 更新受影响的受控模型样例，保持 ASK、DRAFT、失败与取消等非问答结果行为不变。
4. 启用结构化问答生产者，执行确定性闭环及真实模型语义验收。

**独立验收输入**：自动化通过现有受控模型注入方式，驱动真实 worker、Java、数据库和浏览器闭环；真实模型验收复用已有分析素材，分别覆盖单证据、多证据综合、跨素材、段落共用证据和证据不足问题。真实模型调用及可能费用单独记录，不将其混入日常确定性回归。

**验收门槛**：

- 新 ANSWER 不再常规返回缺失片段的旧格式；无证据时仍输出有效片段且不伪造引用。
- 完整执行链路的生成、保存、刷新展示及点击定位全部通过，结构与 Markdown 组合场景无回归。
- 非法引用沿现有流程明确修正或失败，不悄悄删除证据后发布成功答案。
- 真实样例逐项核对“对应文字—证据内容—原视频位置”，多证据推理确有依据，段尾引用未夸大支持范围。
- 记录实际样例、原始回答、引用关联、核查结论及未运行项；没有执行真实语义验收时，只能标注“自动化通过，语义验收未完成”。
- Python、Java 直接受影响的运行时／worker／契约回归，以及前端相关浏览器、类型检查和构建通过；完成本 Spec 全部适用验收场景。

**发布与暂停**：只在第二、三阶段接收与展示能力已就绪后启用新生成格式。若需暂停新格式生成，保留数据库中的片段及新前端读取能力，历史新消息不可退化为丢失关联的数据。不得通过破坏性数据库回退撤销该功能。

### 阶段交付记录

每阶段提交一份简短记录：实际变更模块、可复现的验收输入、检查命令及结果、实际效果证据、已知限制和未运行项。截图只证明排版，接口结果只证明数据；播放定位需交互证据，语义正确需样例核查。只有本阶段门槛全部满足才能标记完成。

本计划是后续实施安排，本次仅更新文档；不代表任何阶段已开始或通过验收。

## Out of Scope

- 发布 GitHub Issue、提交代码实现或部署。
- 为历史答案重新调用模型、重新分析素材或自动回填映射。
- 给回答强制添加事实／推断标签、置信度评分或推理过程展示。
- 新证据卡片、弹窗、悬停预览、自动停止播放或论文参考文献导出。
- 改造证据检索、基础分析、问答范围快照或证据权限模型。
- 富文本编辑器、原始 HTML 执行、数学公式、Mermaid、代码语法高亮、可交互任务列表与外部图片嵌入。
- 用自动化语义判定系统替代实际样例核查。

## Further Notes

用户已确认语义片段引用、多证据关联、不额外区分事实与推断、点击直接播放、共同依据时允许段尾引用，以及旧答案维持原状。

片段表示、存储字段与发布顺序是为落实行为提出的技术方案，不是已经完成的代码修改。实现若发现现有存储能以更小改动保持同等语义，可调整内部结构，但不得丢失明确映射或改变已确认交互。

本次仅编写和更新 Spec，检查文档完整性和差异，不运行应用测试。测试入口已确认采用现有对话端到端测试，并对非法证据绑定补充契约测试。

本轮补充依据：前端依赖目前没有 Markdown 解析库；ConversationPanel 以纯文本插值展示正文；消息表与快照只有正文及整篇引用；Agent Action、worker 和 Java RunResult 尚无片段绑定字段。Markdown 支持细则及规模估算属于本轮设计建议，不能表述为已完成实现或用户逐项确认。
