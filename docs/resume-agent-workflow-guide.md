# 简历第五条：受控 Agent 编排的设计与实现

本文根据 2026 年 10 月 27 日核对的项目代码，整理最新版简历第五条，以及工具调用、提示词组装、上下文管理和多轮对话的实现。重点讲当前浏览器提交任务、Python Worker 执行、Java 校验并发布结果的真实链路。开发用 Mock 和旧 CLI 的行为不能直接当成浏览器功能。

最新版简历第五条描述的是：通过 LangGraph 构建 Agentic Workflow，向模型开放四个只读工具，让它在固定素材和分析版本范围内检索、补读和生成草稿；用参数校验、调用预算、无进展停止和引用检查限制执行；草稿由服务端校验，确认版本和渲染走独立业务流程。

任务领取、租约、恢复和消息确认详见[任务可靠性文档](resume-task-reliability-guide.md)，搜索的索引与融合过程详见[混合检索文档](resume-hybrid-search-guide.md)。本文关注 Agent 在领取任务以后，如何理解请求、选择工具、使用证据并形成结果。

## 一、先快速总结

面试时可以先这样回答：

> 我把 Agent 放在 Python Worker 中执行，用 LangGraph 组织请求理解、动作选择、参数检查、工具执行、结果观察和最终校验这些步骤。流程由程序控制，模型每次只决定下一步要读什么、搜什么，或者是否已经能够回答、提交草稿。
>
> Java 先固定允许读取的素材和分析版本。模型只看到四个只读工具的说明，通过统一的 Action 结构提出调用请求，Python 检查工具名和参数，再交给 Java 执行。工具返回带身份、来源和时间的结构化证据，程序保存已读证据与阅读进度，供下一轮决策使用。
>
> 为了避免反复检索和失控执行，我限制模型调用次数、工具次数、修正次数和执行时间，并在连续没有新信息时停止。回答引用需要能对应到实际读取的证据回执；草稿则强制交给 Java 检查素材、时间、引用、已读范围和时长条件。模型不能直接确认版本或发起渲染。
>
> 多轮对话使用最近 12 条历史消息，加上结构化制作条件、草稿和已读状态。继续同一制作时恢复原状态，新制作则隔离。LangGraph 检查点用于保存任务状态，目前没有实现跨会话的用户偏好或经验检索型长期记忆。

整个过程可以先记成：

```text
用户发送消息
    ↓
Java 保存本轮固定输入，安排 Agent 任务
    ↓
Python 理解请求，Java 校验并绑定执行范围与制作身份
    ↓
模型提出一个 Action
    ↓
程序检查动作、参数、权限和预算
    ↓
执行只读工具 → 保存证据和阅读进度 → 再次让模型决定
    ↓
模型提出回答或草稿
    ↓
引用检查 / Java 草稿校验
    ↓
Java 核验本次执行及回执，发布结果

用户之后的预览、确认版本、正式导出，走独立业务入口
```

## 二、为什么需要受控的 Agent 工作流

模型能够根据问题决定下一步，却不能直接作为权限判断和业务提交的依据。例如，模型可能提出读取范围外的素材，也可能反复搜索同一个问题，或者生成一个看起来合理、实际已经超过视频时长的剪辑片段。

项目因此把“提出建议”和“实际执行”分开。模型提出结构化动作，程序检查后才执行；模型生成草稿，服务端检查后才允许作为有效草稿发布。

LangGraph 可以理解为一个组织执行步骤的框架。一个节点就是一段处理逻辑，节点之间的连线决定下一步到哪里。State，也就是状态，是这些步骤共同读写的数据，例如当前需求、已读证据和草稿。

Agentic Workflow 在这里表示：程序规定有哪些步骤和约束，模型在这些约束中决定下一步动作。它不是完全写死的“必须先列素材、再看概览、再搜索”，也不是允许模型任意访问系统。

例如局部问题可以直接搜索；全片问题通常先看概览；证据足够时可以回答。无论选择哪条路径，都必须经过参数、范围和结果检查。

## 三、从用户消息到实际执行

### 3.1 Java 先保存本轮输入

Java 接纳消息时，把当前消息、最近 12 条历史消息、用户引用、当前制作信息和待回答问题组成固定输入，保存到任务中。

固定输入的意思是：这次任务处理的是什么，在接纳时就确定。恢复执行时仍使用这份输入，不能临时把后来新增的消息混进来，改变原任务含义。

Python Worker 领取任务后，先完成请求理解。模型判断是独立问答、新制作、继续修改、回答待澄清问题，还是关系不清楚。Java 随后检查这个判断是否符合真实业务状态，并绑定执行身份、固定范围和编辑代次。

编辑代次可以理解为“当前制作已经修改到第几次”。它用来区分旧执行与新修改，避免迟到的旧结果被当成当前结果。

模型可以建议“继续当前制作”，但不能自行指定一个不属于当前会话的制作身份。真实身份由程序核对和绑定。

### 3.2 固定范围不仅包括素材 ID

固定范围还包括素材所用的分析版本、索引代次和可读取的证据关联。这样一次执行读到的是有明确版本的数据。

如果执行期间又产生了新分析结果，不能随意把新旧证据混合使用。快照依赖失效时也不能用旧回执掩盖问题。

这里的“快照”主要指保存了本次允许使用的元数据和证据、检索单元关联，不表示把整个视频或所有证据文本复制了一份。

## 四、LangGraph 内部有哪些步骤

实际图定义在 graph.py，主要节点如下：

| 节点 | 作用 |
| --- | --- |
| prepare_turn | 准备本轮执行状态和计数 |
| understand_request | 理解请求类型、修改条件和对话关系 |
| decide_next | 调用模型，让它提出一个下一步动作 |
| check_action | 检查动作、参数、范围、分页位置和预算 |
| call_tool | 执行已经通过检查的工具请求 |
| observe_tool | 核对工具返回，保存证据并更新阅读进度 |
| check_result | 检查回答引用或草稿校验状态 |
| await_input | 暂停，等待需要的输入 |
| apply_input | 将匹配的补答应用到原执行 |
| finalize | 整理本次执行结果 |

不是每个节点都会调用模型。理解请求和决定动作主要依赖模型；范围检查、工具分派、读取回执和业务校验主要由代码完成。

工具循环通常是：decide_next → check_action → call_tool → observe_tool → decide_next。程序通过 next_node 决定下一步进入哪个节点。

## 五、四个只读工具的参数与执行过程

### 5.1 “只读”具体指什么

四个工具不能替用户保存方案版本、确认方案、发起渲染，也不能任意修改项目业务数据。

但只读不等于完全没有数据库写入或外部费用。系统仍会保存调用回执和检索排名；语义检索还可能调用 Embedding 模型生成查询向量。

四个工具主要读取已有视频分析数据，不会因为模型要求看一段画面，就自动执行新的 VLM 分析。真实模式没有开放按需新分析的工具。

下面示例中的 asset-A、evidence-1 等是便于阅读的占位名称，实际使用真实 ID；JSON 只展示与解释有关的字段。

### 5.2 list_assets：查看当前允许使用的素材

参数：

```json
{"cursor": 0}
```

Java 从当前固定范围中分页返回素材信息，不接受模型自行传入另一个项目。主要返回字段包括：素材 ID、文件名、时长、分析版本、索引代次、是否有音频、各证据来源是否就绪，以及采样和分析覆盖信息。

```json
{
  "data": {
    "assets": [{
      "id": "asset-A",
      "filename": "咖啡制作.mp4",
      "duration_ms": 180000,
      "analysis_version": "analysis-A",
      "index_generation": "index-A",
      "source_kinds": ["SPEECH", "VISUAL", "VISIBLE_TEXT"]
    }],
    "next_cursor": null
  },
  "records": []
}
```

SPEECH 是语音转写，VISUAL 是画面描述，VISIBLE_TEXT 是画面中的文字。180000 毫秒等于 3 分钟。这个工具只告诉 Agent 有哪些素材及数据来源，没有返回可用于回答视频事实的原始证据。

### 5.3 get_video_overview：查看内容在时间上的分布

参数：

```json
{"asset_id": "asset-A", "cursor": 0}
```

Java 检查素材范围和来源就绪情况，再按时间读取该素材的已有证据，转换成导航条目。

```json
{
  "data": {
    "entries": [{
      "excerpt": "接下来介绍如何调整咖啡豆的研磨粗细。",
      "source_kind": "SPEECH",
      "purpose": "NAVIGATION",
      "start_ms": 30000,
      "end_ms": 35000,
      "navigation_ids": ["evidence-1"]
    }],
    "next_cursor": null
  },
  "records": []
}
```

它帮助模型决定“30 秒附近值得继续读”。这些条目不会因为出现在概览中就进入已读原始证据集合，不能直接作为最终回答引用。下一章会解释导航如何生成，以及有没有专门的数据表。

### 5.4 search_evidence：查找与问题有关的原始证据

参数：

```json
{
  "query": "如何调整咖啡豆的研磨粗细",
  "source_kinds": ["SPEECH"],
  "asset_ids": ["asset-A"],
  "cursor": 0
}
```

query 是检索文字，Java 要求非空且最多 256 个字符。source_kinds 默认是 SPEECH，必须从三种来源中选择。asset_ids 可以省略，但搜索仍受当前任务和用户选择的范围约束。

查询时，程序先检查固定范围和来源状态。相同快照、相同检索条件已有完成排名时可以复用；否则执行原文包含匹配、向量检索和 BM25 检索，再融合排名。向量检索根据意思接近程度找文本，BM25 根据词语匹配进行排序。

命中的检索单元会通过关联关系找到原始证据。工具返回的是原文、素材、分析版本、来源和时间，而不只是一个相似度分数。

data 还包含 query_id、各路检索状态 channels、候选数量限制、候选是否截断、使用的索引代次、模型调用记录和 next_cursor。内部排名的 hits 不直接原样作为工具结果交给模型，而是转换成 records。

翻页继续使用已完成排名，不能因为翻页就重新付费生成一次查询向量。空结果只表示本次检索没有找到，不能证明视频里不存在相关内容。

### 5.5 read_video_range：读取指定时间内的已有证据

参数：

```json
{
  "asset_id": "asset-A",
  "start_ms": 25000,
  "end_ms": 45000,
  "cursor": 0
}
```

它读取视频 25～45 秒范围内的已有证据。开始时间不能小于 0，结束时间要大于开始时间，且不能超过素材时长。

语音按区间相交判断。例如一句话从 24 秒到 28 秒，读取 25～45 秒时也会返回整条语句记录，不把文字裁成半句。视觉和画面文字按观察时刻判断，使用包含开始、不包含结束的范围，也就是 [25 秒, 45 秒)。

返回的 records 使用两种时间表达：

```json
[
  {
    "id": "evidence-1",
    "asset_id": "asset-A",
    "analysis_version": "analysis-A",
    "source_kind": "SPEECH",
    "text": "如果萃取速度太快，可以把研磨调细一些。",
    "time_kind": "INTERVAL",
    "start_ms": 31000,
    "end_ms": 36000
  },
  {
    "id": "evidence-2",
    "asset_id": "asset-A",
    "analysis_version": "analysis-A",
    "source_kind": "VISUAL",
    "text": "操作人员正在调整磨豆机。",
    "time_kind": "POINT",
    "observed_at_ms": 32000,
    "frame_id": "frame-1"
  }
]
```

INTERVAL 表示一段时间，POINT 表示一个观察时刻。第 32 秒看到磨豆机，不能推出整段 25～45 秒都出现磨豆机。

完整记录还有 temporal_precision、observation 等字段；语音还有 audio_start_ms 和 audio_end_ms，记录音轨时间。剪辑使用已经换算为视频坐标的 start_ms、end_ms，不能再次加减音轨偏移。

检索主要用于定位相关内容，区间读取用于补齐前后文。生成草稿时，只有搜索命中还不够，项目要求完整读取覆盖选段的区间分页。

## 六、统一返回格式、分页与导航数据

### 6.1 工具返回不只是正文

四个工具使用统一的返回结构：

```json
{
  "call_id": "execution-1:tool:0",
  "tool_name": "read_video_range",
  "request_hash": "由程序核对的请求摘要",
  "status": "READY",
  "data": {"next_cursor": null},
  "coverage": {},
  "records": [],
  "dependency": null,
  "error": null,
  "mock": false
}
```

call_id 标识本次调用。request_hash 是对工具名和参数计算出的哈希，也就是便于比较的内容摘要，用于核对请求是否一致。data 放工具自己的返回信息，coverage 放读取范围和进度，records 放可进一步核验的原始证据。

协议定义了 READY、PENDING、ERROR，但当前真实执行器不接受 PENDING 返回。真实读取成功是 READY；失败提供结构化 error，包含代码、类别和说明。不能把模拟工具等待外部结果的行为当成四个真实工具的能力。

### 6.2 为什么需要分页

长视频可能产生几百条语音和画面记录。一次全部返回会增大模型输入、费用和处理时间，而且局部问题通常不需要读完所有内容。

分页还有一个作用：明确告诉 Agent 这次读到的是全部结果还是其中一部分。否则模型可能只看了前面几条，就误称已经总结完整视频。

当前每页最多 100 条，完整返回最多 32768 字节，即 32 KiB。两者都要满足，因为每条记录的长度不同。超过字节上限时把整条留到下一页，不截断原文；单条就超限则明确报错。

cursor 是已跳过的记录数量，不是页码，也不是视频时间。概览和区间查询使用稳定排序和 LIMIT 101 OFFSET cursor，多查一条是为了判断是否还有下一页。

```text
cursor = 0    → 返回 100 条 → next_cursor = 100
cursor = 100  → 返回 100 条 → next_cursor = 200
cursor = 200  → 返回 35 条  → next_cursor = null
```

如果第一批只放得下 60 条，下一页位置就是 60。区间翻页必须保持素材和起止时间不变，只更新 cursor；换了区间就从 0 开始。

next_cursor 为 null 表示该查询没有更多记录。读完已有记录不代表视频每一帧都被分析过。分页也只限制单次返回，累计已读证据仍可能让上下文增长。

### 6.3 导航如何从原始证据生成

当前 get_video_overview 调用 QuestionEvidence.read，不传时间范围，按时间读取快照内属于该视频的证据，然后逐条转换：

| 导航字段 | 来源 |
| --- | --- |
| excerpt | 直接复制证据 text |
| source_kind | 复制证据来源 |
| start_ms、end_ms | 语音区间 |
| observed_at_ms | 视觉观察时刻 |
| navigation_ids | 对应原始证据 ID |
| purpose | 程序固定写 NAVIGATION |

虽然叫 excerpt，当前实现并没有再次生成摘要，也没有合并多条证据生成章节。它更准确地说是按时间排列的证据导航列表。

### 6.4 有没有专门保存导航的数据表

这条工具链路没有独立的导航业务表。读取主要涉及：

| 表 | 保存内容 |
| --- | --- |
| evidence_segments | 原始证据文本、时间、来源、分析版本和附加观察 |
| question_scope_evidence | 固定范围与允许读取的证据 ID 之间的关系 |
| question_tool_receipts | 请求和返回回执，用于核对及复用同一次调用 |

前两张表连接查询后，Java 临时组织导航条目。工具返回 JSON 会进入回执，所以回执中可能保存导航数据，但这不是独立维护的目录业务表。项目虽有 asset_summaries 表，当前概览工具没有从它读取导航。

概览不放入 records，因此不会直接成为已读原始证据。Agent 还要搜索或读取区间才能形成正式引用。由于概览复制了全文，后续读取确实可能重复看到同一段文字；当前设计主要区分用途并减少附加字段，没有做到语义摘要压缩。

## 七、四个工具如何交给模型，模型如何提出调用

### 7.1 工具说明和参数格式来自代码

catalog.py 中用 READ_TOOLS 列出四个允许名称，DESCRIPTIONS 提供说明，contracts.py 定义各工具的参数模型。

Pydantic 是用于声明和检查数据格式的 Python 库。项目用它定义参数类型、默认值、数字范围，并禁止多余字段，再通过 model_json_schema() 生成 JSON Schema。后者就是机器可读的参数格式说明。

model_tools(mock=False) 生成四个工具的名称、用途、参数格式，加入决策提示词。validate_edit_draft 不开放给模型自由选择；模拟用的 inspect_video_range 也不在真实四工具名单中。

### 7.2 真正绑定给模型的是统一 Action 输出

当前代码不是把四个业务工具分别绑定成四个可直接执行的原生函数。四个工具说明放在提示词里，模型通过统一 Action 结构表达下一步。

model.py 使用 with_structured_output，method 为 function_calling。请求理解阶段绑定 Understanding，决策阶段绑定 Action。返回后检查本轮恰好有一个合法结构化调用，再做解析和后续参数校验。strict=False 不表示可以省略本地校验。

Action 有四种 kind：TOOL 调用工具、ASK 提问、ANSWER 回答、DRAFT 提交草稿。例如：

```json
{
  "kind": "TOOL",
  "tool_name": "search_evidence",
  "arguments": {
    "query": "如何调整研磨粗细",
    "source_kinds": ["SPEECH"],
    "asset_ids": ["asset-A"],
    "cursor": 0
  }
}
```

这时只是模型提出请求，还没有执行。check_action 检查工具名单、参数、素材范围、区间翻页和预算，通过后由程序补上 call_id 和 request_hash。

### 7.3 Python 发送请求，Java 再检查和执行

浏览器 Worker 的 RunToolExecutor 通过 POST /internal/v1/agent-runs/{task}/tools 请求 Java，并附上执行凭据和编辑代次。凭据不是模型生成的，也不会因为模型输出另一个 URL 就改变请求地址。

Java 的 AgentRunTools 检查当前执行是否有效、是否仍有资格，再交给 ReadTools。读取可能涉及外部检索，因此不会一直持有业务锁等待网络；完成后还会重新检查执行资格，并关联成功回执。

ReadTools 检查请求哈希、字段、素材范围和快照依赖。相同范围与 call_id 的相同请求已有结果时复用回执；同一调用编号换了参数会冲突，结果尚未确认时也不会盲目重做。

Python 收到结果后核对 call_id、tool_name、request_hash，检查证据所属素材、分析版本和时间，随后更新 observations 与 coverage，再回到 decide_next。

## 八、调用预算和无进展停止如何生效

当前默认限制如下，实际值来自 Limits 配置：

| 限制 | 默认值 | 作用 |
| --- | --- | --- |
| 模型调用 | 16 次 | 限制一次执行反复请求模型 |
| 工具动作 | 20 次 | 限制反复检索和读取 |
| 修正次数 | 3 次 | 限制格式、参数和草稿错误反复修正 |
| 连续无进展 | 3 次 | 没有新信息或有效修正就停止 |
| 活跃执行时间 | 300 秒 | 限制执行持续时间 |
| 单次输出 | 8192 tokens | 限制模型输出长度；token 是模型处理文本的计量单位 |

不是只要工具成功返回，就算有进展。新证据、新的目录页、区间分页推进等可以算进展。重复列同样的素材、重复读同一页，通常不会增加有效信息。

草稿校验也不是每返回一次错误就算进展。首次反馈提供新信息；之后会比较要求、草稿哈希及问题集合，判断错误是否确实减少。预算是硬限制，无进展检测是补充，避免模型把剩余额度都花在重复行为上。

模型调用计数和回执会保存，故障恢复不能把次数归零。调用前登记提交状态，拿到响应后保存；已有成功响应可复用，请求可能已发出却未收到确认时保留不确定状态，不自动重新付费。

代码中的 attempts=2 只用于执行器明确报告“未发生外部提交”的临时工具错误，不表示所有模型请求、搜索请求或网络超时都能安全重试两次。

## 九、回答引用和草稿分别怎样校验

### 9.1 回答必须引用实际读过的证据

工具 records 中的证据被核对后，按 ID 放入 observations。同一证据 ID 如果返回了不同内容，程序会拒绝把它当作不变证据继续使用。

模型提交 ANSWER 时携带 evidence_ids。Python 检查这些 ID 是否已经读过、是否属于允许素材和固定分析版本。Java 发布时进一步用 question_tool_receipts 和 agent_run_tool_calls 核对这些引用是否来自属于本次执行的成功读取回执。

目录中的 navigation_ids、历史聊天里出现过的 ID，都不能仅凭出现过就成为本次有效引用。

当前还有针对无引用回答、全片问题覆盖、视觉问题来源类型的检查，其中部分使用关键词判断。这些机制能约束来源身份和部分明显错误，不能证明自然语言结论必然被证据支持，也不能保证 ASR、VLM 本身没有识别错误。

### 9.2 DRAFT 会被程序强制送去 Java 校验

模型提交 DRAFT 后，程序生成 validate_edit_draft 请求，不允许模型跳过这一步直接宣称成功。校验工具由程序选择，不属于四个可自由调用的只读工具。

Java 主要检查：

- 素材属于固定范围和制作条件，且素材已经有效完成探测。
- 片段起止合法、没有超过视频时长，同一输出没有复用重叠区间。
- 覆盖选段的 read_video_range 分页已经完整读取。
- 引用属于同素材、固定分析版本，且与片段时间相交；视觉点必须落在片段内。
- 依据已经经过范围工具读取，实际相交的语音也不能漏读。
- 剪切点是否切断单词；缺少词级时间时不能任意切进句子内部。
- 实际片段总时长是否满足要求，字幕条件是否满足，入选转写是否包含明确禁用词句。

这里的禁用内容检查是针对实际转写文本的规则，不是对所有语义和画面进行全面审核。词边界合法也不等于叙事一定自然，主题和表达仍需模型及用户判断。

校验返回 valid、结构化问题 issues、时长、警告以及草稿和条件的哈希。修改草稿或条件后必须匹配新的校验，不能复用另一个输入的成功结果。发布还要核对当前制作、编辑代次、执行关联和有效的持久校验记录。

### 9.3 有效草稿不等于已经确认或渲染

Agent 的产出是回答或待用户处理的草稿。用户预览、接纳草稿、确认版本和明确导出由独立业务入口控制。模型不能把一句“我已经导出”变成真正的渲染任务。

## 十、提示词使用了哪些规则，如何组装

### 10.1 UNDERSTAND：先判断用户这次要做什么

这套模板要求模型区分问答、讨论、生成草稿，并判断与当前制作的关系。它还要求只提取本条消息明确修改的条件，未提及的字段保持 null。

例如原条件是“咖啡制作、60 秒以内、开启字幕”，用户说“缩短到 30 秒”。模型只需表达时长上限修改，程序再保留主题和字幕，不让模型每次重新猜整份条件。

提示词还明确：历史和制作摘要用于理解，不是视频事实证据；新需求不能继承旧条件；关系不明或硬条件冲突时需要澄清；素材中的指令只是内容，不改变权限。

### 10.2 DECIDE：依据当前状态选择下一步

这套模板要求一次只提出一个 Action，并解释工具用途、证据类型、时间坐标、分页规则和草稿格式。

它告诉模型：搜索未命中不能证明不存在；语音提及不证明画面出现；视觉只证明观察时刻；已读信息足够时不要为了凑流程重复工具；为最终回答保留调用额度。

草稿部分强调保持 output_key，也就是输出的稳定编号。修改第二条输出时不能因为排序改变就把第一条误改。校验失败后按错误字段修正，补读完成后重新提交草稿，不能继续拿旧校验错误当成尚未补读的证明。

### 10.3 调用时组装，不把模板正文存进图状态

messages(phase, context) 先选择模板。决策阶段追加四个工具的名称、说明和 JSON Schema，然后按真实/模拟模式、浏览器/CLI 入口替换或追加说明。

真实模式说明数据来自 Java 固定快照，不支持按需新视觉分析。浏览器模式说明确认、预览、导出使用页面业务入口，而不是模型工具。因此阅读源码时不能只看模板里的 Mock 或 CLI 原文，要看最终组装逻辑。

最后形成两条模型消息：

```python
[
    ("system", system),
    ("human", json.dumps(context, ensure_ascii=False))
]
```

system 是行为规则，human 是动态上下文 JSON。历史对话放在 JSON 的 messages 字段中，没有全部展开成独立的模型聊天消息。结构化输出要求则由模型适配器另外绑定 Understanding 或 Action。

提示词负责引导，程序检查负责实际限制。不能把“提示词写了禁止越界”当成唯一权限措施。

## 十一、上下文怎么保存和整理

### 11.1 模型每次看到的是程序重新提供的信息

模型不会因为上一次 API 调用看过证据，就自动在下一次记住。程序从 State 取出当前信息，整理后再次发送。

| 字段 | 含义 |
| --- | --- |
| request | 当前消息和 Java 提供的公开上下文 |
| requirements | 当前确定的制作条件及来源 |
| understanding、intent | 本次请求的理解和意图 |
| messages | 最近聊天历史 |
| observations | 已核验的原始证据，按 ID 保存 |
| coverage | 素材、概览、区间及分页进度 |
| draft、validation | 当前草稿与最近校验结果 |
| feedback | 最近的工具反馈或错误 |
| usage | 执行次数等计数 |
| available_assets | 固定范围内素材元数据 |
| reading | 整理后的已读数量、完成区间及准确下一页参数 |
| draft_repair | 针对当前草稿错误的修正信息 |
| budget | 剩余模型调用次数 |

不是每个阶段都有完整证据和草稿。理解请求时主要用当前输入与公开状态；读取工具后，observations 和 coverage 才逐步增加。

### 11.2 整理上下文，避免同一内容重复出现

model_view 会保留程序中的完整状态，另生成发给模型的视图：原始 records 已进入 observations 后，不在 feedback 中重复发送；已读原文对应的导航条目也会从模型看到的概览里省去重复部分。

问答和讨论只保留 observation 中选定的附加字段，例如情绪、语言；DRAFT 模式保留完整附加观察。证据正文和基本时间仍保留。内部素材分页缓存不直接重复发送，阅读状态则整理为 reading，明确提示未读完区间的下一页参数。

这些是字段筛选、去重和进度整理，不是调用另一个模型把全部历史总结成摘要。

### 11.3 当前没有无限上下文能力

最近聊天只取 12 条，工具结果限制单页大小，输入还有请求字节检查。默认 prompt_bytes 为 1 MiB；模型适配器的超限提示仍写着 64 KiB，与当前默认值不一致，应以实际配置为准。字节限制也不等于模型的 token 上限。

当前没有实现自动滚动摘要，也没有把旧证据移出上下文后按需检索回来的完整机制。累计证据过多时可能达到限制并停止。不能把分页描述成已经解决所有长上下文问题。

## 十二、多轮对话如何继续

### 12.1 最近聊天帮助理解指代，制作状态保存具体要求

Java 提供最近 12 条历史消息，是 12 条，不是 12 轮。Python 整理最终历史时也保留最近 12 条，但浏览器新任务的公开历史以 Java 本轮固定输入为准。

除了聊天，Java 还提供当前制作、已有条件及来源、草稿关联和待回答问题。例如用户很早说过“保留字幕”，即使这句话超出最近 12 条，只要它已成为当前制作的有效条件，就能通过制作状态继续保留。

conditions 的来源区分默认值与用户输入，并关联消息。它是结构化业务状态，不是模型自动编写的一段聊天总结。

### 12.2 用一次修改串起流程

第一轮用户说：“剪一个咖啡制作视频，一分钟以内，保留字幕。”系统建立新制作，读取证据，生成和校验草稿。

第二轮用户说：“缩短到 30 秒，其他不变。”Java 将最近聊天和当前制作信息交给 Python，模型判断为继续制作。Java 校验后绑定原制作，Python 从原 thread 的检查点中恢复草稿、证据和阅读进度，把时长条件改为 30 秒，保留其他条件，再生成、校验新草稿。

thread_id 是 LangGraph 区分状态所属工作线程的标识，不等同于操作系统线程。它用于找到哪一份检查点。当前制作代次改变时，旧校验状态可能需要清除，不能因为上一次通过就认为新草稿已经通过。

### 12.3 不同对话关系走不同路径

| 关系 | 如何处理 |
| --- | --- |
| INDEPENDENT：独立问答或讨论 | 使用本轮执行，不直接继承旧制作的私有证据和草稿 |
| NEW_PRODUCTION：新制作 | 创建独立制作身份和 thread，隔离旧条件 |
| CONTINUE_PRODUCTION：修改当前制作 | 核验当前制作未冻结及绑定有效，再复用原制作状态 |
| ANSWER_QUESTION：补答 | 核对具体问题及等待身份，恢复原执行 |
| CLARIFY：关系不清楚 | 提问澄清，不能随意选一份制作继续 |

能看到历史，不等于必须继承全部历史条件。上一条视频要求竖屏 30 秒，新制作不能未经明确依据就自动套用。

### 12.4 等用户补答时如何恢复

Agent 缺少关键条件时返回 ASK，程序保存问题和等待位置。用户回答后，先判断它是否在回答某个待处理问题，再核对 question_id、wait_id、thread、execution 和制作代次等绑定。

匹配后通过 LangGraph 的 Command(resume=...) 恢复原等待位置。普通新问题不会仅因为紧接着出现，就被当作原问题的补答。

## 十三、短期记忆、持久化与长期记忆的区别

提示词告诉模型怎么做，上下文告诉模型当前情况，记忆则是把需要延续的信息保存下来，之后重新取出放进上下文。

项目中的已读证据、阅读进度、草稿、校验和等待状态，可以称为任务范围内的短期记忆。LangGraph 使用 AsyncSqliteSaver 保存到本地 agent.sqlite，检查点记录当前状态及执行位置，用于符合恢复条件时继续工作。

短期记忆说的是使用范围，不代表只能放在内存里。落盘的任务状态仍可以属于任务范围内的记忆。当前 SQLite 是 Worker 本地状态，不是已经实现了多 Worker 共享的分布式记忆服务。

Java 还持久保存聊天、制作条件、草稿关联和待回答问题。这些业务状态可以长期存在，但不能因此宣称实现了自动学习用户偏好的长期记忆系统。

当前没有通用的“提取用户偏好 → 保存跨会话记忆 → 新任务自动检索偏好”流程。Qdrant 检索的是视频证据，不是聊天经验；模型调用回执主要解决执行恢复和重复费用，也不是经验记忆。

普通聊天超过最近 12 条后，没有自动检索全部旧聊天的机制。继续制作依赖已保存条件和状态；若某个细节既不在近期历史里，也未保存为结构化条件，就不能保证模型仍然知道。

## 十四、面试时可以怎样逐步展开

### 14.1 先说明为什么这样设计

可以说：“模型适合判断下一步读什么，但权限、费用和业务提交不能交给模型自由决定。我用固定流程包住模型决策，让模型提出动作，由程序检查并执行。”

然后举一个例子：用户问研磨粗细，Agent 可以先搜索相关语音，再读前后文，证据够了就回答。如果生成剪辑，则还要提交草稿接受 Java 校验。

### 14.2 再说明工具和执行边界

可以说：“四个工具分别负责列素材、看导航、搜索证据和读区间。工具说明及参数 Schema 放在提示词里，模型统一输出 Action；Python 校验后调用 Java，Java 再核对执行身份、固定范围和参数，返回原始证据和回执。”

面试官追问注册方式时，要说清当前绑定的是统一 Action，不要说成直接把四个 Java 方法作为原生函数交给模型执行。

### 14.3 再讲如何避免重复读取和无限执行

可以说：“工具结果进入已读证据集合，分页进度单独保存。下一轮上下文明确给出已读范围和下一页参数，同时限制调用次数、修正次数和时间。重复读同一页不会被当成新进展，连续无进展就停止。”

追问分页时，说明单页最多 100 条、32 KiB，游标记录已读位置，原文不截断。不要说分页意味着上下文永远不会超限。

### 14.4 再讲提示词、上下文和多轮对话

可以说：“提示词分请求理解和动作决策两套，调用时追加工具说明和真实入口约束。上下文包含最近 12 条聊天、结构化条件、证据、进度、草稿和校验反馈。新消息先判断关系，继续同一制作才恢复原状态，新制作隔离。”

追问记忆时，说明本地检查点和数据库持久化已经存在，但没有自动提取用户偏好的跨会话长期记忆，也没有自动滚动摘要。

### 14.5 最后说明结果为什么可以进入业务流程

可以说：“回答引用必须能追溯到实际读取的证据回执；草稿由程序强制送 Java 校验，核对时间、素材、引用、读取范围和条件，并绑定草稿哈希及编辑代次。最终确认和渲染仍由独立业务入口控制。”

需要主动保留的边界是：引用合法不等于语义一定正确，草稿规则通过也不代表剪辑一定好看。当前没有这些语义效果的保证，也不应编造准确率或成本降低比例。
