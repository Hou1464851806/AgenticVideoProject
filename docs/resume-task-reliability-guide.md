# 简历第一条 任务可靠链路的设计与实现

本文对应简历中的“任务可靠链路”，按面试时适合讲述的顺序，先说明整体思路，再展开视频分析、视频渲染和 Python Agent 三条链路。内容以 2026 年 10 月 26 日核对的当前代码为依据。

阅读时始终记住一个区别：**消息被收到了、任务开始执行了、业务结果保存成功了，是三件不同的事。**

## 一 先用一分钟讲清楚整体设计

面试官问“你是怎么保证异步任务可靠性的”，可以先这样回答：

> 视频分析、渲染和 Agent 执行都比较耗时，所以用户请求进来后，我先在数据库里创建任务，再通过 RabbitMQ 通知后台执行。
>
> 数据库提交和发送 MQ 消息不能天然一起成功。我采用 Transactional Outbox：把任务和待发送通知放在同一个数据库事务中保存，再由后台发布器发送消息，收到 RabbitMQ 发布确认且没有发生路由退回后才标记已发布。发送失败会重试，因此允许消息重复投递。
>
> 消费端不直接根据消息开始工作，而是先检查数据库任务状态。通过任务行锁和状态机原子领取任务，避免同一任务被重复启动；提交结果时检查当前 attempt_id，防止失效执行写入。
>
> 视频分析和渲染在 Java 服务内执行，通过本机运行记录判断执行是否退出。Agent 放在 Python Worker 中，Java 无法直接看到它是否还在运行，所以使用租约和心跳管理执行资格。结果先保存到数据库，再确认 MQ 消息；中断后按照任务状态、调用回执和检查点决定如何恢复。

这段回答是开头。接下来按“分析怎么做、渲染怎么做、Agent 有什么不同”逐步展开，不需要一开始就把所有异常情况都讲完。

### 1.1 这里的可靠具体指什么

可靠不表示所有任务最后一定成功，也不表示任何外部操作都只执行一次。当前设计主要解决这些问题：

1. 数据库已经接纳了任务，不能因为一次发送失败就把任务忘掉。
2. 消息重复到达，不能不检查状态就再执行一遍业务。
3. 执行中断后，要能判断哪些工作已经完成，哪些可以继续。
4. 不能继续时，要保留明确的失败原因，不能显示为成功。
5. 已经失去资格的执行，不能再发布新的业务结果。

其中，“原子”表示一组操作一起成功或一起失败。例如“检查待执行状态、创建执行批次、改成运行中”必须放在同一个受锁保护的事务里，不能先查状态、隔一段时间再随意更新。

“幂等”在这里表示：同一请求或消息重复到达，不会重复产生本来只应发生一次的业务效果。它不表示消息不会重复，也不表示重复到达时程序什么代码都不执行。

### 1.2 三条链路的共同部分和差别

| 对比项 | 视频分析 | 视频渲染 | Agent |
| --- | --- | --- | --- |
| 执行位置 | Java 消费线程 | Java 消费线程调用 FFmpeg 子进程 | Python Worker |
| 主要队列 | analysis.v1，媒体准备另走 media.v1 | media.v1 | agent.v1 |
| 当前消费配置 | 分析默认 2 个消费者 | 媒体队列 1 个消费者 | 单消费者 |
| 执行资格 | 数据库当前 attempt 和本机 active 集合 | 同左 | 当前 attempt、租约凭据和到期时间 |
| 主要恢复依据 | 模型回执、远端任务 ID、数据库状态 | 固定渲染输入和任务状态 | Java 任务状态、SQLite 检查点和调用回执 |
| 特别需要注意 | 付费提交结果未知时不能盲目重付 | 文件写入不能随数据库事务回滚 | 失去租约后停止执行，结果仍须 Java 校验 |

这里的消费者是接收 MQ 消息并运行处理代码的程序。Java 消费者由 Spring 管理；Python 消费者使用 aio-pika 接收消息。

## 二 视频分析任务 从上传完成讲起

假设用户上传一段视频，希望系统理解里面的语音和画面。

### 2.1 视频分析不是一个从头运行到尾的大任务

上传完成后，系统先创建媒体准备任务，校验文件、读取媒体信息、准备音频和稀疏帧等分析输入。随后分别推进语音、画面和索引工作；缺少代表帧时，也有单独的画面准备任务。

```text
上传完成
  → MEDIA_PREPARE：媒体校验和准备
  → 语音分支 CONTENT_ANALYZE：ASR 转写
  → 画面分支：必要时 VISION_PREPARE，再 VISION_ANALYZE
  → 保存原始证据和检索单元
  → INDEX_BUILD：生成所需向量，构建并核对检索索引
```

ASR 是语音识别，把音频转换成文本和时间信息。VLM 是视觉语言模型，用来理解抽出的画面。Embedding 是把文本转换成数值向量，供语义检索使用。

上面的分支不是强制先完成 ASR 再执行 VLM。语音和画面可以独立推进；一种来源失败，不应抹掉另一种已成功的结果。没有音轨的视频，语音阶段会标为不适用。

### 2.2 为什么需要 Outbox

上传完成时，需要做两件事：在数据库里创建任务，以及向 RabbitMQ 发送消息。

如果直接先写数据库、再发消息，就可能出现：

```text
任务写入数据库成功
  → 进程崩溃
  → 还没来得及发送消息
  → 后台不知道应该执行这个任务
```

反过来，先发消息再提交数据库，也可能让消费者收到一个尚未成功保存的任务。

Transactional Outbox 的处理方式是增加一张待发送记录表。Outbox 可以理解为数据库里的“待发送通知列表”。上传完成的接纳事务同时保存：

- 待验证的素材记录。
- tasks 中的媒体准备任务。
- outbox_events 中的待发送通知。

它们属于同一个数据库事务。事务回滚时都不生效；事务提交成功时，任务和发送意图都留下来。这个事务不包含向 RabbitMQ 发送消息的操作。

随后，后台发布器扫描 Outbox，发送到对应队列。即使在事务提交后立刻崩溃，重启后也能找到尚未发送的记录。

### 2.3 发布确认不等于任务完成

发布器使用持久队列和持久消息，并等待 RabbitMQ 的发布确认。这里的确认，是 RabbitMQ 对发布端的回应，表示消息已被 broker 接受处理，不表示消费者已经执行完任务。

发布器还使用 mandatory 发布并检查消息退回。原因是消息可能被 RabbitMQ 接收，却没有路由到目标队列。仅收到发布确认，不能忽略这种情况。

发布成功且没有被退回后，Outbox 标记为已发布；失败则保留发送意图并退避重试。退避就是失败后等待一段时间再尝试，当前发送失败等待时间有 2 到 60 秒的上限范围。发布器也会重新提醒长期保持 PENDING、尚未被接纳的任务。

为什么仍然会重复发送？因为存在下面这个时间窗口：

```text
RabbitMQ 已收到消息
  → 发布器还没把 Outbox 改成已发布
  → 进程崩溃
  → 重启后再次发送
```

因此，这套设计采用“至少一次投递”的思路：在服务恢复和持续重试的前提下推进投递，允许重复，由消费端控制重复业务效果。它不承诺永久故障时仍能完成任务，也不承诺所有硬件故障下绝不丢数据。

源码：[TaskDispatch.java](../backend/src/main/java/com/agenticvideo/business/messaging/TaskDispatch.java)。

### 2.4 Java 消费线程实际怎么执行

analysis.v1 的默认消费者数量是 2，ASR、VLM 和索引任务共享这两个消费者。

```text
消费线程 1：领取视频 A 的 ASR 步骤 → 执行 → 保存状态 → ACK
消费线程 2：领取视频 A 的 VLM 任务 → 执行 → 保存状态 → ACK
```

这只是某一时刻可能出现的分配。两个线程也可能分别执行两个视频的 VLM，不是一个线程固定负责 ASR、另一个固定负责 VLM。

每个消费者 prefetch=1，表示它最多持有一条尚未确认的消息。当前消息被确认或拒绝前，RabbitMQ 不再继续给这个消费者发送下一条。

当前代码直接在消费线程里调用 LocalTaskRunner，没有再转交额外工作线程池。普通方法调用不会自动换线程：消费方法调用分析方法，分析方法调用模型接口，这些步骤仍由同一个消费线程推进。

如果转交线程池，代码会把工作提交给另一组线程，然后消费方法可以先返回。那样还需要管理线程池排队和 ACK 时机。当前后台消费本身已经不占用用户上传请求线程，所以没有再增加这一层。

ACK 是消费者发给 RabbitMQ 的消息确认，表示这次通知已经处理妥当，MQ 可以移除它。它和前面发布器收到的发布确认不是一回事。

源码：[TaskConsumers.java](../backend/src/main/java/com/agenticvideo/business/messaging/TaskConsumers.java)、[LocalTaskRunner.java](../backend/src/main/java/com/agenticvideo/business/task/LocalTaskRunner.java)。

### 2.5 重复消息为什么不会重复启动同一个任务

消息里有 taskId。消费者先根据这个 ID 原子领取数据库任务，而不是一收到通知就调用模型。

任务行锁表示：当前事务操作这条任务记录时，另一个也要锁定它的事务需要等待。领取步骤是：

```text
锁定任务行
  → 检查状态是否为 PENDING，是否到达执行时间
  → 创建一个新的 attempt_id
  → 将任务改为 RUNNING，记录 current_attempt_id
  → 提交事务
```

PENDING 表示待执行，RUNNING 表示执行中，SUCCEEDED 表示成功。状态机就是给这些状态规定允许的转换条件，而不是任意修改状态。

attempt_id 表示同一个任务的某一次执行批次。例如 task-A 是“分析这个视频”，attempt-1 是它第一次被领取执行。恢复后可以产生 attempt-2，但仍然属于 task-A。

两个消费者同时收到 task-A 时，第一个把状态改为 RUNNING；第二个获得锁后发现已经运行，就不再启动执行。本机 active 集合还会拦截同一进程中已经在处理的 taskId。

如果数据库已完成业务提交，但 ACK 丢了，消息重投后发现任务已是 SUCCEEDED，也会跳过执行再 ACK。

因此，准确说法是“通过行锁和任务状态机避免重复执行业务”，不是“保证消息不会被重复消费”。

源码：[TaskExecution.java 的 claimLocal 方法](../backend/src/main/java/com/agenticvideo/business/task/TaskExecution.java)。

### 2.6 为什么同一个 ASR 任务会执行多次

ASR 服务采用异步任务：提交音频后先返回远端任务 ID，过一会儿才能拿到转写结果。

本地任务 task-A 和供应商任务 asr-123 是两个不同的任务。task-A 负责管理调用过程；asr-123 是供应商实际进行转写的工作。

```text
第一次领取 task-A
  → 记录准备提交状态
  → 向 ASR 提交音频
  → 保存完整响应和远端任务 ID asr-123
  → 记录下次执行时间，写入新的 Outbox
  → 结束本次 attempt，将 task-A 设回 PENDING
  → ACK，释放消费线程

下一次领取 task-A
  → 发现已有 asr-123
  → 查询 asr-123 的状态
  → 未完成就再安排查询，完成则保存结果并发布证据
```

默认约 5 秒后安排下一次查询，实际还要经过派发和排队。它不是让 Java 消费线程一直睡眠等待供应商完成。

这里重新执行本地任务是正常推进，并不是幂等失效。一个旧通知如果恰好在任务重新待执行且到期时到达，也只能领取数据库允许的下一步；消息本身不决定“必须重新提交音频”。

### 2.7 模型回执为什么要单独保存

回执在这里就是保存下来的调用记录，包括请求状态、供应商响应、远端任务 ID、结果和用量。

假设 ASR 已完成，系统已保存转写内容，但发布语音证据前进程崩溃。恢复时可以读取保存的转写内容，继续本地处理，不必重新向供应商提交音频。

VLM 和 Embedding 也会复用已成功的帧分析或向量批次；完整响应已经保存而后续处理未结束时，可以继续处理响应。

最难处理的是“请求可能已经被接收，但响应没有拿到”：

```text
Java 提交音频
  → 供应商接收并开始转写
  → 返回任务 ID 的响应途中断网
  → Java 只看到了超时
```

超时也可能发生在请求根本没到供应商的时候。Java 无法仅凭超时分辨这两种情况。如果直接重新提交，就可能重复转写、重复计费。

因此代码保留 UNCERTAIN，也就是“提交结果不确定”。如果已保存的响应里能恢复远端任务 ID，就继续查询；如果没有足够信息，就停止自动重新提交。它选择保留失败原因，不能假装这次没有调用过模型。

模型请求在数据库事务外执行，调用前后的状态通过短事务保存。这样不会长时间占着数据库锁等待网络；数据库回滚也不能撤销供应商已接收的付费请求，因此把网络调用写进事务并不能解决外部一致性问题。

源码：[AnalysisProcessing.java](../backend/src/main/java/com/agenticvideo/business/analysis/AnalysisProcessing.java)。

### 2.8 模型结果落库后 为什么还要完成业务处理

这里有两种不同的“保存成功”。

第一种是模型结果保存成功，例如 model_calls 里已经有转写 JSON。第二种是业务处理完成：系统已经把转写内容转换成可引用的语音证据，更新了分析阶段并安排后续索引。

ASR 完成时，同一消费线程调用 completeLocal。它不是额外的 HTTP 请求，也没有另外一个线程代为提交。在完成事务中，代码会：

1. 核对当前 attempt 和任务状态。
2. 读取保存的转写内容，核对语句和字词时间，映射到原视频时间轴。
3. 写入 evidence_segments、retrieval_units 和引用关系。
4. 更新分析阶段，并按条件安排索引构建。
5. 把任务和 attempt 标为成功，保存完成回执。

事务成功返回后，消费线程才 ACK。

```text
模型返回转写结果
  → 保存模型结果
  → 事务内发布业务证据并完成任务
  → 返回消费者
  → ACK
```

索引阶段还涉及写入 Qdrant。系统先写派生索引，再回读核对，通过后发布可用代次；不是只要向量写请求返回成功，就立即认为业务索引已经可用。

源码：[SpeechAnalysis.java 的 publish 方法](../backend/src/main/java/com/agenticvideo/business/analysis/SpeechAnalysis.java)、[SearchIndexBuilder.java](../backend/src/main/java/com/agenticvideo/business/search/SearchIndexBuilder.java)、[SearchIndexes.java](../backend/src/main/java/com/agenticvideo/business/search/SearchIndexes.java)。

### 2.9 完成回执和消费幂等不是同一层机制

execution_reports 保存的是“某次完成提交已经被处理，其输入和返回结果是什么”。相同完成调用再次进入时，代码可以核对内容并返回已有结果，不重复插入证据。

但是，当前本机正常消费流程没有自动重复调用 completeLocal 的逻辑。不要为了介绍这个表，编造出“消费者总会再次提交结果”的场景。

| 情况 | 实际处理 |
| --- | --- |
| 消息重复，任务仍在运行 | 领取时跳过，不进入完成方法 |
| 完成事务成功，ACK 丢失 | 重投后任务已成功，不进入完成方法 |
| 完成事务失败，之后恢复 | 可以重新完成，但前一次事务已回滚，不是重复写入 |
| 调用方再次提交相同完成请求 | 完成方法的回执重放分支返回原结果 |

因此，讲当前视频分析的消费幂等时，重点是行锁和状态机。完成回执是共用完成方法提供的额外幂等能力，不是当前 MQ 防重的主要路径。

### 2.10 Java 本机任务如何恢复 为什么依赖单实例

active 是 Java 进程内的一个集合，记录当前正在执行的 taskId。执行开始时加入，退出时在 finally 中移除。finally 表示正常返回或抛出异常时都会进入的收尾代码；进程直接崩溃时不能指望它执行。

恢复器发现数据库任务仍是 RUNNING，但本机 active 已没有它，就进一步核查并按恢复规则处理。可恢复时，将旧 attempt 标为 EXPIRED，重新安排任务。EXPIRED 在这里表示旧批次资格已撤销，不表示本机线程有一个自动到期的租约。

网络慢而线程仍在 active 中时，恢复器不会仅因为等待时间长就接管它。进程崩溃重启时，旧 Java 线程已经不存在；远端 ASR 任务却可能还在运行，需要根据已保存的远端 ID 查询。

提交结果时还会比对：

```text
请求里的 attempt_id 是否等于 tasks.current_attempt_id
```

不相等就拒绝新的结果写入。任务行锁确保检查和业务状态修改不会被并发事务任意穿插。

为什么依赖单实例？假设 A 在执行 task-A，而 B 的恢复器也扫描同一数据库。B 的 active 没有 task-A，但这只说明 B 没有执行，不说明 A 已停止。B 就可能错误撤销 A 的资格。行锁只能让修改依次发生，不能修正这个判断依据。

当前分析执行的一般临时失败有次数受限的自动重试；付费提交不确定、模型结果不合法等错误不会当成普通临时失败盲目重付。已安排好安全重试后可以 ACK 当前通知，因为新的调度意图已经落库；终态失败保存后拒绝消息到死信队列。

死信队列是存放被拒绝消息的队列，便于排查。当前没有“进死信就自动再次执行”的承诺。

源码：[TaskRecovery.java](../backend/src/main/java/com/agenticvideo/business/task/TaskRecovery.java)。

### 2.11 视频分析的面试回答

> 上传完成后，我先在同一个事务里保存素材、媒体任务和 Outbox。后台发布器把任务通知发到 RabbitMQ，允许重复投递。
>
> 分析由 Java 消费线程执行。消费者通过行锁和状态机领取任务，生成 attempt_id；正在执行或已完成的任务不会因重复消息再次启动。ASR 和 VLM 是独立任务，共享默认两个分析消费者，不是各占一个固定线程。
>
> ASR 提交后保存远端任务 ID，等待期间通过新的 Outbox 安排查询，不一直占住消费线程。模型回执单独保存，恢复时复用成功结果；付费提交结果未知时停止自动重付。
>
> 最后在事务里发布证据并更新任务状态，成功后 ACK。本机任务恢复依赖 active 集合和数据库状态，因此当前有单实例边界。

## 三 视频渲染任务 从用户点击导出讲起

### 3.1 确认方案和正式导出是两个操作

用户接受草稿后，Java 保存并确认不可变方案版本。不可变表示已经保存的版本不会被原地改写。正式渲染还需要用户另行请求导出。

导出请求指定具体版本、其中一条输出和 720p 或 1080p 规格。服务端检查确认记录、素材归属和可用性，固定片段顺序、剪辑区间、字幕、素材地址与哈希、编码参数和渲染器版本。

这样排队期间不会因为用户又发了一条聊天消息，渲染时就擅自换成另一份草稿。

接纳事务检查容量并保存 render_requests、EXPORT_RENDER 任务和 Outbox。相同幂等键与相同请求返回原记录；同一键换了版本或参数则拒绝。新幂等键的导出请求不能一概宣称会自动复用已有成片。

源码：[ExportRequests.java](../backend/src/main/java/com/agenticvideo/business/render/ExportRequests.java)。

### 3.2 渲染由谁执行

任务投递到 media.v1。这个队列当前只有一个消费者，prefetch=1，与媒体准备工作共享。

消费者先原子领取任务，然后直接调用媒体处理代码。Java 启动 FFmpeg 子进程，并等待其执行结束。子进程是操作系统运行的另一个程序，不等于额外的 Java 工作线程池。

FFmpeg 承担实际切片和编码，Java 负责准备参数、调用、检查结果和管理任务状态。整个耗时过程不放在一个长期数据库事务中。

### 3.3 每个 attempt 都有自己的文件地址

领取渲染任务时，代码创建一条初始为 STAGED 的产物记录，并分配类似下面的地址：

```text
exports/{requestId}/{attemptId}.mp4
```

STAGED 表示尚未发布。创建这条记录时，文件可能根本还没有生成。

不同 attempt 使用不同对象路径，避免恢复执行直接覆盖旧批次的文件。后续发布时，代码会检查产物 ID 和路径是否属于当前 attempt。

### 3.4 FFmpeg 实际做哪些工作

渲染器下载方案引用的素材，检查文件大小、哈希和媒体信息，再按方案切取片段。各片段统一分辨率、帧率和音频规格后拼接，根据方案添加字幕，编码为 H.264 视频、AAC 音频的 MP4。

参数由服务端根据结构化方案生成，不接受模型直接提供的一整条可执行命令。

完成后检查成片媒体信息、时长，计算文件大小和 SHA-256，再上传到本次 attempt 的对象地址。SHA-256 是用于识别内容的哈希值；相同内容会产生相同值，用来核对文件身份。

源码：[MediaRenderer.java](../backend/src/main/java/com/agenticvideo/business/media/MediaRenderer.java)。

### 3.5 上传成功为什么还不等于成片发布成功

对象存储和数据库是两个系统，数据库事务回滚不会自动删除已上传的 MP4。因此采用以下顺序：

```text
生成文件
  → 检查文件并上传对象存储
  → 调用完成方法
  → 检查当前 attempt、产物身份、媒体规格和对象大小
  → 事务内将产物改为 AVAILABLE，关联导出请求，完成任务
  → 返回消费线程
  → ACK
```

AVAILABLE 表示业务已经认可这个产物可以使用。文件物理存在和业务允许访问是两个状态。用户之后通过授权接口获取短期播放或下载链接；链接过期只需重新授权，不必重渲染。

源码：[RenderArtifacts.java](../backend/src/main/java/com/agenticvideo/business/render/RenderArtifacts.java)。

### 3.6 FFmpeg 渲染到一半崩溃怎么办

首先区分失败的是谁。

如果只是 FFmpeg 报错退出，而 Java 仍然运行，Java 执行器会捕获错误，将任务和 attempt 标记失败，保存失败原因，再拒绝消息到死信队列。当前普通渲染失败分支不会像安全分析失败那样自动安排重试。后续重新发起渲染时，从固定输入重新开始。

如果整个 Java 服务崩溃，任务可能遗留为 RUNNING。服务重启后，本机恢复器核查遗留任务，撤销旧 attempt，并在次数限制允许时通过 Outbox 重新安排执行。

当前没有渲染检查点。虽然会先生成各片段的中间文件，但没有把“哪些片段已可靠完成”作为可恢复进度持久保存。正常执行退出时清理临时工作目录；启动时也会清理符合规则的遗留目录。因此不能声称会从上次渲染的百分之五十继续。

如果以后长视频重渲染成本成为问题，可以设计分段检查点，校验并复用已完成片段；这不是当前已有能力。

源码：[MediaProcessing.java](../backend/src/main/java/com/agenticvideo/business/media/MediaProcessing.java)、[WorkDirectories.java](../backend/src/main/java/com/agenticvideo/business/media/WorkDirectories.java)。

### 3.7 已上传但尚未发布的文件为什么可能被清理

这是一个确实可能浪费计算资源的故障窗口：

```text
渲染成功，文件已上传
  → 完成事务尚未提交
  → Java 崩溃
```

当前文件检查结果由渲染器返回给完成方法，完成事务提交后才写入产物元数据。崩溃时对象可能完整存在，但数据库里仍是 STAGED，不能只凭对象存在就直接认定可以发布。

当前没有实现接管旧 attempt 已上传文件的恢复流程。恢复执行使用新 attempt 和新地址，旧 attempt 失效后的 STAGED 对象由清理逻辑回收。清理失败时保留待清理状态，后续扫描继续尝试。发布失败不是立刻删除文件，必须先满足对应 attempt 已失败、过期或取消等清理条件。

旧 attempt 失效不等于旧文件一定无效。可以通过重新核验文件、确认固定输入归属、协调接管与清理来复用它，但需要额外流程。当前选择实现简单，代价是部分故障下会重新渲染。

### 3.8 视频渲染的面试回答

> 用户确认方案后，还需要单独发起导出。接纳时固定版本、素材和编码参数，并在同一个事务里保存渲染请求、任务和 Outbox。
>
> media.v1 的 Java 消费线程领取任务后启动 FFmpeg。每个 attempt 使用独立文件路径，渲染和上传完成后检查产物，再事务性发布成片并完成任务，最后 ACK。
>
> FFmpeg 普通执行失败会记录失败，服务崩溃则由恢复器按规则重新调度。当前没有断点续渲染，也没有恢复复用已上传但未发布文件的能力；失效 attempt 的未发布对象会被清理。

## 四 Agent 任务 从用户发送一条消息讲起

### 4.1 为什么需要单独的 Python Worker

Python Worker 是一个独立后台进程，接收 Agent 任务，运行 LangGraph 和模型调用。Java 仍然负责用户权限、任务状态、证据范围、草稿校验和业务结果发布。

LangGraph 把 Agent 执行过程组织成多个节点，例如理解请求、决定下一步、检查动作、调用工具、观察结果和检查最终输出。节点之间按照当前状态流转。

Java 与 Python 不共享内存，所以 Java 不能使用自己的 active 集合判断 Python 是否还活着。这是引入租约和心跳的原因。

### 4.2 Java 先保存用户消息和固定输入

用户发送消息后，Java 在会话锁下保存消息、对话轮次、AGENT_TURN 任务、固定输入、输入哈希和 Outbox。

固定输入是这次执行应使用的消息和上下文。重投时不能再把最新聊天拼进去，否则同一任务可能第一次理解一个问题、第二次又理解另一个问题。

Outbox 将通知投递到 agent.v1。当前 Python 使用单消费者和 prefetch=1，并通过独占消费及本机锁等约束避免随意启动多个执行者。存在租约协议并不表示当前已经实现并验收多个 Worker 横向扩容。

### 4.3 为什么 MQ 只发通知 而不直接让 Worker 按消息执行

消息可以携带完整数据，很多事件处理系统就是这样设计的。但“拿到了输入”和“现在有权执行”不是一回事。

例如消息在队列等待时用户取消了任务；或者结果已经保存但 ACK 丢失导致重投。消息内容即使完整，也不能证明当前仍应执行。

因此 Worker 收到 taskId 后，向 Java 的 claim 接口领取任务。Java 原子检查状态，创建 attempt 并授予租约，同时返回固定输入。

这里检查的是最新执行资格，返回的是原先固定的任务输入，不是最新聊天。

完整消息也可以搭配领取协议。当前既然已经需要领取交互，就顺便返回输入，不必在消息中再携带一份完整副本。代价是增加 HTTP 交互并依赖 Java 可用；当前工具调用和结果发布本来就依赖 Java，所以接受这个取舍。

### 4.4 租约和心跳到底是什么

租约就是有期限的执行许可。领取成功后，Java 返回 attemptId、leaseToken 和 leaseExpiresAt。

- attemptId 标识当前执行批次。
- leaseToken 是执行凭据，调用内部接口时要携带。
- leaseExpiresAt 是许可到期时间。

当前 Java 领取时授予约 60 秒租约。Worker 在执行时运行心跳监督逻辑：无进度事件时默认约 10 秒请求一次心跳，节点进展也会触发检查。Java 验证资格后将到期时间延长到当前时间之后约 60 秒。

```text
领取任务，得到执行许可
  → Agent 执行，同时发送心跳
  → Java 确认仍允许继续并续租
  → Worker 使用新的到期时间继续监督
```

心跳失败、超过最后确认的期限或收到 STOP 时，Worker 取消本地执行。工具和结果接口仍会检查当前 attempt 及租约，不能只相信 Worker 自己会停止。

本地停止并不保证供应商撤销已经接收的请求，付费结果未知仍需单独处理。

源码：[worker.py](../agent-service/agent_service/worker.py)、[TaskExecution.java 的 claim 和 heartbeat 方法](../backend/src/main/java/com/agenticvideo/business/task/TaskExecution.java)。

### 4.5 Python 理解意图 Java 决定允许的范围

Agent 先判断用户是在问视频内容、开始制作、修改草稿，还是回答之前的澄清问题，再将结构化理解提交给 Java。

Java 根据当前会话和制作状态确定可信绑定，包括素材证据范围 scope、执行身份和编辑代次 editGeneration。scope 表示本次允许读取的固定素材与分析证据集合；编辑代次用于区分同一制作过程中不同轮次的有效编辑状态。

模型可以提出理解，不能自行授予权限。后续工具调用和结果提交都必须符合这些绑定。

### 4.6 Agent 循环怎样运行

Agent 不是一次模型调用直接产生最终结果，而是按需重复下面的过程：

```text
模型提出下一步动作
  → 程序检查动作、参数和预算
  → 调用 Java 工具读取证据
  → 保存观察结果
  → 再交给模型判断
  → 信息足够时回答或生成草稿，不足时继续读取或询问用户
```

真实模型可选择四个只读工具：list_assets、get_video_overview、search_evidence、read_video_range，分别用于列出素材、读取概览、检索证据和阅读指定时间范围。

Worker 的工具请求携带当前 attempt、租约凭据和编辑代次。Java 校验后才执行工具，并保存读取回执。生成草稿后，由程序安排 Java 强制校验，不让模型自行跳过。循环还受模型调用次数、工具调用次数、修复次数和无进展次数等限制。

Agent 可以生成草稿，但不能因此自行确认版本和正式导出。

源码：[graph.py](../agent-service/agent_service/runtime/graph.py)、[catalog.py](../agent-service/agent_service/tools/catalog.py)、[AgentRunTools.java](../backend/src/main/java/com/agenticvideo/business/agentrun/AgentRunTools.java)。

### 4.7 SQLite 检查点和调用回执分别保存什么

检查点是 Agent 执行状态的持久记录，例如已经读到哪些证据、当前草稿是什么、图接下来准备执行哪个节点。它用于恢复执行，不是最终业务结果的授权证明。

Python SQLite 还保存模型调用标识、输入哈希、响应和预算使用记录。同一调用恢复时，如果已有成功响应，可以复用；如果提交可能发生但响应未知，就停止自动重付。重试不会给原执行重新发一份预算。

Java PostgreSQL 则保存任务、授权范围、工具回执、草稿校验和对用户公开的结果。两者不能互相替代。

恢复是基于检查点和回执继续推进，不是恢复进程崩溃前的 CPU 执行位置，也不能保证任意节点中的任意外部操作都只执行一次。

源码：[calls.py](../agent-service/agent_service/runtime/calls.py)、[persistence.py](../agent-service/agent_service/runtime/persistence.py)。

### 4.8 结果为什么必须提交给 Java

Python 运行结束后，可能得到答案、通过校验的草稿、需要用户补充的信息，或者失败原因。Worker 通过 HTTP 提交给 Java。

Java 会核对执行资格、结果身份和编辑代次。答案引用必须能对应本执行的成功工具读取回执，并属于允许的证据范围；草稿必须对应当前有效的持久校验记录。

这里能保证引用来自已读证据，不表示程序已经证明回答每一句话都被证据充分支持。

检查通过后，在一个事务里保存公开消息、引用、草稿或澄清问题，同时更新任务、attempt 和执行结果。Worker 收到成功响应后才 ACK。

如果结果要求用户澄清，任务进入 WAITING_INPUT。问题已经落库，本次通知可以 ACK，不会一直占着消费者等待用户回复。

源码：[AgentRunResults.java](../backend/src/main/java/com/agenticvideo/business/agentrun/AgentRunResults.java)。

### 4.9 这里为什么更需要考虑重复提交结果

与 Java 内部方法调用不同，Python 向 Java 提交结果要经过网络：

```text
Java 已提交结果事务
  → HTTP 成功响应在途中丢失
  → Python 不知道提交是否成功
```

结果发布接口因此支持相同结果重放：已有结果与新提交一致时返回原处理结果，不再重复写一条助手消息；内容不同则拒绝，同时仍校验提交身份。

不过当前 Worker 不是无限循环重发 result 请求。正常通信故障会导致未确认消息在连接关闭后重新投递；如果再次领取发现 Java 已有持久完成结果，就直接跳过执行并 ACK。

所以要同时理解：发布方法本身支持幂等重放，而 MQ 重投通常先由任务状态拦住。不能把两者混成同一条必经路径。

### 4.10 Worker 崩溃后怎样恢复

Worker 崩溃后心跳停止，Java 恢复器检查租约到期的运行任务。在锁定并再次确认过期后，将旧 attempt 标为 EXPIRED，把未取消的任务改回 PENDING，并写入新的 Outbox。

Worker 再领取时获得新 attempt 和租约，但继续使用原来固定的执行输入与对应检查点。已保存的模型回执可复用，付费结果未知不能强制从头重付。显式重试也只允许符合可恢复条件的失败，不是任何失败都可以自动清空后重来。

在远程协议中，旧执行失去租约但迟到提交结果确实是需要考虑的情况。Java 会校验 current_attempt_id、凭据和有效期，拒绝失效执行发布新结果。

取消时，Java 先记录取消请求，Worker 心跳收到 STOP 后停止本地工作并回报；若 Worker 已不可达，租约恢复会处理取消状态。收到取消请求不表示外部模型已经停止或费用已撤销。

Agent 的失败如果已作为业务结果保存，Worker 可以 ACK；传输故障则保持未确认并重新连接。不要套用“所有 Agent 业务失败都会进死信”的说法。当前畸形通知会被拒绝到死信队列。

源码：[AgentRunRecovery.java](../backend/src/main/java/com/agenticvideo/business/agentrun/AgentRunRecovery.java)。

### 4.11 Agent 的面试回答

> Java 接纳用户消息时固定执行输入，并将 Agent 任务和 Outbox 一起落库。Python Worker 消费 agent.v1 后，先向 Java 领取 attempt 和租约，再运行 LangGraph。
>
> 执行期间通过心跳续租，失去租约就停止。模型理解用户意图后，由 Java 绑定允许的证据范围和编辑代次；工具调用和结果提交都要带执行凭据。Python 保存检查点、模型回执和预算，Java 保存业务状态与公开结果。
>
> Worker 提交答案或草稿后，Java 校验已读引用和草稿校验记录，在事务中发布结果，再由 Worker ACK。崩溃后通过租约过期重新调度，沿原执行状态恢复，不自动重置预算或重复未知付费请求。

## 五 回到简历原句 哪些词应该怎样解释

### 5.1 最终一致是什么意思

它不是数据库和 RabbitMQ 在每个瞬间都同步，而是先可靠保存数据库中的任务与发送意图，再通过发布、重试和消费逐步推进。中间可以存在“任务已经创建，消息还没发出”的状态。

最终一致不表示最终一定业务成功。任务最终明确失败，也比一直显示运行中却没有恢复依据更可解释。

### 5.2 至少一次和幂等如何配合

至少一次投递允许重复，消费幂等控制重复产生的业务效果。这里不是让 MQ 绝不重复，而是让重复消息到达时仍按数据库状态处理。

提交阶段使用事务，避免“证据已写入但任务还没完成”的部分数据库提交。外部模型调用和对象存储操作不能随数据库事务回滚，需要各自的回执、状态和清理流程。

### 5.3 三种复用不要混在一起

| 说法 | 具体含义 |
| --- | --- |
| 重复消息不重复执行 | 任务已运行或已完成，领取时跳过 |
| 模型回执复用 | 恢复时使用已有模型响应或远端任务 ID，不重新发起同一次模型工作 |
| 完成结果重放 | 同一完成请求重复调用时，返回已有业务处理结果，不重复写业务记录 |

视频分析当前主要依赖第一项处理 MQ 重复；第二项处理付费恢复。第三项是提交方法提供的能力，不能描述成本机消费线程必然会发生的步骤。

### 5.4 面试时不要说过头

- 不说“消息绝不会丢、所有调用恰好一次”；说清 Outbox、确认、重试和幂等分别处理哪个故障窗口。
- 不说“所有任务都靠 Worker 租约”；Java 本机分析与渲染使用 active 和 attempt，Python Agent 才通过网络租约维持资格。
- 不说“ASR 和 VLM 各占一个线程”；它们共享分析队列的消费者。
- 不说“ACK 就是整个业务成功”；ASR 安排下一次查询后也会 ACK，Agent 发布澄清问题后也会 ACK。
- 不说“死信队列会自动重试”；当前没有这个默认行为。
- 不说“渲染能断点继续、旧成片一定复用”；当前没有这两项能力。
- 不说“租约到期就能取消供应商请求”；租约控制本系统执行资格，不能撤销已经发生的外部工作。
- 不说“消息只放 ID 才可靠”；消息内容和执行授权是两个选择，可靠性来自完整协议。

## 六 最后用三个故障问题检查理解

### 6.1 数据库创建任务成功 发消息前崩溃怎么办

任务与 Outbox 已在同一事务保存。重启后发布器继续发送。如果数据库事务本身没提交，则两者都没有生效，不会留下只创建一半的数据库状态。

### 6.2 业务结果已保存 ACK 前断线怎么办

消息可能重投。消费者检查任务已完成，跳过业务执行再确认。不要回答“再执行一遍，然后靠完成回执兜住所有操作”。

### 6.3 外部工作已经做了 但本地没确认怎么办

先区分外部工作是什么。模型调用有远端任务 ID 或已保存响应时继续恢复；付费提交未知且缺少恢复信息时停止自动重付。渲染文件上传后尚未发布，当前没有接管复用能力，可能重新渲染并清理旧对象。Python 结果已经被 Java 保存但响应丢失，后续领取会看到完成状态，发布接口也支持一致结果重放。

这三个问题分别对应任务意图、业务结果和外部副作用。把具体发生在哪里讲清楚，就不需要用一句“加重试保证可靠”概括所有情况。

## 七 补充 项目里的重试到底由谁安排

### 7.1 先区分消息重投和任务重试

RabbitMQ 能重新投递尚未确认的消息，但它不知道某次模型调用是否可以再次付费，也不知道业务允许失败多少次。

当前项目把“是否再执行、什么时候再执行、已经失败多少次”放在 Java 和数据库里管理。RabbitMQ 负责传递通知，没有使用 TTL 重试队列或延迟消息插件来安排业务重试。TTL 指消息允许保留的时间；有些系统利用消息到期和死信转发组织延迟重试，但当前项目没有采用这条路线。

需要分别理解下面三种情况。

### 7.2 消息发送失败 由 Outbox 发布器再次发送

如果 RabbitMQ 暂时连接不上，或者发布确认没有成功，发布器不会删除发送记录，而是更新这条 Outbox：

```text
status = PENDING
available_at = 下一次允许发送的时间
```

发布器默认约每秒扫描一次。扫描时只取已经到达 available_at、对应任务也允许调度的记录。失败后等待时间依次增加为 2、4、8、16、32、60 秒，之后最多等待 60 秒。

例如 10:00:00 发送失败，安排 10:00:02 再发。等待的这两秒，发布器不需要一直占着线程睡眠；它把时间记进数据库，后续扫描时再处理。

因此，这里的延后发送发生在应用和数据库里，不是 RabbitMQ 在内部替我们计时重试。重启也不会让这条已提交的发送记录消失。

### 7.3 分析执行失败 先保存重试安排 再 ACK

假设 task-A 是一个分析任务，attempt-1 发生了允许安全重试的临时错误。执行器在同一个数据库事务里完成以下操作：

```text
将 attempt-1 标为 FAILED
  → 增加 task-A 的失败计数
  → 将 task-A 改回 PENDING
  → 清除旧的 current_attempt_id
  → 将 next_execution_at 设为约 5 秒后
  → 新增一条 available_at 为约 5 秒后的 Outbox
  → 提交事务
```

next_execution_at 表示任务最早允许再次执行的时间；available_at 表示通知最早允许发送的时间。一个约束业务任务，一个约束发送记录。

事务提交成功后，消费线程 ACK 当前消息。约 5 秒后，发布器发送新通知，消费者重新领取 task-A，创建 attempt-2，再根据数据库里已经保存的结果继续工作。

```text
业务任务：仍是 task-A
执行批次：attempt-1 变为 attempt-2
MQ 通知：新创建一条
```

为什么失败了还 ACK？因为这个失败已经被处理，下一次执行的安排也已可靠保存。当前消息不需要一直留着承担重试职责。

如果保存重试安排的事务没有提交成功，就不能按这条成功路径 ACK。否则可能把消息移除了，却没有留下后续安排。

当前本机分析分支对 ANALYSIS_EXECUTION_FAILED 增加 local_failure_count，小于 3 才安排重试，达到 3 则记录终态失败。这里是失败计数，不是简单地限制整个任务最多领取三次：ASR 正常延后查询也会产生新 attempt，而且正常 defer 会重置这个失败计数。

付费提交结果不确定、模型响应不合法等情况，不按普通临时错误自动重试。渲染普通执行失败也不走这条分析重试逻辑。

### 7.4 未确认消息遇到连接断开 由 RabbitMQ 重新投递

另一种情况是消费者还没来得及 ACK，连接就断开了。RabbitMQ 可以将未确认消息重新投递。这是消息重投，不是 Java 已经判断业务可以重做。

消费者再次收到通知后，还要查看数据库：任务已成功就跳过；仍有有效执行就不能抢占；执行已经退出或租约过期，则由相应恢复器处理资格并安排恢复。

当前死信队列用于保存被拒绝的消息，没有自动把死信循环送回原队列。进入死信不等于已经安排下一次执行。

### 7.5 面试时怎样回答重试问题

> 业务重试由 Java 和数据库管理，不是交给 RabbitMQ 自动决定。发送失败时，Outbox 发布器记录下次发送时间并退避重试。允许重试的分析失败，则在事务里更新任务状态、失败次数和下次执行时间，同时新增 Outbox；提交成功后 ACK 当前消息，到期再投递新通知。消费者断线造成的未确认消息重投是另一层机制，重新收到消息后仍要检查业务执行资格。

源码：[发布重试](../backend/src/main/java/com/agenticvideo/business/messaging/TaskDispatch.java)、[任务失败处理与 deferLocal](../backend/src/main/java/com/agenticvideo/business/task/TaskExecution.java)、[消费确认](../backend/src/main/java/com/agenticvideo/business/messaging/TaskConsumers.java)。

## 八 补充 同步调用 VLM 和 Embedding 为什么还能恢复一部分

### 8.1 同步调用不表示整个任务只有一次调用

同步调用的意思是：发出一次请求后，当前线程等待响应，再继续执行后面的代码。

一个视频有多张代表帧，VLM 可以分别调用；需要生成向量的文本很多，Embedding 可以分批调用。每次调用仍是同步的，但每次成功后都单独保存记录，不必等整个视频分析完成才一次性保存。

恢复依靠这些数据库记录，不依靠保留旧线程，也不是把程序跳回崩溃前的某一行。

### 8.2 VLM 每完成一张不同图片 就保存一次进度

假设有五张内容不同的代表帧，系统在 vision_model_calls 中建立对应调用记录。尚未提交时状态为 READY。

处理一张图片时，步骤是：

```text
短事务：记录 SUBMITTING，表示准备发起调用
  → 事务外：同步调用 VLM 并等待响应
  → 短事务：保存完整原始响应
  → 解析并检查观察内容和用量
  → 短事务：保存结果，状态改为 SUCCEEDED
  → 开始下一张图片
```

假设前三张已成功，第 4 张还没提交时进程崩溃。恢复后重新读取数据库，会得到：

| 图片 | 数据库中的状态 | 新执行的动作 |
| --- | --- | --- |
| 图片 1 | SUCCEEDED | 跳过模型调用 |
| 图片 2 | SUCCEEDED | 跳过模型调用 |
| 图片 3 | SUCCEEDED | 跳过模型调用 |
| 图片 4 | READY | 调用 VLM |
| 图片 5 | READY | 调用 VLM |

程序仍然可以从列表开头遍历，但遍历到已成功记录就 continue，也就是直接进入下一轮循环。这不需要再次调用前三张图片的模型。

实际记录按分析版本、图片内容哈希和模型匹配。同一分析版本中，相同图片内容可以共用模型调用结果，但图片在视频里出现的时间分别保留。不能把这种复用理解成丢掉重复画面的时间信息。

### 8.3 未成功的部分也不能一律重新调用

第 4 张处理到不同位置时崩溃，恢复动作不同：

| 崩溃位置 | 数据库留下了什么 | 恢复方式 |
| --- | --- | --- |
| 准备提交之前 | READY | 可以发起调用 |
| 已保存响应，尚未完成解析和结果保存 | 原始响应 | 读取响应，继续本地处理 |
| 成功结果已提交 | SUCCEEDED 和结果 | 跳过 |
| 请求可能发出，但没有保存到响应 | 提交中或不确定记录 | 停止自动重付，不能直接重新调用 |

例如 VLM 已返回响应，数据库也保存成功，只是解析前崩溃，下次就使用原响应解析。代码中的 RESUME_RESPONSE 表示恢复处理已保存的响应，不是重新向供应商请求一次。

如果供应商已处理图片，但响应在网络途中丢失，当前同步 VLM 调用没有 ASR 那样用于后续查询的远端异步任务 ID。系统不能承诺找回那次结果，也不能假设没有计费。因此“支持部分恢复”不等于“所有中断都能自动继续完成”。

### 8.4 Embedding 按文本批次保存进度

Embedding 可以一次处理多条文本，当前待处理文本按每批最多 10 条组织，并在 embedding_batches 中保存批次输入、状态、原始响应和向量结果。

例如 25 条待处理文本，分成三批：

```text
批次 0：文本 1 到 10
批次 1：文本 11 到 20
批次 2：文本 21 到 25
```

前两批成功、第三批尚未提交时中断，恢复后跳过批次 0 和批次 1，只处理批次 2。第三批已有响应时继续解析；提交结果未知时停止自动重新调用。

所有批次完成后才继续写入 Qdrant。如果向量已保存，随后 Qdrant 写入失败，恢复时可以跳过成功的 Embedding 批次，重新进行索引写入，不需要再生成相同向量。

新 attempt 表示这次恢复由谁执行，不表示把此前图片调用和文本批次记录清空。

### 8.5 面试时怎样回答部分恢复问题

> 同步只表示一次调用要等待响应，整个任务仍然可以拆成多次调用。VLM 按不同图片保存调用记录，Embedding 按文本批次保存记录，每部分成功后独立提交。恢复时重新读取状态，成功的跳过，已有响应的继续解析，未提交的才发起调用。如果请求可能提交但没有响应，就停止自动重付，而不是把所有未成功记录都重新调用一遍。

源码：[VLM 和 Embedding 的执行循环](../backend/src/main/java/com/agenticvideo/business/analysis/AnalysisProcessing.java)、[图片调用记录](../backend/src/main/java/com/agenticvideo/business/analysis/VisualAnalysis.java)、[Embedding 批次记录](../backend/src/main/java/com/agenticvideo/business/search/SearchIndexes.java)。

## 九 补充 语音结果之后的索引构建 如何异步执行

### 9.1 先区分两种同步和异步

相对于语音分析任务，索引是异步的：语音发布时只安排索引任务，不等待向量生成和 Qdrant 写入完成。

但索引任务被领取后，消费线程会同步调用 Embedding、等待响应，再写 Qdrant。这两句话并不矛盾：前一句说两个任务之间的关系，后一句说一个任务内部如何执行。

不需要额外线程池才能称为异步任务。通过持久任务和 MQ，让一项工作稍后由后台消费者领取执行，也是在异步推进。

### 9.2 语音发布事务中保存哪些内容

ASR 转写结果已经保存在模型调用记录里，接下来完成语音业务处理：

```text
数据库事务开始
  → 校验并写入语音证据
  → 写入检索单元及引用关系
  → 调用 indexes.enqueue，安排或复用索引任务
  → 更新语音任务和 attempt 为成功
数据库事务提交
  → ACK 语音任务消息
```

检索单元是供搜索使用的文本记录。例如一段转写语句可以形成一个检索单元，同时保留它对应哪些原始证据。

enqueue 在这里表示接纳任务，不表示立刻调用模型。需要新建索引任务时，它会保存 INDEX_BUILD、索引构建记录、批次信息和 Outbox；如果已有符合条件的索引任务在运行，则复用。

这些数据库操作与语音业务发布一起提交。事务失败时，证据和新创建的调度安排一起回滚；不会因为这次事务只成功了一半，留下语音证据而漏掉对应的新任务安排。

此时没有在事务里调用 Embedding，也没有向 Qdrant 写入数据。

### 9.3 事务提交后 另一轮消费才开始索引工作

```text
Outbox 到期并发送 INDEX_BUILD 通知
  → analysis.v1 队列
  → 某个消费线程领取任务
  → 读取固定的文本批次
  → 调用 Embedding 并保存各批结果
  → 向 Qdrant 写入索引数据
  → 回读核对
  → 发布索引并完成任务
  → ACK 索引任务消息
```

不一定由另一条线程执行，也可能是刚才处理语音的线程随后领取到了索引任务。关键是这是一次独立的任务领取和消息处理，不是原语音发布事务继续等待耗时操作。

### 9.4 索引任务内部也没有一个从头包到尾的大事务

| 步骤 | 是否在 PostgreSQL 事务里 | 目的 |
| --- | --- | --- |
| 领取任务、创建 attempt | 是 | 原子获得执行资格 |
| 记录 Embedding 准备提交状态 | 是，短事务 | 保存调用进度 |
| 调用 Embedding，等待响应 | 否 | 执行外部模型请求 |
| 保存响应和向量结果 | 是，短事务 | 为恢复留下依据 |
| 写入 Qdrant | 否 | 写入实际检索数据 |
| 回读 Qdrant 并核对 | 否 | 检查构建结果是否符合要求 |
| 发布索引并完成任务 | 是，短事务 | 一起更新业务可用状态和任务状态 |

短事务不是特殊的数据库功能，只是把事务限制在必要的数据库操作内，尽快提交，不长期占着锁等待外部服务。

Qdrant 是独立的检索服务。PostgreSQL 的事务回滚不能撤销已经完成的 Qdrant 写入，所以不能靠给整个 Java 方法加事务，就让两个系统一起回滚。

### 9.5 为什么还要区分写入索引和发布索引

系统用 generationId 标识某一次构建的索引版本，也叫索引代次。构建时把这个标识带到 Qdrant 数据里；写入并核对成功后，再在数据库中发布这一代索引，告诉查询流程可以使用它。

```text
Qdrant 已写入新一代数据
  → 回读核对通过
  → 数据库事务重新检查执行资格
  → 发布可用索引代次，完成任务
```

这样不会仅因为已经写进去一部分数据，就把这一代当成构建成功。重建时原有有效代次仍可继续使用，新的代次通过检查后才更新发布记录。

当前索引任务固定的是它接纳时的检索单元。如果构建过程中又发布了新的观察记录，完成时还有检查并安排后续构建的逻辑，不是让当前任务的输入在执行过程中随意变化。

### 9.6 面试时怎样回答索引事务问题

> 索引相对于语音分析是独立的异步任务。语音发布事务只保存证据并安排索引任务，提交后由 Outbox 发通知。索引消费者再生成向量、写入 Qdrant 并回读核对，这些网络操作都在 PostgreSQL 事务外。调用状态和结果用短事务保存，核对通过后再在事务里发布可用索引并完成任务，最后 ACK。

源码：[语音结果发布](../backend/src/main/java/com/agenticvideo/business/analysis/SpeechAnalysis.java)、[索引任务接纳与发布](../backend/src/main/java/com/agenticvideo/business/search/SearchIndexes.java)、[Qdrant 写入](../backend/src/main/java/com/agenticvideo/business/search/SearchIndexBuilder.java)、[索引核对与任务完成](../backend/src/main/java/com/agenticvideo/business/task/TaskExecution.java)。

## 十 补充 为什么可以称为视频分析流水线

### 10.1 流水线指的是多个步骤有顺序地协作

视频分析可以叫作“视频分析流水线”。这里的流水线，是把一项较大的工作拆成多个步骤，前面的步骤提供结果，后面的步骤拿到所需结果再继续处理。

例如，ASR 需要音频，所以要先完成音频准备；Embedding 需要文本，所以要先有语音或画面分析产生的证据。把这些依赖关系组织起来，就是视频分析的整体流程。

不是只要有多个任务，就一定构成流水线。关键是这些任务共同完成同一个目标，而且前后存在明确的输入、输出和执行条件。

### 10.2 项目中各阶段如何衔接

从一段视频上传完成开始，可以这样理解：

```text
视频上传完成
  ↓
媒体校验与准备
  ├─ 准备音频 → ASR 转写 → 发布语音证据
  └─ 准备代表帧 → VLM 分析 → 发布画面和文字证据

已经发布的证据
  ↓
安排索引构建任务
  ↓
Embedding 生成文本向量
  ↓
写入 Qdrant，核对后发布索引
```

这张图表达的是业务依赖。通常媒体准备会尝试准备音频和代表帧；缺少代表帧时还可以安排单独的画面准备任务。没有音轨的视频不需要执行 ASR。

语音和画面是两个分支，可以分别推进。它们不是固定由两个专属线程执行，也不是一定先把语音全部做完才开始画面分析。

索引也不是必须一直等到两个分支都成功才构建。系统根据已经发布的证据安排索引任务；如果构建期间又产生了新证据，会检查并按需要安排后续构建。因此，一种来源失败，不会直接抹掉另一种来源已经成功的结果。

### 10.3 下一阶段不是由 RabbitMQ 自己决定的

RabbitMQ 不知道“ASR 完成后应该构建索引”。这个顺序写在 Java 业务代码里。

以语音分析完成为例：

```text
Java 发布语音证据
  → 在数据库事务中安排或复用索引任务
  → 需要新建任务时，同时保存索引任务和 Outbox
  → 事务提交后，发布器发送通知
  → 消费者领取索引任务，执行下一阶段
```

所以，这条流水线由三部分配合：Java 代码规定何时可以进入下一步，数据库保存任务输入、状态和结果，RabbitMQ 通知消费者执行。

“异步流水线”表示这些阶段通过后台任务逐步推进，用户请求不需要一直等待所有阶段结束。它不表示每个阶段内部都使用异步网络接口。VLM 和 Embedding 即使采用同步调用，也可以是这条异步流水线的一部分。

### 10.4 为什么更适合说阶段任务 而不是子任务

从业务上看，媒体准备、语音分析、画面分析和索引构建都属于一次视频分析，所以把它们称为子任务并非完全无法理解。但面试时，“子任务”容易让人联想到另一种具体设计：

```text
创建一个父任务
  → 父任务统一创建多个子任务
  → 等待全部子任务完成
  → 汇总并更新父任务结果
```

当前实现不应直接描述成这种统一父子任务调度。更准确的说法是“阶段任务”：相关任务通过素材、分析版本和阶段状态关联，由业务代码安排后续处理。

另外，阶段和数据库任务也不必一一对应。例如 Embedding 和写入 Qdrant 是两个处理步骤，但目前都在 INDEX_BUILD 任务中推进。VLM 对多张图片的调用记录，也不等于每张图片都有一条独立的 MQ 任务。

因此，不要把整个流程理解成“每个小步骤都必须新建一个任务”。项目是在需要独立调度和恢复的地方拆出任务，在任务内部用调用记录保存更细的进度。

### 10.5 拆成阶段之后 失败时有什么好处

假设语音转写和画面分析都已成功，索引写入失败。因为前面的结果已经保存，恢复索引工作时不需要重新转写音频、重新理解所有图片。

如果失败发生在某个 VLM 调用或 Embedding 批次中，还可以进一步查看调用记录，跳过已成功部分，处理能够安全恢复的部分。

不过，“流水线”这个名字本身不会带来恢复能力。能够恢复，是因为代码保存了任务状态、调用结果和后续调度安排，并明确规定了何时重试、何时停止。付费提交结果未知时仍然不能盲目重新调用。

### 10.6 面试时怎样介绍这条流水线

> 我把视频分析组织成了一条由数据库任务和 MQ 推进的异步流水线。视频上传后先进行媒体校验和准备，再分别做语音和画面分析，将结果保存成带时间信息的证据。已有证据发布后，再安排向量生成和检索索引构建。各阶段保存自己的状态和结果，失败时根据已完成的部分恢复，避免每次都从头分析整段视频。

如果面试官继续问使用了什么工作流框架，可以回答：

> 这条分析流水线由 Java 业务代码、数据库状态和 RabbitMQ 协作实现，没有使用独立的通用工作流引擎。LangGraph 用于 Python Agent 的理解、工具调用和结果生成流程，不负责调度这条视频基础分析流水线。

工作流引擎是专门管理步骤依赖、调度和执行状态的软件。当前项目没有把这些分析步骤交给这样的通用引擎，而是按现有业务需要在 Java 中实现。

源码：[媒体处理](../backend/src/main/java/com/agenticvideo/business/media/MediaProcessing.java)、[语音分析与后续索引安排](../backend/src/main/java/com/agenticvideo/business/analysis/SpeechAnalysis.java)、[画面分析](../backend/src/main/java/com/agenticvideo/business/analysis/VisualAnalysis.java)、[索引任务](../backend/src/main/java/com/agenticvideo/business/search/SearchIndexes.java)。

## 十一 面试时可以怎样逐步展开

先用第一节的一分钟回答讲清共同流程：保存任务和发送意图、投递通知、领取执行资格、保存结果、确认消息。随后按视频分析、视频渲染、Agent 的顺序说明差别。面试官追问某个环节时，再展开对应的异常情况，不必开头就把所有状态、表名和超时时间说出来。

### 11.1 先解释为什么需要这套设计

**问：你为什么使用 Outbox，而不是创建任务后直接发送 MQ？**

> 因为数据库提交和发送消息是两个操作。如果任务已经保存，但发送前服务崩溃，就会留下没人处理的任务。我把任务和待发送通知放在同一个数据库事务里保存，再由发布器发送。发送失败时，数据库里仍有通知记录，可以继续重试。RabbitMQ 已经收到消息但发布状态没保存时，也可能重复发送，所以还需要消费端检查任务状态，不能只靠 Outbox 解决所有问题。

**问：消息重复了，消费者怎样保证幂等？**

> 消费者先根据任务 ID 领取任务。领取时锁定任务行，检查它是否待执行、是否到达执行时间，然后创建本次 attempt，把任务改为运行中，这些操作一起提交。另一个消费者再来时，看到任务已经运行或完成，就不会再次启动业务。如果结果已保存但 ACK 丢失，重投后也会因为任务已完成而跳过。这里允许重复收到消息，但控制重复业务执行。

### 11.2 用视频分析讲清任务如何推进和恢复

**问：以视频分析为例，整个任务是怎样执行的？**

> 上传完成后先创建媒体准备任务，准备好音频和代表帧，再分别推进语音和画面分析。分析任务由 Java 消费线程执行，ASR、VLM 和索引工作共享分析消费者。ASR 提交后保存供应商任务 ID，尚未完成就保存下次查询时间和新的 Outbox，结束本次执行并 ACK。下一次领取时查询原任务，不重新提交音频。结果准备好后，事务内发布证据、更新任务状态，并安排后续索引构建。

**问：模型调用失败后，为什么不直接从头重试？**

> 因为请求超时不代表供应商没有接收。直接重发可能导致重复处理和计费。我会保存每次调用的状态、原始响应和成功结果。恢复时，已成功的直接复用；有响应但还没处理完的，继续解析；ASR 已有远端任务 ID 的，继续查询。如果可能已提交但没有响应，也没有可查询的任务 ID，就停止自动重付，保留不确定状态。

**问：VLM 和 Embedding 是同步调用，为什么还能恢复已完成的部分？**

> 同步是指一次请求发出后等待响应，不表示整个视频只有一次请求。VLM 按不同图片保存调用结果，Embedding 按文本批次保存结果。如果前三张图片已完成，后面的还没提交，恢复时从数据库读取进度，跳过前三张，只处理能够安全继续的部分。恢复的是已保存的业务进度，不是让原来的线程从崩溃位置继续运行。

**问：重试由 RabbitMQ 负责吗？失败后为什么还能 ACK？**

> 是否允许重试、什么时候再执行，由 Java 和数据库决定。允许重试的分析失败，会在事务里保存失败次数、下次执行时间和新的 Outbox，然后 ACK 当前消息。这里 ACK 表示本次通知已处理，后续安排已经保存，不表示整个分析已成功。RabbitMQ 对未确认消息的重新投递是另一回事，收到重投消息后仍要检查任务状态。当前死信队列也不会自动重新执行任务。

**问：语音结果保存后，索引是在这个事务里直接构建吗？**

> 语音发布事务保存证据并安排索引任务，不在里面等待 Embedding 或写 Qdrant。事务提交后，索引任务通过 MQ 通知被领取，再生成向量、写入 Qdrant 并回读核对。这些网络操作在 PostgreSQL 事务外执行，状态和调用结果用短事务保存，最后再事务性发布可用索引并完成任务。

### 11.3 接着说明渲染为什么需要单独管理文件

**问：视频渲染和视频分析的可靠性处理有什么不同？**

> 两者共用 Outbox、任务领取和 attempt 校验，但渲染会产生实际文件。用户单独发起导出时，我先固定方案版本、素材和编码参数，再创建渲染任务。Java 消费线程领取后启动 FFmpeg，每个 attempt 使用独立的文件路径。渲染和上传完成后，还要检查产物并在数据库中发布，才能作为正式成片使用，随后才 ACK。文件已经上传与业务发布成功是两件事。

**问：FFmpeg 渲染到一半崩溃，能从中间继续吗？**

> 当前没有渲染检查点，不能从完成百分比继续。如果只是 FFmpeg 报错，Java 会记录任务失败，普通渲染失败不会自动走分析任务的重试流程。如果整个 Java 服务崩溃，重启后的恢复器会按规则检查遗留任务，在次数限制允许时重新调度。重新执行仍然从固定输入开始，不会自动复用上次的中间文件。

**问：文件已经上传，但发布失败，为什么还可能重新渲染？**

> 因为数据库事务不能回滚对象存储中的文件。当前实现没有接管旧 attempt 未发布文件的恢复流程，所以新执行使用新路径，旧执行失效后的未发布对象由清理程序回收。旧文件不一定坏了，重新核验后复用是可以设计的，但当前没有实现。这个取舍是流程比较简单，代价是部分故障下会浪费已经完成的渲染工作。

### 11.4 最后说明 Python Agent 为什么使用租约

**问：Agent 放在 Python Worker 后，执行管理有什么不同？**

> Java 不能通过自己的内存判断 Python 是否还在执行，所以 Worker 收到通知后，需要向 Java 领取本次 attempt 和有期限的执行许可，也就是租约。执行期间通过心跳续租；如果租约失效就停止本地工作，Java 的工具和结果接口也会检查执行资格。Python 保存检查点和模型回执，Java 保存任务状态和公开结果。Worker 提交结果并收到成功响应后，才确认 MQ 消息。

**问：为什么消息只通知任务 ID，还要再领取一次？**

> 拿到了任务内容，不代表现在仍有权执行。排队期间任务可能取消，也可能已经完成却因为 ACK 丢失而重投。因此领取时要检查数据库中的当前资格，同时返回这次任务原先固定的输入。完整消息也可以配合领取机制使用；当前既然需要这次交互，就通过领取返回输入。代价是多一次 HTTP 请求，并依赖 Java 服务可用。

**问：Worker 失联后又回来提交旧结果，会发生什么？**

> 心跳停止后，Java 在租约到期时撤销旧 attempt，并按规则重新安排任务。旧 Worker 之后即使恢复连接，也不能凭旧资格发布新结果，因为接口会检查当前 attempt、租约凭据和有效期。新的执行则根据原输入、检查点和调用回执恢复。租约能控制系统内的执行和发布资格，但不能撤销供应商已经接收的模型请求。

### 11.5 被问到设计边界时，要把本机和远程执行分开

**问：Java 视频分析和渲染也靠心跳租约恢复吗？可以直接部署多个实例吗？**

> 当前本机任务使用数据库状态和 Java 进程内的 active 集合判断执行是否仍在运行，没有采用 Python Worker 那套网络租约。线程还在 active 中时，不会仅因为网络慢就接管。这也使本机恢复依赖单实例：另一个实例看不到正在执行任务的实例的 active 集合，可能误判任务已退出。因此不能因为使用了行锁和 attempt，就宣称当前本机恢复已经支持多实例部署。

回答这些问题时，始终说明“哪一步已经成功、哪一步还没成功、恢复时读取什么记录”。例如“模型结果已保存，但证据事务没提交”和“证据事务已提交，但 ACK 没发出”需要不同处理，不能都概括成重新执行一次。
