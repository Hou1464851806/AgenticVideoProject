## 1. 输入理解与假设／缺失信息

### 1.1 项目定位与需求背景

项目面向视频理解与剪辑：用户上传视频，系统准备媒体、分析语音和画面、建立检索证据；Agent 根据自然语言请求读取证据、生成回答或剪辑草稿；用户接受草稿后冻结方案版本，再按显式操作预览或导出。

工程难点来自不同环节的约束叠加：上传可能中断，消息可能重复，进程可能退出，外部模型可能已经收费但响应丢失，模型输出可能合法却不符合用户意图，渲染还会竞争 CPU、内存和磁盘。面试应围绕这些具体问题解释设计。

技术栈的当前口径为 Java／Spring Boot、Python／LangGraph、PostgreSQL、Redis、RabbitMQ、S3 兼容对象存储、Qdrant、FFmpeg，以及模型调用和 Langfuse 观测适配。当前 [Compose 配置][S01]使用 Silo；简历中的 MinIO 应核对历史使用背景，或改为“S3 兼容对象存储”。

### 1.4 先讲清楚两条主链路和状态归属

```mermaid
flowchart LR
  A[上传与分片确认] --> B[媒体验证与准备]
  B --> C[语音和视觉分析]
  C --> D[证据与索引]
  U[用户消息] --> J[Java 固定上下文并接纳任务]
  J --> W[Python Worker 与 LangGraph]
  D --> R[受控读取工具]
  W --> R
  R --> W
  W --> V[Java 校验与结果发布]
  V --> Q[证据问答或剪辑草稿]
  Q --> H[用户显式接受草稿]
  H --> F[冻结方案版本]
  F --> E[显式请求正式导出]
  Q --> P[显式请求草稿预览]
```

图中为业务依赖的概念图，不表示 ASR、视觉、索引在当前实现中已全部并行。草稿预览、接受草稿和正式导出是不同操作；不能说 Agent 生成草稿后自动确认并导出。

| 状态或数据 | 当前归属与作用 | 面试要说明的边界 |
| --- | --- | --- |
| 项目、素材、任务、执行代次、方案版本、证据身份 | PostgreSQL 是业务事实来源 | 业务状态不能以 MQ 是否还有消息或 LangGraph 是否结束替代 |
| 任务通知 | RabbitMQ 与 Outbox | 消息用于唤醒执行；重复通知允许出现 |
| 原始视频、帧、预览和导出产物 | 对象存储 | 对象写入与业务数据库提交不是同一事务 |
| 检索索引 | Qdrant 派生数据 | 可按受控代次重建；不得成为权限和版本事实来源 |
| Agent 执行进度、调用回执和消耗 | Python SQLite／checkpoint 及业务关联记录 | checkpoint 回退不能撤销外部付费请求；持久卷丢失不在当前恢复保证内 |
| 上传准入额度 | Redis 令牌桶 | 这是限流证据，不等于已有完整业务缓存体系 |
| Trace 与模型轨迹 | Langfuse 适配与日志 | 观测故障不应改写业务结果；现有接入不等于跨语言全链路追踪已贯通 |

当前 Java 本地任务执行依赖单实例 active 集合和数据库 attempt；Python Worker 使用租约、心跳和持久化执行记录。两者不能笼统说成“全部由分布式租约控制”。当前形态也不应直接扩写为多实例高可用架构。

## 3. 项目优势：核心亮点、证据与简历保留建议

以下五条是面试的主要技术亮点。项目层面的实现有证据；“我的动作”应以本人能够解释和复现的部分为准。代码存在不自动证明个人掌握，也不推导团队成果。

### 3.1 可靠任务执行与付费副作用边界

- **问题背景：** DB 提交、消息投递、任务执行和外部模型调用跨越多个故障窗口，重复消息和进程退出无法简单消除。
- **技术方案：** 用持久化任务与 Outbox 保存执行意图；消息确认和恢复扫描推进调度；通过 attempt／generation 等身份限制当前执行资格；已保存的付费响应复用，提交结果未知时停止自动重新付费。
- **收益与边界：** 可以解释重复投递、迟到完成和回执后退出的处理路径；不能写成“确保任务不被重复执行”或“全链路 exactly-once”。
- **证据：** [任务分发][S03]、[本地任务执行][S04]、[任务状态转换][S05]、[Agent Worker][S08]、[调用持久化][S20]；[Worker 集成测试][T01]和[恢复与预算测试][T02]是测试源码证据。
- **简历建议：** 直接保留机制，收窄保证范围；准备一个真实复现的故障窗口后再强化“验证了哪些状态”的描述。

### 3.2 分片直传、恢复与上传准入

- **问题背景：** 视频文件大，上传易中断，单用户重复创建上传也会占用存储和处理资源。
- **技术方案：** 浏览器使用预签名地址直传对象存储，服务器维护分片确认和 writer 身份，恢复时核对存储分片；新上传使用 Redis Lua 用户级令牌桶准入。
- **收益与边界：** 已确认分片可复用，准入错误有明确语义。当前是页面内两个文件并发、单文件分片串行；没有单文件并行上传的性能成果。
- **证据：** [前端上传][S09]、[上传服务][S10]、[准入控制][S11]、[历史限流验证][H01]。
- **简历建议：** 可以保留分片恢复与准入控制；“并行分片提速”和吞吐收益只能在实施和测量后新增。

### 3.3 草稿接受与不可变版本保证业务一致性

- **问题背景：** 用户可能双击确认、确认旧草稿，或在 Agent 仍执行时修改需求；模型输出不能自行成为正式业务版本。
- **技术方案：** 绑定草稿、消息、校验结果和版本身份；服务端验证当前资格；接受草稿时在事务内保存并确认版本，结合幂等键与数据库约束避免重复业务发布。
- **收益与边界：** 能讨论并发确认、事务回滚、旧草稿拒绝和重复请求返回同一结果。接受草稿不等于自动发起导出。
- **证据：** [草稿接受][S16]、[结果发布][S15]、[历史生命周期验收][H02]、[冻结版本 ADR][D01]。
- **简历建议：** 直接保留，是最适合后端面试深入到事务、锁和约束的一条。

### 3.4 受控 Agent 把模型建议与业务权限分开

- **问题背景：** 模型会输出非法结构、错误引用或不满足时长的草稿，也可能反复无效修改。
- **技术方案：** LangGraph 编排，真实模式只开放四个读取工具；动作经过 schema、预算与范围检查；Java 强制校验草稿，保存、确认和导出由确定性业务流程控制。
- **收益与边界：** 模型不能仅凭一段输出越过业务确认。结构和业务校验通过仍不能证明语义正确；定向修正尚有已记录问题。
- **证据：** [图编排][S18]、[工具目录][S19]、[预算策略][S22]、[工具服务][S14]、[结果发布][S15]。
- **简历建议：** 直接保留“受控工具、业务校验、确认边界”；长期记忆、多模型路由、MCP 和通用沙箱暂不作为已完成亮点。

### 3.5 可回查的媒体证据与混合检索

- **问题背景：** 视频回答和剪辑需要回到原始时间位置；关键词、近义表达和不同证据来源的检索表现不同。
- **技术方案：** ASR 时间和真实帧 PTS 归入原视频时间线；结合 Dense、BM25 与 RRF；固定项目和素材范围，检索后回查业务证据，保留稳定分页及引用身份。
- **收益与边界：** 能解释“为什么引用属于这段视频”和“为什么历史结果不会随索引重建任意漂移”。稀疏采帧并未覆盖全部画面，RRF 也不保证每个查询优于 Dense。
- **证据：** [代表帧采样][S25]、[证据检索][S12]、[索引代次][S13]、[历史检索基线][H03]。
- **简历建议：** 保留可追溯证据与检索机制；准确率提升、自然长视频泛化效果为“未验证／需补测”。

## 4. 项目短板：优先级、并发机会与异常处理边界

### 4.1 先统一最重要的工程能力

后端兼 Agent 开发最需要展示以下五种能力：

1. **业务建模与状态归属：** 能说明每个阶段的输入、输出、状态来源和不可破坏的规则。
2. **跨边界一致性：** 能说明事务能管到哪里，消息重复和外部副作用如何核对。
3. **故障恢复：** 能区分确定失败、尚未完成和结果未知，选择重试、复用、查询、补偿或停止。
4. **资源与成本约束：** 能控制并发、排队、远端在途任务、付费调用和媒体资源。
5. **可验证性：** 能通过测试、故障注入、日志和评测证明结论，并主动解释证据边界。

Agent 系统同时有网络与进程的执行不确定性，以及模型内容的不确定性。业务幂等、权限和版本约束仍应由确定性代码保证；内容质量则需要固定样本、错误分类和人工判定口径。

| 成本与延迟，P0 基础边界、P1 测量 | 消费者限制、调用预算、用量记录与付费复用 | 远端 ASR 在途上限、跨入口额度、阶段 P95、实际费用核对 | 消费者只有两个，为什么远端还能积累任务？ | 不能用线程数代表远端并发或账单上限 |
| 安全边界，保住现有规则，深挖可后置 | 工具白名单、项目范围、版本验证、显式确认 | 系统化越权／注入用例与隔离压力验证 | 模型伪造 projectId 或旧引用会怎样？ | 不能声称已实现通用沙箱或完全防住提示注入 |
| 可观测性，P1；最小事件随 P0 做 | 业务 ID、调用回执、Langfuse 局部接入 | 跨 Java、MQ、Python、工具和产物的统一关联与阶段耗时 | 一次用户失败如何定位到具体调用和状态迁移？ | 不能把局部 trace 等同于全链路贯通 |

### 4.3 本项目哪些任务可以并发

**先确认任务是否独立、共享什么资源、失败后如何收敛，再决定是否使用线程池。** 当前已经存在并发控制，新增线程池不能绕开现有任务生命周期。

| 位置 | 已有实现 | 并发机会与建议 | 优先级与约束 |
| --- | --- | --- | --- |
| MQ 消费媒体／分析任务 | `media.v1` 并发 1；`analysis.v1` 默认 2；prefetch 为 1；监听器同步执行后 ACK | 先验证现有消费者对实际工作的约束，再调整配置 | 基础治理优先；不能先 ACK 再把任务随意放入内存队列 |
| 前端分片上传 | 全页面最多两个文件传输，单文件按顺序上传分片 | 浏览器实现有界分片调度、全页面总额度与公平分配 | 可选 P1；属于前端异步调度，不是 Java 线程池 |
| 检索通道 | 现有各检索通道按代码顺序调用 | 独立 BM25 与向量链路可并发；Dense 仍依赖查询向量 | 首选 P1 试点；必须稳定合并、保留降级状态，避免重复付费 Embedding |
| VLM 帧分析 | 帧级调用有独立回执，循环串行 | 对独立帧使用共享有界执行器 | 在总预算与调用生命周期清楚后实施；每帧分别记录未知状态 |
| Embedding 批次 | 批次级回执与成功复用，循环串行 | 独立批次并发后统一验证、发布索引代次 | 同上；部分成功不能冒充整代次可用 |
| 远端 ASR | 提交后保存 provider task ID，延迟查询并释放本地执行槽 | 单独限制远端未终结任务数，查询原任务 | P0 容量契约；本地消费者数量不是远端在途数量 |
| 素材下载 | 渲染前逐个下载与检查 | 小规模有界 I/O 并发可能减少等待 | 次于检索试点；同时考虑对象存储、磁盘和临时空间 |
| FFmpeg 片段处理 | 当前逐片段处理，再按原顺序拼接 | 独立片段理论上可并行，最终按方案顺序汇合 | 较后；先测 CPU、内存、磁盘，不能按完成顺序拼接 |
| 预览和正式导出 | 共用媒体消费者路径 | 若测得相互阻塞，再考虑优先级或资源隔离 | 待验证；不要先新增服务或队列再找收益 |
| Agent 连续动作 | 下一步通常依赖上一轮观察与校验 | 仅在数据依赖明确时并发独立读取 | 不默认并发多轮决策、保存、确认或发布 |

当前业务容器配置为 2 CPU、1280 MiB，Java 与本地 FFmpeg 共享容器资源；这是配置事实，不是压测结论。Java 堆以外还有原生内存、子进程和文件缓存，不能仅按线程数判断安全容量。

**线程池的推荐落点与设计要求：**

- 第一处优先考虑[证据检索][S12]的独立通道；使用应用级共享、有界队列的执行器，任务返回各自结果，由协调者统一排序和融合。
- 后续才考虑[分析处理][S17]中的独立帧与批次。不能每个视频各建一个“有界”线程池，却使所有视频的全局并发无上限。
- 线程池之外仍要限制 HTTP 连接、提供方额度、远端 ASR 在途任务、数据库连接和临时空间；查询 Embedding 也必须计入提供方总额度。
- 任务排队时间应纳入总时限；超时后须检查真实 I/O、进程与回执状态，`Future.cancel` 不等于远端操作撤销。
- 拒绝策略必须显式。不得静默丢弃任务；`CallerRunsPolicy` 会把工作转回调用者，不应在 HTTP 或 MQ 线程上不加分析地使用。
- 避免父任务占满同一个池后等待子任务，造成线程饥饿。聚合时不要并发写现有共享可变 Map／JSON 对象。
- 一项子任务失败或取消后停止继续派发；已发出的付费请求仍需保存回执。子任务未退出前不能清理其工作目录或宣布所有资源已释放。
- 保留快速回退到串行／更低并发的配置。性能收益必须在相同素材、资源、模型与故障条件下比较。

### 4.4 流程中出现异常时如何处理

异常处理的首个问题是“系统已经做了什么、知道多少”，而不是“统一重试几次”。

| 情况 | 应采用的策略 | 不应采用的策略 |
| --- | --- | --- |
| 输入、权限或业务约束确定不合法 | 明确拒绝，保留可解释错误 | 换模型、绕过权限或无限重试 |
| 暂时故障，且确认可安全重放 | 有界重试、退避、必要时抖动，共享重试预算 | SDK、业务层、MQ 各自独立放大次数 |
| 请求可能已产生付费或写入副作用 | 标记结果未知，保存身份并核查 | 把超时等同于没执行，直接新建请求 |
| 已取得 provider task ID | 查询同一任务、复用原响应 | 为了“恢复”重新提交付费任务 |
| 响应已落盘但业务处理未完成 | 复用回执向前完成 | 回退 checkpoint 后再次付费 |
| 外部产物存在但本地发布未完成 | 对账、补发或按业务规则清理 | 假设数据库回滚已经撤销外部写入 |
| 可选能力不可用 | 显式缩减能力并返回降级状态 | 把空结果或部分结果伪装成完整成功 |
| DB、权限事实或关键身份不可用 | 停止依赖这些事实的操作 | 绕过确认或权限以追求表面可用性 |

下面是按实际流程整理的异常矩阵。右栏为需要继续证明或实施的内容，不代表当前均已具备。

| 流程位置／异常 | 已有实现或现状 | 待验证与后续处理要求 |
| --- | --- | --- |
| 新建上传被限流 | Redis 令牌桶，超额与基础设施不可用区分错误；安全幂等重放有单独路径 | 核对前端按重试提示响应；不能绕过 Redis 故障准入 |
| 上传业务事务失败 | 已消耗的准入 token 不自动随 SQL 回滚返还 | 解释保守计费取舍，避免补偿返还引入重复额度 |
| 分片 PUT 卡住或网络中断 | 有重试／恢复流程；PUT 没有应用层 AbortSignal 总时限 | 复现慢连接，补端到端 deadline 与中断；浏览器中断不保证存储端未写入 |
| 分片写入成功、确认响应丢失 | 恢复会核对存储分片并重建确认状态 | 并发化后由一个协调者负责恢复，进度按 part 去重，避免重复统计 |
| 上传完成与 DB 写入之间失败 | 存在完成、核对和后续任务链路 | 用故障注入证明对象存在但业务未完成时如何恢复、谁清理 |
| 暂停／取消发生在 I/O 中 | 当前多在 await 之间检查；可发送取消请求 | 区分用户状态、客户端停止、远端收敛，测量资源释放而非只看按钮 |
| 媒体损坏、解码或哈希检查失败 | 有媒体检查与失败状态 | 确认不可恢复错误不进入无意义重试，资源与配额最终释放 |
| 抽帧失败但语音可用 | 媒体准备有保留可用能力的处理路径 | 验证后续回答不会暗示看过画面，明确视觉证据缺失 |
| ASR 提交结果未知 | 保存提交状态，未知结果不自动再次付费 | 演示“提交后、回执前”窗口及人工核查路径 |
| ASR 已有 task ID，但查询失败 | 保存原 ID、延迟查询，存在查询期限 | 远端任务在本地超时后可能继续；在途名额不能未经核查直接释放重用 |
| VLM／Embedding 部分成功 | 帧／批次回执，成功结果与保存响应可复用 | 并发化时逐子调用收口；一个失败不能抹掉其他成功或未知记录 |
| 模型响应 body 很慢 | 连接和请求有 timeout，body 使用 InputStream 读取 | 不能据此认定整个 body 已有时限；注入慢 body 验证，结果尚未确认 |
| Qdrant／某个检索通道失败 | 有通道可用、降级、不可用的表示 | 验证剩余通道、引用、排序和用户提示；不能宣称仍有完整语义检索能力 |
| 模型输出结构错误 | schema 和有限修正 | 与业务修正区分；定向修正方案尚未实施 |
| 草稿格式合法但时长／引用不合法 | Java 业务校验，非法草稿不能成为可接受结果 | 复现持续无效修正；固定失败样本和停止原因 |
| 旧 attempt／旧草稿迟到 | 执行身份和当前资格检查 | 证明不会覆盖新结果；迟到外部产物还需按归属核对或清理 |
| FFmpeg 超时、退出或取消 | 单命令时限、轮询取消、终止／强制终止、工作目录清理 | 多命令总时限、子进程退出和删除失败的收敛仍需系统化验证 |
| 成片已上传但发布失败 | 对象存储与 DB 发布存在跨边界窗口 | 分别验证可复用产物、孤儿对象、重复完成及清理补偿 |
| DB 已提交结果但 MQ ACK 丢失 | 有重投、幂等发布与 Worker 集成测试 | 按原业务身份重放，不能为了 ACK 再执行全部副作用 |
| Langfuse 不可用 | 观测可选，不作为业务事实来源 | 验证主流程可继续，观测丢失可诊断，不能谎报轨迹完整 |
| 临时文件／对象清理失败 | 已有清理模块和启动目录处理 | 核对重入、重试、引用保护和告警；不把一次 finally 等同于完整清理闭环 |

**每个重要阶段都应能回答八个问题：**

1. 进入条件是什么，谁拥有当前执行权？
2. 会产生哪些数据库、远端请求、文件或计费副作用？
3. 结果和回执保存在哪里，写入发生在副作用之前还是之后？
4. 哪些失败可安全重试，重试由哪一层负责？
5. 结果未知时能否查询原操作，何时停止自动推进？
6. 谁释放连接、线程、远端名额、临时文件和存储预留？
7. 用户看到失败、等待核对、降级还是可恢复状态？
8. 用哪一个可重复的故障实验证明上述行为？

### 4.5 一致性、幂等与重试应讲到哪一层

**Outbox 的保证范围：** 业务状态与待发布意图可以同事务提交；relay 仍可能重复发布。publisher confirm 解决发送方与 broker 之间的确认，consumer ACK 是消费侧确认，二者不等同于业务副作用完成。

**幂等不能只说“加一个 Redis 锁”：** 需要说明幂等身份、作用域、请求内容、最终结果、并发竞争、过期身份和持久化约束。任务、attempt、模型调用和方案版本不是可以混用的 ID。

| 身份 | 用途 | 不能替代的身份 |
| --- | --- | --- |
| 用户请求的 idempotency key | 同一业务请求的重放与冲突判断 | 不能证明外部模型没有执行过 |
| task ID | 同一任务的持久化跟踪 | 不能识别当前执行尝试 |
| attempt／generation／lease token | 限定当前执行和发布资格，具体字段依链路而定 | 不能撤销已经发出的远端请求 |
| call ID 与输入哈希 | 付费调用身份、响应复用和输入一致性 | 不能由新 attempt 随意生成新身份而绕过旧回执 |
| provider task ID | 查询已提交的远端异步任务 | 不等于内部任务已成功发布 |
| draft／validation／revision 身份 | 绑定被校验、被接受及被冻结的对象 | 不等于当前 UI 展示的内容一定仍可确认 |

准备三个最有价值的故障窗口：

- **事务提交后、消息尚未成功发布：** 持久化意图仍在，由分发恢复；重投依赖消费幂等。
- **付费请求已发送、响应未持久化：** 外部可能已执行；无安全查询或幂等保证时保留 UNKNOWN，停止自动再付费。
- **业务结果已提交、ACK 丢失：** 重投核对持久化结果，不重复发布，也不重新进行完整模型调用。

补偿是新的业务动作，例如删除无引用对象或释放预留；它也可能失败，需要可重入和核对。数据库回滚不能取消已经运行的 FFmpeg、撤销远端计费或自动删除对象。面试中可以解释编排与事件通知的取舍，但不要把已有链路未经设计地称为完整 Saga 框架。

### 4.6 Agent 已记录的真实问题与未实施方案

[定向修正规格][D03]记录了一个具体失败：用户要求约 12–20 秒的剪辑草稿，输出中的 `output_durations: null` 先消耗修正机会，之后多版草稿仍超时；补读行为又不能准确表示草稿是否改善，最终共享修正预算耗尽。

该记录中的草稿时长为 32.02 → 38.74 → 32.02 秒，存在删除一个完整片段后得到 19.38 秒候选的情况。这些是**历史故障样本数据**，本次没有重跑，不是准确率或性能指标。

| 层次 | 已有实现 | 后续计划 |
| --- | --- | --- |
| 结构合法性 | schema 校验和有限修正 | 在明确语义的模型输入边界规范化特定字段；不通用地把所有 null 改为空列表 |
| 业务合法性 | Java 校验时长、引用、范围和确认资格 | 提供有依据的删段／边界候选，最终仍走完整校验 |
| 语义质量 | 依靠模型结合证据进行选择 | 固定样本评价语义完整性，不把时长合格等同于内容合格 |
| 成本与停止 | 总调用、活动时间、修正和无进展限制 | 分开格式／业务预算，独立判断草稿持续无改善，读取进展不清零草稿停滞 |

**状态：方案文档已经存在，尚未实施。** 面试可以讲“发现了什么、现有机制为什么没覆盖、准备怎样验证”，不能讲成问题已解决。详见[分阶段实施计划][D04]。

### 4.7 评测、可观测与成本证据如何补齐

评测分四层，避免将测试通过数等同于模型效果：

1. **确定性业务回归：** 幂等、权限、版本、取消、预算、回执复用、旧结果拒绝。
2. **脚本模型／故障注入：** 控制指定返回、超时、进程退出和重复投递，验证公开入口行为。
3. **固定素材与真实模型：** 预先固定问题、正确证据和评判口径，保留失败轮次及实际费用。
4. **人工媒体验收：** 连续观看、讲话音画同步、字幕和选段语义，不能由 FFprobe 或抽样帧完全替代。

| 指标／记录 | 口径要求 | 当前状态 |
| --- | --- | --- |
| 任务终态 | 成功、失败、取消、结果未知分别计数；明确超时未终结任务 | 分散记录已存在，统一报告待补 |
| 阶段耗时与 P95 | 区分排队、执行、提供方等待、总耗时；记录样本数和失败样本处理方式 | 未验证／需补测 |
| 在途与资源 | 活跃任务、队列长度、远端 ASR、连接、CPU、内存、磁盘和工作目录 | 配置上限部分存在，系统化测量待补 |
| Agent 成功与修正 | 预先定义成功条件，区分结构／业务／语义错误和预算停止 | 固定质量集待补；修正失败样本已有记录 |
| 检索 Recall@k／MRR | 固定语料、相关性标注、开发集／保留集；报告逐查询结果 | 历史小样本基线已有，泛化效果未验证 |
| Token／成本 | 区分提供方上报、估算、复用、未知与无法定价；失败请求也计入 | 用量机制已有，账单对账与硬预算待补 |
| Trace 关联 | 贯通业务请求、task、attempt、execution、call、provider 和产物身份 | 局部关联已有，全链路待验证 |

历史检索基线只有小型合成语音语料与少量固定查询，且已有查询出现 Dense 排名优于 RRF。应保留这一反例，进一步区分 ASR 漏识别、召回遗漏、融合排序和回答生成错误，不把所有失败归因于向量数据库。

[Worker Langfuse 记录][H04]验证了真实观测服务接收，但使用脚本模型和模拟 Java 接口；[生命周期记录][H02]含真实模型验收，但复用了受控既有视觉证据。它们分别证明对应边界，不能合并宣传为“自然视频全链路质量已全面验收”。

| 编号 | 优先级 | 唯一主要交付物 | 为什么优先 | 完成凭据 |

| E1 | P0，第一个 Sprint | 外部等待、取消与恢复的最小可验证闭环 | 当前最容易被追问且无法完整证明的是“卡住或未知时怎样收敛” | 故障矩阵、可重复用例、状态／调用数／资源证据 |
| E2 | P0，后续独立 Sprint | 分析和媒体资源的有界准入闭环 | 加并发前先限制资源和远端在途任务 | 额度作用域、排队／拒绝语义、过载与恢复报告 |
| E3 | P1 | 一个检索并发试点及对照实验 | 工作相对独立，便于验证取消、合并和降级 | 固定输入下结果等价、并发上限、耗时与故障对比 |
| E4 | P1，可选替换项 | 并行分片上传与协调恢复 | 大文件单文件吞吐可能受串行限制，但收益尚待测量 | 分片去重、恢复／取消、总并发和传输对照 |
| E5 | P1 | 跨链路关联与成本／延迟报告 | 让已做机制能被定位、解释和持续比较 | 一次请求可追到各阶段与费用状态，失败有完整归因 |
| E6 | P2，默认唯一深度点 | 证据驱动的 RAG 质量闭环 | 基于现有直接证据形成差异化，避免堆框架 | 固定评测集、逐查询错误分析、单项改动对照 |
| E7 | P1 候选，独立排期，不与 P0 捆绑 | Agent 定向修正 | 已有具体失败与独立规格，适合后续受控实施 | 按现有规格复现并通过分类预算、候选、停止与恢复验收 |

每个 Sprint 最多承担一个 P0 级交付物。E1 的回归集是其验收组成部分，不另开一个横跨全系统的评测平台。E3 与 E4 在短周期内二选一；E6 默认选 RAG，若目标岗位更偏媒体调度，可替换深度方向，但不能同时扩展记忆、多模型路由、MCP 和 K8s。

## 6. 每个迭代点详细实施方案与验收标准

### 6.1 E1：外部等待、取消与恢复最小闭环

**目标与优先级：** 先能回答“哪个步骤卡住、是否已经产生副作用、能否重试、多久收敛”。这是 P0；没有清楚的失败契约，增加并发只会扩大未决状态。

**实施步骤：**

1. 绘制上传 PUT、模型 HTTP body、提供方异步查询、FFmpeg 的等待与副作用表；列出现有超时及责任层。
2. 先复现慢 body、分片响应停滞、付费响应后崩溃、结果提交后 ACK 丢失等最小场景；已有用例优先复用。
3. 仅对证明存在的缺口补总时限、取消传递与异常分类；避免将未知付费请求改成通用重试。
4. 核对 SDK、业务重试和 MQ 恢复的总尝试次数，明确唯一负责重试的一层及其他层职责。
5. 固定失败回归样本与脱敏证据，记录用户终态、外部调用次数和资源退出。

**涉及模块：** [BailianHttp][S26]、[AnalysisProcessing][S17]、[LocalTaskRunner][S04]、[前端上传][S09]、[媒体检查][S24]、[调用持久化][S20]及现有恢复测试。按复现结果选择修改范围，不预设全部重写。

**验收：** 各等待在配置的 deadline 与约定清理宽限内收敛；取消后不再派发新工作；已保存响应不重复调用；未知提交不自动重付费；迟到结果不能成为当前结果；测试实际断言调用数、业务状态、进程／连接释放。具体时间阈值根据基线确定，当前为“未验证／需补测”。

**风险与降级：** 超时过短会把正常慢请求判为失败；先在受控环境测量，配置可回退。无法确认远端结果时保留待核查状态，不以重试掩盖。

**完成后才可新增的简历表述：** “梳理上传、模型调用和媒体处理的失败窗口，建立超时、取消、回执复用与结果未知的分类恢复规则，并通过慢响应、进程退出和 ACK 丢失场景验证。”

### 6.2 E2：分析与媒体任务的有界准入

**目标与优先级：** 让并发额度对应真实资源，明确满载后的用户语义。属于独立 P0 Sprint。

**实施步骤：**

1. 列出本地执行槽、FFmpeg、磁盘预留、远端 ASR、VLM／Embedding、查询 Embedding 的独立额度。这是资源清单，不要求在一个 Sprint 同时重写所有调度；最小交付优先补远端 ASR 在途边界，并验证现有本地媒体上限。
2. 先测当前配置下的混合负载，确认哪种资源首先饱和；保留串行基线。
3. 明确应用级、用户级、任务级的额度作用域；当前单实例先做最小实现，不引入无需求的分布式协调。
4. 远端异步任务按已提交且未确认终结的身份占位；本地延迟查询、重启、结果未知不应造成名额虚假释放。
5. 规定满载时排队、延迟接纳或显式拒绝的策略；避免 DB 持久队列之外又积累无界内存队列。

**涉及模块：** [消费者][S02]、[任务状态][S05]、[分析处理][S17]、[证据检索][S12]、[媒体渲染][S23]、[Compose][S01]与应用配置。是否新增字段或迁移由额度持久化需要决定。

**验收：** 负载超过额度时实际在途数不突破配置；过载不会静默丢任务；远端未知任务的额度有可解释状态；重启后额度可从持久化事实重建或核对；取消后资源最终释放；记录排队与执行耗时、CPU／内存／磁盘。吞吐、P95 和安全容量均需实测。

**风险与降级：** 额度可能过低导致等待变长，或状态核对不全导致名额泄漏；保留管理核查路径及降低接纳速率的配置，不以删除未知回执释放额度。

**完成后才可新增的简历表述：** “按本地媒体处理与远端模型任务分别实施有界准入，覆盖排队、过载拒绝、重启核对和取消释放，避免用消费者数量代替远端在途上限。”

### 6.3 E3：独立检索通道的有界并发试点

**目标与优先级：** 在一个范围清楚的业务点证明线程池设计能力，属于 P1。先保持结果契约，再衡量延迟收益。

**实施步骤：**

1. 把检索依赖画清楚：查询向量生成在 Dense 之前；BM25 可独立推进；同模型／维度的查询向量避免重复生成。
2. 固定权限范围、索引代次与输入，使用共享有界执行器；每个通道返回独立结果。
3. 协调者按稳定顺序融合，保留 RRF、平分规则和分页快照；不并发修改原有共享容器。
4. 给排队与调用设置整体 deadline，保留单通道失败的降级语义。
5. 比较串行／并发在正常、慢通道、失败、取消和满载下的表现。

**涉及模块：** [QuestionEvidence][S12]、[SearchIndexes][S13]、[读取工具测试][T03]；执行器配置位置实施时确定。

**验收：** 确定性输入下引用、顺序、分页和可用状态符合原契约；不增加重复查询 Embedding；实际并发不超过配置；一个慢通道不能使整个请求无限等待；拒绝和取消不泄漏执行资源。P95／吞吐改善以固定环境测量结果为准，不预先填写百分比。

**风险与降级：** 外部限流增加、DB 连接竞争、非稳定合并；可切回串行或降低并发，保留原结果契约。

**完成后才可新增的简历表述：** “将独立检索通道改为有界并发，统一控制排队与调用时限，在通道失败时保留可用证据，并验证融合顺序、分页及引用身份保持稳定。”

### 6.4 E4：并行分片上传，可选 P1

**目标与优先级：** 改善单个大文件的传输等待；它可替换 E3，不能在短 Sprint 中两项同时扩张。

**实施步骤：**

1. 先测当前单文件串行传输，判断瓶颈是否在网络、存储或校验。
2. 使用页面级总额度和每文件额度分配分片，确保多文件公平；并发值根据测量确定。
3. 引入单一恢复协调者，核对 writer 身份、分片列表、ETag 和确认状态；进度按分片集合计算。
4. 加入实际 PUT 中断与 deadline；暂停、取消后停止发新片，核对可能已经写入的在途片。
5. 仅在所有所需分片确认后 complete；覆盖重复确认、响应丢失、重选文件和恢复竞争。

**涉及模块：** [uploads.ts][S09]、[UploadService][S10]、[MultipartStorage][S30]及现有上传浏览器／接口测试。

**验收：** 页面总在途片数有上限；失败片不会污染成功集合；进度不重复累计；没有提前 complete；恢复不因并发 token 使用产生串扰；上传完成后仍区分媒体验证状态；记录相同文件和网络条件下的传输耗时。

**风险与降级：** 并发可能放大恢复冲突、内存占用与存储限流；保留单文件分片串行开关，不改变现有分片协议的业务含义。

**完成后才可新增的简历表述：** “实现页面级有界分片调度与统一恢复协调，覆盖在途取消、重复确认、已上传片核对和完整性检查，支持多文件公平共享上传额度。”

### 6.5 E5：统一关联、延迟与成本报告

**目标与优先级：** 将分散的证据组织成一次请求的可解释轨迹，属于 P1。必要的故障事件随 E1 实施，本项不重建业务状态系统。

**实施步骤：**

1. 统一 request、task、attempt、execution、call、provider、artifact 等已有身份的关联字段；日志不输出凭据或完整敏感提示词。
2. 分别记录排队、外部等待、执行、恢复、取消与最终发布，避免用一个总耗时遮盖瓶颈。
3. 成本报告区分上报／估算／复用／未知，保留模型和价格版本；记录失败轮次。
4. 从用户失败反查到具体状态迁移和调用回执，再核对结果是否发布。
5. 验证观测服务不可用时业务继续且丢失可诊断；只有真实贯通后才使用“全链路追踪”的表述。

**涉及模块：** [tracing.py][S27]、[调用上下文][S21]、[ModelUsage][S28]、[任务分发][S03]、[Worker][S08]及相关接口日志。

**验收：** 选择成功、取消、UNKNOWN 和恢复案例，均可串起关键身份与事件；无法定价明确显示未知；未把估算写成实付；报告耗时分母、样本与失败处理方式；注入 Langfuse 故障不改变业务终态。

**风险与降级：** 高基数字段、敏感数据泄露、观测写入阻塞；结构化事件做必要裁剪，观测失败保持非关键依赖，业务回执仍按原可靠性要求持久化。

**完成后才可新增的简历表述：** “贯通任务、执行与模型调用的关联记录，按阶段拆分排队、外部等待和执行耗时，区分上报、估算及未知成本，并验证观测故障下业务仍可完成。”

### 6.6 E6：只选择一个 P2 深度点，默认 RAG 质量闭环

**目标与优先级：** 证明能够用证据定位效果问题并作取舍，而不是只会接入向量数据库。没有可靠基线前不优先增加重排框架。

**实施步骤：**

1. 固定代表性素材、问题、证据时间区间、无答案问题和相关性标注；划分开发集与保留集。
2. 分别评估原文、Dense、BM25、RRF，保留逐查询排名和失败。
3. 将错误归入上游观察缺失、切分、召回、排序、上下文选择或生成；先改一个主因。
4. 对单项改动进行相同条件对照；质量、延迟、成本与降级一起记录。
5. 真实模型调用单列，复用已分析素材；必要时人工判断选段语义与引用支撑。

**涉及模块：** [证据检索][S12]、[索引代次][S13]、分析／证据形成模块、[历史检索基线][H03]和新建固定评测材料。

**验收：** 可复跑原始样本并得到逐查询结果；公开样本数与标注规则；负例与保留集不遗漏；改动没有被用来反复调参保留集；不能通过减少难例制造提升。准确率、Recall、MRR 和延迟均按实际结果报告。

**风险与降级：** 小样本过拟合、标注不一致、把 ASR 错误误归检索；保留旧索引和检索路径，必要时不采纳未显示收益的改动。

**完成后才可新增的简历表述：** “建立固定视频证据检索评测集，按上游观察、召回、融合与回答分层归因，对开发集和保留集分别报告逐查询结果，并验证索引切换与降级行为。”

### 6.7 E7：Agent 定向修正作为 P1 候选，沿用已有独立计划

已有[规格][D03]和[实施计划][D04]，本文不另造一份冲突实现方案。重点是特定列表字段语义、输出级候选、分类修正预算、独立草稿进展和明确失败反馈。

涉及现有 [draft_repair.py][S29]、[policy.py][S22]、图节点与模型上下文，以及 Java 草稿校验和浏览器结果展示。具体文件与阶段按原计划执行。

验收须覆盖原始失败重放、无合法候选、已合格输出保护、引用补读后重新校验、补答／重启后预算不重置，以及未知付费提交不重试。真实模型验收与确定性回归分开；未取得证据前，不将候选可计算写成实际质量改善。

风险是增加修正机会却增加费用、候选时长合法但语义断裂；保留总调用与时间上限、Java 完整校验和用户确认。若时间不足，先固定失败样本，不把整个修正计划塞入 E1。

完成后才可新增：“针对草稿持续超时与共享修正预算耗尽的问题，提供受约束的删段候选并区分格式／业务修正，保留独立停滞判断、总调用预算和完整业务校验。”

## 7. 按 2／4／8 周的时间盒安排与裁剪规则

**假设每周 20 小时。** 以下是时间分配建议，不是交付保证；每周最后约 4 小时用于验收、证据整理和口述准备。实际小时不足时先缩范围，不压缩关键故障验收。

| 周次 | 时间盒 | 本周交付物 | 范围约束 |
| --- | --- | --- | --- |
| 第 1 周 | 约 8 小时梳理／复现，8 小时补最小缺口，4 小时核验 | E1 的失败矩阵、固定复现及首条闭环 | 不新增线程池、队列或模型 |
| 第 2 周 | 约 8 小时完成修复，8 小时故障回归，4 小时材料 | E1 最小集通过，准备一个恢复案例和一个 Agent 失败案例 | 只补最关键外部等待，不扩建评测平台 |
| 第 3 周 | 约 6 小时资源基线，10 小时额度实现，4 小时核验 | E2 有界准入与满载语义 | 本周唯一 P0；不同时做通道和上传并行 |
| 第 4 周 | 约 10 小时一个试点，6 小时对照与核心关联，4 小时口述 | E3 或 E4，加 E5 最小关联报告 | 如 E2 未收口，砍并发提速，先完成资源与恢复证明 |
| 第 5 周 | 约 10 小时关联／统计，6 小时故障核验，4 小时文档 | E5 核心成本、延迟和故障报告 | 不引入新的观测平台替换现有工具 |
| 第 6 周 | 约 10 小时数据与标注，6 小时基线，4 小时复核 | E6 固定样本、基线及错误分类 | 先做基线，不为追求新名词加 reranker |
| 第 7 周 | 约 10 小时一个主因改进，6 小时对照，4 小时归因 | E6 单项改动的保留集结果 | 无改善可保留旧实现，负结果也是取舍证据 |
| 第 8 周 | 约 8 小时阶段回归，8 小时演示与自测，4 小时简历 | 证据包、演示、简历与面试口述 | 不临时增加第二个 P2 或完整 E7 |

不同期限的完成目标：

- **2 周版：** 只交付 E1，包括最小固定回归和失败恢复证据。已有能力的讲解准备同时完成。
- **4 周版：** E1、E2 及一个 P1 核心试点；至少具备最小关联记录。若 P0 超时，取消性能试点，不能带着未闭合故障宣称完成。
- **8 周版：** P0、P1 核心加一个 E6 深度点；E7 若成为更重要的投递需求，应替换相应时间盒，不能在原范围上叠加。

统一裁剪规则：先砍新框架和多实例扩展，再砍第二个并发点、完整仪表盘、额外模型和超出代表性的评测规模；保留幂等、未知付费停止、取消、权限、旧结果拒绝、最小故障复现与最终证据记录。

实施阶段按项目测试约定执行：单行为→所在模块与直接影响→完整阶段的 Java／Python 非付费回归和后端打包；涉及前端再补类型、构建及当前有效入口浏览器验证。付费模型与人工媒体验收单列，分别记录通过、失败、跳过和未运行。

## 8. 简历改写前后对照

### 8.1 已有实现的安全表述

“改写前”是对现有简历和讨论表述的概括，不当作逐字引用。建议遵循 **PAR + Tech：问题／场景→个人动作→机制与取舍→结果或边界**；没有测量数据时写覆盖的状态和验证项。

| 改写前的方向或风险 | 改写后的建议 | 状态与使用条件 |
| --- | --- | --- |
| 用 Outbox、MQ、租约确保任务不被重复执行 | 面向异步视频分析与 Agent 执行，使用持久化任务、Outbox 和执行身份约束处理重复投递与迟到结果；对已保存模型响应进行复用，对提交结果未知的调用停止自动重付费 | 已有实现；不能扩大为所有副作用只发生一次 |
| 分片上传、断点续传、Redis 限流 | 实现预签名分片直传与存储分片核对，结合 writer 身份和用户级 Redis Lua 令牌桶，覆盖恢复、重复请求和准入故障的处理路径 | 已有实现；并行分片和速度提升未完成 |
| Agent 自动剪辑并生成视频 | 基于 LangGraph 编排证据读取与草稿生成，仅开放受控读取工具，由 Java 校验范围、引用和剪辑约束；草稿经用户接受后冻结版本，预览和导出由显式操作触发 | 已有实现；不声称模型拥有确认权限 |
| 混合检索提高准确率 | 结合 Dense、BM25 与 RRF 检索语音和视觉证据，固定素材范围并回查引用身份；保留通道降级和稳定分页，已有小样本基线，泛化效果待评测 | 机制 Direct；准确率提升未验证 |
| 完整链路追踪和成本优化 | 接入 Agent 轨迹与模型调用记录，区分上报用量、估算和未知结果；跨语言关联、端到端 P95 与实际费用核对待完善 | 局部实现；不能写成完整 E5 结果 |

### 8.2 可压缩使用的简历段落草稿

下面是项目层面的候选表述。正式使用前，按本人实际负责、理解和验证的范围选择，不默认全部保留。

- **可靠任务与调用恢复：** 面向异步媒体处理和 Agent 执行，结合 PostgreSQL 任务状态、Outbox、RabbitMQ 确认及执行身份校验，处理重复投递和迟到完成；复用已保存模型回执，对提交结果未知的付费请求停止自动重试。
- **上传与准入控制：** 实现预签名分片直传、writer 身份校验和存储分片核对，支持中断恢复；使用 Redis Lua 用户级令牌桶控制新上传接纳，并区分额度耗尽与准入服务故障。
- **版本与确认一致性：** 绑定草稿、消息和校验身份，在事务内完成用户接受与方案版本冻结，结合幂等和数据库约束处理重复确认、过期草稿与并发修改。
- **受控 Agent 与证据检索：** 使用 LangGraph 编排读取、决策和校验，结合 Dense／BM25／RRF 与原视频时间证据；限制模型工具权限和执行预算，由 Java 约束引用、范围及剪辑合法性。

如果版面只容纳三条，优先保留可靠任务、确认一致性、受控 Agent；上传和检索细节放进面试储备。具体投递 JD 明确后再调整，不能为了关键词声称已有 MCP、K8s 或长期记忆。

### 8.3 后续成果的使用门槛

第 6 节每项“完成后才可新增”的句子均为未来模板。使用前应同时具备：对应代码、行为验收、可定位的记录、本人可展开的取舍。性能和质量数字还需基线、样本、环境和指标口径；否则继续写“未验证／需补测”。

## 9. 面试追问自测清单与准备方法

### 9.1 面试中按什么优先级讲

| 顺序 | 核心内容 | 为什么重要 | 需要准备到什么程度 |
| --- | --- | --- | --- |
| 1 | 业务链路、状态归属和不可破坏的规则 | 决定面试官是否相信你理解完整系统 | 不看代码画出两条主链路，解释每种状态由谁负责 |
| 2 | 事务、幂等和保证范围 | 最能体现后端基本功与工程判断 | 画出三个崩溃窗口，讲清 SQL 条件、约束和同 key 冲突 |
| 3 | 失败恢复、补偿和降级 | 从“能跑”进入“故障时仍可解释” | 用一个可复现场景展示恢复前后状态和真实调用次数 |
| 4 | LLM 不确定性与受控执行 | 体现 Agent 工程能力而非 API 包装 | 区分结构、业务、语义错误，讲清工具权限和人工确认 |
| 5 | 有界并发、资源与过载 | 直接回答线程池和稳定性追问 | 解释现有消费者边界、远端 ASR 例外和一个并发试点 |
| 6 | 评测、观测和成本 | 为前面每项结论提供证据 | 说明样本、分母、失败轮次、trace 关联与估算边界 |
| 7 | RAG 深度及架构演进 | 在基本盘可信后形成差异化 | 能分析某条查询为何失败，并说明何时值得扩展 |

这里是讲述顺序，不是“第六项之前不用测试”。每个已有主张都需要对应验证证据。

### 9.2 技术深度自测：每个名词至少展开两到三层

| 主题 | 第一层：为什么 | 第二层：怎么实现 | 第三层：故障、取舍与证据 |
| --- | --- | --- | --- |
| Outbox | DB 与 MQ 双写为何有窗口？ | 哪个事务写业务与意图，谁扫描与确认？ | confirm 丢失为何会重发，如何阻止重复业务发布？ |
| ACK | 为什么手动 ACK？ | 在持久化结果前还是后确认？ | 先入线程池再 ACK 会改变什么保证？ |
| 幂等 | 哪些操作需要重放？ | key 的作用域、内容哈希和唯一约束是什么？ | 同 key 不同 body、并发插入、旧结果如何处理？ |
| attempt／租约 | 为什么需要执行身份？ | Java 本地与 Python Worker 分别如何判断当前资格？ | 旧执行仍在跑时，如何挡住迟到发布？ |
| 付费回执 | 为什么不能所有失败都重试？ | PREPARE／提交／响应／成功分别记录什么？ | 响应丢失、落盘失败、卷丢失各有什么边界？ |
| 线程池 | 当前瓶颈是 I/O 还是 CPU？ | 全局并发、队列、拒绝和 deadline 放在哪里？ | 父子同池等待、取消未生效、限流放大如何验证？ |
| 异步 ASR | 为什么消费者数量不足以限制远端任务？ | task ID 和轮询如何持久化？ | 本地超时但远端仍运行时，名额怎么核对？ |
| 上传恢复 | 为什么需要 writer 和分片核对？ | ETag、part number、确认状态如何关联？ | 并行片同时失败时，谁恢复，谁统计进度？ |
| Redis 令牌桶 | 为什么在接纳新上传时限流？ | Lua、Redis 时间、补充速率、TTL 如何配合？ | Redis 不可用、SQL 回滚、幂等重放怎么处理？ |
| FFmpeg | 为什么需要独立资源预算？ | 超时、停止、强杀、目录生命周期是什么？ | 多片段并发后一个失败，如何退出和清理？ |
| LangGraph | 状态机比单个模型调用多解决什么？ | 状态、节点、回边和停止条件是什么？ | checkpoint 恢复为什么不能撤销计费？ |
| Tool Calling | 为什么只开放读取工具？ | schema、scope、身份与预算由哪层核查？ | 模型伪造项目或引用会在哪里被拒绝？ |
| RRF | 为什么融合不同排序？ | 排名、常数、平分及分页如何稳定？ | 为什么某条查询反而变差，如何选择是否采纳改动？ |
| PTS／时间证据 | 为什么不能只按标称帧率算时间？ | 实际时间戳如何关联语音、帧和剪辑范围？ | 稀疏采样遗漏与语义剪断如何验证？ |
| 成本统计 | 为什么调用次数不是账单？ | 上报、估算、复用、未知如何记录？ | 失败轮次和无法定价模型如何报告？ |
| 降级 | 哪些能力是可选的？ | 降级状态如何传递给工具与用户？ | 为什么 DB／权限故障不能用同样方式放行？ |

自测时若只能回答第一层，就暂不把该名词作为简历核心亮点；若第三层无证据，明确说“已有机制，故障实验尚待补充”。

### 9.3 五份最值得准备的材料

1. **一页主链路与状态图：** 上传分析链、Agent 制作链、数据归属、确认边界。
2. **一页幂等与失败窗口表：** 至少覆盖 DB→MQ、模型提交→回执、结果提交→ACK。
3. **一个可重复的恢复演示：** 记录故障前后状态、调用次数、最终发布次数和资源收敛。
4. **一个 Agent 真实问题复盘：** 使用定向修正失败样本，区分现状、原因分析、未实施方案和验收办法。
5. **一个并发对照实验：** 相同资源与输入，加入慢依赖／取消／过载，说明收益和代价；尚未实施时只讲设计，不冒充结果。

所有演示只使用脱敏材料。个人贡献材料应补充“我做了哪个判断、如何发现 AI 生成方案的边界问题、怎么设计验收”，而不只展示生成代码量。

### 9.4 面试话术与真实场景复盘

通用讲述结构：**场景约束 → 必须守住的规则 → 技术方案 → 一个故障窗口 → 测试证据 → 代价与剩余边界。**

项目开场可使用以下内容，并按本人实际职责调整：

> 这个项目是一个视频理解与剪辑工作台，包含分片上传、媒体分析、证据检索、Agent 草稿和显式确认后的导出。工程上我重点关注业务状态、模型调用副作用和资源边界：任务通知允许重复，但旧执行不能发布新结果；已保存模型响应可以复用，结果未知时不自动重新付费；模型只能读取受控证据和生成草稿，正式版本由后端校验并经用户接受后冻结。目前已有本地实现和历史验证，端到端资源上限、统一性能报告和更完整的质量基线还在后续计划中。

可准备的真实场景坑点有三类：

- **协议与业务语义不一致：** `null` 与空列表、数值规范化和“继续当前制作”的关系判断，会使看似合理的模型返回被业务拒绝。准备字段含义、公开入口测试和用户结果，不只讲解析异常。
- **模型循环看似有动作但目标没有改善：** 新读取并不意味着草稿时长更接近要求。用已记录失败说明为什么需要独立进展判断；不要声称方案已经实施。
- **测试接入与真实依赖不同：** Langfuse 接收成功、脚本模型通过和真实模型／自然素材成功是不同层次。主动说明每份验证究竟覆盖了什么。

### 9.5 避坑与证据自检

- 不把“任务结果不重复发布”扩大成“任何任务只执行一次”。exactly-once 必须限定协议和事务边界，不能用口号代替分析。
- 不把“有 timeout 参数”直接说成整条调用链有硬时限。
- 不把“有线程池”直接说成高并发，不把局部池上限直接说成全局资源上限。
- 不把“schema 合法、Java 校验通过”直接说成模型内容正确。
- 不把“checkpoint”直接说成长久记忆，不把不同模型职责直接说成动态路由。
- 不把“有 Langfuse”直接说成全链路可观测，不把 token 估算直接说成真实费用。
- 不把测试源码、历史通过数和当前验证结果混写；所有指标保留环境、样本、日期和分母。

- [Java 17 ThreadPoolExecutor](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)：线程、队列与拒绝策略；无界队列不能当作整体资源限制。
- [Java 17 BodyHandlers.ofInputStream](https://docs.oracle.com/en/java/javase/17/docs/api/java.net.http/java/net/http/HttpResponse.BodyHandlers.html#ofInputStream())：响应体以流继续读取，不能仅凭 send 返回或请求 timeout 推定 body 全程已受控。
- [AWS 超时、重试、退避与抖动](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)：重试会放大负载，超时不能证明副作用未发生。
- [LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)：区分执行 checkpoint 与跨线程存储；项目是否采用某能力仍以源码为准。
