# 简历第二条：分片上传与限流的设计与实现

本文对照当前项目代码，解释视频如何上传、上传中断后如何继续，以及 Redis 如何限制创建新上传的速度。先读快速总结，再沿着一次上传的完整过程往下看。

## 一、先快速总结

面试时可以先这样回答：

> 视频文件比较大，所以我采用分片直传。浏览器把视频按 8 MiB 分片，向 Java 服务申请预签名 URL，再直接把分片传到对象存储。Java 负责权限检查、上传记录、签名、分片核对和完成上传，上传过程中的文件数据不经过 Java 转发。
>
> 上传中断后，Java 向对象存储查询实际已经上传的分片，浏览器只补传缺少的部分。恢复前会核对文件大小和 SHA-256，避免用户重新选择了其他文件。
>
> 为了控制连续上传带来的后续处理压力，创建新上传会话时使用 Redis Hash 和 Lua 实现按用户的令牌桶限流。上传完成后，在数据库事务中创建素材、媒体准备任务和 Outbox 通知，接入后台任务处理流程。

这条设计解决三个具体问题：大文件不必经过业务服务转发；传输中断后不必重新上传已经成功的分片；用户不能无限制地连续创建新上传。

需要提前分清：这里的限流限制的是“创建新上传会话的频率”，不是每秒传输的字节数，也不是分析任务的执行并发数。它能约束新素材进入系统的速度，但不保证分析队列永远不会积压。

## 二、先认清浏览器、Java 和对象存储分别做什么

对象存储是保存文件内容的服务。项目通过兼容 S3 的接口执行分片上传、查询和完成操作。理解这段流程时，重点在这些接口及其职责，不必把它限定为某一个对象存储产品。

| 参与方 | 负责什么 |
| --- | --- |
| 浏览器 | 读取用户选择的文件，计算校验值，切分并上传，显示进度 |
| Java 服务 | 检查权限和额度，保存上传记录，签发上传地址，核对实际分片，创建后台任务 |
| 对象存储 | 接收分片，保存实际内容，查询分片，把分片组成完整文件 |
| Redis | 保存每个用户的限流余额及更新时间 |
| PostgreSQL | 保存上传会话、分片记录、容量预留和素材等业务数据 |

正常过程可以按下面这条线理解：

```text
选择文件并计算校验值
    ↓
请求 Java 创建上传会话，检查权限、容量和限流
    ↓
Java 初始化对象存储的分片上传
    ↓
浏览器申请某一片的预签名 URL
    ↓
浏览器把这一片直接传给对象存储
    ↓
Java 查询并核对这一片，登记成功
    ↓
重复上述步骤，直到所有分片传完
    ↓
Java 核对全部分片，要求对象存储完成文件组装
    ↓
Java 创建素材、媒体准备任务和 Outbox 通知
```

## 三、创建上传会话之前，先确认要上传的文件

### 3.1 文件大小和 SHA-256 分别有什么用

用户选择视频后，前端读取文件名和文件大小，并计算整个文件的 SHA-256。

SHA-256 是根据文件内容计算出的校验值。相同内容应当得到相同结果；内容发生变化，结果通常也会变化。可以把它理解为用来核对文件内容的一串标识。

续传时，只比较文件名是不够的。两个不同视频可能都叫“视频.mp4”；只比较大小也不够，两个文件可能恰好一样大。因此，项目同时比较文件大小和 SHA-256。

例如，用户昨天上传视频 A，今天重新打开页面选择了视频 B，即使名字相同，只要校验值不一致，服务端就拒绝把 B 接到 A 的上传中。

前端计算得到的校验值首先是一项声明，不能证明对象存储里最终收到的内容一定正确。完整文件还会在后续媒体准备任务中接受检查。

### 3.2 为什么使用 Web Worker

计算校验值需要读取整个文件。文件较大时，如果这项工作一直占用负责页面交互的主线程，页面可能不够流畅。

项目使用浏览器的 Web Worker 执行这项工作，并把计算进度返回页面。Web Worker 是浏览器中的后台执行环境，与负责运行 Agent 的 Python Worker 不是一回事。

对应前端代码：[uploads.ts](../frontend/src/uploads.ts)、[fileHash.worker.ts](../frontend/src/fileHash.worker.ts)。

## 四、创建上传会话：为这次上传保存一份记录

上传会话不是登录会话，而是描述一次文件上传的业务记录。后续申请分片地址、暂停、恢复、完成和取消，都围绕同一个上传会话进行。

浏览器提交文件名、大小、SHA-256、幂等键和页面标识。Java 先检查用户是否有权操作该项目，再检查文件和容量限制。

当前默认限制包括单文件 2 GiB、每个项目原始素材总量 5 GiB，以及最多 10 个素材。这些值可以配置，不是写死的业务承诺。GiB 和 MiB 是按 1024 进位的容量单位，例如 1 MiB 等于 1024 × 1024 字节。

### 4.1 为什么未完成的上传也要占用额度

假设项目只剩下 1 GiB 可用额度，用户同时创建两个各为 800 MiB 的上传。如果只统计已经完成的文件，两个请求都可能通过，最终就超过限制。

因此，创建上传时会预留容量和素材名额。后续请求检查额度时，会把这些尚未完成的上传也算进去。代码通过数据库行锁协调相关检查和预留，避免并发请求各自检查后一起超额。

“行锁”在这里可以理解为：事务检查和修改某条相关记录时，其他需要取得同一把锁的事务先等待，不能同时完成相互冲突的判断。

### 4.2 幂等键如何避免重复创建

假设服务端已经创建成功，但响应在网络中丢失。浏览器没有收到结果，就再次发送创建请求。

如果每次都创建新记录，一个文件就可能对应多个上传会话。因此，浏览器为这次创建提供一个幂等键。服务端发现同一用户已经使用这个键创建过相同上传，就返回已有记录。

“幂等”在这里的具体含义是：同一个创建请求重复提交，不会重复创建上传会话。

服务端还会核对项目、文件名、大小、校验值和页面控制关系。不能拿同一个键提交另一个文件，再要求服务端把它当作原请求。

已有会话的合法重试会先返回原记录，不会再次执行创建限流、再次扣除令牌。

### 4.3 初始化对象存储中的上传

创建数据库记录后，Java 调用对象存储，初始化一次分片上传，并保存对象存储返回的上传标识。

需要区分两个 ID：业务上传会话 ID 用于定位数据库记录，对象存储上传 ID 用于定位对象存储中的那次分片上传。后续上传、查询和完成分片时，需要关联到同一次上传。

对应代码：[UploadController.java](../backend/src/main/java/com/agenticvideo/business/upload/UploadController.java)、[UploadService.create](../backend/src/main/java/com/agenticvideo/business/upload/UploadService.java)。

## 五、Redis 令牌桶具体如何实现

### 5.1 使用什么数据类型

项目使用 Redis 的 Hash 类型。每个用户对应一个 Key，例如：

```text
upload:admission:用户ID
```

Hash 可以理解为一张包含字段和值的小表。这个 Hash 只有两个关键字段：

| 字段 | 含义 |
| --- | --- |
| balance | 上次计算后剩余的令牌数量，可以带小数 |
| updated | 上次计算的时间，单位为毫秒 |

Redis 中没有存放三个独立的“令牌对象”，而是用 balance 这个数字表示还有多少资格。

同一用户在不同项目创建上传，共用同一个桶，因为 Key 根据用户 ID 生成。

### 5.2 令牌桶是什么

可以把每个用户想象成有一个小桶。创建一次新上传需要从桶里取走一个令牌。没有令牌，就先等待；随着时间经过，令牌逐渐补回来，但不能超过桶的容量。

项目默认桶容量是 3，每 60 秒补充 1 个令牌。这意味着满桶时可以连续接受 3 次创建请求；如果持续提交，长期补充速度是每分钟 1 个。

不能把这个配置说成“每分钟固定允许 3 次”。桶容量描述最多能积攒多少，补充周期描述资格恢复的速度，这是两件事。

### 5.3 请求到来时，如何计算余额

Java 调用 Lua 脚本，传入用户对应的 Key、桶容量和补充周期。Lua 是运行这段限流逻辑的脚本语言，脚本在 Redis 服务端执行。

脚本通过 TIME 命令取得 Redis 当前时间，再通过 HMGET 读取 balance 和 updated。如果 Key 不存在，就从满桶开始。

如果已有记录，则按下面的方式计算：

```text
经过的时间 = 当前时间 - 上次更新时间
补充数量 = 经过的时间 ÷ 60000
当前余额 = min(3, 原来的余额 + 补充数量)
```

min 表示取较小值，作用是保证桶最多只有 3 个令牌。实际代码还会将负的时间差按 0 处理，避免时间回退时反而扣掉余额。

例如，上次剩余 0.5 个令牌，距离现在过了 30 秒，就补充 0.5 个，当前共有 1 个，可以接受一次新上传。

这里没有定时任务每分钟给用户添加令牌。只在请求到来时，按经过的时间计算即可。

### 5.4 判断通过还是等待

如果当前余额至少为 1，脚本扣除 1 个令牌，返回 0，表示允许通过。

如果不足 1，则不扣除，计算还需要等多久：

```text
等待毫秒数 = 向上取整((1 - 当前余额) × 60000)
```

例如只剩 0.25 个，还差 0.75 个，就要等待约 45000 毫秒，也就是 45 秒。

Java 收到正的等待时间，会返回 HTTP 429。429 表示请求过于频繁。响应中还会带上 Retry-After，告诉客户端建议等待多少秒。

### 5.5 被拒绝时为什么也更新时间

无论通过还是拒绝，脚本都会通过 HSET 保存计算后的余额和当前时间。这样下一次请求只计算从这次更新之后经过的时间。

被拒绝时更新时间不会导致用户一直拿不到令牌，因为已经补充出来的小数余额也保存了：

```text
第 0 秒：余额为 0
第 30 秒请求：余额补到 0.5，拒绝，保存 0.5 和当前时间
第 60 秒请求：再补 0.5，达到 1，通过后扣成 0
```

### 5.6 为什么设置三分钟过期

脚本用 PEXPIRE 给整个 Key 设置过期时间，默认是容量乘以补充周期：

```text
3 × 60000 = 180000 毫秒 = 3 分钟
```

用户三分钟没有请求，就可以删除这条限流记录。即使此前已经用空，三分钟也足够补满，所以再次访问时按满桶处理是合理的。

这是为了清理不活跃用户的数据，不是每三分钟统一重置一次额度。每次执行脚本时都会重新设置这个过期时间。

### 5.7 为什么需要 Lua

如果 Java 分别执行读取和扣减，剩余一个令牌时，可能有两个请求都读到 1，都判断自己可以通过，最后都写入 0。这样一个令牌放过了两个请求。

Lua 将读取、补充、判断、扣减和保存放在一次脚本执行中。Redis 执行脚本期间，其他请求的命令不能插入这段过程，所以第二个请求会看到第一个请求扣减后的余额。

这里依靠脚本执行期间不会被其他命令穿插执行，没有另外使用分布式锁。也不要把这种原子执行理解为数据库事务的自动回滚能力。

### 5.8 Redis 出问题怎么办，限流有什么边界

Redis 连接失败或查询超时时，当前实现返回 HTTP 503，表示上传准入服务暂时不可用，不会直接放行新上传。Java 不自动重试这次扣令牌操作，因为响应丢失时，Redis 可能已经完成扣减，再调用一次可能再次扣除。

Redis 扣减和 PostgreSQL 创建上传记录不是一个共同事务。如果已经扣除令牌，后续创建流程却失败，当前实现没有补回这个令牌。因此，这里统计的是创建尝试所消耗的资格，不能保证每扣一个令牌都对应一个最终创建成功的会话。

已创建上传的续传、分片登记和完成操作，不会再次调用创建限流。令牌桶保护入口，文件大小、项目容量和前端并发限制则分别控制其他方面。

对应代码：[UploadAdmission.java](../backend/src/main/java/com/agenticvideo/business/upload/UploadAdmission.java)、[upload-admission.lua](../backend/src/main/resources/upload-admission.lua)、[UploadErrors.java](../backend/src/main/java/com/agenticvideo/business/upload/UploadErrors.java)。

## 六、浏览器如何分片直传

每片大小为 8 MiB，最后一片可以小一些。例如 20 MiB 文件分为 8、8、4 MiB 三片。浏览器使用 file.slice 取得对应字节范围，不需要先生成三个独立本地文件。

上传每片之前，浏览器向 Java 申请该分片的预签名 URL。预签名 URL 是服务端使用对象存储凭据生成的临时地址，允许持有者在有效期内执行限定的操作。

例如，一个地址允许给指定上传的第 3 片写入数据。浏览器不需要持有对象存储的长期密钥，也不能随意把地址改成其他对象或其他操作。当前默认有效期为 300 秒。

浏览器通过 HTTP PUT 把这一片直接发往对象存储。PUT 在这里就是向指定位置写入分片数据的请求方法。

当前前端最多同时处理两个文件，每个文件内部依次上传分片。因此不能说成“一个视频的所有分片并发上传”。

## 七、分片上传成功后，Java 为什么还要核对

对象存储接收分片后返回 ETag，浏览器再把分片编号、大小和 ETag 提交给 Java。ETag 是对象存储返回的分片标识，不能把它直接当作整个文件的 SHA-256。

Java 不会直接相信浏览器说的“这一片成功了”，而是查询对象存储中的实际分片，检查是否存在、编号是否正确、大小是否符合预期，以及 ETag 是否一致。

核对通过后，才登记到数据库的 upload_parts 表。该表记录某次上传有哪些分片已确认。重复登记同一片时更新原记录，不会不断新增重复行。

例如，20 MiB 文件的最后一片应该是 4 MiB。如果对象存储中这一片大小不对，不能只因为浏览器显示 100% 就认为上传正确。

对应代码：[UploadService.recordPart](../backend/src/main/java/com/agenticvideo/business/upload/UploadService.java)、[MultipartStorage.parts](../backend/src/main/java/com/agenticvideo/business/upload/MultipartStorage.java)。

## 八、上传中断后如何继续

### 8.1 用一个例子理解断点续传

假设文件有 10 片，前 6 片已经成功，第 7 片上传时断网。网络恢复后，目标是保留前 6 片，只传第 7 至第 10 片。

浏览器发起恢复请求时，提交文件大小、SHA-256 和页面标识。Java 检查文件是否与原来一致、上传是否仍有效，以及当前页面能否继续控制这次上传。

检查通过后，Java 查询对象存储的实际分片列表，核对编号和大小，用查询结果更新数据库，再把已确认分片返回浏览器。浏览器跳过这些编号，只补传缺少的部分。

### 8.2 为什么不能只查数据库

实际可能发生：

```text
第 6 片已经进入对象存储
    ↓
浏览器还没来得及通知 Java 登记
    ↓
网络断开
```

此时数据库只记录了前 5 片，但第 6 片实际存在。如果仅凭数据库恢复，就会重复上传第 6 片。

因此，恢复时以对象存储中实际存在的分片为依据。数据库记录方便管理进度，但恢复时需要重新核对实际情况。

### 8.3 刷新页面后能自动继续吗

页面仍然打开时，浏览器还保留所选文件，可以继续上传。刷新或关闭页面后重新进入，当前实现需要用户重新选择原文件，计算并核对校验值后才能续传。

不能说成“关闭浏览器以后仍会后台上传”，也不能说成“不需要重新选择文件就一定可以恢复”。

单片遇到可重试的网络或服务错误时，前端最多自动重试两次。重试前先通过恢复接口查询实际进度；如果发现该片已经成功，就不再传一次。自动重试用尽后保留成功分片，提示用户稍后继续。

## 九、为什么由 Java 查询分片，不让浏览器直接查询

### 9.1 浏览器不是技术上不能查，而是需要另行授权

浏览器目前拿到的是上传某一片的预签名 URL，它不包含列出分片的权限。不能把上传请求改成查询请求继续使用。

如果要让浏览器直接查询，需要设计额外的受限查询授权，并配置对象存储允许相应的浏览器跨域访问。当前项目没有提供这条路径。

“跨域访问”可以简单理解为：页面所在地址与对象存储地址不同，浏览器需要对象存储明确允许这种访问。现有上传配置也需要允许浏览器读取 ETag，否则页面拿不到分片确认信息。

### 9.2 浏览器拿到的列表，服务端仍不能直接相信

浏览器是用户能够控制的环境。用户可以修改前端代码，也可以直接构造接口请求。因此，浏览器提交“第 1、2、3 片已完成”，不能自动成为服务端登记成功的依据。

即使正常浏览器刚刚查询了对象存储，经过浏览器重新提交给 Java 后，这份列表对 Java 来说仍然是客户端输入。当前项目没有额外机制让服务端验证这份转交结果的真实性。

浏览器直接查询可以用于显示进度，但要用于更新数据库、判断上传能否完成，服务端仍需要可靠的核对方式。当前实现就是 Java 自己向对象存储查询。

### 9.3 查询本来就是服务端恢复流程的一部分

恢复上传还需要检查文件一致性、会话状态和页面控制资格。这些工作仍要由 Java 完成。查询实际分片后，Java 还要更新数据库。

因此，把查询放在恢复接口内，可以完成检查、查询、登记，再一次性把确认后的列表返回浏览器。如果让浏览器先查询，这些服务端工作并不会因此消失。

查询返回的是分片编号、大小和 ETag 等信息，不包含视频内容。处理这些信息的开销通常远小于转发整个视频。因此，由 Java 查询分片，与浏览器直传大文件的设计并不冲突。

## 十、如何避免两个页面同时控制一次上传

上传会话中保存当前页面标识、写入凭证和写入资格到期时间。浏览器申请分片地址、登记分片和完成上传时，需要带上写入凭证。

可以理解为：服务端记录“目前由哪个页面继续这次上传”。另一个页面尝试恢复时，如果原页面资格仍然有效，就不能直接接管。资格到期后，恢复流程可以分配新的凭证，旧凭证不能继续通过服务端检查。

代码中的写入资格有效期为 330 秒，正常相关操作会延长它。这和整个上传会话的过期时间不是一回事：前者控制当前页面的写入资格，后者控制这次上传可以保留多久。

还需要分清，已经签发的对象存储 URL 有自己的有效期。更换数据库中的写入凭证，不会立即让这些 URL 全部失效。因此不能把这套机制解释为绝对阻止所有已经在途的分片写入。

## 十一、所有分片传完后，如何完成上传

### 11.1 传完分片还不等于拥有完整对象

分片全部上传后，还需要请求对象存储把它们组成一个完整文件。浏览器调用 Java 的完成接口，Java 重新查询并检查分片数量、连续编号、各片大小及总大小。

检查通过后，Java 将分片编号和 ETag 列表交给对象存储完成组装。不是 Java 把所有分片下载下来再拼接。

### 11.2 对象存储完成了，但响应丢了怎么办

对象存储可能已经完成组装，但 Java 没收到响应。代码会查询完整对象是否存在，后续重试也会先检查对象状态。如果对象已存在且大小符合要求，就可以继续完成数据库中的业务步骤。

这避免了把“没收到响应”直接等同于“对象存储没执行成功”。

完成过程还会取得一个有有效期的操作凭证，防止多个完成请求同时执行关键步骤。最终写入业务结果时，会再次检查该凭证和上传状态。已完成的会话再次提交合法完成请求，则返回已有状态。

### 11.3 为什么最后还要写数据库

对象存储保存的是文件内容，业务系统还需要知道：这个文件属于哪个项目、对应哪个素材、下一步要执行什么任务。

因此，确认完整对象后，Java 在一个数据库事务中创建素材记录、MEDIA_PREPARE 媒体准备任务和 Outbox 通知，同时将上传标记为完成，将容量预留转成已分配状态。

事务意味着这些数据库变更一起提交或一起回滚，不会只创建素材却遗漏对应任务。对象存储的组装操作不属于这个 PostgreSQL 事务，不能把整个过程说成跨数据库和对象存储的共同事务。

Outbox 是数据库中保存的待发送通知记录，后续由发布程序投递给 RabbitMQ。详细机制见[第一条任务可靠链路文档](resume-task-reliability-guide.md)。

### 11.4 上传完成不等于素材已经验证通过

上传接口完成后，前端会显示“传输完成，待媒体验证”。后续媒体准备任务还要检查文件真实内容、大小、SHA-256 和媒体信息，并进行音轨、画面等准备工作。

所以需要区分：文件已经传完，是传输阶段的结果；素材能够被系统使用，还需要后续验证。

## 十二、取消或长期不继续上传时怎么办

未完成的分片也会占用对象存储空间，不能只删除页面进度就不再处理。

取消上传时，服务端先保存取消状态，撤销原写入资格，并记录清理任务。长时间没有活动而过期的会话，也会进入清理流程。默认无活动过期时间为 24 小时，正常相关活动会延长时间。

清理程序中止未完成的分片上传，并删除相关残留对象。由于已签发 URL 和在途操作可能短时间内仍有影响，代码会考虑这些有效期，并持续核对存储残留；不是一收到取消请求就直接认定所有字节已经消失。

容量释放也要与清理结果对应。如果对象存储暂时不可用，不能假装清理成功，提前认为空间已全部释放。

对应代码：[UploadCleanup.java](../backend/src/main/java/com/agenticvideo/business/upload/UploadCleanup.java)。

## 十三、面试时可以怎样逐步展开

先用第一节的快速总结建立完整流程。面试官继续追问时，再按问题选择对应部分，不必一开始就把每个字段和超时时间全部说出来。

**问：为什么使用分片直传？**

> 视频比较大，如果浏览器先把文件传给 Java，再由 Java 转发到对象存储，业务服务就要承担整个文件的传输。我让浏览器拿预签名 URL 直接上传，Java 负责授权和状态管理。文件按 8 MiB 分片，中断后查询实际成功的分片，只补传缺少的部分，避免整个文件从头上传。

**问：断点续传的依据是什么？**

> 恢复时先核对文件大小和 SHA-256，确认用户选择的仍然是原文件。然后由 Java 查询对象存储的实际分片列表，核对编号和大小，更新数据库，再返回给浏览器。不能只看数据库，因为可能某片已经上传成功，但登记请求还没到 Java，网络就断了。

**问：Redis 用了什么类型，如何限流？**

> 使用 Hash，每个用户一个 Key，保存令牌余额和上次更新时间。请求到来时，通过 Lua 根据时间差计算补充数量，最多补到桶容量，然后判断能否扣除一个。默认最多积攒 3 个，每 60 秒补充一个。Lua 保证这段读取和修改不会被其他请求穿插，避免并发重复使用同一个令牌。余额不足就返回等待时间，由接口返回 429。

**问：为什么不让浏览器直接查询对象存储？**

> 浏览器可以在获得额外查询授权后直接查，但服务端还要检查会话、文件一致性和写入资格，并用实际分片更新数据库，不能直接信任客户端提交的列表。因此当前由 Java 查询并核对，再把结果返回浏览器。查询只传分片信息，文件内容仍然直传对象存储。

**问：上传结束后如何进入分析？**

> Java 核对全部分片，调用对象存储完成组装，确认完整对象大小后，在同一个数据库事务中创建素材、媒体准备任务和 Outbox 通知，并标记上传完成。后续通过 RabbitMQ 通知消费者处理，接上任务可靠链路。传输完成时素材还待验证，不能立即认为它已经可用。
