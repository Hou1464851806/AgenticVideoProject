# 项目面试介绍：视频分析的可靠执行与基于证据的对话剪辑

## 一、可以直接口述的项目介绍

### 1.1 正常展开时使用的版本

> 我做的是一个基于受控 Agent 的视频理解与剪辑工作台，是个人独立开发项目。它面向已经有视频素材、需要查找内容并制作短片的用户。
>
> 用户通常需要反复观看素材，找到相关内容，再手动选段、调整时长和字幕。我希望把内容查找和初步剪辑编排结合起来：视频上传后，系统分析语音和采样画面，保存带时间位置的证据；用户通过对话提问或提出剪辑要求，系统根据实际读到的内容生成回答和草稿。用户可以继续修改、预览，确认后再单独导出成片。
>
> 我重点设计了两条链路。第一条是视频上传后的可靠分析，因为处理耗时长，而且涉及外部模型调用，所以需要处理任务接纳后通知失败、消息重复、执行中断和付费调用恢复。我的做法是用数据库保存任务状态，通过 Outbox 和 RabbitMQ 派发，再根据执行身份和调用回执控制恢复与结果发布。
>
> 第二条是从自然语言需求到剪辑草稿。Agent 可以自主检索和补读，但只能使用四个只读工具，在固定素材和分析版本范围内工作。Java 校验回答引用和草稿的时间、素材、已读范围及用户条件；多轮修改保留制作状态，最终确认和渲染走独立业务入口。
>
> 整体上，Java 负责业务状态、证据和结果校验，Python 用 LangGraph 组织 Agent 执行，FFmpeg 完成媒体处理。我可以先用视频上传后的分析过程，介绍任务链路是怎样设计的。

这段介绍到这里就可以停下来，让面试官选择继续听哪一条。如果对方没有指定方向，再从第一条展开，不必一次讲完全部细节。

### 1.2 时间较短时使用的版本

> 我独立开发了一个视频理解与剪辑工作台。用户上传视频后，可以通过对话查找内容、生成和修改剪辑草稿，预览并确认后再导出。我的两个重点是：让视频分析等耗时任务在重复消息和执行中断时仍有明确状态与恢复依据；让 Agent 根据可回查的视频证据生成草稿，并由服务端控制校验、确认和渲染。前者主要涉及数据库事务、消息队列和任务恢复，后者涉及混合检索、工具调用、多轮状态与业务校验。

本文根据 2026 年 10 月 27 日核对的简历、项目代码和当前浏览器功能整理。后面的咖啡视频是用于解释流程的假设例子，不是用户量、效果或性能的实测记录。技术选择部分说明当前设计的理由和取舍，不表示项目已经逐一实施并压测过所有替代方案。

## 二、项目背景：用户想完成什么，为什么需要这些功能

### 2.1 从一件具体的事情开始理解

假设用户有一段二十分钟的咖啡教学视频，希望剪出一条三十秒以内的研磨操作介绍，保留原声和字幕。

如果完全手动操作，需要先看视频，找到研磨部分，判断前后文，再在时间线上选段、调整顺序和时长，最后检查字幕并导出。如果有多条素材，查找和比较的工作还会增加。

项目希望帮助用户先找到相关内容，再生成一个能够检查和修改的初稿。用户仍然可以回看原视频、预览结果和决定是否接受。当前没有把剪辑质量完全交给模型，也没有用自动导出来代替用户确认。

### 2.2 从需求推导出要做的事情

| 用户需要什么 | 系统因此要做什么 |
| --- | --- |
| 上传自己的大视频文件 | 支持分片直传、恢复和服务端核对 |
| 知道视频说了什么、出现什么 | 转写语音，分析采样画面与画面文字 |
| 快速找到相关内容 | 保存带时间的证据，建立检索索引 |
| 用自然语言提出制作要求 | 理解主题、时长、字幕及修改关系 |
| 看见可继续调整的初稿 | 生成带素材和时间区间的结构化草稿 |
| 确认后得到对应成片 | 绑定已确认版本，执行媒体渲染 |
| 等待或失败时知道发生了什么 | 保存任务和阶段状态，提供可解释的恢复结果 |

这里每一项技术都有对应的使用需要。面试中先说明需要解决什么，再介绍采用的技术，比直接从技术栈列表讲起更容易让人理解。

### 2.3 怎样判断功能是否完成了它的目的

上传完成只说明文件传输结束，不能直接说明视频可以分析；某种分析完成，也不代表所有来源已经就绪；模型返回了草稿，不代表用户已经确认；文件渲染出来，也不代表已经通过发布检查。

这些状态需要明确区分，用户才能知道现在可以做什么、还在等什么、哪里失败了。两条核心链路都围绕这个要求设计。

## 三、两条核心链路怎样连接

第一条是“上传后，可靠地把视频变成可用分析数据”，重点对应简历第一条，并借助第三、四条说明任务实际在做什么。

第二条是“从对话需求到基于证据的剪辑草稿，再到确认导出”，重点连接简历第三、四、五、六条。分片上传与限流是支撑入口，对应第二条，可以作为后端面试的补充话题。

```text
用户上传视频
    ↓
第一条：媒体准备 → 语音和画面分析 → 保存证据 → 建立并发布索引
    ↓
用户提出问题或制作要求
    ↓
第二条：理解需求 → 检索与补读 → 回答或草稿 → 校验与修改
    ↓
用户预览 → 确认当前草稿 → 单独请求正式导出
    ↓
后台渲染与产物发布 → 用户播放或下载
```

可靠任务机制也用于 Agent 和渲染，所以两条链路并不是互不相关的两个系统。面试时用视频分析讲清可靠机制，用对话剪辑讲清这些能力怎样帮助用户完成工作。

架构职责可以先记成：

| 部分 | 主要职责 |
| --- | --- |
| 浏览器 | 上传、发送需求、查看状态、预览、确认和导出操作 |
| Java | 权限、任务、视频分析、证据和检索、草稿校验、版本与产物发布 |
| Python Worker | 理解消息，执行 Agent 工作流，管理已读证据和草稿状态 |
| PostgreSQL | 保存业务状态、证据、调用回执和版本等权威记录 |
| RabbitMQ | 通知后台处理任务 |
| 对象存储 | 保存原视频、派生媒体和成片文件 |
| Qdrant | 提供可重建的向量与 BM25 检索数据 |

“权威记录”指判断业务是否成功、哪一版有效时，以这里保存并核验的状态为准。Python 检查点和 Qdrant 索引不能代替 Java 管理的确认与发布状态。

## 四、第一条核心链路：视频上传后的可靠分析

### 4.1 可以先这样口述

> 视频上传后，我先安排媒体准备，再分别推进语音、画面和索引工作。它们耗时较长，所以先接纳为后台任务，用户通过状态查看进度。任务和待发送通知放在同一个数据库事务中，后续通过 RabbitMQ 派发。消费者收到通知先领取任务，提交结果时再次核对当前执行身份。外部模型调用单独保存回执，恢复时复用已经成功的部分；提交结果不确定时停止自动重付。这样每一步是否完成、失败后能否继续，都有持久记录可查。

### 4.2 第一步：媒体准备，明确输入能不能使用

对象上传完成后，还需要验证文件、读取时长和媒体信息、准备音频与稀疏画面。输入不合法时，应报告验证失败，不能继续让模型处理一个不可用文件。

FFprobe 用于读取媒体信息，FFmpeg 用于解码、音频准备、抽帧和后续渲染。这里的抽帧保留原视频实际时间，方便把分析结果准确放回原视频位置。

### 4.3 第二步：把耗时操作拆成有明确结果的阶段

```text
MEDIA_PREPARE：媒体准备
    ├─ CONTENT_ANALYZE：ASR 语音转写
    └─ 画面准备（需要时）→ VISION_ANALYZE：VLM 画面分析
                    ↓
             原始证据与检索单元
                    ↓
             INDEX_BUILD：索引构建
```

ASR 是语音识别，输出转写文字和时间；VLM 是视觉语言模型，理解抽出的图片；Embedding 把文本变成数值向量，供语义检索使用。

语音和画面独立推进，一种来源失败不应抹去另一种已成功结果。没有音轨时，语音阶段可以标为不适用。索引按已固定的证据集合构建，新证据后续再通过相应构建接纳进入索引，不要求所有来源都先成功才能有任何可用内容。

拆阶段的目的，是让完成情况与恢复范围清楚。例如 ASR 成功、视觉失败，后续不必把已经完成的语音转写再付费执行一次。

### 4.4 第三步：任务和通知一起保存

如果先保存任务、再直接发 MQ，进程可能在两步之间退出。反过来先发消息，也可能在数据库尚未成功保存时就让消费者开始处理。

项目使用 Transactional Outbox：在一个 PostgreSQL 事务中保存任务和待发送通知，之后由发布器把通知发给 RabbitMQ。Outbox 可以理解为数据库中的“待发送通知列表”。

事务表示这些相关数据库修改一起提交，失败就一起撤销。它不把 RabbitMQ 网络发送也变成数据库事务的一部分，而是先可靠记录“这条通知需要发送”。

发布器收到发布确认，并核对没有路由退回后，才标记已发布。发送失败保留待处理记录，后续再尝试。发布确认表示消息代理接收情况，不能解释成任务已经执行成功。

### 4.5 第四步：通知重复，仍然先核对任务资格

消息可能已发送成功，但进程在更新 Outbox 前退出。恢复后再次发送，就会重复。

所以消费者收到的是任务通知，不能直接无条件执行。它在短事务中锁定任务行，检查是否待执行、是否到执行时间，再创建 attempt 并更新任务状态。attempt 是一次具体执行的身份，用于区分先后执行。

领取事务提交后就释放锁，模型请求和媒体处理在事务外进行。提交新结果时再核对当前 attempt，防止失效执行写入。

状态机就是规定任务在什么状态可以做什么，例如待执行可以领取、已完成不能重新启动。幂等是重复请求不重复产生本应只发生一次的业务效果，不表示消息不会重复。

### 4.6 第五步：模型调用保存回执，恢复有依据

回执是一次调用的持久记录，包含状态、请求身份和收到的响应等。模型提交前先登记，提交后尽快保存返回内容，避免恢复时只知道“任务没完成”，却不知道外部调用到哪一步。

ASR 通常先返回提供方任务 ID。未完成时，程序保存下次查询安排，结束本次执行；后续通知继续查询同一个远端任务，不重新提交转写。

VLM 和 Embedding 在这里是同步调用，但成功响应仍会保存。恢复时检查已有成功记录，跳过已成功的调用或批次，继续允许执行的剩余部分。

最重要的判断是：本地超时不代表远端没有执行。如果请求可能已经提交，却没有确认响应，项目保留“不确定”状态并停止自动重新付费。当前没有承诺能自动解决所有未知提交。

### 4.7 第六步：核对完成情况，再发布可用结果

语音、视觉观察和检索单元保存到 PostgreSQL。索引任务固定本次处理的数据和配置，写入 Qdrant，回读核对后再切换为有效索引代次。

“代次”就是一次构建对应的一版索引。写入新代次时，旧有效代次可以继续使用；不能写到一半就让查询依赖未完成数据。

数据库提交和外部索引写入不能放进同一个本地事务，所以使用“先构建和核对，再发布”的流程。Qdrant 保存可重建索引，业务记录仍保存在 PostgreSQL。

### 4.8 当前执行与恢复有哪些边界

视频分析和渲染在 Java 本进程的消费线程中执行，通过本机运行集合配合数据库状态判断执行情况；默认分析消费者数为 2，并非一个专门执行 ASR、一个专门执行 VLM。消息被领取后在当前消费线程执行，没有再转交额外线程池。

Python Agent 是远程 Worker，Java 通过租约和心跳判断执行资格。租约是有到期时间的执行许可，心跳用于续期。它与 Java 本机任务的运行记录不同，不能把全部链路都描述为同一种租约恢复。

当前部署有单实例约束，尚不能按“任意 Java 实例都能接管所有本机任务”介绍。增加实例需要重新处理执行归属与恢复判断，不能只增加消费者数量。

安全失败、正常等待、付费提交未知也要区分。重试和延后执行由应用保存状态、时间及新通知，不是 RabbitMQ 自动理解业务错误。ACK 表示本条通知已处理妥当，可能是成功、已记录延后，也可能是已记录终态失败，不必等整个视频所有阶段成功才确认这条消息。

## 五、第二条核心链路：从自然语言需求到确认成片

### 5.1 可以先这样口述

> 用户说“生成一条三十秒的研磨介绍”，系统先判断这是新制作还是修改已有草稿，再固定素材范围。Agent 通过搜索和区间读取找到相关证据，形成带素材、时间和引用的草稿。模型每次只提出一个动作，程序控制工具权限、参数、预算和状态。草稿必须交给 Java 校验，用户可以继续修改和预览；确认时核对当前草稿及校验记录，再形成不可变版本，正式导出另行创建渲染任务。

### 5.2 第一步：把视频内容组织成可以回查的证据

例如一句转写保存为“视频 A，第 31～36 秒，介绍研磨粗细”，一帧视觉观察保存为“视频 A，第 32 秒，操作磨豆机”。它们还带分析版本和证据 ID。

这样检索命中后，能够回到原视频核查；生成草稿时，也有实际选段位置。语音的区间和画面的观察点统一到同一原视频时间轴，但保留不同时间含义，不能把一帧看到的内容扩展成整个区间都发生了。

当前是稀疏画面分析，控制了处理量和模型费用，也带来遗漏可能。证据未命中不能证明视频中不存在某内容，ASR 和 VLM 结果本身也可能有识别错误。

### 5.3 第二步：理解需求，并确定对话关系

模型先判断本轮是问答、讨论还是制作，并判断是独立请求、新制作、继续修改或回答待澄清问题。

Java 接纳时提供最近 12 条历史消息、当前制作条件和待回答问题。12 条是消息数，不是 12 轮对话。当前制作条件单独保存，例如主题、时长、字幕和输出数量，不依赖模型每次从历史中重新推测。

用户说“缩短到二十秒，其他不变”，模型只提取明确修改，程序保留其他条件。用户明确说“另外做一个新主题”，则建立独立制作，不能把上一份条件自动带入。

模型提出的关系还要经过 Java 核验，再绑定真实制作身份、固定范围和编辑代次。编辑代次表示当前制作修改到哪一次，用于防止旧执行影响新修改。

### 5.4 第三步：检索定位，再补读上下文

Agent 可用的四个工具是：

| 工具 | 用途 |
| --- | --- |
| list_assets | 查看固定范围内有哪些素材和已就绪来源 |
| get_video_overview | 查看按时间组织的内容导航 |
| search_evidence | 搜索与问题相关的原始证据 |
| read_video_range | 读取指定时间范围的原始证据及前后文 |

搜索用稠密向量找到意思接近的表达，用 BM25 补充词语匹配，还保留数据库原文包含匹配。RRF 根据各路名次合并结果，避免直接把含义不同的原始分数相加。RRF 分数用于排序，不是事实可信度。

检索到“磨细一些”后，Agent 可以读取前后区间，判断这句话适用于什么情况，再决定是否选入草稿。搜索命中不等于已经读完整上下文；剪辑选段要求完整读取覆盖该区间的分页。

工具结果每页最多 100 条，还受 32 KiB 大小限制，next_cursor 告诉模型是否需要继续。分页限制单次输入，不代表累计上下文不会增长。

当前概览是从证据文本、来源和时间动态生成的导航列表，不是自动生成的章节摘要，也没有独立导航业务表。导航用于定位，正式引用来自实际读取的 records。

### 5.5 第四步：用受控工作流组织模型决策

LangGraph 中的节点代表处理步骤，例如理解请求、决定动作、检查动作、执行工具、观察结果和校验结果。模型决定下一步需要什么，程序决定哪些动作可以执行。

四个工具的名称、说明和参数格式放进提示词。实际模型适配器绑定统一的 Action 结构，模型输出工具名和参数，不是直接执行 Java 方法。

Python 检查白名单、参数、素材范围、游标和预算，再通过绑定当前任务的内部 API 调用 Java。Java 重新检查执行资格、范围和请求身份，再返回结构化结果并保存回执。

只读工具不开放保存版本、确认或渲染。它们仍可能保存调用记录、检索排名，也可能产生查询 Embedding 费用，因此“只读”不是“没有任何写入和费用”。

### 5.6 第五步：保存证据和进度，让下一轮有依据

工具返回的原始证据经检查后进入 observations，阅读进度进入 coverage。下一轮模型输入包含需求、已读原文、完成区间、待翻页位置、草稿、校验反馈和剩余预算。

提示词分请求理解与动作决策两套，调用时追加工具说明和当前入口规则。程序整理输入，去掉重复原文和不需要的附加字段，不会把全部内部状态无差别塞给模型。

继续同一制作时可以复用已读证据和草稿；新制作隔离。LangGraph 的 SQLite 检查点保存执行状态，支持符合条件的恢复。当前没有跨会话自动学习用户偏好的长期记忆，也没有完整的自动滚动摘要机制。

默认限制包括 16 次模型调用、20 次工具动作、3 次修正、3 次连续无进展和 300 秒活跃执行时间。计数和调用回执会保存，故障恢复不能通过归零预算无限执行。

### 5.7 第六步：草稿必须经过 Java 校验

模型生成的草稿必须写清输出、片段顺序、素材 ID、起止时间和依据。模型提交 DRAFT 后，由程序强制发起校验，不允许模型自行跳过。

Java 检查素材和时间是否合法、选段是否完整读取、引用是否属于固定版本并与片段相交、剪切点是否切断词语、总时长与字幕条件是否满足等。

失败时返回具体字段和原因，Agent 在修正预算内调整。成功结果绑定草稿哈希、条件哈希、制作和编辑代次。哈希是根据内容计算的摘要，用来判断当前输入是否与被校验的输入一致；它本身不判断语义质量。

回答也要检查引用：Python 核对已读证据，Java 发布时核对本次执行的真实成功读取回执。合法引用能证明来源身份和读取关系，不能单独证明自然语言结论必然正确。

### 5.8 第七步：用户修改、预览，再确认当前草稿

用户可以继续说“缩短到二十秒”，系统恢复当前制作状态、合并修改并重新校验。用户也可以显式请求草稿预览，预览成功不代表已经接受草稿。

确认请求绑定所见草稿消息、校验记录、内容哈希和编辑代次。Java 在事务中核对当前草稿，形成并确认不可变方案版本。不可变表示已接受内容不再被原地覆盖，后续渲染引用明确版本。

幂等键和唯一约束处理重复确认，避免重复生成本应只有一份的版本。当前确认后不能把冻结版本当成仍可原地修改的草稿；旧草稿恢复编辑、从冻结版本派生编辑不能当成已开放能力介绍。

### 5.9 第八步：按明确版本导出，核对后发布文件

用户确认后，还要单独请求正式导出。系统固定方案版本、输出和渲染参数，创建媒体任务，使用 FFmpeg 生成文件。

文件上传后先属于未发布产物，提交时还要核对任务与执行资格，成功后才对用户发布。这是第一条可靠任务机制在渲染中的应用。

当前 FFmpeg 中途崩溃没有从视频中间位置继续的检查点能力，允许重新执行时从固定输入重做。普通渲染失败也不能直接套用分析任务的自动重试策略。失效执行上传的 STAGED 文件由清理逻辑处理，当前没有自动认领旧执行完整文件的机制。

## 六、技术为什么这样选择

### 6.1 第一条链路的选择与取舍

| 选择 | 对应问题与理由 | 需要理解的取舍 |
| --- | --- | --- |
| 后台任务 | 分析和渲染耗时长，用户需要先得到接纳状态并查看进度 | 必须额外设计状态、取消、失败和恢复 |
| PostgreSQL 事务与行锁 | 任务和业务数据本来就在数据库，领取及提交需要一起核对修改 | 事务要短，不能包住几分钟的网络或媒体处理 |
| Outbox | 任务提交后仍要留下通知发送依据 | 需要发布器、重试和积压管理，并允许重复通知 |
| RabbitMQ 通知 | 将请求接纳与后台执行分开，通过队列推动任务处理 | MQ 不掌握完整业务状态，消费者仍需领取和核验 |
| 状态机与 attempt | 同时处理并发领取、重复通知和失效结果 | 状态与迁移规则必须明确，不能只增加一个状态字段 |
| 模型回执 | 恢复时区分已成功、已提交、未确认等情况 | 不能消除网络不确定性，某些情况只能停止并保留原因 |
| 分阶段结果与索引代次 | 保留已成功部分，避免半成品索引成为当前版本 | 会增加阶段与版本管理，但恢复和查询边界更清楚 |

数据库定时扫描也能实现任务调度，当前任务量并不能证明非用 MQ 不可。这里选择 MQ 的理由是明确分离接纳、派发和消费，而不是宣称项目已经需要大规模分布式调度。

同样，当前任务领取没有必要再加一层 Redis 分布式锁：执行状态与业务提交都在 PostgreSQL，短事务可以完成一致核验。Redis 在本项目主要用于上传入口准入限流，不是所有并发问题的统一答案。

### 6.2 第二条链路的选择与取舍

| 选择 | 对应问题与理由 | 需要理解的取舍 |
| --- | --- | --- |
| ASR 与采样 VLM | 把语音和画面变成可查询、可定位的观察 | 有识别误差，稀疏采样会遗漏内容 |
| PostgreSQL 保存证据、Qdrant 提供检索 | 将完整业务归属和引用关系，与相似度检索分开 | 两边不能靠一个本地事务提交，需要版本与发布管理 |
| 向量、BM25 和原文匹配 | 用户可能用近义描述，也可能找专名、数字或原句 | 召回互补是设计目的，相关性收益仍需实际评估 |
| RRF | 用名次融合不同检索方法，不依赖原始分数尺度一致 | 它是排序方法，不是语义事实判断，也不保证最优排序 |
| Python 与 LangGraph | 组织决策、工具、补答、修正和检查点 | 增加跨语言协议与本地状态运维，不能代替业务校验 |
| 四个只读工具与固定范围 | 给模型必要的信息获取能力，同时限制操作范围 | 自主能力有限，不能随意访问新素材或主动付费重分析 |
| 结构化条件与草稿 | 多轮修改要保留要求，渲染需要明确时间和素材 | 要维护字段、身份、版本以及错误反馈 |
| Java 校验与独立确认 | 模型结果需要成为可核对的业务对象，用户需控制最终版本 | 规则能核对硬条件，不能保证剪辑语义和观感 |

普通 while 循环也可以实现决策和工具调用。选择 LangGraph，是因为当前已经有多种分支、等待、恢复和状态保存需求，使用框架组织这些步骤更直接。若只有一次固定调用，未必需要完整 Agent 工作流。

Java 和 Python 的分工也有成本。Java 保留业务事务、权限和结果发布，Python 负责模型编排；双方通过严格结构化契约通信。必须一起核对字段、哈希和执行身份，不能只让 Python 判断通过就直接写正式版本。

可以准备一条更具体的个人工作回答：

## 八、面试时怎样逐步引出技术追问

建议按“用户问题 → 当前流程 → 最关键的失败情况 → 采用的机制 → 取舍”展开。不要在开场同时背出所有配置、类名和异常分支。

| 讲述位置 | 可以自然补充的一句话 | 可能引出的追问 |
| --- | --- | --- |
| 接纳后台任务 | 任务写入数据库和发消息不能天然一起成功 | 事务、Outbox、消息确认 |
| 消费任务 | 消息可能重复，所以我先领取再执行 | 行锁、状态机、幂等、并发 |
| 请求模型 | 超时不一定表示对方没有执行 | 超时与重试、第三方接口一致性 |
| 发布索引 | 外部索引写完，还要核对后才切换有效代次 | 多存储一致性、版本、失败恢复 |
| 查找内容 | 用户措辞和视频原话可能不同 | Embedding、BM25、RRF |
| 生成草稿 | 搜索命中不代表已经读完整上下文 | 检索与补读、证据、时间模型 |
| 执行 Agent | 模型提出动作，程序检查后执行 | 工具调用、结构化输出、权限 |
| 多轮修改 | 聊天解释指代，结构化状态保存要求 | 上下文、记忆、状态恢复 |

面试官转向某个点后，先回答那个具体问题，再接回业务。比如问“行锁为什么不一直持有”，就解释短事务领取与长时间模型调用的区别，不必马上把整个 Agent 工作流重新讲一遍。

## 九、可能的追问与可以直接回答的思路

### 9.1 为什么不直接在接口里处理完视频再返回？

> 媒体验证、模型分析和索引构建耗时不同，还可能等待外部任务。让一次 HTTP 请求一直等，会把用户连接和后台执行绑在一起，断线也不便于判断实际结果。我先持久接纳任务，返回任务身份和状态，后台按阶段处理，用户可以继续查看或恢复操作。代价是需要明确设计状态和失败处理，这也是任务链路的主要工作。

### 9.2 Outbox 是否保证绝不重复？

> 不保证。它解决任务提交后仍有通知记录可继续发送的问题。消息发成功、更新记录前崩溃，恢复后就可能再发。所以发布端允许至少一次投递，消费端通过数据库状态和执行身份避免重复业务效果。发布确认、消费 ACK 和业务结果提交是三个不同环节，不能互相替代。

### 9.3 两个消费者同时收到同一任务，怎么办？

> 它们都需要在数据库事务中锁定并检查任务。第一个完成领取以后，任务已经不是可直接领取的状态，另一个就不能再次启动同一执行。锁只覆盖领取修改，不覆盖后续模型调用；结果提交时还要核对当前 attempt。这个设计依赖明确状态迁移，不能只做一次普通查询再在事务外更新。

### 9.4 MQ 为什么只通知，不把全部数据放进去？

> 当前任务会取消、重试和改变执行资格，业务数据及固定输入已经在数据库里。消息带任务身份，消费者领取时读取该任务已保存的输入，并核对当前状态，这样旧通知不会直接带着过期资格执行。把完整数据放消息里也是可行模式，但仍需要处理去重、版本和取消。我的任务本来就需要数据库记录，所以采用通知加领取。

这里读取的是该任务固定输入，不是每次取最新聊天或最新素材来改变任务含义。

### 9.5 模型调用超时，为什么不直接重试？

> 因为请求可能已经到达服务商并产生费用。先看调用回执：已有完整响应就复用；ASR 已有远端任务 ID 就继续查询；能够确认未提交的情况才按策略尝试。若可能已提交但没有确认，保留不确定状态并停止自动重付。一次网络异常不能同时证明业务失败和费用未发生。

### 9.6 分析中断后，真的可以从原位置继续吗？

> 要看哪一层。已经保存的语音、视觉结果或向量批次可以复用，ASR 可以查询原任务，但不是恢复模型内部运行到某个计算步骤。恢复依赖的是业务阶段和调用记录。渲染又不同，FFmpeg 当前没有中途续渲染检查点，允许重新执行时按固定输入重做，不能把分析的恢复能力套到所有任务上。

### 9.7 为什么需要 attempt，有任务状态还不够吗？

> 状态说明任务现在处于哪个阶段，attempt 说明当前哪一次执行有资格提交。例如旧执行失效后产生了新执行，任务仍然可能是运行中。仅检查运行中，无法区分新旧提交；还需要比较当前执行身份。远程 Agent 的租约决定何时失去资格，attempt 区分具体执行，职责不同。

### 9.8 增加实例后，当前设计能直接用吗？

> 不能把现有单实例实现直接说成完整多实例接管。数据库领取和结果身份校验有共享基础，但 Java 本机运行集合只知道本进程情况，Python 检查点也保存在本地。扩展时需要重新设计执行归属、恢复判断和状态存储，确保一个实例不会把另一个仍在运行的任务误判为失效。这属于后续扩展，不是当前已验证能力。

### 9.9 为什么不用一段很长的提示词，直接让模型生成剪辑？

> 最终草稿必须引用真实素材和时间，只靠提示词不能核对这些业务事实。我先把视频分析为带时间的证据，让模型按需检索、补读，再生成结构化片段。程序检查范围和预算，Java 检查草稿的实际条件。提示词引导如何选择，代码负责执行和核验，两者共同工作。

### 9.10 为什么混合检索，RRF 又解决什么？

> 用户可能说近义表达，也可能找人名、数字或原句。向量和词语匹配提供不同候选，原文包含匹配补充明确字符串查找。各方法的原始分数含义不同，所以我用 RRF 按排名合并。它是当前可解释的融合方案，但相关性是否更好需要用实际问题评估，不能只因为用了混合检索就宣称准确率提高。

### 9.11 搜索已经返回原文，为什么还要读区间？

> 搜索找到的是相关候选，可能只有一句结论，缺少前面的条件。例如“磨细一些”可能只适用于萃取过快，剪掉前提就改变意思。区间读取补齐附近记录。当前草稿要求完整读取覆盖片段的分页，引用也要与片段相交。程序能检查读取和时间关系，语义是否完整仍需要模型和用户判断。

### 9.12 Agent 怎样知道之前读过什么，会不会反复搜索？

> 工具结果按证据 ID 保存，区间与分页进度单独记录。下一轮上下文会给出已读原文、完成范围和准确的下一页参数，并去掉部分重复内容。重复读取通常不会产生新进展，连续无进展会停止，同时还有调用和时间预算。这能限制重复执行，但不能保证模型每次都选择最有效动作。

### 9.13 多轮对话是不是把所有聊天都交给模型？

> 当前使用最近 12 条消息，加上结构化条件和当前制作状态。聊天帮助理解“刚才那个”，条件、草稿和证据负责准确继续工作。继续同一制作才恢复原检查点，新制作隔离。超出历史范围且未保存为条件的信息不会自动检索回来，目前也没有跨会话学习用户偏好的长期记忆。

### 9.14 为什么草稿要 Java 再检查一次？

> 模型输出只是一个候选方案，可能引用了错误 ID、超过视频时长或者没有满足硬条件。Java 持有业务状态和原始证据，可以按确定规则核对素材、时间、引用、读取范围、时长和字幕。校验成功还要绑定当前草稿和条件，防止改过以后仍用旧通过记录。但规则校验不等于证明内容精彩或语义完全正确。

### 9.15 修改草稿和点击确认同时发生，怎么办？

> 确认携带用户看到的草稿消息、校验记录、哈希和编辑代次。后端在事务中检查它是否仍是当前可接受草稿，旧身份不能确认新内容，重复提交通过幂等记录和唯一约束复用结果。接受后形成不可变版本，再单独请求导出，这样实际渲染有明确输入，不会随聊天后续变化。

### 9.16 FFmpeg 已上传文件，但任务提交失败，能直接让用户下载吗？

> 文件存在不代表已经属于有效业务结果。程序还要核对任务和执行资格，成功发布后才对用户开放。当前失效执行的 STAGED 文件交给清理逻辑，没有自动认领它作为新结果。这样可能浪费一次计算，但保留了明确的发布边界。若以后要复用，需要验证输入、完整性和归属，不能只凭文件名存在就采用。

## 十、用具体故障检查自己是否理解

下面是学习和验证场景，不表示本次已经重新执行了这些测试。回答时按“留下什么记录 → 谁做判断 → 下一步怎样处理 → 用户看到什么”展开。

| 场景 | 应当能够解释的重点 |
| --- | --- |
| 任务提交成功，MQ 暂时不可用 | Outbox 保留待发送记录，任务有状态，不伪装成已执行 |
| 消息已发送，发布器还没更新就退出 | 可能重投，消费端仍先核对领取资格 |
| ASR 成功，视觉执行中断 | 保留语音结果，依据视觉调用回执恢复允许继续的部分 |
| 模型已提交，本地没有收到确认 | 结果未知，不能无条件重新付费 |
| 结果保存成功，消费 ACK 丢失 | 重投后根据已完成状态跳过重复业务执行 |
| 索引写入成功，发布事务失败 | 外部数据不自动成为当前有效索引，按状态重新核对 |
| Agent 不断读同一页 | 阅读进度、无进展检测和预算如何生效 |
| 用户把 30 秒改成 20 秒 | 如何保留其他条件、复用证据、重新校验当前草稿 |
| 旧 Agent 结果晚到 | 当前 attempt、租约、制作代次和发布条件怎样拒绝失效结果 |
| 用户重复确认 | 请求身份与唯一约束如何避免重复生成版本 |

理解透彻还包括说明用户能获得什么：任务失败原因可查、成功部分不会无故被抹掉、证据能回到原片、草稿条件明确、确认和导出对应同一版本。

如果以后需要补充量化结果，可以分别测量分析阶段耗时、恢复时复用的调用数量、检索命中质量、草稿硬条件通过情况和用户实际修改量。测量前只能说设计目标和验证方法，不能填写虚构比例或生产规模。

## 十一、接下来怎样阅读和练习

先按开场介绍讲清项目，再选择一条链路，用咖啡视频例子完整走一遍。能说清正常流程以后，再逐个加入故障。暂时讲不清的地方回到对应源码，不用靠增加术语填补。

| 主题 | 阅读入口 | 读完应该能回答什么 |
| --- | --- | --- |
| 当前功能与架构 | [项目 README](../README.md) | 用户实际能做什么，各部分由谁负责 |
| 可靠任务细节 | [任务可靠链路文档](resume-task-reliability-guide.md) | Outbox、领取、ACK、模型恢复和三种任务的区别 |
| 分析执行 | [AnalysisProcessing.java](../backend/src/main/java/com/agenticvideo/business/analysis/AnalysisProcessing.java)、[TaskExecution.java](../backend/src/main/java/com/agenticvideo/business/task/TaskExecution.java) | 远端调用、短事务和完成发布怎样连接 |
| 证据与检索 | [混合检索文档](resume-hybrid-search-guide.md) | 原始证据、检索单元、索引与回答引用怎样关联 |
| Agent 与上下文 | [受控 Agent 文档](resume-agent-workflow-guide.md) | 工具调用、提示词、状态、多轮对话和执行预算 |
| 消息与结果绑定 | [AgentRuns.java](../backend/src/main/java/com/agenticvideo/business/agentrun/AgentRuns.java)、[AgentRunResults.java](../backend/src/main/java/com/agenticvideo/business/agentrun/AgentRunResults.java) | 本轮输入怎样固定，结果怎样核对回执和当前身份 |
| 草稿与确认 | [EditDraftValidation.java](../backend/src/main/java/com/agenticvideo/business/plan/EditDraftValidation.java)、[DraftAcceptances.java](../backend/src/main/java/com/agenticvideo/business/agentrun/DraftAcceptances.java) | 模型草稿怎样通过校验，用户接受的究竟是哪一份 |
| 上传补充话题 | [上传与限流文档](resume-upload-and-rate-limit-guide.md) | 分片直传、恢复核对、令牌桶和 Lua 为什么放在入口 |

练习时可以请人依次问：“为什么做这个项目？”“用户怎么用？”“挑一条讲完整。”“在这一步崩溃怎么办？”“为什么选这种做法？”“当前还做不到什么？”能连贯回答这些问题，再深入具体数据库或中间件知识。
