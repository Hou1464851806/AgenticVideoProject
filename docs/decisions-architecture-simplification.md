# 整体架构减重决策

日期：2026-10-26。状态：用户已选定方案 A；本文记录方向，不表示减重工作已经实施。

## 目标与决定

项目同时承担可使用的视频工具与后端工程实践两项目标。用户明确继续将 Redis、RabbitMQ 等后端工程实践作为项目的重要产出。

采用方案 A：保留现有架构骨架，定向减少退役协议、重复协调与文档不一致带来的维护成本，不以最少组件数作为优化目标。

- 保留 Vue 3 + TypeScript 前端、Spring Boot 模块化单体和 Python LangGraph Worker。
- 保留 PostgreSQL、Qdrant、S3 兼容对象存储、RabbitMQ 与 Redis。Redis 上传准入限流继续沿用已确认契约，不改为进程内限流。
- 保留事务 Outbox、消费幂等、任务恢复、取消与迟到结果校验，以及外部付费请求结果未知的处理。
- 本地 Langfuse 作为按需启用的观测工具，不成为普通运行的必选依赖。
- 不因统一数据库的形式要求而立即迁移当前 Agent SQLite 状态；生产化或部署边界变化时再评估。

## 选择理由与取舍

现有系统已有实现与验证投入，RabbitMQ 和 Redis 具有用户明确要求的工程实践价值。单纯删除组件会引入迁移及回归成本，也会削减项目产出。当前更有价值的减重是消除不再使用的执行路径，并让职责、状态与文档对应起来。

接受的代价是继续维护多个基础设施、凭据、持久卷及更新流程，并理解 PostgreSQL 业务状态与 Python 运行状态之间的恢复关系。现有 Compose 的资源上限不代表实测占用，本决策不声称性能或资源压力已经验证。

未选择方案 B：取消独立 Redis、改用单实例进程内上传限流。该方案可以减少一个运行依赖，但不符合当前保留 Redis 工程实践的目标。

## 后续减重范围

1. 核对旧 Worker HTTP 协议、配置开关与调用引用；保留或迁移当前仍使用的 DTO，清理确认退役的入口与分支。
2. 更新架构文档，使其准确描述 Java 内媒体和分析执行、Python Worker，以及实际 checkpoint 存储；历史决策注明替代关系。
3. 结合已确定的视频分析与 Agent 最终规格，收敛 Agent 节点和状态。节点合并必须保留付费调用、等待与恢复边界，不能仅按节点数量优化。
4. 保持 Langfuse 可选；若有资源压力，先实测 Java HTTP 与媒体执行的资源竞争，再决定是否需要调整部署边界。

本轮仅记录选型。上述事项是后续工作方向，不表示已完成代码清理或启动全量重构。

## 成功标准

- 上传、分析、问答、草稿、预览与导出行为不退化。
- 按受影响范围验证幂等、取消、重启恢复及付费结果未知的处理。
- 清理后只保留当前必要的执行协议，共享契约不因删除旧入口而损坏。
- 当前架构文档与实际部署、状态存储一致，普通运行不依赖 Langfuse。
