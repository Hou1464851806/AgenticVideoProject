# 视频分析、分层检索与剪辑 Agent 最终设计规格

日期：2026-10-24。代码核对基准：`2546074ec23e5a7dddf701758115a94836f0f8f4`。

本文记录本次讨论确定的目标设计，不表示待实现能力已经完成。当前只编写文档，不修改应用代码，不执行模型分析。实现状态来自源码静态检查，不以设计文档中的计划代替代码事实。

本规格作为后续这部分重构的实施依据。与此前视频理解、Agent 改进草案不一致的地方，以本规格确定的三层内容结构和四节点 Agent 为目标；历史文档继续保留作为背景，不同时执行两套设计。

## 1. 目标与范围

系统面向两个相关目标：回答视频内容问题，以及生成和修改视频剪辑草稿。视频上传后的分析采用固定任务流程；用户对话采用一个受控 Agent Loop；确认和渲染继续由业务流程执行。

核心版本必须完成：

1. 将视频组织成全片内容概览、视频内容上下文、原始观察三层表示。
2. 采用镜头检测与代表帧分析，并用间隔采样补充长镜头，检测失败时明确退回均匀采样。
3. 对概览、上下文和原始观察三层建立索引，Qdrant 保存向量、Chunk 原文和元数据，支持跨层检索、上下文展开和原始范围阅读。
4. 为剪辑提供有来源和边界依据的片段选项。
5. 使用四个主要节点运行 Agent，保存显式内容计划，在草稿提交后执行硬校验和内容审查。
6. 支持同一制作的多轮修改，正确复用读取结果并使旧检查失效。

本次不要求兼容旧数据、旧接口和旧 checkpoint，不建设数据迁移、双写或兼容适配层。可以直接调整数据库、Java/Python 类型和前端契约。新数据库必须能够完整初始化；同一目标版本运行期间，任务恢复、幂等和固定范围仍然必须可靠。实施过程中重置开发数据应是明确的开发操作，不能让程序遇到未知数据后自动删除。

不以模型质量评分、提升百分比或大规模评测作为本方案成立的前提。仍需验证功能正确性、跨语言契约和代表性真实使用链路。不能将自动化测试通过描述为已经证明剪辑审美或内容理解质量提高。

## 2. 领域对象

| 对象 | 含义 | 边界 |
| --- | --- | --- |
| 原始媒体 | 视频、音频、采样图片 | 最初来源，二进制放对象存储 |
| 原始观察 Observation | ASR 转写、画面描述、可见文字 | 第一层模型输出，仍可能识别错误 |
| 镜头 Shot | 画面切换形成的原片区间 | 不等于语义事件，也不是强制剪辑边界 |
| 视频内容上下文 VideoContentContext | 由观察组织的完整论述、步骤或事件及必要关系 | 派生解释，不替代原始观察 |
| 全片内容概览 VideoOverview | 摘要、内容目录和覆盖说明 | 导航入口，不证明完整分析 |
| 片段选项 ClipOption | 一个具体区间及实际入选内容、边界依据 | 不自动保证语义完整 |
| 内容计划 ContentPlan | 本次作品需要表达的信息、理由和顺序 | 随用户目标改变，不写回素材事实 |
| 草稿 Draft | 有序源区间和输出设置 | 由程序校验后交用户预览与确认 |

不再把底层数据对象统一称为“证据”。使用 `observation_ids`、`observations` 等名称。某条观察可以成为某个判断的依据，但“依据”不是另一套数据实体。

三层通过引用连接，不要求单父节点树。一条观察可以被多个上下文引用；一个上下文可以跨镜头。第一版使用 PostgreSQL 引用表，不引入图数据库。

## 4. 上传后的分析流程

### 4.1 任务依赖

媒体验证通过后固定文件哈希、素材时长和时间映射，创建分析版本。复用已经准备的音频和图片，不重复下载和转换同一产物。

| 子任务 | 输入 | 输出 | 执行职责 |
| --- | --- | --- | --- |
| 分析初始化 | 素材身份、时间映射、配置 | 分析版本、阶段记录 | Java analysis/task |
| ASR | 已准备音频、时间映射 | 句词级语音观察 | Java analysis/bailian |
| 镜头检测 | 视频、检测配置 | 有序镜头区间 | Java media 调用 FFmpeg |
| 混合采样 | 镜头、视频、采样预算 | 帧、PTS、采样原因、未覆盖范围 | Java media |
| 视觉观察 | 采样图片 | 画面和文字 POINT 观察 | Java analysis/bailian |
| 上下文组织 | 可用观察、镜头、覆盖状态 | 内容上下文、陈述、关系、缺口 | 程序组装输入，文本模型组织语义 |
| 概览生成 | 已发布上下文、覆盖信息 | 摘要与目录 | 程序提供顺序，文本模型概括 |
| 检索发布 | 三层完整内容及引用 | Chunk、向量、文本与元数据、索引代次、发布记录 | Java search 按已有结构分块，调用 Embedding 向量化，不调用大模型判断切分边界 |

ASR 与视觉分支可并行；上下文组织等待这些分支进入终态。某来源失败时，允许基于可用来源组织结果，但必须标明缺失，不生成替代事实。上下文或概览生成失败时，原始观察仍可使用，相关阶段标记失败，不能填充虚构概览。

逻辑子任务不等于新微服务。耗时媒体操作与外部调用复用现有任务、Outbox 和调用回执；远程 Worker 使用租约，本机执行的区别见 4.5。轻量记录整理不必独立投递消息。

### 4.2 镜头与采样

核心版本使用 FFmpeg 场景变化检测，检测参数属于分析配置。得到边界后映射到原片时间；可变帧率不能简单使用帧号除以名义 FPS。

每个镜头优先选择中间附近、避开边界的代表帧；实际帧时间以解码结果为准。长镜头根据配置的最大观察间隔补充采样。总帧预算不足时按全片时间分布选择，保存被跳过的镜头或范围。预算和最大间隔为配置，不承诺固定帧数覆盖任意长度视频。

没有切换是合法的单镜头结果。只有检测执行失败才使用均匀稀疏采样，并保存失败原因。均匀采样也失败则视觉准备失败，不伪装为已完成。两种结果都保留实际采样点；采样点数量不能换算成完整视觉覆盖。

清晰度择优、近重复过滤和学习式镜头检测不属于第一阶段必做。

### 4.3 内容上下文组织

程序按时间整理语句、相交镜头及有界邻近观察，并提供相邻语句。时间相交只表示候选关联，不表示语义一致。长视频分窗口处理，窗口包含主要记录和少量参考记录；记录归属和引用由程序管理，跨窗口关系通过明确 ID 连接。

模型输出完整表达、步骤或事件，并对具体陈述分别标注口述、视觉支持或推断。程序检查 ID、来源范围、字段和引用完整性。程序不能证明语义判断正确，也不把模型输出的分数当作可靠概率。

例如“只有预热完成后才能开始萃取”支持操作前提；同时刻灯亮的图片不能证明预热已经完成。音画不一致时分别保存两项观察与未确认说明，不强制融合。时间先后不能自动转换为因果或操作依赖。

导航范围从引用记录位置计算，用于找回内容，不是动作精确范围或最终剪辑区间。跨度过大的内容优先保留独立上下文并建立关系。

### 4.4 发布

每个结果引用明确的分析版本与依赖身份。发布记录说明 ASR、视觉、上下文、概览、索引各自状态。新结果生成期间不改变已创建 scope 的可见记录集合。核心版本不提供执行中刷新 scope。

概览仅根据已有上下文生成，目录项必须引用有效上下文，不能独立创造事实。发布后仍保留失败、采样不足和未知边界等说明。

### 4.5 任务领取、租约与执行结果隔离

核心方案保留 PostgreSQL 原子领取，不额外引入 Redis 分布式锁。任务状态、当前执行身份和结果都保存在 PostgreSQL 中，领取和提交可以分别通过短事务保持一致。数据库行锁只覆盖状态变更，不跨越媒体处理或模型调用。

| 职责 | 机制 | 不能替代的部分 |
| --- | --- | --- |
| 消息可靠投递 | 业务事务保存任务和 Outbox，发布者发送 RabbitMQ 消息并处理确认，消费者按协议确认消息 | 消息可能重复，收到消息不代表取得执行资格 |
| 并发领取 | Java 在事务内锁定任务行，检查状态并创建当前 attempt | 不负责判断长时间失联的执行者是否仍能继续 |
| 故障恢复 | 远程 Worker 心跳续约，恢复流程检查过期租约并重新安排领取 | 租约过期不能终止旧进程或撤回外部请求 |
| 旧执行结果隔离 | 提交时核对 current_attempt_id、租约和业务状态 | 不保证外部付费请求只发生一次 |
| 重复请求处理 | 领取请求身份、结果回执和业务幂等约束 | 不能用幂等代替执行资格检查 |

#### 4.5.1 当前实现与目标保留项

[TaskExecution](../backend/src/main/java/com/agenticvideo/business/task/TaskExecution.java) 已使用 `SELECT ... FOR UPDATE` 领取任务。对于远程 Python Agent Worker，Java 创建 attempt_id、记录 executor_id 和 claim_request_id，将任务设为 RUNNING，并设置 current_attempt_id；当前租约为 60 秒。相同执行者和领取请求在租约有效时重试，返回原领取结果，处理领取成功但响应丢失的情况。心跳验证当前执行身份和凭据后续约，期限不是整个任务的最大运行时间。

[AgentRunRecovery](../backend/src/main/java/com/agenticvideo/business/agentrun/AgentRunRecovery.java) 已处理远程 Agent 的过期执行：锁定并重新检查状态，将旧 attempt 标记为 EXPIRED，将可恢复任务设回 PENDING、清除当前执行引用，并写入新的 Outbox 通知；取消任务按取消状态收尾。重新领取产生新的 attempt。恢复不重置付费预算，也不表示可以无条件重发结果未知的模型请求。

[AgentRunResults](../backend/src/main/java/com/agenticvideo/business/agentrun/AgentRunResults.java) 的结果发布在事务内检查执行资格和业务绑定，再保存结果；工具入口同样检查有效执行。新提交必须属于当前 attempt、租约有效且业务状态允许。已经成功提交过的同一结果可幂等返回原结果，不把这种响应当作旧执行再次发布。检查与写入必须处于同一并发控制范围，不能先在事务外检查，再无条件更新。

Java 本机媒体任务当前使用 claimLocal，保留 attempt 身份，结合进程状态和取消状态管理执行，没有远程 Worker 的网络心跳租约。目标继续保留这一区别；将来若把本机任务拆成独立 Worker 或扩展为多实例执行，必须同时调整领取和恢复规则，不能直接沿用进程内活动记录判断其它实例是否失联。本节保留现有机制，不将分布式媒体 Worker 扩展列为本次新增能力。

#### 4.5.2 Worker 失联后恢复的例子

以下以远程 Agent 任务为例，时间用于说明交接过程，不承诺恢复调度的精确时刻。

| 时间 | 事件 | 数据与处理 |
| --- | --- | --- |
| 0 秒 | Worker A 领取任务 | current_attempt_id=A1，租约到 60 秒 |
| 20 秒 | A 无法连接后端，无法续约，但进程尚未停止 | 此后没有成功续约，仍按上次确认的期限处理 |
| 60 秒后 | 恢复流程发现租约过期 | A1 过期，任务重新等待领取，写入 Outbox |
| 65 秒 | Worker B 领取 | current_attempt_id=B1，建立新租约 |
| 70 秒 | A 恢复网络并提交旧结果 | A1 不等于 B1，拒绝旧结果，不覆盖 B 的业务结果 |

租约处理“什么时候允许别人接手”，attempt_id 处理“这是谁的执行结果”。即使尚未有 B 接手，A 的过期租约也不能继续用于新的工具操作或发布。Worker 按最后确认的租约期限停止继续执行，后端仍必须检查资格，因为不能依赖旧进程一定及时停止。UUID attempt_id 通过与数据库当前身份比较实现隔离，不是给任意外部存储使用的递增 fencing token。

#### 4.5.3 为什么不增加 Redis 锁

如果 Redis 锁只覆盖领取过程，数据库依然要原子检查和创建 attempt，租约和结果隔离也要保留。这会增加一次协调和依赖，目前没有已确认的领取竞争瓶颈需要它。如果整个执行期间持有 Redis 锁，TTL 和续期本身就是租约，只是将执行资格放到 Redis，而任务结果仍在 PostgreSQL；检查 Redis 后再写数据库之间仍可能发生过期和接手，不能依靠一次锁检查保证写入安全。

因此本方案只保留数据库这一处执行资格依据。Redis 继续用于已有的限流职责，不新增锁键、续期脚本或双重租约。若后续因实际压力重新评估 Redis 锁，需要原子获取并设置 TTL、用唯一持有者标识原子续期和释放，同时考虑故障切换；这些是候选方案的要求，不是当前实施项。

外部调用另按调用记录处理：旧 Worker 已经发出的模型请求可能仍在服务商处运行。失去租约后停止发起新的有副作用操作，结果未知时优先查询或恢复原调用，不能把任务重领等同于重新付费调用。

## 5. 数据结构与存储

以下为目标逻辑字段；实现时可使用关系表和 JSON 组合，但不能省略来源关联和有效性约束。ID 由程序生成，模型仅引用输入中已有 ID。PostgreSQL 保存完整业务内容、关系、Chunk 清单和发布状态；Qdrant 保存可重建的向量、Chunk 原文和元数据副本，搜索可以直接返回其中的文本；二进制保存在对象存储。这是目标架构中的索引副本，不是旧新系统迁移双写。

| ContentScope | id、project_id、允许素材、固定发布身份、可见概览、上下文及观察集合和允许索引代次 |
| ClipOption | option_id、scope_id、asset_id、source_in_ms、source_out_ms、duration_ms、selected_speech、observation_ids、context_ids、boundary_basis、limitations、conditions_hash |

Observation 使用判别结构：SPEECH 为 INTERVAL，保存 `start_ms/end_ms`、词级信息和音轨溯源时间；VISUAL/VISIBLE_TEXT 为 POINT，保存 `observed_at_ms`。不能通过相同 start/end 字段让调用方猜类型。

上下文 `claims` 保存 `text、basis、observation_ids、limitations`；basis 为 SPEECH_REPORT、VISUAL_OBSERVATION 或 INFERENCE。混合来源支持的结论拆成来源明确的陈述，综合解释标记 INFERENCE。

上下文关系保存 `target_context_id、relation、supporting_observation_ids、explanation`。首版只表达必要前提、解释/指代、明确步骤关系，不建立泛化知识图谱。概览 sections 保存标题、上下文 ID 和导航范围。

ClipOption 在工具回执中固定身份，不需要成为全局素材表。它绑定输入条件和来源，供同一制作复用。长列表不能全部塞进模型上下文，可按相关项读取。候选生成不枚举所有可能起止组合，采用完整语句端点及有界附近安全词边界，保留少量不同切法。镜头边界只是备选；保留原声时不得绕开词级限制。

当前制作的需求、计划、草稿及检查摘要持久化在 Java 业务侧，Python checkpoint 保存执行中间状态和读取缓存。接受本轮结果时由 Java 核对执行资格、当前制作版本和哈希后原子更新。崩溃恢复不能依靠模型重新猜测已接受的计划。

## 6. 检索与工具契约

### 6.1 三层 Chunk、索引与召回

#### 6.1.1 存储职责

PostgreSQL 是完整内容和引用关系的权威来源。Qdrant 中每个点对应一个已发布代次中的 Chunk，保存其向量、正文和定位元数据。搜索不必为了显示正文逐条回查 PostgreSQL；授权、当前可访问状态与 scope 资格仍由后端检查，不能信任模型传入的项目或范围。

完整概览、上下文展开、按时间连续阅读、制作校验从 PostgreSQL 获取。Qdrant 不承担关系数据库职责，也不因保存正文就成为制作确认的权威来源。

#### 6.1.2 各层切分规则

**分析阶段组织语义，索引阶段按已有结构分块。** 上下文组织和概览生成由文本模型识别完整步骤、论述、必要前提及目录结构；索引程序读取这些已保存的对象，按既有字段和边界生成 Chunk。索引阶段不再调用大模型重新判断语义边界，也不使用相邻句子的 Embedding 相似度决定切点。Embedding 仅负责将已经确定的 Chunk 文本转换为向量。

JSON 是业务对象的保存与交换格式，不是切分单位。程序从 summary、目录项、claims 的 text 与 limitations、观察的 text 等字段提取内容；ID、时间和引用保留为元数据。不能把整个 JSON 序列化后按字符切割，将键名、ID 和时间数字混入正文。

| 层次 | 默认 Chunk | 较长内容的处理 | 保留关联 |
| --- | --- | --- | --- |
| OVERVIEW | 一条全片摘要；非空目录部分另按章节形成目录 Chunk | 摘要按完整句分段；目录按完整目录项组合，不把全片压成单一超长向量 | overview_id、section_ids、context_ids |
| CONTEXT | 一个内容上下文的正文 | 按完整陈述或子步骤组合；不足以理解的前提通过关系展开，不复制其他上下文全文 | context_id、claim_ids、observation_ids |
| OBSERVATION | 一句 ASR、一条画面描述或一条可见文字 | 超长文本先按句、再按标点边界切分；仍超限时按字符边界切分并标记片段不完整 | observation_id、frame_id（如有）、原文位置 |

核心版本不额外建立所有相邻语句的滑动窗口索引。上下文层已承担语义组织；如后续发现原始句子召回不足，再增加有明确来源的窗口，避免第一版大量重复。

优先将已有内容对象保留为完整块，再检查所选 Embedding 模型的输入长度和工具结果字节上限；未超限时不为凑目标长度拆碎对象。需要拆分时，程序按保存顺序组合完整目录项或陈述，在长度限制内形成子块；单条仍超限才按句子、标点及最终的字符边界拆分。chunk_profile 固定分词器版本、目标 token 数、硬上限和文本构建规则，必须在模型接入时依据实际输入限制确定，不能用字符数冒充 token 数。超过硬上限不得直接截尾。首版不设置机械重叠百分比；标题作为标明的来源标题可以随子块重复，正文不默认重叠。条件句尽量作为整体；被迫切分时标记 requires_expansion，调用方必须展开来源后解释。

程序只能利用分析阶段已经明确的步骤与关系，不能仅凭文本长度推断哪些陈述存在依赖。陈述与其 limitations 一起保留；若过长而必须拆开，标记 requires_expansion。跨块的必要前提通过上下文引用展开，不宣称每个 Chunk 都语义自足。字符拆分也必须再次检查真实 token 数和字节数，不能把字符数当作长度约束的替代。

子 Chunk 保存 source_spans，定位到原对象字段及 Unicode 码点区间，使用半开区间。标题、正文、陈述的拼接各自记录来源；不能给拼接后全文附一个虚假的单一原文偏移。切分只产生索引单元，不修改原始观察或内容上下文。

#### 6.1.3 Chunk 正文的产生

索引阶段不新增 LLM 改写或语义切分调用。正文直接来自已保存的摘要、目录项、上下文陈述或观察文本。程序只做字段选择、稳定拼接及来源标签，例如“语音说明”“视觉观察”“推断”。正文中的数字、否定和限制不能被清理掉。claims 的 limitations 与相应陈述一起保留；较长 unresolved 和关系列表在展开接口读取，命中结果提供有无缺口的提示。

一条 Chunk 的 text 同时用于稠密 Embedding、BM25 与字面匹配，不另造一个模型生成的搜索摘要。text_hash 对最终 UTF-8 文本计算，规则变化生成新 profile 和索引代次。概览和上下文正文虽也是分析阶段的模型产物，索引阶段仍将其作为来源文本复制，且标明所在层次，不能伪装为原始观察。

例如，context_03 的标题为“开始萃取”，claims 保存“只有预热完成后，才能开始萃取”和“按下萃取按钮，开始制作咖啡”。未超限时，程序将标题和两条陈述组成一个 Chunk：

```text
开始萃取
语音说明：只有预热完成后，才能开始萃取。
语音说明：按下萃取按钮，开始制作咖啡。
```

context_03、两条陈述的 observation_ids、导航时间与来源字段位置放入元数据。新增的来源标签由稳定模板生成，原文位置只指向实际来源字段。随后对上述正文调用 Embedding；这里没有第二次模型总结或语义切分。这个例子只说明字段提取与拼接，完整结构仍遵循第五节。

##### 从 JSON 字段到 Chunk：咖啡教程示例

一个 Chunk 是一段检索文本，可以包含标题和多句话，并不要求一句话对应一个 Chunk。以下 JSON 为说明字段提取而省略部分业务字段，不替代完整契约：

```json
{
  "context_id": "context_02",
  "title": "准备咖啡粉",
  "claims": [
    {"text": "称取18克咖啡粉。", "basis": "SPEECH_REPORT", "observation_ids": ["speech_05"]},
    {"text": "将咖啡粉放入粉碗，并整理表面。", "basis": "SPEECH_REPORT", "observation_ids": ["speech_06"]},
    {"text": "使用压粉器将咖啡粉压平。", "basis": "SPEECH_REPORT", "observation_ids": ["speech_07"]}
  ]
}
```

程序使用 JSON 解析器或已有类型对象，明确读取 title、claims 中的 text、basis 以及适用的 limitations。它不递归收集所有字符串；context_id 与 observation_ids 用于关联，不拼进正文。basis 通过固定映射转换为“语音说明”等来源标签。未超限时，上述对象生成一个块：

```text
准备咖啡粉
语音说明：称取18克咖啡粉。
语音说明：将咖啡粉放入粉碗，并整理表面。
语音说明：使用压粉器将咖啡粉压平。
```

超长对象按以下确定性流程处理：

1. 先组装完整正文，检查包含标题和标签后的 token 数，以及为工具响应元数据留出空间后的字节预算。能完整容纳就生成一个块。
2. 需要拆分时，按原顺序逐条加入完整陈述及其限制说明。加入下一条将超过配置的分块长度时，结束当前块，再开始下一块。
3. 单条陈述超过目标长度、但仍满足硬上限时，允许单独成块；单条超过硬上限时，才进一步按句子、标点及字符边界拆分，重新检查长度并标记 requires_expansion。
4. 为每块生成稳定身份、顺序和实际来源位置，再执行向量化。拆分不修改原对象，不按文本比例生成新的剪辑时间。

假设这个上下文后面还有大量说明而必须拆分，可能第一块保留称量和整理表面，第二块保留压粉及后续说明。这是边界示意，实际例子中的三句短文本无需拆分。两个块的元数据关系如下，完整索引仍遵循下一节：

| 字段 | 第一块 | 第二块 |
| --- | --- | --- |
| layer | CONTEXT | CONTEXT |
| entity_id | context_02 | context_02 |
| chunk_id | chunk_02_01 | chunk_02_02 |
| ordinal | 0 | 1 |
| observation_ids | speech_05、speech_06 | speech_07 及后续实际引用 |
| source_spans | 第一块使用的字段位置 | 第二块使用的字段位置 |

关联完整对象时使用层次、对象身份和固定分析版本；每块同时保存所属素材、索引代次等信息。ordinal 表示同一对象在该代次中的块顺序，不表示视频中的精确切点。命中任一块后，Agent 可用 entity_id 调用 read_video_context，由 PostgreSQL 返回完整上下文及引用，内容较长时继续分页。完整对象无需靠向量搜索寻找其他块来还原；分块清单也可按对象身份和 ordinal 定位同对象的块。概览通过对应素材和固定 scope 调用 get_video_overview，原始观察通过其时间定位调用 read_video_range。

概览采用相同原则。假设 summary 是“视频介绍意式咖啡的制作过程，包括设备预热、准备咖啡粉、启动萃取和成品展示”，sections 有“设备预热”“准备咖啡粉”“启动萃取”三个章节，并分别关联 context_01、context_02、context_03。短摘要完整形成一个 SUMMARY 块，三个章节分别形成 SECTION 块，目录只有标题就只提取标题，不额外生成说明。四个块都属于该视频的同一概览；目录块额外保留各自上下文引用。这里是对不同字段建立索引，并没有把摘要拆成四段。只有摘要本身超过长度限制才按完整句进一步拆分；长目录项按前述规则处理。Chunk 数量由内容结构和长度共同决定，不预先规定每个视频必须产生多少块。

#### 6.1.4 Qdrant 点结构

同一兼容的 Embedding 配置下，三层放入同一 collection，通过 layer 过滤；使用 dense 和 bm25 两个命名向量。不同维度或不兼容模型使用不同 collection，查询按配置分组，不能把向量混用。

```text
point.id = 根据 index_generation 与 chunk_id 生成的稳定 UUID
vectors
  dense：Chunk 正文的稠密向量
  bm25：同一正文的稀疏表示
payload
  project_id / asset_id / analysis_id / publication_id
  index_generation / chunk_id / text_hash / chunk_profile
  layer：OVERVIEW / CONTEXT / OBSERVATION
  entity_id / chunk_kind / ordinal
  title / text
  source_spans
  navigation：time_kind 与对应时间字段
  source_kind（仅 OBSERVATION）
  section_ids / context_ids / observation_ids（适用的引用）
  has_unresolved / requires_expansion
```

navigation 区分 POINT、INTERVAL、ASSET；概览全片范围使用 ASSET，目录及上下文的区间仅为导航范围。原始观察切成多个文本块后，若无法准确对应到更细的词级时间，就保留原观察时间，不能按文本长度插值推算切点。

payload 提供过滤、定位、分组和展示，不自动参与向量语义计算。对 project_id、asset_id、index_generation、layer 以及实际使用的 source_kind 等过滤字段建立 payload 索引；正文无需为普通展示额外建立 payload 全文索引，BM25 和字面通道已负责文本召回。调用方不会收到底层向量或存储凭据。

#### 6.1.5 构建、核对与发布

先固定 PostgreSQL 中三层内容版本，生成确定的 Chunk 清单及正文；批量生成向量，再写入新的 Qdrant 代次。核对数量、点身份、文本哈希、来源元数据和必要向量配置后，才在 PostgreSQL 原子发布代次。核对不通过则不发布，旧可用代次继续服务。跨数据库不依赖分布式事务，未发布数据不可检索。

模型请求结果未知时沿用调用回执规则，不自动重付；已生成且输入与配置一致的向量可以复用。部分层生成失败时，清单只包含成功层，并明确报告各层状态，不把缺层视为没有内容。

scope 固定允许的发布身份和代次；新代次不会覆盖旧执行的正文。旧代次在仍被活动 scope 或执行引用时不得清理。用户删除或权限撤销仍受业务访问控制，不因 scope 固定而继续暴露已禁止内容。

#### 6.1.6 召回与结果组织

当前核心方案不增加 rerank 精排：三路召回后由 Java 执行 RRF，再按对象合并，以组内最高 Chunk 分数确定层内对象最终排序。后续可选精排的接入位置、职责和取舍见第12.1节；当前不新增重排调用、节点或模型依赖。

保留 LITERAL、DENSE、BM25 与 RRF。字面通道查询 PostgreSQL 的同一 Chunk 正文；向量和 BM25 通道可直接返回 Qdrant 正文。所有通道在召回前使用相同项目、允许素材、发布代次和层次约束。返回后批量核对对象可见性与发布身份即可，不要求为展示文本逐条重取完整对象。外部索引身份或文本完整性异常必须报告，不能让模型判断权限，也不能伪装成普通无命中。

**原生能力与项目职责。** Qdrant 原生支持稠密检索、BM25 检索及通过 Query API 的 prefetch 与 RRF 进行混合查询。本项目使用其中的稠密和 BM25 召回能力，但不在 Qdrant 中先融合两路；Java 获取三条通道各自的排名后统一执行一次三路 RRF。不是因为 Qdrant 缺少融合能力，也不是项目自行实现了向量近邻搜索或 BM25 算法。[Qdrant 混合查询](https://qdrant.tech/documentation/search/hybrid-queries/)、[BM25 稀疏表示](https://qdrant.tech/documentation/inference/inference-bm25/)

| 环节 | 职责归属 | 本项目的处理 |
| --- | --- | --- |
| 稠密文本表示 | 外部 Embedding 模型 | Java 调用模型，管理配置与回执 |
| DENSE 召回 | Qdrant | 使用 dense 命名向量和范围过滤，返回通道候选 |
| BM25 召回 | Qdrant | 使用本方案的 qdrant/bm25 文本处理与 bm25 稀疏表示，项目不自写 BM25 算法 |
| LITERAL 召回 | PostgreSQL | 对同一 Chunk 正文做原文子串匹配，与 BM25 词项相关性检索区分 |
| 三路 RRF | Java search | 按各通道排名统一融合，不将原始相似度与 BM25 分数直接相加 |
| 业务结果组织 | Java search/tools | 范围校验、通道状态、层内对象分组、最高 Chunk 分数排序、固定排名与分页、读取入口 |
| 候选内容使用 | Agent | 根据原文选择展开对象，核查来源并规划剪辑 |

选择 Java 融合的直接原因是需要合并 Qdrant 外部的 PostgreSQL 字面匹配结果。将三路排名集中处理，能够保持同一融合规则，并接入现有的通道状态和排名保存流程。代价是应用需要维护少量排序逻辑，并接收各通道候选。权限、分组与分页是业务职责，但它们本身不意味着 RRF 必须由 Java 执行。

当前源码 SearchIndexBuilder 创建 dense 和 bm25 配置，SearchVectors 分别调用命名向量查询，QuestionEvidence.rank 获取 PostgreSQL 字面排名及 Qdrant 两路排名，在 Java 计算 1/(60+rank) 并累加。当前 QuestionEvidence.rank 先执行 PostgreSQL 字面匹配，再按 DENSE、BM25 顺序循环，SearchVectors 使用同步 HttpClient.send，因此当前是串行召回，没有实现下述受控并发。上述三路融合已有基础实现；本规格的三层分组、Chunk 原文 payload 和按对象最高分排序仍按阶段实施，不因原有 RRF 代码存在就视为全部完成。

若未来明确只保留 DENSE 与 BM25 两个通道，可以评估使用 Qdrant 原生融合，再由 Java 处理业务结果；当前不因此改变三通道方案。不能先把 DENSE 与 BM25 融成一个排名，再与 LITERAL 做第二次 RRF，并声称等价于一次三路融合：第一次融合产生的新名次会改变原通道的贡献。

##### 多路召回的受控并发（待实现）

目标方案使用由 Spring 管理的专用受控执行器，三条独立任务并发执行；可以用 CompletableFuture 配合显式指定的执行器汇总。沿用同步 HTTP 与 JDBC 调用，不为此强制重写整个服务为响应式接口，不使用默认公共线程池，也不为每次请求新建线程池。

```text
固定查询、scope、层次与索引配置，保存查询及调用身份
                    ├─ 任务一：Embedding → Qdrant DENSE
                    ├─ 任务二：Qdrant BM25
                    └─ 任务三：PostgreSQL LITERAL
                                      ↓
                      汇总各通道结果、状态和截断信息
                                      ↓
                    Java 层内三路 RRF → 对象合并 → 固定分页
```

稠密任务内部必须先获得查询向量再查询 Qdrant；BM25 和字面匹配不等待 Embedding。Java 工作线程负责执行调用，实际近邻检索和 BM25 计算仍由 Qdrant 完成。RRF 在有限候选上顺序计算，不另做并行。各任务返回独立的通道结果，不并发修改共享 ranks、scores、结果 JSON 或普通 HashMap；汇总者在收齐终态结果后统一组合。数据库事务和连接不跨线程传递，不在持有业务行锁的事务中等待远端调用。

**并发限制。** 执行器配置有限工作线程和有界等待队列，限制是服务实例共享的，不是每个用户请求各自拥有一套线程池。结合数据库连接池、HTTP 连接资源及模型限额设置容量，不预设未经验证的数值。多个内容层或索引配置在各自通道任务内顺序处理，不再为每个层和素材无限提交子任务；同一次查询、同一 Embedding 配置复用查询向量，由稠密任务负责生成和复用，不因三层查询重复付费。

队列已满时明确返回检索繁忙错误，不使用 CallerRunsPolicy 将耗时工作转移到请求线程，也不静默丢弃任务。若提交过程只有部分任务已接纳，取消尚未开始的任务，对已开始调用按回执规则收尾，不发布一份被误认为完整完成的排名。恢复或重试仍核对原 query_id 和调用身份，不能通过重新投递所有分支重置预算或重复付费。未来多实例部署需要按下游总容量分配每个实例的上限，单实例执行器不宣称集群级限流。

**超时与取消。** 查询使用统一截止时间，包含排队与执行时间；连接、HTTP 请求和 JDBC 查询设置有限超时，并受剩余查询时间约束。任务启动前、Embedding 返回后及下一次远端调用前检查剩余时间；已过期不继续发起 DENSE 请求。仅给 Future 设置等待超时不能停止底层 I/O，因此必须设置实际客户端超时，并在中断时按客户端能力取消。连接池获取等待也应有界。

达到截止时间后，冻结可接纳结果与通道终态，尝试取消尚未开始或仍在执行的工作。已取消 Future 不等于远端请求或本地阻塞调用已经结束；底层调用退出前仍受执行器资源上限约束。迟到结果可以用于记录原调用回执，但不能更改已冻结排名或已返回页面，取消也不保证远端计算和费用撤销。

**通道失败与汇总。** 通道记录区分成功、成功但零命中、不可用、部分索引配置成功的降级，以及依赖未就绪；超时、队列拒绝等原因放在错误信息中，不伪装成零命中。已知的只读检索超时或依赖暂不可用时，可在统一截止时间内汇总其他成功通道，以可用通道的原始名次执行 RRF，并在响应中明确缺失通道和覆盖状态，不增加新分数补偿。没有任何成功通道时返回 ERROR，不能返回普通空 hits。

付费 Embedding 提交后响应未知时，保存 UNKNOWN 回执，不自动再调用模型；遵循公共信封的结果未知处理，本次搜索返回明确错误并保留其他已完成通道记录用于恢复。权限、scope 身份、索引完整性异常及内部程序错误不按普通通道故障降级，必须报告并终止正常结果发布。已保存的部分状态用于诊断和恢复，不让 Agent 把错误当作素材不存在。

**咖啡查询示例。** 查询“使用18克咖啡粉的准备步骤”时，任务一等待 Embedding，任务二已可搜索 BM25，任务三可查询原文子串。LITERAL 没有完整子串命中也可以正常成功。三路结束后按同一套 RRF 规则融合，完成顺序不决定排名。若 BM25 已知超时而 DENSE、LITERAL 正常，则按成功通道融合并报告 BM25 不可用；若 Embedding 付费结果未知，则停止正常结果发布并保留回执，不靠重新调用模型掩盖未知状态。并发预期减少独立等待的叠加，但不承诺一定缩短实际耗时，仍需观察下游资源竞争。

每个选中层内分别融合 Chunk 排名，再按固定素材、分析版本和 layer 下的 entity_id 分组。同一对象的多个 Chunk 合并为一个命中，明确采用组内最高 Chunk 的 RRF 分数作为对象排序依据，不累加组内分数。保留得分最高的至多两个匹配 Chunk；more_matches 仅表示本次保留的候选集合中还有未展示的匹配块，不表示已经找到该对象全部相关内容。Chunk 同分按 chunk_id 排序；对象同分按 asset_id、analysis_id、entity_id 排序，身份字段按固定字典序比较。合并只组织结果，不拼接或重新总结原文。同一查询跨层时不将概览、上下文和观察强行混成统一语义排名。初始候选上限为每层每通道 50，层内融合最多 100 个 Chunk；这些是成本上限，不保证召回所有相关对象，截断必须报告。

搜索响应返回 query_id、conditions_hash、各层与通道状态、候选截断说明、next_cursor 和 hits。首次请求冻结分组后的身份与排名，分页不重新调用模型或改变结果。多层结果按 OVERVIEW、CONTEXT、OBSERVATION 的固定层序轮流取各层下一名，页面总数和字节上限仍按 6.2；每条保留 layer_rank，不暗示跨层分数可比。若 byte 上限只能返回更少结果，准确继续游标。

SearchHit 包含：

- layer、entity_id、asset_id、素材名称、analysis_id、index_generation、layer_rank。
- matched_chunks：chunk_id、text、title、source_spans、navigation、requires_expansion。
- 关联入口：对应 overview、context 或原始观察的定位信息。
- has_unresolved、more_matches，以及来自发布记录的覆盖状态提示。
- read_next：类型化的建议读取工具和合法参数；由程序构造，不接受模型在素材中注入工具指令。

不把 RRF 分数当可信度。默认返回所选匹配 Chunk 的完整 text，不只返回 ID，也不临时生成新摘要。超过传输上限的单条 Chunk 应在构建阶段切分；异常超限时明确报错，不能暗中截断后称为原文。

搜索结果存入 search_hits，与已展开上下文和已读 observations 分开。即使命中 OBSERVATION，也可能只是一段原文，不自动获得“完整范围已读”回执。核心版本中具体视频事实回答和剪辑均先通过原始范围工具核查相关观察；概览命中只支持内容定位，不替代具体事实依据。

##### layer 过滤、通道召回与咖啡教程示例

payload.layer 标记 Chunk 所属的内容层，固定为 OVERVIEW、CONTEXT、OBSERVATION 三种，不是只有后两层。工具参数 layers 是要搜索的层次列表；后端校验后拆成各层召回分支，将对应 layer 条件应用到 DENSE、BM25 和 LITERAL 通道，先过滤再选取各层候选。layer 不参与文本向量计算，也不是权限凭据；项目、允许素材、固定发布身份和索引代次由可信执行上下文约束。source_kind 表达语音、视觉或可见文字等观察来源，与内容层不同，仅过滤 OBSERVATION 分支。当前源码中的 sourceKind 过滤不是本方案三层 layer 的已有实现。

假设 Agent 已选定 video_01，用户要求保留“使用18克咖啡粉的准备步骤”，工具业务参数为：

```json
{
  "query": "使用18克咖啡粉的准备步骤",
  "asset_ids": ["video_01"],
  "layers": ["CONTEXT"]
}
```

DENSE 将查询转换成与已发布索引兼容的查询向量，在 Qdrant 的 dense 向量上检索。BM25 使用相同查询的词项表示，在本方案的 bm25 稀疏通道检索；其词频、词项稀有程度和长度处理由固定配置决定，不调用生成式模型。两个通道分别返回 Chunk 身份、原文、元数据和通道内排名。BM25 对“18 克”等词项的匹配还受分词影响，不保证“十八克”等写法自动等价。Java 后端融合排名和组织业务对象；不把这些职责交给 Agent 临时计算。

以下是同一 CONTEXT 层中的假设候选。文本列只展示概述，实际检索使用完整正文；A、B 来自较长上下文，不能据此认为几句短文本也要拆分。

| Chunk | 所属对象 | 内容概述 | DENSE 名次 | BM25 名次 | RRF 分数约值 |
| --- | --- | --- | --- | --- | --- |
| A | context_02：准备咖啡粉 | 称取18克、装粉、整理表面 | 2 | 1 | 0.03252 |
| B | context_02：准备咖啡粉 | 布粉、压粉及操作说明 | 1 | 3 | 0.03227 |
| C | context_04：清理器具 | 清理使用18克咖啡粉后的残粉 | 4 | 2 | 0.03175 |
| D | context_01：设备预热 | 制作前的预热条件 | 3 | 未进入候选 | 0.01587 |

采用等权 RRF，k=60，名次从 1 开始：score(chunk) = 各有效通道中 1 / (60 + rank) 的和。未进入某通道候选的块不获得该通道贡献。表格仅演示 DENSE 与 BM25 的融合；LITERAL 有命中时按相同规则增加第三个通道贡献。不是把稠密相似度与 BM25 原始分数直接相加，也不把通道故障当作正常无命中；状态通过既有信封报告。

A 的分数为 1/62 + 1/61，B 为 1/61 + 1/63。按最高 Chunk 分数分组后，context_02 排第一，分数为 A 的 0.03252，matched_chunks 包含 A、B；context_04 排第二，context_01 排第三。C 虽然有词项重合，但实际讲清理，RRF 不会自行理解并剔除这种语境差异，需要 Agent 阅读判断。最高分规则避免长对象因块多而累计占优，代价是不累加多块共同提供的支持。分组无法恢复通道候选上限之外的对象，截断说明仍需保留。

SearchHit 返回 context_02 的层次、对象与素材身份、layer_rank、A/B 完整正文及各自来源定位，并提供 read_next=read_video_context(context_id=context_02)。RRF 分数可用于后端排序诊断，不要求模型计算，也不是事实可信度。此例中的排名和分数用于验证算法，不能描述为真实素材检索效果。

#### 6.1.7 Agent 展开阅读

大素材库任务可以先 search_video_content(layers=[OVERVIEW]) 找相关视频，再 get_video_overview 获取完整目录，随后 read_video_context 展开步骤，最后 read_video_range 精读候选。asset_ids 未指定时搜索当前 scope 允许的全部素材，而非整个数据库。

精确查询可以直接搜索 CONTEXT 或 OBSERVATION，不要求概览先命中。“十八克咖啡粉”可能不在全片摘要中，却在 ASR 观察里。命中后通过 context_ids 回溯上下文；关系从 PostgreSQL 读取，不用反复向量搜索猜关联。

例如搜索“咖啡制作教程”在概览层找到 A1，目录指出 C3“启动萃取”；读取 C3 发现 C1“预热条件”，再读取两者对应原始范围。Agent 形成计划并调用 get_clip_options。概览或上下文导航区间不直接作为剪辑区间。若用户已指定 A1，可跳过概览搜索直接读目录。

对于上述18克咖啡粉案例，Agent 先查看 A/B 的完整匹配原文，再按 context_02 调用 read_video_context，从 PostgreSQL 读取该固定版本的完整陈述、观察引用、关系和缺口，必要时继续分页。若其中明确关联预热前提，再读取 context_01；不因为 D 检索排名较低就忽略该前提。随后调用 read_video_range 核查准备步骤及必要前提的原始观察，完成所需范围阅读后调用 get_clip_options 比较实际可用切法。检索顺序表示优先查看哪些候选，原片顺序表示素材怎样展开，最终剪辑顺序由需求和内容计划决定，三者不能等同。已经知道对象 ID 后直接展开，不通过反复向量搜索拼凑完整对象。

##### Agent 如何选择检索层次与读取入口

层次选择由既有 Agent 决策节点根据当前缺少的信息完成，不新增分类节点或复杂度评分器。工具说明和主循环指令提供以下默认规则；后端校验参数、权限和执行范围，不按业务关键词硬编码全部路线。模型可调整选择，但不能绕过范围阅读和草稿校验要求。

| 当前信息需求 | 优先动作 | 判断依据 |
| --- | --- | --- |
| 已有有效对象 ID 或读取结果 | 复用结果，或按 ID 直接读取 | 不为已知对象重复搜索；缓存必须属于当前有效 scope |
| 尚未确定相关视频 | 搜索 OVERVIEW | 找素材、了解全片主题 |
| 需要完整步骤、事件或前提 | 搜索 CONTEXT，或展开目录已有 ID | 获取完整表达及关系 |
| 需要数字、原话或具体画面位置 | 搜索 OBSERVATION | 定位原始观察，再核查相关范围 |
| 最佳入口不明确或单层不足 | 扩大层次，必要时同时搜索三层 | 增加覆盖，接受更多候选和阅读成本 |

搜索用于发现未知对象；get_video_overview、read_video_context 和 read_video_range 用于读取已经能够定位的内容。Agent 不必每次依次搜索三层。未指定 asset_ids 时，只搜索当前 scope 内允许的素材；指定素材时仍受同一范围约束。以下调用为业务参数示例，省略可信身份和公共信封；ID、时间与结果为假设素材，不是实测结果，范围按实际返回定位确定。

**案例一：从素材库寻找咖啡教程。** 用户问“从我的素材库里找一段适合做意式咖啡教程的视频”。先搜索概览：

```json
{
  "tool_name": "search_video_content",
  "arguments": {"query": "意式咖啡制作教程", "layers": ["OVERVIEW"]}
}
```

假设命中 video_01 的完整制作教程、video_08 的机器清洁介绍和 video_12 的探店素材。每条 SearchHit 返回匹配原文、素材身份、layer_rank、状态与读取入口。Agent 根据原文选择 video_01，调用 get_video_overview(asset_id=video_01)，获取预热 context_01、准备 context_02、萃取 context_03 等目录 ID，再展开需要的步骤。若用户原本已指定 video_01，可以直接读取概览，省略搜索素材。

**案例二：询问咖啡粉用量。** 用户问“video_01 用了多少克咖啡粉”，优先查询语音观察，不预先猜测答案：

```json
{
  "tool_name": "search_video_content",
  "arguments": {
    "query": "咖啡粉用量 多少克",
    "asset_ids": ["video_01"],
    "layers": ["OBSERVATION"],
    "source_kinds": ["SPEECH"]
  }
}
```

假设返回 speech_05，原文“这里我们称取18克咖啡粉”，时间20.2—23.4秒，关联 context_02。Agent 根据邻近语句定位调用 read_video_range，例如读取18—26秒并处理未完成分页，核查是否存在“以前18克，这次16克”这样的修正，再引用观察回答。示例范围不定义固定扩展秒数。若指代或条件不清，再展开 context_02。这个问答无需内容计划，也无需先搜索概览。

**案例三：询问完整准备步骤。** 查询“开始萃取之前的准备步骤和必要条件”，使用 asset_ids=[video_01]、layers=[CONTEXT]。假设命中 context_02 和 context_03；Agent 展开 context_03 后发现明确前提指向 context_01，再按 ID 读取预热与准备上下文，核查支撑回答的原始范围。关系是继续阅读的入口，前提没有进入搜索前几名也可以被读取；时间接近本身不能生成这种前提关系。

**案例四：制作30秒教程并保留准备步骤。** 用户已指定 video_01 时，先直接 get_video_overview，按目录 ID 展开预热、准备、萃取和成品上下文，形成暂定计划，再读取候选原始范围并调用 get_clip_options。目录足够清楚时，不必再搜索上下文。若需要定位具体操作，可查询“称量咖啡粉 布粉 压粉”，选择 OBSERVATION 和 SPEECH，再读取相应完整范围。用户随后要求缩短到25秒时，优先复用有效计划基线和读取记录，补充缺少的切法，不重新固定执行三层搜索；检查结果依照第七、九节失效与重做。

**案例五：入口不明确，同时搜索三层。** 用户问“哪些素材里讲过萃取前的准备，能不能做一条短教程”：

```json
{
  "tool_name": "search_video_content",
  "arguments": {
    "query": "咖啡萃取前的准备",
    "layers": ["OVERVIEW", "CONTEXT", "OBSERVATION"]
  }
}
```

结果示意如下；文字仅为表格概述，实际 matched_chunks 返回完整所选正文：

| 返回位置 | layer | layer_rank | 命中对象 | 后续决策 |
| --- | --- | --- | --- | --- |
| 1 | OVERVIEW | 1 | video_01 的咖啡教程概览 | 读概览选择素材与步骤 |
| 2 | CONTEXT | 1 | context_15：萃取前预热 | 直接展开步骤和关系 |
| 3 | OBSERVATION | 1 | speech_28：“灯稳定后再启动” | 读原始范围并核查关联上下文 |
| 4 | OVERVIEW | 2 | 另一个相关视频的概览 | 根据当前信息缺口决定是否继续读 |

各层独立召回、RRF 融合和对象合并，再按第6.1.6节的固定层序轮流返回。位置1不表示比其他层更相关，layer_rank 只在所属层解释。相同内容可能跨层出现，不跨层强行合并成一个对象；Agent 根据关联 ID 避免重复展开。多层搜索增加候选数量、传输和阅读成本，因此明确数字问答不默认搜索三层。

**无命中或信息不足时的处理。** 搜索正常但概览未命中某个细节时，可以改查观察；结果太宽泛时，缩小素材范围或改查上下文；对象已明确但页面未读完时，继续分页或展开，而不是重复搜索。返回的分析缺失、通道故障和候选截断必须保留，不解释为“视频中不存在”。涉及权限或身份无效时按公共调用信封停止执行，不通过换层绕过。后续调用仍受总预算和无进展限制约束。

#### 6.1.8 查询生成、改写与后续调整

Query 改写由现有 Agent 决策节点完成。模型根据用户目标、已确认需求、已有读取结果和当前信息缺口，填写 search_video_content 的 query、layers、asset_ids 等业务参数；可以改写用户表达、将复杂任务拆成具体信息需求，也可以根据返回结果调整下一次查询。不单独增加改写节点、独立 Agent 或每次搜索前的额外模型调用。一次决策可以直接产出 CALL_TOOL 动作及查询参数。

后端不再次调用大模型改写查询，也不暗中生成各通道不同的搜索表达。接纳后的同一 query 用于 DENSE、BM25 和 LITERAL；Embedding 编码和 BM25 分词属于检索表示处理，不是生成式查询改写。查询变化时视为新的搜索条件，重新创建 query_id 和排名，不沿用旧查询的分页游标。原有工具调用记录保留实际 query 和结果身份，新的查询不覆盖旧记录。

**咖啡教程案例。** 用户说“用 video_01 做一条30秒咖啡教程，准备步骤一定要保留”。30秒是成片硬约束，继续保存在 requirements 中，不必出现在素材检索词里。Agent 先寻找准备内容：

```json
{
  "tool_name": "search_video_content",
  "arguments": {
    "query": "咖啡制作的准备步骤和必要条件",
    "asset_ids": ["video_01"],
    "layers": ["CONTEXT"]
  }
}
```

展开相关上下文后，若仍需要定位称量、布粉和压粉原话，再生成下一次查询：

```json
{
  "tool_name": "search_video_content",
  "arguments": {
    "query": "称量咖啡粉 布粉 压粉",
    "asset_ids": ["video_01"],
    "layers": ["OBSERVATION"],
    "source_kinds": ["SPEECH"]
  }
}
```

第一步是将制作请求转换成内容检索需求，第二步是根据已读结果定位细节；都不修改用户目标，也不要求每轮机械执行两次搜索。信息足够时直接读取或继续规划。

查询生成遵循以下约束，写入工具说明与决策提示词：

- 不猜测答案。用户问“用了多少克咖啡粉”，查询应围绕“咖啡粉用量 多少克”，不能凭空加入“18克”。用户明确提供或已读观察中实际出现的数字可以用于后续定位，但不能把检索命中本身当作完整事实核查。
- 保留用户要求精确查找的原话、数字、单位、型号、名称，以及影响含义的否定和条件。查找原句时优先保留原句，不用概括性表达替换关键措辞；不得以提取关键词为由改掉数值或删除“不”“只有……才……”等限制。
- 将检索表达与业务约束分开。未放入 query 的时长、画幅或必须保留的内容仍保存在需求中；“保留准备步骤”不能被改写为“原来的十秒一帧不改”，除非用户明确要求。
- 查询中采用尚未核实的操作术语作为探索方向时，不把它记录成素材已包含的事实。搜索发现候选后仍按既有规则展开与核查。
- 已知对象优先按 ID 阅读，已有有效结果优先复用。调整查询应针对具体信息缺口，重复等价查询不视为取得新进展，仍受既有无进展与总预算限制。

程序检查参数结构、长度、范围和游标条件，不新增模型调用来评价每一次改写是否忠实。用户原始消息和需求始终保留，改写后的 query 只是一次工具输入，不能取代需求或扩大权限。

### 6.2 模型可见工具

| 名称 | 参数 | 返回 |
| --- | --- | --- |
| list_assets | cursor | 素材元数据、各层分析状态、next_cursor |
| get_video_overview | asset_id、cursor | 摘要、目录页、覆盖与缺口、next_cursor |
| search_video_content | query、asset_ids、layers、source_kinds、cursor | 三层 SearchHit（含匹配 Chunk 原文）、关联入口、通道及层状态、排名身份、next_cursor |
| read_video_context | context_id、cursor | 分页陈述、关系、观察引用、缺口、next_cursor |
| read_video_range | asset_id、start_ms、end_ms、cursor | 原始观察、实际范围、next_cursor、读取进度 |
| get_clip_options | context_id、asset_id、start_ms、end_ms、desired_duration_ms、cursor | 候选区间、实际转写、引用、边界依据、限制、next_cursor |

layers 为非空且无重复的 OVERVIEW/CONTEXT/OBSERVATION 列表；source_kinds 仅限制 OBSERVATION 分支，不过滤概览或上下文，未选择 OBSERVATION 却传该字段时返回参数错误。

分页字段为空表示结束；首屏为 0，后续使用原条件和返回游标。分页条件变化必须从首屏开始。结果超限必须分页或明确报错，不能静默丢掉关系和原始内容。首版沿用请求 65536、结果 32768 UTF-8 字节的上限；查询最多 256 个 Unicode 码点；普通列表每页最多 20 项，原始观察每页最多 100 项，片段选项最多返回 5 个。按字节上限提前结束页面时，游标依据实际返回记录推进；单条记录本身超限则返回明确错误。约束集中声明，Java/Python 使用同一组边界样例。

`desired_duration_ms` 是候选生成偏好，不修改制作硬时长。候选区间必须位于当前 scope，且对应原始范围已完整读取；否则返回 NEED_RANGE_READ 和所需范围。无可用切法返回空 options 与明确原因，不通过切断词或放宽条件补齐。实际入选转写复用 SpeechTimings 的选择算法。

核心工具都是固定范围读取或派生计算，不开放付费局部分析、保存、确认或渲染。

### 6.3 公共调用信封

模型只填写工具名和业务参数。project_id、execution_id、scope_id、允许素材与业务凭据由可信执行上下文注入，不能进入模型可修改参数。

请求：`call_id、tool_name、arguments、request_hash`。响应：同一调用身份、`status、data、coverage、error`。核心读取响应 status 为 READY 或 ERROR；异步任务等待留在业务运行层，不让模型轮询生产任务。

错误应区分参数可修复、需要补读、依赖未就绪、权限/范围无效、外部调用结果未知。权限和身份错误停止执行，不让模型修补身份。网络结果未知不自动重付；工具内部错误不能转换成“没有找到”。

## 7. 四节点 Agent

### 7.1 流程

1. 初始化：理解本轮意图与制作关系，加载状态，合并明确修改，绑定范围并使旧检查失效。
2. Agent 决策：自主阅读、更新计划、选段、提问、回答或提交草稿。
3. 工具执行：参数和范围校验、执行、回执与读取进度更新，返回主循环。
4. 草稿校验与审查：硬校验失败返回问题；通过后调用审查；必要时在额度内返回主循环。

普通检查函数不独立成图节点。等待用户、终止和恢复属于运行机制。问答使用初始化、主循环和工具；具体素材答复必须引用合法已读观察，独立问答不能改当前制作。一般讨论无需机械读取素材。操作请求说明页面入口，不伪装成已确认或已导出。

### 7.2 Action

使用以 kind 为判别字段的严格联合类型，每轮一个动作，禁止无关字段：

| kind | 数据与前置条件 |
| --- | --- |
| CALL_TOOL | tool_name、arguments；工具必须在白名单内 |
| UPDATE_PLAN | 完整 ContentPlan；当前意图必须为制作 |
| ASK_USER | question、缺失条件或冲突；不能用来重复索要已授权读取权限 |
| ANSWER | content、observation_ids；剪辑无法完成时说明原因，不能绕过提交检查 |
| SUBMIT_DRAFT | 完整 Draft，可附完整 plan_update；无更新时必须有当前需求和 scope 下的计划 |

SUBMIT_DRAFT 可附 plan_update，避免仅为同步最终选择额外调用一次模型。程序先核对并保存计划，再校验草稿，不能留下仅一半更新成功的状态。相同内容重复 UPDATE_PLAN 不计有效进展。

ContentPlan 包含 goal_summary、items、open_issues。每项含稳定 item_id、message、context_ids、inclusion_reason、required_context_ids、selected_option_ids、unresolved。数组表示暂定顺序。用户要求与模型根据素材提出的保留理由必须区分。

Draft 保留当前多输出结构和稳定 output_key。片段具有本草稿内稳定 clip_key、asset_id、source_in_ms、source_out_ms、observation_ids、reason。计划项到输出/片段的对应关系使用显式映射，支持多对多；最终提交映射必须解析到本草稿真实片段。结构映射成立不等于语义成立。

### 7.3 状态与所有权

| 状态组 | 内容 | 生命周期 |
| --- | --- | --- |
| request | 当前消息、理解结果、关系、澄清关联 | 本轮 |
| production | ID、requirements、requirement_sources、scope、plan、draft | 跨轮，Java 保存当前业务状态 |
| reading | search_hits、概览/上下文页、observations、range_reads、pending_pages | 同一 scope 内复用，Python 缓存，Java 回执为权威 |
| selection | options 及其来源、生成条件 | 来源与条件有效时复用 |
| execution | action、pending_tool、feedback、usage、no_progress、content_revision_count、waiting | 本轮，checkpoint 与调用日志 |
| checks | validation、content_review 及输入绑定 | 只对对应输入有效 |

原始观察和模型提示词不必全部复制到业务表；保存稳定引用，调用时读取。凭据不进入状态、提示词和追踪内容。

### 7.4 每次调用的输入与上下文组装

#### 7.4.1 工具结果、持久状态与模型输入

工具结果先进入执行状态，再由 Python 上下文组装程序按本次调用目的选择输入。不能把整个状态、全部历史消息和三层视频内容每轮原样发送给模型。

| 对象 | 保存什么、由谁管理 | 如何用于模型调用 |
| --- | --- | --- |
| 工具结果 | Java 返回的结构化回执，包含实际数据、身份、状态、覆盖说明、分页和错误 | 提供本次操作的事实结果，不直接等同于全部模型上下文 |
| 持久业务状态 | Java 保存需求、计划、草稿及检查摘要；完整素材内容保存在 PostgreSQL | 加载当前有效目标、制作基线与结果绑定 |
| 执行状态 | Python checkpoint 与调用日志保存动作、读取缓存、待处理页、工具调用和预算；Java 读取回执为权威 | 支持恢复和复用，按需读取稳定引用，不把所有原文重复复制进业务表 |
| 单次模型输入 | Python 按调用目的选择的指令、状态信息、相关原文和反馈 | 本次调用的有限视图；未发送某段历史文本不表示删除持久记录 |

处理顺序为：决策产出 CALL_TOOL → Java 执行并返回 → Python 保存调用回执、更新读取状态 → 程序选择下一次输入 → 模型生成下一步 Action。模型不能自行把搜索命中标记为完整范围已读。

reading 中必须区分 search_hits、已展开的概览/上下文页、observations、range_reads 和 pending_pages。搜索命中只表示找到了候选；完整上下文已读取仍不等于对应原始时间范围已读；分页未完成时不能声明完整读取。

#### 7.4.2 三类模型调用的输入

| 调用目的 | 必要输入 | 通常不需要发送 |
| --- | --- | --- |
| 请求理解 | 当前用户消息、当前制作摘要、已确认需求及来源、必要澄清历史 | 整个素材库、全部原始观察和历史工具结果 |
| Agent 决策 | 固定指令、Action/工具契约、当前目标和有效条件、当前计划、相关候选与原文、最新工具结果、准确阅读进度、有效反馈和预算 | 与当前信息需求无关的历史原文、被新版替代的反馈、凭据 |
| 内容审查 | 当前需求、计划、按成片顺序的实际入选内容、必要原始上下文、本轮修改 | 完整搜索探索历史和无关素材；剪辑理由不能代替实际入选文本 |

上述是逻辑内容分组。固定指令、结构化状态消息和工具结果消息的具体排列按模型接口实现；若使用原生 tool 消息，必须遵守调用与结果配对协议，不能删除调用后留下孤立结果。不得因改变消息包装而丢失来源身份或状态含义。

决策工具说明包含第6.1.7节的层次选择规则及第6.1.8节的查询约束，允许在 CALL_TOOL 中直接生成或调整 query，无独立改写节点，后端不再次改写。素材里的指令只作为待分析内容，不作为系统指令执行。计划保存简短决策记录，不保存模型内部思维过程。

#### 7.4.3 咖啡教程：内容怎样逐步进入模型输入

以下为逻辑输入示例，不是额外接口或实测记录。用户要求“用 video_01 生成30秒咖啡教程，保留准备步骤”。搜索上下文命中 context_02，工具返回匹配 Chunk 原文“称取18克咖啡粉，放入粉碗并整理表面”、query_id、对象及版本身份、来源定位和 read_next。Python 将其保存为 search_hits，下一次决策输入为：

```text
当前需求：video_01，30秒，保留准备步骤。
当前计划：尚未形成。
最新结果：context_02，准备咖啡粉；附匹配 Chunk 的完整原文与来源。
阅读状态：仅搜索命中，尚未展开完整上下文，原始范围尚未读取。
下一步可用入口：read_video_context(context_id=context_02)。
工具与执行约束：允许动作、剩余预算、有效反馈。
```

模型据此调用 read_video_context。返回完整陈述“称取18克”“整理粉面”“压粉”、speech_05—speech_07 引用、相关步骤和分页状态后，Python 保存已读页。下一次输入使用这些展开内容和阅读进度；对同一来源、同一版本的重复文本可省去旧搜索副本，但仍保留检索身份和调用回执。如果仍有 next_cursor，明确表示上下文未读完。

随后读取原始范围，假设得到：speech_05 在20.2—23.4秒说“这里我们称取18克咖啡粉”；speech_06 在23.4—27.8秒说“放进粉碗以后，先把表面整理均匀”；speech_07 在27.8—31.6秒说“然后用压粉器把咖啡粉压平”。此时决策输入保留这些原文、时间、身份及必要词级信息，不只保留“这里是准备步骤”的摘要。

范围完整读取后，get_clip_options 返回 option_id、实际起止时间、时长、实际入选转写、观察引用、边界依据和限制。这些选项与需求、计划一起进入后续决策，供模型比较能否保留称量和操作信息、能否与其他步骤组成30秒草稿。范围或选项不完整时应补读，不能用上下文摘要替代缺少的实际内容。

提交后，审查输入按成片顺序组织实际入选文本，附需求、计划和必要原始上下文，检查预热条件或准备步骤是否被遗漏。审查不需要重看第一次搜索到素材的全部过程，也不能只读“保留了准备步骤”这样的选取理由。

#### 7.4.4 去重、分页与长度控制

上下文组装采用程序规则，不新增每轮总结全部历史的模型调用。具体 token 配额、消息模板和各类内容预算在接入所选模型时确定，目前不声明未经验证的固定数值。

- 优先保留固定规则、当前需求、有效计划与反馈，以及当前动作必需的原文和时间。通常将最新工具结果带入下一次决策；结果过大时通过既有分页或显式目录组织，保留实际完成状态，不静默隐藏关键内容。
- 按对象、来源位置和固定版本识别重复内容。完整上下文已包含的同源搜索片段可以只呈现一次；观察与概括即使表达相似也不能直接互相替代，更不能跨版本或凭语义相似去重。
- 暂时无关的历史内容保留稳定引用和读取目录，模型需要时通过现有工具重新读取。内容曾经读过但当前没有进入模型输入，要让目录与当前提供的原文可区分，不能让模型误认为摘要就是原始文本。
- 分别记录工具实际分页进度和当前输入选取了哪些内容。输入长度裁剪不修改权威阅读回执，也不能把部分页改成已读完整对象。工具 next_cursor 仍有值时保留待续读提示。
- 长度预算同时考虑固定指令、工具定义、状态、原文和预留输出空间。先删除同源重复内容和无关历史；仍无法容纳必要原文时缩小本次候选范围、继续分页读取或明确输入不足，不截断原句后假装内容完整。
- 精确选段与审查保留实际入选文本、关键数字、否定、条件、来源、时间及限制。概览或模型摘要不能代替这些字段；也不为节省输入而删除素材缺口或未确认说明。
- 内容审查缺少必要输入时，返回需要补充的范围，由主循环补读；若无法在预算内完成则返回未完成，不能在输入不足时给出已完整审查的状态。

#### 7.4.5 多轮修改中的输入复用

用户第二轮要求“缩短到25秒，但保留准备步骤”时，请求理解读取当前消息、已有条件和制作摘要。初始化更新需求，使旧检查失效。下一次决策输入新的25秒目标、保留准备要求、其余有效条件、旧计划与草稿基线、同一 scope 下相关原文和读取记录、仍适用的选项，以及需要重做检查的说明。

不必重新发送第一轮完整搜索历史，也不必重新分析视频。已有读取回执可以复用，但本轮精确选段需要的原文仍须实际放进输入或重新读取；“数据库保存过”不等于模型这次已经看到。计划、草稿确定后，按新输入重新校验和审查，旧通过结果不作为本轮有效结论。

#### 7.4.6 按引用和状态选择相关内容

核心版本采用“模型决定要读什么，程序按明确状态与引用组装输入”。不增加相关性判断模型、每轮历史总结模型或独立上下文选择节点。Agent 通过查询、读取、更新计划和选段表达关注对象；Python 程序按调用目的及这些对象的引用选择内容，不重新理解整个素材库。具体 token 配额仍需在模型接入时确定，以下行为作为实现规则。

| 判断或操作 | 职责 |
| --- | --- |
| 哪些内容适合教程、优先缩短哪一步、是否寻找另一种表达 | Agent 根据目标与可见内容判断 |
| 查找当前计划项、草稿片段、候选和反馈引用的上下文及观察 | 程序沿明确引用读取 |
| 判断同一来源与版本的文本是否重复、旧反馈是否失效 | 程序按身份、字段位置与输入绑定处理 |
| 记录分页、原始范围读取完成度和本次提供的原文 | 程序维护，模型不能自行声明完成 |
| 发现新的语义前提或提出补读需求 | Agent；程序只展开已经明确的引用关系 |
| 计算输入预算、缩减可省内容和报告必要输入缺失 | 程序；不在预算不足时伪造完整检查 |

尚未形成计划时，优先提供当前需求和最新检索、读取结果，供 Agent 判断下一步。形成计划后，以当前计划、草稿、正在比较的选项和未解决问题为选择依据：纳入它们引用的原文和必要上下文，保留整条作品的结构。已明确的必要前提即使没有直接入选也不能仅因检索排名低而删除。程序不按自由文本的关键词或相似度自行宣布某段永远无关。

历史搜索到的对象没有被当前计划、候选或问题引用时，可以暂时不发送全文，但保留调用记录与可访问入口。Agent 后续发现需求时仍能重新搜索或读取。全部候选均不可见时，不要求模型凭记忆选择，需提供目录或新的有界结果页。

**不同内容的取舍规则：**

| 内容 | 当前调用如何处理 | 持久记录如何处理 |
| --- | --- | --- |
| 当前实际入选原文 | 需要比较或检查的片段保留文字、时间、来源和限制；其他部分至少保留整体顺序与时长，进入精确判断前加载原文 | 保留稳定来源和草稿引用 |
| 正在比较的候选 | 提供有界候选的实际内容，已放弃且未被问题引用的候选不反复发送全文 | 保留工具回执和条件 |
| 必要前提、指代与未解决事项 | 根据明确关系和反馈保留或补读，不按消息新旧机械删除 | 保留对应关系和问题状态 |
| 历史搜索与读取结果 | 同版本完整读取已覆盖的同源搜索文本只呈现一次，无关全文改为目录 | 不删除原调用身份或覆盖旧结果 |
| 旧错误与旧检查 | 已修复或因输入改变而失效的详细反馈可移出当前输入，只保留必要的失效说明 | 继续作为历史记录保存 |
| 读取记录 | 紧凑列出对象、范围、版本和未完成页；按需展示相关条目 | 保留权威回执，裁剪提示词不改变状态 |

“准备包括称量和压粉”的上下文概括不能代替“称取18克”的原始观察。只有同来源、同版本、同字段范围的重复文本可以按身份去重；不能凭语义相似把概括当原文，也不把相同句子在不同时间的出现合并成一个观察。

#### 7.4.7 读取目录与本次可见原文

每次组装时，程序区分“系统曾经获取过的内容”和“本次输入实际包含的内容”。可以使用如下逻辑目录，不要求新增业务实体：

```text
读取进度：
- context_02：固定版本，已读完，可按ID重新读取。
- video_01 / 20.2—31.6秒：范围已读完，关联speech_05—speech_07。
- context_03：仅第1页已读，存在next_cursor。

本次提供的原文：
- speech_05、speech_06、speech_07。

本次仅提供目录：
- context_01、context_04；需要精确判断时加载对应原文。
```

可见范围由实际组装结果产生，不由模型自行填写。已读不等于本次原文可见，目录也不构成内容依据。程序可以从有效缓存加载所需原文，或由 Agent 调用现有工具补读。工具返回的范围和分页信息与输入裁剪结果分别维护，不给未完整读取的对象生成完成回执。

#### 7.4.8 超出上下文长度时的处理顺序

1. 计算完整请求的预算，包括系统指令、工具定义、状态和正文，并预留输出空间。单次工具结果符合字节上限，不代表累计模型输入仍可容纳。
2. 去除同源重复文本及已失效的详细输入，例如已被范围读取覆盖的搜索副本和已解决错误反馈。旧需求的历史版本保留在记录中，当前有效条件不能删除。
3. 将暂时不参与判断的历史全文换为对象目录和读取入口，保留当前作品的顺序、各段时长和引用。正在比较的原文、必要条件及相关反馈不能静默裁掉。
4. 缩小本次同时比较的候选数量，按有界批次继续读取与比较，保留已处理情况、剩余入口和分页状态；未看的候选不能被标成不相关。具体选取范围由当前动作和引用决定，不由程序凭关键词猜测。
5. 必要信息仍无法容纳时，明确报告输入不足。可继续缩小当前比较任务、补读所需内容，或在现有流程中向用户说明范围冲突；不能静默改变用户目标或返回完整检查通过。

局部候选比较可以分批，最终内容审查仍需足以判断整条作品顺序、实际入选信息及必要关系的输入。核心方案不把最终整体审查自动降为互不关联的分段审查。若整条草稿与必要上下文仍无法容纳，返回未完成或请求调整任务范围，不把几次局部通过汇总成整体通过。

#### 7.4.9 咖啡教程多轮修改中的实际选择

第一轮制作30秒教程时，Agent 搜索到准备、机器清洁、成品展示等候选。计划尚未形成，最新候选原文帮助它选择。展开 context_02 并形成“预热→准备→萃取→成品”的计划后，输入主要围绕计划项、选段和未解决事项组织。暂未采用的清洁结果不再每轮发送全文，但记录和访问入口保留，不能宣称清洁内容永远无关。

准备片段引用 context_02、speech_05—speech_07 和20.2—31.6秒的示例范围。程序利用这些关联获取称量、整理粉面和压粉原文，去掉已被覆盖的同源搜索片段，同时保留实际时间和用量信息。

第二轮“缩短到25秒，但保留准备步骤”的首次决策仍要看到整条作品的计划、片段顺序和时长；如果完整入选文本本来就短，直接保留全部入选文本。不能只输入准备步骤，或由程序根据“缩短”这个词预先删除其他片段的内容。Agent 比较整体后决定优先缩短萃取说明和成品展示，再调用工具获取更短选项，程序据此将新候选和相关原文放进后续输入。

准备步骤虽不一定修改，仍作为明确保留条件和计划项存在；与修改内容相关的必要前提继续可见或可展开。最终提交前，按25秒目标提供完整审查所需内容并重新检查，不能把“未改的部分曾经通过”当作新编排整体通过。

### 7.5 校验与审查

Java 保留来源、版本、时间、范围读取、观察引用、词边界、字幕、重叠和时长检查，并增加计划/草稿映射检查。合法引用不能证明内容正确。

硬校验通过后，审查检查信息遗漏、原意变化、上下文断裂、无观察支持的画面主张和明显重复。输出具体计划项、片段、观察引用、解释和建议；不直接改草稿、不调用工具、不自行决定下一轮。

审查结论分为 NO_BLOCKING_ISSUE、NEEDS_REVISION、INSUFFICIENT_CONTEXT。程序处理预算与路由。审查不能只读 reason 或完整来源句子，必须读取实际选中转写。需要更多依据时返回所需范围，由主循环补读。

第一版允许一次内容修订机会；修订后重新硬校验并再审查最终编排。若仍有阻断问题，返回未完成说明及草稿，不标记可确认。规则修复和格式修复受现有总预算限制。风格建议不作为阻断条件，模型不拥有无限否决权。

Validation 绑定 requirements_hash、draft_hash；Review 绑定 scope_id、requirements_hash、plan_hash、draft_hash。新输入使旧结果失效，即使只是需求变化而草稿尚未变化。用户接受接口只接受当前完整绑定且完成检查的草稿；预览和正式接受继续区分。

## 8. 跨语言契约

将公共 JSON Schema 与正反样例集中在仓库 `contracts/video-agent/`（待新增）。覆盖 Observation、Context、Overview、RetrievalChunk、SearchHit/SearchResult、ToolRequest/Result、ClipOption、Requirements、ContentPlan、Draft、Validation、Review、AgentResult。Java 与 Python 的边界类型均严格解析，不做字符串转整数等隐式转换，拒绝未知字段。模型输出和 HTTP 是系统边界；内部已验证对象不重复防御性校验。

统一约定：snake_case JSON 字段；ID 为程序生成的不透明字符串；整数毫秒，区间为半开 `[start_ms,end_ms)`；时间点仅用 observed_at_ms；缺失与 null 的允许位置由 Schema 确定；集合语义与有序数组明确区分。

哈希采用双方一致的 JSON 规范化：对象键排序、UTF-8、无多余空白、不改写字符串、数组保持顺序、参与这些业务哈希的输入对象禁止浮点字段；该限制不适用于 Qdrant 向量值。需要集合排序的字段在业务规范化阶段完成，再计算 SHA-256。哈希只覆盖明确列出的业务输入，不混入调用时间、模型输出格式或数据库序号。Java/Python 共享样例验证中文、空数组、null、布尔值、毫秒和顺序变化。

scope 是问答与制作共同的内容范围，内部路由从 questions 统一到 content-scopes 或等价命名；生产绑定和工具入口共用相同 scope 语义。最终路径在契约阶段一次确定，旧路径不保留适配。Draft 中 evidence_ids 改为 observation_ids，相关 Python 类型、Java 规范化、保存内容、前端引用与渲染读取同时更新。

审查由 Python 发起模型调用，但 Java 接纳结果时核对执行身份和所有输入绑定。不能信任模型返回的哈希；模型只返回内容，绑定由程序生成。Java 不需要重复调用审查模型。

## 9. 多轮案例与有效性

以下时长为验收样例，必须由测试素材或受控样例提供相应切法，不能当作任意素材均有解。

第一轮需求为 30 秒咖啡教程。Agent 浏览概览和相关上下文，发现启动萃取关联预热前提；更新计划，读取原始范围并取得选项，选择预热 4 秒、准备 10 秒、启动 7 秒、停止 4 秒、成品 5 秒。提交完整草稿，Java 校验通过后审查内容，通过才返回可确认结果。

第二轮要求缩短到 25 秒并保留准备。初始化更新需求但保留其余条件；同一 scope 的观察、上下文和范围读取继续使用。旧计划作为基线，更新为预热 4、准备 10、启动 4、停止 4、成品 3 秒。短切法已有则复用，缺少则调用候选工具，缺少原始读取则补读。提交可同时携带更新计划。

旧校验、旧审查全部失去当前有效资格，重新按新需求、新草稿检查。准备步骤“保留”是内容要求，不默认锁定毫秒；本例不改其范围是最小修改选择。用户明确要求一帧不改时才记录范围锁定。

独立提问“需要多少咖啡粉”只读取和回答，不改变上述制作。明确“另做一条成品展示”建立新制作，不继承教程条件。没有满足时长的语义完整组合时说明冲突，不截断条件来凑时长。

## 10. 分阶段实施

### 阶段一：领域契约和存储基础

修改：contracts、数据库初始化结构、Java analysis/search/tools/plan 类型、Python editing/tools/contracts/state、共享样例；梳理 agentrun 和前端字段消费。

交付：三层对象、Chunk 来源位置与切分配置、Qdrant payload、三层 SearchHit 和分页契约、时间语义、工具信封、计划与审查绑定、统一 observation 命名、可初始化的目标数据库。先固定边界再实施行为，避免双方各自扩展。

验收：Java/Python 对相同样例解析结果一致；无效区间、未知字段、伪造 ID、错误哈希失败；全新数据库可初始化，外键与引用约束有效；无需任何旧数据或旧接口。验证 POINT/INTERVAL/ASSET、三层枚举、Unicode 原文位置、层筛选与游标条件；记录此阶段尚无新增分析和 Agent 行为。

任务契约保留验收：并发领取只产生一个当前 attempt；同一领取请求重试返回原执行；重复消息不能启动第二个有效执行。不新增 Redis 锁协议。远程租约与本机执行契约分别验证，不将本机任务描述为已支持分布式失联恢复。

### 阶段二：分析流水线与三层数据

修改：media、analysis、bailian、task、search 索引构建。为文本组织调用提供明确适配器，复用现有调用记录、用量与异步任务机制，不新增通用模型路由平台。

交付：镜头与混合采样、原始观察、上下文及概览、覆盖说明、三层按已有结构生成 Chunk、Embedding 向量化和带文本的索引发布；分块本身不调用大模型。

验收：单镜头长视频仍有内部采样；检测失败走明确的稀疏路径；可变帧率保留真实时间；静音视频不产生虚构语音；音画错位不按时间强合并；每个上下文和目录均可回查来源；观察缺失明确披露；失败或恢复不会重复发布相同业务结果。三层生成成功时均有可定位的 Chunk，来源缺失时对应层状态明确；验证分块只读取已保存字段并执行确定性规则，不调用生成模型判断边界或改写正文；同一内容版本与 chunk_profile 产生一致的块文本和来源位置；完整小对象不被无故拆碎，JSON 键名、ID 与时间不混入正文；数字、否定和来源标签保留；长文本不静默截尾，强制拆分标记需要展开；原文位置可还原来源；验证咖啡例子中的标题和三条短陈述生成一个多句 Chunk，长对象按顺序拆分后可通过共同 entity_id 和版本展开完整对象；摘要块与目录块独立组织，不把多个目录块误认为摘要被拆碎；Qdrant 正文与 PostgreSQL Chunk 清单一致；发布失败不替换旧代次，重试不重复生成业务内容。

### 阶段三：分层检索与片段选项

修改：search 的执行器配置、通道任务和结果汇总、tools、SpeechTimings、Python tools/catalog/java；将通用边界计算集中到 Java。

交付：六个核心工具、受控执行器并发执行 Embedding 加 DENSE、BM25、LITERAL，汇总后在 Java 统一三路 RRF、三层匹配文本直返、层内对象合并、跨层阅读入口、固定分页与排名、候选实际文本和读取前置条件。

验收：主题检索可进入上下文再读原文；原话检索可回到上下文；越权、跨 scope 引用失败；上层阅读不能冒充原始范围已读；分页稳定；没有切法时明确返回原因；切法文本与字幕选择使用同一时间规则；通道故障不伪装成无内容。概览检索能发现相关素材，概览未命中不阻断下层精确检索；重复 Chunk 不挤占同对象的多个结果；按上述假设名次验证 RRF 计算，并加入 LITERAL 命中的三通道样例，确认 Java 对各通道原排名统一融合、没有先做两路融合再进行二次 RRF；验证组内最高分排序与稳定同分规则，新增较低分的同对象块不提高该对象得分；每对象至多展示两个匹配块，more_matches 不冒充完整召回；验证三种 layer 的召回前过滤与 source_kind 的适用范围；多层分页无漏项重项；source_kinds 不错误排除上层结果；返回原文且不要求逐条读取完整对象；授权变更即时生效，索引重建不改变旧 scope 结果；搜索记录不自动计为原始范围阅读。

并发验收：使用受控阻塞点验证 BM25 和 LITERAL 可在 Embedding 完成前启动、DENSE 只能在查询向量就绪后执行，不用脆弱的总耗时阈值代替依赖验证。覆盖共享线程/队列上限、提交拒绝、排队过期、底层调用超时、迟到结果、单通道失败和全通道失败；验证结果未知不自动重付、同配置多层查询只生成一次查询向量、没有共享可变结果的并发写入。相同通道结果以不同完成顺序返回时，RRF、对象排序及分页保持一致。并发能力在此阶段实现验收前仍标记待实现，不能以现有串行混合检索通过代替。

## 12. 后续可选增强

| 增强 | 触发需要 | 与核心的关系 |
| --- | --- | --- |
| 对象相关性重排（rerank） | 相关内容已经进入候选，但排名靠后或无关候选导致反复展开 | 对象合并后重排有限候选，不能替代完整阅读与内容审查；见12.1 |
| 短序列理解 | 动作顺序或状态变化无法由单帧确认 | 新增序列观察，重新组织相关上下文 |
| Agent 局部补查 | 当前制作存在明确观察缺口 | 业务层安排付费任务，新执行绑定新 scope |
| CLIP 图像检索 | 文本描述漏掉用户需要的视觉细节 | 独立图文向量空间，结果仍需观察核查 |

| 专用 OCR / 局部高分辨率 | 小字和数字识别不足 | 补充可定位的文字观察 |
| 说话人分离 | 多人访谈需要保留观点与问答归属 | 扩展语音观察，不默认对所有视频执行 |

### 12.1 可选 rerank：适用问题、接入流程与边界

当前核心版本不增加精排。层次与素材过滤、三路 RRF、同对象合并、直接读取和关系展开先构成完整检索链路；这些设计可以控制候选规模，但不能仅凭设计断言排序质量已经足够。后续根据实际查询与 Agent 阅读记录判断是否需要 rerank，不为技术栈完整机械增加一次模型调用。

| 实际问题 | 优先处理方式 |
| --- | --- |
| 相关内容已经召回，但经常排得靠后 | 可考虑 rerank 改善候选相关性排序 |
| 高排名结果词项相似、实际意图不同 | 可考虑 rerank，减少无效展开 |
| Agent 连续展开无关对象才找到目标 | 检查候选与查询，若主要问题是排序则考虑 rerank |
| 分析漏掉动作，或 ASR 文本错误 | 改善分析；重排不能补出不存在的观察 |
| 正确内容没有进入候选集合 | 检查查询、过滤、分块及召回规模 |
| 剪辑删除必要前提、改变原意 | 完整范围阅读和内容审查 |
| 越界、切断单词或时长不合规 | 后端确定性校验 |

沿用咖啡案例：查询“使用18克咖啡粉的准备步骤”，A 讲称量装粉，B 讲布粉压粉，C 讲清理使用18克后的残粉。RRF 根据通道名次融合，不读取语境，C 仍可能靠前。常见 cross-encoder reranker 将查询与候选文本一起处理，可能识别“准备”和“清理”的差异，把准备上下文提到前面；这只是预期作用，不是已经验证的效果，也不能保证每次排对。模型只重排输入候选，未被召回的对象不会因此出现。

若后续实施，优先采用以下流程，保持对象展开接口不变：

```text
同一层内三路召回
  → Chunk 级 RRF
  → 按完整对象合并，以最高 Chunk 分数初排
  → 选择有限对象，以查询、标题和有限匹配 Chunk 原文进行 rerank
  → 保存最终对象排名及模型配置、输入与调用身份
  → 返回匹配原文和展开入口
  → Agent 读取完整上下文、原始范围，再规划和审查草稿
```

先合并对象，可避免一个长上下文占用多个重排名额。初始重排输入使用标题和有限匹配原文，不为排序预先加载所有完整对象；保留来源和限制，输入过长不能静默截断。代价是重排模型可能看不到完整前提，因此后续展开阅读仍然必要。候选数量、输入长度及成本上限应在选定模型后确定，此处不预设未经验证的数值。

当前最高 Chunk RRF 分数是对象最终排序依据；启用增强后，它用于选择与初排候选，参与重排的对象最终顺序由 rerank 分数决定。不能同时声称最终顺序仍完全由 RRF 决定。实施增强时需明确未进入重排窗口的对象如何保留、稳定同分规则及失败处理，并固定整次查询的最终排序，不能翻页时再次调用模型改变顺序。三个内容层分别处理，不直接比较跨层重排分数，也不改变权限范围。

| 机制 | 负责判断什么 | 不承担什么 |
| --- | --- | --- |
| RRF | 综合多通道的已有名次 | 不重新理解查询与候选正文 |
| rerank | 有限候选与当前查询的相关性 | 不保证事实正确，不决定完整作品编排 |
| Agent 阅读与规划 | 当前缺少什么、需要展开哪里、怎样组织作品 | 不用搜索排名替代来源核查 |
| 内容审查 | 实际入选内容是否遗漏前提、改变原意或存在其他内容问题 | 不只是重新排序候选 |

例如成品展示与“准备步骤”查询相关性较低，但仍可能适合整条教程；预热即使排名低，也可能是已读上下文明示的必要前提。不能让重排分数代替这些业务判断。重排多一次推理，是否能通过减少 Agent 的无效阅读抵消延迟和费用，需要结合实际查询观察，不预先承诺更快或更准确。

核心验收不依赖 rerank 模型。未来增强可先用固定响应检查候选范围、排名保存、分页和原文保留，再用代表性咖啡查询观察排序及阅读行为；真实效果与程序行为分开记录，不要求先建立大规模评测，也不把受控样例通过当作效果提升证明。
