# 视频上传准入 Redis 令牌桶限流规格

整理日期：2026-10-17（Asia/Shanghai）。状态：用户已授权按本规格实施；实现与验证状态见第 13 节及最终验收记录。

## 1. 问题与目标

当前视频上传完成后会创建 `MEDIA_PREPARE` 任务；媒体校验成功后自动进入 ASR、VLM，并由分析结果触发 Embedding 索引构建。连续创建并完成新视频上传可能持续产生模型调用开销。仅限制手动分析接口无法覆盖这条自动链路。

本次在新上传会话创建前增加按用户隔离的 Redis 令牌桶，限制新视频进入后续自动分析链路的频率。额度不足直接拒绝，避免先接纳任务再无限排队。项目保持单实例部署。

成功标准：并发请求不能突破用户额度；同用户跨项目共享额度，不同用户相互隔离；合法幂等重放不重复扣令牌；额度不足或 Redis 不可用时，不创建新上传会话、存储预留或对象存储上传。

这是一项上传及自动分析的准入保护，不是模型费用配额。单次视频的时长、帧数与模型调用量不同，不能将准入次数换算为固定费用，也不能宣称覆盖全部模型调用入口。

## 2. 已确认决定与范围

| 编号 | 决定 |
| --- | --- |
| D01 | 保持当前单实例部署，不同时实施多实例扩容。 |
| D02 | 只新增上传准入 Redis 令牌桶，保留现有登录、注册内存限流。 |
| D03 | 桶按已认证用户的数据库用户 ID 隔离，同一用户的所有项目共享额度。 |
| D04 | 桶容量为 3，首次使用为满桶；每 60 秒补充 1 个令牌，每次新上传准入消耗 1 个。 |
| D05 | 超限直接拒绝，不自动排队等待额度。 |
| D06 | 合法幂等重放不重复扣减；同幂等键但参数不一致继续按现有冲突规则拒绝。 |
| D07 | 扣令牌发生在幂等、文件和项目配额检查之后，全局磁盘容量检查之前。 |
| D08 | 扣减后不返还，包括后续容量检查失败、数据库失败、上传失败、取消和素材校验失败。 |
| D09 | Redis 不可用时返回 503，拒绝新上传，不回退为进程内限流或直接放行。 |
| D10 | Redis 状态丢失后接受恢复满桶，不备份到 PostgreSQL。 |

技术方案采用 Spring Data Redis 与短 Lua 脚本，不引入 Redisson。实现专用于当前上传准入场景，不建设通用限流框架、注解、AOP 或多算法切换层。

不在本次范围：分析重试、已有素材手动分析、搜索及对话限流；模型出口限流；每日 token 或金额预算；任务并发控制；上传/下载字节带宽控制；Redis 高可用集群、会话共享与完整多实例改造。

## 4. 请求流程与事务边界

```text
POST /api/v1/projects/{projectId}/uploads
  → 请求、身份、项目归属校验
  → 开始现有 SQL 事务，锁用户行
  → 检查幂等键
      → 合法重放：复用原上传，不访问令牌桶
      → 参数或 writer 冲突：沿用现有冲突响应，不扣令牌
      → 新请求：锁项目行，检查文件大小与项目字节/数量配额
          → Redis 原子补充并尝试扣减令牌
              → 额度不足：429，结束事务
              → Redis 不可用：503，结束事务
              → 获准：全局磁盘容量检查
                  → 创建上传会话与存储预留，提交 SQL 事务
                  → 沿用现有操作资格机制初始化对象存储上传
```

Redis 调用前不取得全局容量锁，以免阻塞其他用户的容量准入。调用时仍持有当前用户及项目行锁，必须设置明确且较短的连接和命令超时。

Redis 扣减与 PostgreSQL 提交不属于共同事务。本次不增加分布式事务、补偿返还或令牌预留协议。SQL 回滚不会恢复令牌，因此准确语义是“新上传准入尝试消耗额度”，不是“仅成功创建的上传计数”。

对象存储初始化发生在 SQL 提交之后：失败时上传记录已存在；同 key 合法重试沿用原上传及初始化恢复逻辑，不再次扣令牌。Redis 不可用不应阻断这类合法重放；对象存储等其他依赖仍可能导致其失败。

令牌桶键不包含项目 ID，不能通过新建或切换项目获得新额度。用户 ID 来自服务端身份，不从请求体接受。

## 5. 令牌桶算法与存储

### 5.1 状态及计算

使用一个业务命名空间下的用户级 key，例如 `upload:admission:{userId}`，保存可用令牌余额及上次补充时间。实现允许表达部分令牌，避免丢弃不足 60 秒的累计时间；不得每次访问都重新开始补充周期。

设容量为 `C`，每个令牌补充周期为 `P` 毫秒，上次余额为 `b`，距离上次更新经过 `elapsed` 毫秒：

```text
补充后余额 = min(C, b + elapsed / P)
余额 >= 1：允许，余额减 1
余额 < 1：拒绝，retryAfterMs = ceil((1 - 余额) × P)
```

默认 `C=3`、`P=60000`。补充依据经过时间按需计算，不依赖后台定时任务。所有时间以 Redis 服务端时间为准，不依赖应用实例时钟。

### 5.2 原子操作与过期

Lua 一次执行读取状态、补充、准入判断、条件扣减、状态写入与 TTL 设置，返回是否允许及等待毫秒数。不得在 Java 中拆成先查余额再扣减，也不额外加分布式锁。

闲置 key 至少保留从空桶恢复满桶所需时间；默认不早于最后一次访问后 180 秒过期。届时即使重建满桶，也不会比自然补充获得更多额度。拒绝不会推迟令牌自然补充，不能变成“每次被拒绝后再等 60 秒”。

桶容量与周期由配置注入，启动时验证这些外部配置为合法正值。首版不提供运行时无损修改存量桶策略的管理接口；变更参数按配置重启处理，并记录所用参数，验收不能混用旧状态。

### 5.3 不确定扣减结果

业务层不自动重试扣减脚本。客户端超时或连接中断可能发生在 Redis 已扣减但响应尚未收到之后；返回 503，不返还、不根据猜测重放扣减。客户端重试在尚未创建 SQL 记录时也可能再次消耗额度，这是本次接受的失败边界。

对底层客户端的重连、重放配置进行核对，避免额外配置导致不确定扣减被无条件重复提交。不承诺 Redis 与网络故障下的精确一次扣减。

## 6. HTTP 与浏览器契约

沿用现有 `requestId`、`error.code/message/retryable/details` 响应结构，仅增加专用错误投影，不重构全项目异常处理。

| 情况 | HTTP | error.code | retryable | 等待信息 |
| --- | --- | --- | --- | --- |
| 令牌不足 | 429 | `RATE_LIMITED` | true | `details.retryAfterMs` 为实际等待毫秒；`Retry-After` 为向上取整的秒数 |
| Redis 连接、超时或服务不可用 | 503 | `UPLOAD_ADMISSION_UNAVAILABLE` | true | 提示稍后重试；不编造准确恢复时间 |

429 示例（等待时间仅为示例）：

```json
{
  "requestId": "<请求标识>",
  "error": {
    "code": "RATE_LIMITED",
    "message": "上传过于频繁，请约 42 秒后重试",
    "retryable": true,
    "details": { "retryAfterMs": 41234 }
  }
}
```

此时 `Retry-After: 42`。等待时间是响应时的估计，不能保证其他并发请求不会先使用后来补充的额度。

Redis 基础设施故障保留可定位日志，不记录凭据。脚本编程错误、非法配置等应快速暴露，不伪装成额度不足，不笼统吞掉所有运行时异常。

前端保留结构化错误码及等待信息。上传创建遇到上述两类错误，停止当前快速自动重试，展示服务端提示，允许用户稍后手动重试。`retryable=true` 表示该错误允许未来重试，不表示应立即重试。

保持其他上传恢复与分片重试规则；不新增倒计时、后台排队、自动等待后恢复或页面布局。创建被拒绝时保留可理解的失败状态，不表现成已经开始传输。

## 7. 依赖、配置与部署

后端增加 `spring-boot-starter-data-redis`，版本跟随现有 Spring Boot 依赖管理。使用一个专用上传准入组件和一个 Lua 资源文件；具体类名实施时按模块惯例确定。

在根 Compose 增加独立应用 Redis，不复用 Langfuse Redis。固定镜像版本及摘要、验证现有 ARM64 环境兼容性，设置健康检查、资源限制及 API 的启动依赖；不发布宿主端口。本次不为令牌状态配置持久化，接受 Redis 重建后恢复满桶。

Redis 设置有限内存和 `noeviction` 策略，避免因普通内存淘汰提前恢复活跃用户额度。达到资源限制而无法执行准入时拒绝新上传，不自动放行。

配置需覆盖 Redis 地址、连接/命令超时、桶容量及补充周期。容量默认 3，周期默认 60 秒；超时与 Redis 内存/容器限额在实施联调时给出明确值并写入配置说明，不能依赖长时间无限等待。没有未经验证的吞吐或延迟 SLO 承诺。

沿用当前启动脚本与环境配置方式，按需要更新说明，不为一次性配置操作新增脚本框架。应用运行中 Redis 故障仅令新上传准入失败；不把 Redis 连接检查扩散到所有 HTTP 请求，不改变现有认证和任务执行职责。

## 12. 常见 Redis 限流方案与选型

| 方案 | Redis 常见实现 | 取舍与适用情况 |
| --- | --- | --- |
| 固定窗口 | 计数器、TTL、原子脚本 | 最简单；窗口交界处短时间可接近两倍额度，适合粗粒度次数限制。 |
| 滑动窗口日志 | ZSET 保存请求时间，原子清理/计数/写入 | 精确限制任意连续窗口内次数，存储随窗口内记录数增长；不等于禁止窗口内集中突发。 |
| 滑动窗口计数 | 相邻窗口计数加权 | 内存开销较小、边界较平滑，但属于近似统计。 |
| 令牌桶 | 余额与补充时间，Lua 原子计算 | 容量与长期补充速率可以分别设置，适合允许小批量上传、限制持续提交。 |
| 漏桶 | 水位与排空时间，或配合排队调度 | 直接拒绝与等待后匀速执行是不同语义；本次不引入任务排队。 |

本次选择令牌桶，是因为需要初始允许上传 3 个视频，同时长期按每分钟 1 个恢复机会，而不是仅设置某个窗口内总次数。

Redisson 不是本次依赖。已核查的 `RRateLimiter` 实现按消费记录经过 interval 恢复许可，不能直接将“3 个许可/180 秒”等同于本规格的独立容量 3、每 60 秒补充 1 个。这里针对所核查实现的行为，不作为所有未来版本的永久结论；若后续改选，必须按固定版本重新验证语义。
