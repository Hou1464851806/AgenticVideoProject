## 项目开场

我的项目是一个视频理解与剪辑工作台。用户上传素材后，系统在后台进行语音、画面和内容分析，形成可检索的内容。用户可以询问视频内容，也可以提出剪辑要求。Agent 根据需求检索和阅读素材，生成回答或剪辑草稿；草稿通过规则校验和内容审查后，由用户确认，再按固定版本渲染。

我的设计重点有两部分。一部分是后端可靠性，包括大文件上传、异步任务和版本确认；另一部分是让 Agent 有足够的内容依据来规划剪辑，包括视频的三层表示、分层检索、显式内容计划和审查。设计以固定业务流程为主，没有为了扩展性提前建设通用工作流平台。

## 第一条【优先准备】：分片上传与限流

**业务问题**：视频较大，上传中断后重传成本高；文件经过业务服务会占用带宽；连续上传会增加后续分析压力。

**完整口述回答**

我的设计把文件传输和业务管理分开。浏览器先向后端创建上传会话，后端检查用户权限和上传限制，再生成分片上传所需的预签名 URL。浏览器把分片直接上传到对象存储，后端负责会话、签名、分片核对和完成上传，不转发视频文件本身。

上传过程中保存上传身份和分片信息。比如网络断开时已经上传了前六片，恢复后先核对服务端实际存在的分片，再继续缺失部分，不只是相信浏览器本地显示的进度。所有分片完成后，由后端核对并完成合并，随后执行媒体验证；对象存储上传完成还不代表视频已经可以进入分析。

限流放在创建上传会话的位置，用 Redis 令牌桶按用户控制新上传进入的速度。补充令牌、判断余额和扣减需要作为一次原子操作，所以通过 Lua 执行。这样既保留文件直传的效率，也在任务入口控制新增压力。

这是一种入口控制，不能保证后续分析绝不积压，也不会限制已经发出的上传 URL 的每个网络请求。当前先解决用户连续创建上传的情况，不引入自适应限流或复杂调度。

**典型异常**：上传中断，恢复后核对已上传分片，只补传缺失部分，不重新发送整个文件。

**必要追问：预签名 URL 是否意味着谁拿到都能上传？**

在签名允许的有效期和范围内，它就是上传凭据。因此签发前要验证用户和会话，限制目标对象、操作和有效期；完成上传时还要核对会话与对象归属。不能把拿到 URL 当作拥有整个项目的权限。

**必要追问：Lua 原子性是否等于数据不会丢？**

不是。Lua 保证脚本中的判断和更新不被其它命令穿插，持久化是另一件事。令牌桶保存准入状态，任务和业务结果仍由 PostgreSQL 管理。

## 第二条【优先准备】：任务可靠链路

**业务问题**：分析耗时较长，需要异步执行；数据库写入与消息发送可能不一致；重复消息和执行中断不能导致重复业务结果。

**完整口述回答**

我先在同一个 PostgreSQL 事务中保存任务和 Outbox 事件，再由发布流程发送 RabbitMQ 消息，并根据发布确认更新状态。这样任务创建成功以后，即使消息暂时没有发出去，数据库里也保留着待发送记录，可以继续发布。

这能支持至少一次投递，但可能重复。例如消息已经被 RabbitMQ 接收，发布进程却在更新 Outbox 前退出，恢复后就会再次发送。因此 Worker 收到消息后要先领取任务，而不是直接执行。后端通过数据库短事务检查任务状态，创建执行身份并更新 current_attempt_id；事务结束就释放行锁，耗时处理放在事务外。

对于远程 Worker，租约和心跳用于判断何时允许恢复调度，attempt_id 用于判断谁可以提交新结果。执行完成后，后端核对执行资格、保存业务结果并更新状态，Worker 确认提交成功后再 ACK。相同结果重复提交时返回已保存的结果。

例如结果已经提交，但 Worker 在 ACK 前退出，消息会再次投递。后端发现任务已经完成，返回已有状态，不重新执行。这里消息确认、执行资格和业务幂等各自负责不同环节，不宣称消息永不重复或外部模型恰好调用一次。

我保留 PostgreSQL 原子领取，不额外增加 Redis 锁。任务和结果本来就在数据库中，可以在事务里核对执行资格再写入。当前 Java 本机任务与远程 Python Agent 的恢复方式不同，不为了形式统一而把所有任务改造成独立分布式 Worker。

**典型异常**：结果已保存但 ACK 丢失，再次消费返回已有结果。

**必要追问：租约和 attempt_id 为什么都需要？**

A 领取任务时身份是 A1，随后失联，租约过期后任务重新安排执行。B 接手获得 B1，A 恢复后带着 A1 提交的新结果会被拒绝。租约决定什么时候允许接手，attempt_id 区分新旧执行。已经在有效执行期间保存的成果仍然保留，新执行可以复用。这个例子解释远程租约协议，不表示当前本机分析已经实现跨机器接管。

**必要追问：有数据库行锁为什么还要租约？**

行锁只覆盖领取时的短事务，提交后就释放了。不能在几分钟的模型调用期间一直占着事务。执行期间使用保存的身份和租约判断资格，心跳和结果提交分别使用短事务。

**必要追问：请求超时就重试模型调用吗？**

不能一概重试。查询类操作可按策略重试；付费提交超时可能已经被服务商执行，需要先查看调用身份和保存的响应，能查询就恢复原调用。缺少结果不代表没有发生费用。

## 第三条【优先准备】：视频分析流水线

**业务问题**：逐帧分析成本高；孤立的转写和图片描述不足以表达完整步骤；某阶段失败不应要求重做整个视频。

**完整口述回答**

我把视频分析设计成固定流程。媒体准备后，ASR 提取带时间位置的语音，视觉分支通过镜头检测选择代表帧，并用间隔抽帧补充长镜头，再调用 VLM 描述画面和可见文字。结果都对齐原片时间，便于后续回查和选段。ASR 和视觉分支没有直接数据依赖时可以并行。

这些输出首先作为原始观察保存。程序按时间整理语句、镜头和画面观察，并附上来源 ID，再由模型组织完整步骤和必要关系，形成视频内容上下文，最后根据上下文生成全片概览。三层分别用于了解主题、理解步骤和核查具体内容。镜头变化不等于步骤变化，时间相近也不等于两项观察一定表达同一件事，因此不能只按时间强行合并。

比如咖啡教程中，ASR 说使用十八克咖啡粉，图片显示称量动作。原始观察分别保存口述和画面描述，上下文把相关观察组织成准备步骤，概览再列出准备、萃取和成品等目录。模型推断与原始描述分开保存；仅凭灯亮的画面，不能直接写成预热已经完成。

阶段状态、结构化成果和调用记录保存到 PostgreSQL，媒体文件保存到对象存储。假设 ASR 已成功，执行 VLM 时进程退出，恢复时重新安排 VLM 阶段，读取已经准备好的图片，不重新运行 ASR；VLM 内部已有成功观察也可以复用。这里依靠保存的状态恢复，不依靠某个 Worker 一直记住整条流程。

取舍上，我用镜头代表帧加间隔补充控制成本，不承诺逐帧覆盖；流程依赖在业务代码中明确，不引入通用 DAG 引擎，也不要求每个逻辑步骤都独立部署。

**典型异常**：ASR 已完成而 VLM 中断，只恢复未完成的视觉工作，保留语音和采样成果。当前独立阶段和部分调用恢复已有基础，完整目标流水线仍按规格实施。

**必要追问：程序和模型分别负责什么？**

程序负责时间映射、来源引用、输入组织和字段检查；模型负责理解步骤、概括和关系判断。程序可以验证引用是否存在，不能证明模型语义一定正确，因此需要保留原始观察和未知说明。

**必要追问：为什么需要三层，不只保存一个视频摘要？**

摘要适合判断视频主题，但会丢掉数字、条件和细节。上下文帮助理解一个完整步骤，原始观察用于核查具体说法和时间位置。三层是不同阅读粒度，不是三份互相替代的答案。

**必要追问：为什么不用成熟工作流引擎？**

目前分析流程固定，已有任务、Outbox 和阶段记录，增加明确的依赖推进规则即可。引擎会引入新的运行和状态管理方式。只有流程数量和恢复复杂性确实增长时，再评估是否值得替换现有编排职责。

## 第四条【优先准备】：分层检索与选段

**业务问题**：用户可能找整部视频、一个步骤或一句原话；只用一种粒度和一种匹配方式容易漏掉需要的内容。

**完整口述回答**

我的设计对全片概览、内容上下文和原始观察都建立索引。PostgreSQL 保存完整业务对象，Qdrant 保存向量、Chunk 原文和元数据。分析阶段已经组织好语义，索引阶段由程序选择 JSON 中的文本字段，按已有结构拼接分块，不额外调用大模型重新判断语义边界。

小对象可以整体成为一个 Chunk，一个 Chunk 可以有多句话。例如准备步骤的标题、十八克粉量和称量动作可以放在同一块。超长对象按已有条目和句子拆开，保留同一个对象 ID、分析版本和来源位置，使多个块能够关联回完整上下文。

查询时由 Agent 根据当前需求决定查哪一层，以及使用什么 query。找咖啡教程素材可以先查概览；已知视频、想找准备步骤可以直接查上下文；询问多少克可以查原始观察，不应把猜测的十八克预先写进查询。稠密向量匹配语义，BM25 补充关键词匹配，用 RRF 融合各自排名，避免直接比较不同通道的原始分数。

同一上下文的多个 Chunk 命中后合并成一个对象，以组内最高 Chunk 分数排序。返回层次、对象 ID、时间信息和匹配原文。Agent 可以先判断相关性，再按 ID 展开完整上下文；用于剪辑时还需要读取实际范围和必要前提，再选片段，不能把搜索摘要直接当成完整素材。

例如检索准备步骤时，可能命中一句十八克，却遗漏前面的准备条件。因此需要展开阅读。当前核心方案不增加 rerank，优先把原文、来源和后续阅读做完整，精排留到候选排序确实影响使用时再考虑。

**典型异常**：命中一句话但缺少条件，展开完整上下文和原始观察后再回答或选段，不根据片段猜完整含义。

**必要追问：RRF 是大模型打分吗？**

不是。它根据各通道中的名次计算融合分数，例如累加 1/(60+名次)。对象合并后使用最高 Chunk 分数，而不是把所有块相加，避免长对象仅因为块多就得到更高分。分数表示检索排序依据，不是事实可信度。

**必要追问：你的实现为什么还有第三路字面匹配？**

简历强调向量和 BM25 两种主要召回方式，当前项目还保留 PostgreSQL 字面匹配，便于匹配明确原话。Qdrant 分别提供稠密和 BM25 结果，Java 将字面结果一起做三路 RRF。Qdrant 自身有融合能力，但不能直接替项目合并数据库这一外部通道，所以统一在 Java 融合。这个细节被问到时说明，不把它误述为只有两路实现。

**必要追问：JSON 怎么向量化？**

不是把整段 JSON 的键名和 ID 全部送去向量化。程序读取摘要、陈述和观察文本等字段，保留来源标签、数字和限制条件，形成 Chunk 正文；ID、layer 和版本等作为元数据。Embedding 对已经组装好的文本生成向量。

## 第五条【优先准备】：受控 Agent 编排

**业务问题**：问答通常只需要找到并读懂内容，剪辑还需要安排步骤、选取区间和满足时长；完全固定流程不够灵活，完全自由执行又难以控制。

**完整口述回答**

我采用受控 ReAct 循环，把主要流程收敛为请求初始化、Agent 决策、工具执行、草稿校验与内容审查四个节点。模型根据需求和当前信息缺口选择动作，后端工具负责查找素材、展开内容和提供片段选项，状态和执行预算由程序管理。

简单问答可以直接检索和阅读后回答，不强制生成内容计划。剪辑需求则维护显式计划，写明需要表达的内容、顺序和对应素材。例如三十秒咖啡教程需要准备、萃取和成品，Agent 先明确这些目标，再检索和阅读相关内容，选择实际片段，形成草稿。

每次调用模型不是把所有历史都塞进去。程序根据当前需求、计划和草稿引用，选择相关原文、最新工具结果和有效反馈。模型负责决定还缺什么信息、下一步查什么；程序负责按明确引用选择内容、去重和控制长度。读取记录只表示曾经读过，本次输入是否包含原文需要另外区分。

草稿先经过后端确定性检查，例如时间范围、时长和引用是否合法，再由模型审查是否保留关键步骤、是否满足用户要求。硬校验失败先修正，不必浪费一次语义审查调用。内容审查是辅助判断，不能保证模型永远正确，因此保留用户预览和确认。

用户再要求缩短到二十五秒但保留准备步骤时，Agent 更新需求和计划，复用仍相关的素材读取，主要调整可压缩部分。原先针对三十秒草稿的检查不能直接沿用，新草稿要重新校验和审查。这样统一循环就能覆盖两类需求，不需要再增加多 Agent 或复杂度评分模块。

**典型异常**：为了满足二十五秒时长删掉了准备步骤，时间校验可能通过，但内容审查应指出它违反用户要求，返回决策节点调整草稿。

**必要追问：这算自主 Agent 还是 Workflow？**

分析流水线是固定 Workflow；对话部分是固定边界中的 Agent Loop。模型可以决定检索、阅读和计划调整的顺序，但不能绕过工具权限、预算和结果检查。它具有任务内的决策能力，不是任意修改系统流程的完全自主 Agent。

**必要追问：为什么需要显式计划？**

剪辑是多步骤任务，只靠一连串工具调用不容易看出哪些要求已经覆盖。计划把准备、萃取等内容目标保留下来，修改时能对照用户要求，审查时也有明确依据。这是为了可追踪和可修改，不表示计划本身已经证明内容正确。

**必要追问：上下文太长怎么办？**

先去重并移出过期反馈、无关历史，只保留目录和引用；再减少候选批次并分页阅读。数字、否定、必要条件以及当前审查所需的原文不能悄悄截掉。如果必要内容仍放不下，就补充分步处理或明确缩小范围，不能声称已经完整审查。

## 第六条【优先准备】：确认与版本绑定

**业务问题**：多轮修改后旧检查可能失效，用户可能确认旧草稿，也可能重复点击确认，渲染还需要稳定的输入。

**完整口述回答**

我把需求、内容计划、草稿和检查结果绑定起来。检查通过只代表那组具体输入通过，不能把它作为整个会话永久有效的标记。用户修改需求、计划或草稿后，程序判断旧检查是否仍对应当前输入，不对应就重新执行相关检查。

用户确认时，后端在短事务里锁定会话相关记录，核对当前草稿、需求和有效检查结果，再创建正式方案版本。使用幂等键识别同一次确认请求的重试，结合唯一约束避免重复生成正式版本。确认成功后，版本内容固定，渲染只读取这个版本，后续对话不会改变正在渲染的输入。

比如用户先得到三十秒草稿，又要求改成二十五秒。此时即使客户端还显示旧确认按钮，提交旧草稿身份也不能接受。后端必须根据当前版本判断，而不是相信前端已经禁用了按钮。重复点击当前版本的确认，则返回已经创建的结果。

这部分用数据库事务和明确版本关系就能解决，不需要引入通用版本平台或分布式事务。我的取舍是保留用户确认，把生成建议、接受方案和实际渲染分开。

**典型异常**：需求和草稿已更新，用户仍提交旧草稿确认，后端拒绝并要求使用当前草稿。

**必要追问：行锁和幂等键为什么都要？**

行锁用于把检查当前状态和创建版本放进一致的并发控制过程；幂等键识别同一次请求的重复发送；唯一约束保证不能出现不允许的重复业务记录。它们负责不同问题，不是同一机制的重复。

**必要追问：确认后为什么冻结版本？**

渲染可能持续一段时间。如果读取的是不断变化的草稿，用户再次修改可能让输出和确认时的内容不一致。冻结的是本次接受的方案，后续修改生成新的草稿或版本，不改写已确认版本。

### Q01请讲清楚这个系统从上传视频到生成成片的完整过程。

**口述回答**

我的项目面向视频素材的理解和剪辑。用户上传素材之后，可以直接问视频里讲了什么，也可以提出“帮我生成一条 30 秒咖啡教程”这样的需求。

整个过程分为两部分。第一部分是上传后的分析。浏览器通过预签名 URL 把分片直接上传到对象存储，Java 后端管理上传会话、核对分片，并在文件完成后进行媒体验证。验证通过后，系统异步执行语音识别、镜头检测、抽帧和视觉分析，再把结果组织成全片概览、内容上下文和原始观察三层结构，并建立检索索引。

第二部分是用户对话。Python 中的 Agent 根据需求调用 Java 提供的工具，查找相关内容，展开上下文，读取具体时间范围，再选择片段。如果是剪辑需求，Agent 会维护一份内容计划，说明作品需要表达哪些信息、以什么顺序表达、分别使用哪些素材。

草稿生成后，Java 检查时间、引用、字幕和时长等规则，模型再审查内容是否完整、有没有改变原意。通过后交给用户预览和确认，确认的版本固定下来，由独立的媒体流程渲染。

这样分工以后，模型负责内容理解和选择，后端负责业务状态、权限、可靠执行和确定性规则。

**追问：为什么视频分析使用固定流程，对话使用 Agent？**

视频分析的输入和目标相对稳定，每次都需要从同一种媒体中提取信息，适合固定流程。用户请求则不同，有时只问一个数字，有时需要跨素材编排，无法预先规定完全相同的读取步骤，所以让 Agent 根据已有结果决定下一步。

### Q02 为什么采用预签名 URL 直传？断点续传和上传完成怎样确定？

**口述回答**

视频文件比较大，如果所有文件都先经过 Java 服务，业务服务就要承担大量传输带宽和连接开销。因此我把文件传输交给对象存储，Java 主要负责授权和业务管理。

上传开始时，后端创建上传会话，记录文件大小、声明的文件哈希和分片信息，再按需签发分片上传地址。浏览器完成分片上传后报告结果，服务端结合对象存储中的实际记录进行核对。

断点续传时，系统先确认用户选择的还是同一个文件，再查询已经存在的分片，只补传缺失部分。这里不能只相信浏览器本地记录，因为浏览器可能在收到响应之前断网，而对象存储实际上已经保存了分片。

所有分片完成后，服务端完成对象上传，并创建媒体验证任务。此时只能说明文件传输结束，后续还要检查实际大小、哈希、格式和解码情况。通过这些检查后，素材才进入分析流程。

**追问：最后一个分片已经上传成功，但浏览器没有收到响应，怎么办？**

先核对存储侧的分片状态。已经成功的分片可以直接复用，不需要重新上传整个文件。完成上传的业务请求也需要能够识别重复提交，返回同一次上传对应的结果。

### Q03 为什么把 Redis 令牌桶放在创建上传会话的位置？Lua 解决了什么问题？

**口述回答**

我的限流目标是控制新上传任务进入系统的速度。因为上传完成后还会产生媒体处理和模型分析，如果用户短时间连续创建很多上传，后续任务会迅速积压。

因此，我在创建上传会话时按用户执行令牌桶限流。令牌按时间补充，请求进入时消耗一个令牌；令牌不足就告诉用户需要等待多久。同一用户跨项目使用同一个桶，避免通过切换项目绕过限制。

一次判断涉及读取剩余令牌、根据经过的时间补充令牌、判断是否允许和更新状态。如果拆成多个 Redis 请求，并发请求可能同时读到相同余额。使用 Lua，可以让这些步骤在一次脚本执行中完成，中间不被其他请求插入。[Redis 脚本执行说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)

不过，这个限流控制的是请求进入速度。一个两小时视频和一个十秒视频，处理成本显然不同，所以后面还需要文件配额、任务并发和模型调用预算，分别控制不同资源。

**追问：Redis 不可用时怎么办？**

对于新上传会话，我选择明确返回暂时不可用，让用户稍后重试。已有上传和已接纳任务继续按自身状态执行。限流服务异常不应该被解释成用户已经成功获得上传资格。

<a id="q04"></a>

### Q04Transactional Outbox 解决什么问题？为什么还需要消费幂等？

**口述回答**

创建异步任务时，会同时涉及数据库和消息队列。如果先提交数据库，再发送消息，可能出现任务已经保存但消息没有发出去；如果先发送消息，再提交数据库，又可能出现消费者收到消息，却找不到对应业务记录。

我的做法是在同一个数据库事务中保存任务和 Outbox 事件。事务提交后，发布流程读取 Outbox，把消息发送到 RabbitMQ，确认成功后再更新发布状态。这样，数据库里始终保留着需要发送消息的记录，发布失败后可以继续处理。

但这仍然可能产生重复消息。例如 RabbitMQ 已经收到消息，而发布进程在更新 Outbox 前退出，恢复后就可能再次发送。因此，消费侧收到消息后，要先根据数据库任务状态领取执行资格，不能收到一次消息就无条件执行一次业务。

发布确认、消费者 ACK 和业务结果提交分别解决不同环节的问题，不能相互替代。[RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)

**追问：消费成功之后、ACK 之前崩溃，会怎么样？**

消息可能再次投递。再次消费时，系统读取任务或调用回执，如果结果已经提交，就复用已有结果；如果只是消息重复但任务正在执行，也不能再创建一个同样的执行。

<a id="q05"></a>

### Q05任务为什么用 PostgreSQL 领取？租约和 attempt_id 为什么都需要？

**口述回答**

我把消息投递、任务领取和执行结果提交分开处理。业务创建任务时，在同一个数据库事务里写入任务和 Outbox，再由发布流程通知 RabbitMQ。Worker 收到消息，只知道有任务可以尝试领取，还没有取得执行资格。消息可能重复，所以不能每收到一次就直接执行。

真正领取时，Worker 请求 Java 后端。Java 在 PostgreSQL 的短事务中锁住任务行，检查任务状态，创建一次执行的 attempt_id，再把任务改为 RUNNING，保存 current_attempt_id 和租约。事务提交后就释放行锁，后面的模型调用不会一直占着数据库锁。如果领取成功但响应丢失，同一个执行者携带原来的领取请求 ID 重试，在租约有效时可以拿回原领取结果。

任务 ID 表示要完成的事情，attempt_id 表示其中一次执行。对于远程 Python Worker，当前租约是 60 秒，执行期间通过心跳续约。如果 Worker 长时间失联，后端检查到租约过期，就使旧执行失效，把任务重新安排为待领取，并通过 Outbox 发送通知。新的 Worker 接手后会创建新的 attempt。

举个例子，A 在第 0 秒领取任务，执行身份是 A1，租约到第 60 秒。第 20 秒 A 断网，之后没有续约，但进程还在运行。租约过期后，系统回收任务，B 在第 65 秒接手，身份变成 B1。第 70 秒 A 恢复网络，带着 A1 提交结果，后端发现它已经不是当前执行，就拒绝这次提交。这里租约决定什么时候允许接手，attempt_id 决定哪一次执行能够提交结果。检查资格和保存新结果在同一个事务中完成，避免检查之后身份已经改变却仍写入结果。

我没有额外增加 Redis 分布式锁，因为数据库已经通过短事务完成原子领取，任务和结果也在数据库里。如果 Redis 只锁领取过程，它只是重复了一部分协调；如果整个任务都持有 Redis 锁，就要依靠 TTL 和续期，这仍然是一种租约，而且还要处理 Redis 执行资格与数据库结果之间的一致性。当前保留一处执行资格依据更简单。

Java 本机媒体任务则使用本机执行身份、进程状态和取消状态管理，没有照搬远程 Worker 的网络心跳机制。两者共同的要求是结果必须属于当前有效执行；如果未来把本机任务拆成独立 Worker，需要连同恢复机制一起调整。

**追问：已经有 RabbitMQ 的 ACK 和重新投递，为什么还需要租约？**

ACK 表示消息在消费协议中的处理情况，不表示业务进程永远健康。重新投递也不能证明原来的 Worker 已经停止。任务领取后仍可能失联、暂停或继续执行旧请求，所以数据库需要独立保存执行身份和有效期限。Outbox 与消息确认负责可靠通知，租约和恢复流程负责接手，attempt_id 负责拒绝旧执行，三者不能相互替代。

**追问：只检查 attempt_id，不检查租约可以吗？**

不够。租约已经过期而恢复流程尚未运行时，current_attempt_id 可能暂时还是 A1，但 A 已经失去继续执行的资格。新操作和新结果提交需要同时检查当前身份、有效租约和允许的任务状态。已成功提交的结果重试则走幂等返回，不重新发布一次。

**追问：Redis 锁过期后旧 Worker 不就停止了吗？**

不会。过期只让其他 Worker 有机会拿到锁，不会终止旧进程。因此即使采用 Redis 锁，旧请求也可能迟到，业务结果的接收方仍要判断当前执行身份。锁如果覆盖整个任务，TTL 就是租约，续期就是心跳机制，并没有消除租约。真正实现 Redis 锁还需要原子获取和过期时间、唯一持有者标识，以及原子的比较后续期和释放，不能无条件删除锁。

**追问：为什么不加 Redis 锁减少数据库竞争？**

可以作为有实际压力后的候选优化，但当前每次领取只锁一条任务记录，而且事务很短，不持锁执行模型。增加 Redis 后，数据库状态检查仍然需要保留，还增加了网络访问和故障依赖。我会先确认瓶颈是否确实来自同一任务的领取竞争，再决定是否值得加入，不会只因为是分布式任务就使用分布式锁。

**追问：60 秒如何确定？任务超过 60 秒怎么办？**

60 秒是当前每次租约的有效期，不是任务总超时。Worker 持续续约就可以运行更久。期限需要结合心跳间隔、网络延迟、进程暂停和允许的恢复等待时间确定：太短容易误判失联，太长接手慢。续约无法确认时，Worker 按最后确认的期限停止继续执行，后端也检查有效期限，不能只依赖 Worker 自己停止。

**追问：attempt_id 是不是 fencing token？**

它在本项目中用来区分执行次数，数据库通过是否等于 current_attempt_id 拒绝旧写入。当前使用 UUID，不是单调递增的 fencing token，不能直接要求任意外部服务据此判断请求新旧。对外部存储或提供方的操作，还要按它们支持的条件写入、幂等键或任务查询能力设计。

**追问：旧 Worker 已经调用了付费模型，撤销执行资格能取消费用吗？**

不能保证。我们能够控制业务结果是否被接纳，但远端可能已经完成计算。因此模型调用要保存回执和提供方任务身份。请求超时后，如果结果未知，应优先查询或恢复原调用，不能直接重新提交一次付费请求。重新领取任务也不能重置已经使用的预算。这套机制保证的是有效执行的结果才能发布，不能宣称所有外部操作都恰好执行一次。

<a id="q06"></a>

### Q06用户连续修改草稿，又重复点击确认，怎样保证确认的是当前版本？

**口述回答**

我把需求、内容计划、草稿和检查结果关联起来。检查通过只说明对应输入通过，不能把“曾经检查成功”当作之后所有版本都有效。

例如原来是 30 秒教程，后来要求缩短到 25 秒，需求已经改变。即使草稿暂时还没修改，旧检查也不能继续用于确认。新草稿完成后，要重新执行对应检查。

确认时，后端在一个短事务中锁定相关业务记录，重新核对当前草稿、需求和检查结果，再创建正式版本。所有会修改当前制作状态的入口，都需要遵守一致的并发控制规则。

幂等键用于识别同一次请求的重复提交，唯一约束用于限制不能重复出现的业务结果。正式接受后，版本不再被后续对话修改，渲染读取这个固定版本。

**追问：为什么已经有行锁，还需要唯一约束？**

行锁保护的是当前事务中的并发操作，唯一约束表达的是数据库必须始终满足的业务规则。两者作用不同。应用代码即使换了调用路径，数据库也应该拒绝重复生成同一个业务结果。

<a id="q07"></a>

### Q07 为什么同时使用 Java 和 Python？怎样避免两边出现两套规则？

**口述回答**

Java 主要承担业务系统职责，包括账号和项目权限、上传、任务状态、内容存储、工具接口和草稿校验。Python 主要承担 Agent 执行，包括模型调用、动作选择、上下文组装和执行状态恢复。

我没有让两个服务分别计算同一套业务规则。例如视频时间区间是否合法、选中哪些字幕、是否切断单词，这些判断都集中在 Java。Python 获取片段选项以后进行内容选择，再把草稿交回 Java 检查。

双方通过明确的数据契约交互，包括字段名称、类型、时间单位、区间含义和错误类型。时间统一使用整数毫秒，区间统一采用左闭右开形式，避免一边使用浮点秒、一边使用毫秒产生误差。

这个划分的代价是多了一次服务间通信和契约维护，但模型开发与业务状态管理可以保持清晰边界。

**追问：双方对相同内容计算哈希，为什么可能不一致？**

JSON 字段顺序、数字表示、空值处理和数组顺序都可能影响结果。所以不能各自随意序列化后计算哈希，需要统一规范化规则，并用相同样例验证 Java 和 Python 的结果。

<a id="q24"></a>

### Q24 PostgreSQL 的 MVCC 能否替代行锁？

**口述回答**

MVCC 主要让事务按照可见性规则读取数据版本，减少普通读写之间的冲突。但两个事务同时读取“当前草稿尚未确认”，随后都准备创建正式版本，仍然需要控制并发修改。

这个场景可以使用行锁，让相关修改按顺序进行，再配合唯一约束保证业务结果不重复。隔离级别越高也不等于所有业务规则自动成立，应用仍然要明确操作顺序和失败处理。[PostgreSQL MVCC](https://www.postgresql.org/docs/current/mvcc-intro.html)、[显式锁](https://www.postgresql.org/docs/current/explicit-locking.html)

**追问：持有行锁时能不能调用模型？**

不应该。模型调用耗时不可控，会让事务和锁长期占用。应在事务外完成模型工作，提交时用短事务重新核对状态。

<a id="q26"></a>

### Q26 Redis Lua 的原子性是不是意味着数据不会丢？

**口述回答**

不是。原子执行说明脚本运行过程中不会被其他命令穿插，不代表执行结果一定持久保存，也不等于出现错误时自动回滚全部写入。

项目中的令牌桶是准入状态，可以接受 Redis 重启后恢复满桶，但业务任务和结果不能依赖这种临时状态保存。因此，限流数据放 Redis，业务记录仍然放 PostgreSQL。

**追问：长脚本会有什么影响？**

脚本执行会影响其他命令的处理，所以限流脚本只做有界、简单的计算和读写，不应该扫描大量数据。[Redis 脚本文档](https://redis.io/docs/latest/develop/programmability/eval-intro/)

<a id="q27"></a>

### Q27 HTTP 请求超时是否意味着服务端没有执行？

**口述回答**

不意味着。请求可能没有送达，也可能已经执行成功，只是响应没有返回。客户端看到的超时，通常只能说明没有及时得到结果。

因此，查询请求和产生业务结果的请求需要分别考虑重试。创建任务、确认版本这类操作应使用稳定请求身份查询或复用结果。付费模型调用还要保存回执，优先恢复原调用。

**追问：只要加一个幂等键就够了吗？**

还需要服务端真正保存和核对这个键对应的请求内容与结果。相同键但参数不同，不能随意复用；记录和业务写入之间也要有正确的事务关系。

<a id="q28"></a>

### Q28 浏览器直传有哪些网络和安全问题？

**口述回答**

预签名 URL 让浏览器在有限时间内执行指定存储操作，因此服务端必须先验证用户对项目和上传会话的权限，再签发限定对象和操作的地址。

传输通过 HTTPS，浏览器跨域访问需要正确配置 CORS，但 CORS 不能代替身份授权。上传完成后，后端仍然要核对真实文件，不能因为浏览器报告成功就把它标为可用素材。

**追问：用户拿到签名地址以后退出登录，地址会自动失效吗？**

不一定，取决于存储系统和签名机制。通常需要依靠较短有效期和有限操作范围减少暴露，业务侧仍要检查上传完成和后续使用资格。

<a id="q29"></a>

### Q29 浏览器怎样获取任务和 Agent 的进度？

**口述回答**

这个场景主要是服务端持续向浏览器发送进度，SSE 比较适合，用户操作仍然通过普通 HTTP 请求提交。相比频繁轮询，它可以更及时地推送变化，又不需要建立一套双向消息协议。

事件流只负责通知，数据库中的任务和制作状态仍然是恢复依据。断线后，如果事件还在保留范围内，可以按游标继续；如果游标已经过期，就重新读取当前快照。

**追问：为什么不能只依靠推送消息恢复页面？**

消息可能丢失、过期或重复。当前状态必须可以独立读取，否则刷新页面后就无法知道实际执行结果。

<a id="q30"></a>

### Q30 怎样计算视频区间是否重叠、是否完整覆盖？

**口述回答**

我统一使用左闭右开区间 `[start, end)`。两个区间重叠的条件是，较大的起点小于较小的终点。因此 `[0,10)` 和 `[10,20)` 相邻，但不重叠。

检查多个区间时，可以先按起点排序，再扫描合并，时间复杂度主要来自排序。判断一个范围是否已完整读取，需要确认合并后的区间能够覆盖目标范围，而且不能存在未读分页。

**追问：时间范围覆盖了，是否代表内容理解完整？**

不代表。区间计算解决的是读取范围问题。语义是否完整，还要看原始观察的采样情况、转写结果和上下文关系。

## 查阅：视频内容组织

<a id="q08"></a>

### Q08为什么需要“全片概览—内容上下文—原始观察”三层结构？

**口述回答**

这三层对应的是用户理解视频时的三个问题：这段视频大致讲什么，其中某个步骤是什么意思，以及具体哪句话、哪个画面支持这个判断。

原始观察保存 ASR 转写、画面描述和可见文字，保留时间和来源。它适合核查细节，但直接把大量零散观察交给 Agent，模型需要每次重新整理关系。

内容上下文把相关观察组织成完整步骤、论述或事件，并保留必要前提。例如“开始萃取”是一个步骤，但它可能依赖前面的“预热完成”。概览再把这些上下文整理成全片摘要和目录，帮助 Agent 先确定需要阅读哪里。

三层结构让 Agent 可以先粗读，再逐步展开，也允许直接从原始观察搜索某个数字或原话。上层负责降低阅读成本，下层负责保留具体来源。语义组织在分析阶段完成，后续索引程序利用已有的摘要、步骤和语句结构生成检索块，不再让大模型重新划分一遍。

**追问：为什么不把三层做成严格的树？**

一条观察可能同时支持两个上下文，一个完整步骤也可能跨越多个镜头。强行限制单一父节点会丢失这些关系。因此使用引用关联即可，不需要为了层次结构引入图数据库。

<a id="q09"></a>

### Q09 镜头检测、代表帧和间隔采样分别解决什么问题？

**口述回答**

镜头检测先找出画面变化明显的位置，帮助系统了解视频的视觉结构。得到镜头区间后，可以在每个镜头中选择代表帧交给视觉模型，减少逐帧分析的成本。

但一个镜头内部也可能发生很多事情。例如固定机位拍摄咖啡制作，十分钟都没有切镜头。因此，我还会按最大观察间隔补充采样，避免长镜头只有一张图片。

采样受到总预算限制。如果无法覆盖全部镜头和时间范围，需要保存哪些位置实际分析过、哪些位置没有覆盖。图片的时间使用实际解码得到的时间戳，不能简单用帧号除以平均帧率。

这里的取舍是：稀疏采样适合发现主要内容，但可能漏掉短暂动作，所以单帧观察只说明那个时刻看到了什么。

**追问：什么时候需要短序列理解？**

当问题涉及动作过程或状态变化时，比如“有没有把杯子拿起来”，单帧通常不够。可以分析连续的一小段视频，比较动作前后状态。它的成本更高，因此优先用于明确存在动作理解需求的范围。

<a id="q10"></a>

### Q10 ASR、镜头和视觉观察怎样组成内容上下文？程序和模型分别做什么？

**口述回答**

程序先完成确定性的整理工作：把观察映射到原片时间，找出相邻语句、相交镜头和附近视觉观察，再把这些记录连同 ID 一起交给模型。

模型负责判断哪些记录能够组成一个完整步骤或论述，以及是否存在指代、解释或必要前提。它输出的每条陈述都需要引用来源，并区分语音说明、视觉观察和推断。

例如语音说“预热完成后才能开始萃取”，这能够支持一个操作前提。如果同时刻图片里有一个亮灯，只能记录灯亮，不能自动推断预热已经完成，除非还有明确依据。

程序再检查引用 ID 是否存在、是否来自允许范围、结构是否完整。这样可以检查来源关系，但语义是否判断正确仍然需要后续阅读和审查。最终保存的陈述、步骤和关系也成为索引分块的依据，索引程序复用这些结构，不重新调用大模型组织语义。

**追问：音频已经讲下一步，画面还停留在上一步，怎么办？**

时间接近只表示它们值得一起查看，不表示它们必然描述同一件事。音画不一致时分别保留观察，并说明对应关系不确定，不强行融合成一个事实。

<a id="q36"></a>

### Q36上下文层总结错了，层次越多是不是错误越严重？

**口述回答**

确实存在这种风险。三层结构的收益是减少重复阅读和整理，但每一层概括都会引入信息遗漏或理解偏差。

因此，上下文中的陈述需要保留观察引用，概览需要指向实际上下文。推断与直接观察分开保存，缺失信息不能被补成确定事实。Agent 找到内容后，可以沿引用向下阅读，关键选段最终回到原始观察。

原始观察本身也可能识别错误，所以这些关联提供的是核查路径，而不是绝对正确的保证。用户仍然能够查看原片。

**追问：为什么不直接只读原始观察？**

短视频和精确查询可以直接读。但素材规模较大时，每次从大量观察重新整理步骤会增加成本，也容易遗漏关系。上层结构提供导航，具体结论仍然可以向下核查。

## 查阅：分块、召回与阅读

<a id="q11"></a>

### Q11为什么三层使用不同的 Chunk 策略？

**口述回答**

我的设计是“分析阶段组织语义，索引阶段按已有结构分块”。分析阶段已经通过模型把原始观察组织成步骤、论述和内容目录，所以索引阶段可以直接利用这些边界，不需要再调用一次大模型判断怎样切分。

三层内容虽然以 JSON 保存，但 JSON 只是承载格式。程序会提取摘要、目录项、陈述和观察中的文本，把 ID、时间和引用放进元数据，不会把整个 JSON 字符串按长度直接切开。

具体来说，概览按摘要和完整目录项组织，内容上下文优先保留完整步骤，原始观察一般以一句 ASR 或一条画面描述为单位。没有超过长度限制就完整保留；过长时，程序再按已有陈述和句子边界拆分，并检查真实 token 数和字节数。

例如“开始萃取”上下文包含“只有预热完成后，才能开始萃取”和“按下萃取按钮”。长度允许时，程序把标题、来源标签和两条陈述放进同一个块。这里的语义关系来自前面的分析结果，索引程序只是读取和组织已经保存的内容。

一个 Chunk 可以包含多句话。例如“准备咖啡粉”中的称取18克、整理粉面、压粉三条陈述，长度允许时就和标题组成一个块。较长对象拆成多个块后，每块都有自己的 chunk_id，但共享完整对象的 entity_id，并保留块顺序、版本和各自的来源引用。搜索命中其中一块以后，Agent 可以按对象 ID 展开完整上下文，不必重新搜索其他块。

PostgreSQL 保存完整对象和关系，Qdrant 保存向量、Chunk 原文和元数据。Chunk 确定后才调用 Embedding，它负责向量化，不负责决定切分边界。这样可以复用前面的分析结果，减少重复模型调用和新的内容偏差。

**追问：既然都保存成 JSON，究竟什么内容被向量化？**

向量化的是程序提取和拼接出的内容文本。例如标题“开始萃取”加两条带来源标签的陈述。context_id、observation_ids 和时间信息用于过滤与定位，保存在元数据中，不作为普通正文一起向量化。

**追问：程序具体怎样从 JSON 提取字段并组装 Chunk？**

先用 JSON 解析器或已经定义好的类型读取对象，再按对象类型选择固定字段。比如“准备咖啡粉”的上下文，程序读取 title，再按 claims 的顺序读取 text 和限制说明，根据 basis 加上“语音说明”标签。它不会把所有字符串都拼起来，ID 和时间用于元数据。组装结果可以是下面这一整块：

```text
准备咖啡粉
语音说明：称取18克咖啡粉。
语音说明：将咖啡粉放入粉碗，并整理表面。
语音说明：使用压粉器将咖啡粉压平。
```

这一个 Chunk 包含三句话，分别引用 speech_05、speech_06、speech_07，共同属于 context_02。生成模型在分析阶段已经组织好这些陈述，索引阶段只执行明确的字段读取和拼接规则。

**追问：完整对象太长时，程序怎么拆分？**

程序先检查完整文本，标题和来源标签也计入长度。确实超限时，按原顺序把完整陈述逐条放入当前块，加入下一条会超过配置长度就开始下一块。单条超过目标长度但没有超过硬上限，可以单独保留；单条本身超过硬上限，才按句子和标点进一步拆分，必要时按字符边界拆分并再次检查真实长度。被迫切开完整表达时，标记需要展开，不把文本变短等同于语义仍然完整。

**追问：多个 Chunk 怎样关联回完整对象？**

每块有独立 chunk_id，同一上下文的块共享 entity_id，例如 context_02，还保存素材、分析版本、块顺序 ordinal 和各自观察引用。假设长上下文分成两块，第一块引用称量和整理表面的观察，第二块引用压粉及后续观察，两块仍属于同一个上下文。Agent 命中任何一块后，可以用 context_02 读取 PostgreSQL 中的完整对象，较长时分页读取。这个关联是确定的，不需要再靠向量相似度猜下一块在哪里。文本拆分也不会按字数比例推算新的剪辑时间。

**追问：一个视频概览会不会被分成很多块？**

要区分摘要和目录。咖啡教程的一段短摘要可以完整保留为一块；“设备预热”“准备咖啡粉”“启动萃取”三个目录章节另外形成目录块，并分别指向对应上下文。这时共有四个概览层 Chunk，但摘要没有被拆成四段。只有摘要本身超长才继续按完整句拆分，所以数量取决于章节和文本长度，不是每个视频固定切成多少块。

**追问：为什么不统一按固定字数切分？**

固定字数容易把条件和结论分开，例如把“只有预热完成后”与“才能启动”切成两块。已有结构提供了更合适的边界，所以先保留完整陈述，再处理长度限制。程序不会凭空理解所有依赖；确实需要强制拆开时，要保留关联并标记需要展开，由 Agent 读取完整上下文。

**追问：会不会先调用 Embedding 比较相邻句子的相似度，再决定切点？**

当前方案不会。那是另一种切分方法，而我们的分析阶段已经形成步骤和陈述结构，没有必要在首版再引入一套相似度判断。Embedding 在这里仅用于已经生成的 Chunk 的检索表示。

**追问：简历中的“按照语义进行切分”怎样说更准确？**

我会说“利用分析阶段形成的语义结构，按摘要、完整步骤和原始语句生成检索分块，超长内容再按句子边界拆分”。这样能够明确语义来自内容组织，不会让人误以为索引阶段又调用大模型进行语义切分。

<a id="q12"></a>

### Q12稠密检索、BM25 和字面匹配分别适合什么需求？为什么采用 RRF？

**口述回答**

用户查询可能是主题，也可能是非常具体的原话。比如“找咖啡准备步骤”包含语义表达，适合稠密检索；“18 克”“某个型号”这类词项，BM25 更容易发挥作用；用户明确寻找一句原话时，可以使用字面匹配。

不同通道的评分含义和范围不一样，直接相加容易让某个通道因为数值较大占据优势。因此我使用 RRF，根据候选在各通道中的名次进行融合，让多个通道都排在前面的内容获得更好的综合排名。[Qdrant 混合检索说明](https://qdrant.tech/documentation/search/hybrid-queries/)

目标设计会使用受控执行器并发运行“Embedding 加稠密检索”、BM25 和 PostgreSQL 字面匹配，统一汇总结果后再做 RRF。当前代码还是先字面匹配、再 DENSE、最后 BM25 的同步串行调用，并发部分尚待实现。

Qdrant 本身已经支持稠密、BM25 和原生混合查询。项目复用它的两路召回能力，同时保留 PostgreSQL 的原文子串匹配，所以由 Java 获取三个通道的排名并统一执行 RRF。我们没有自行实现向量搜索或 BM25 算法，应用侧实现的是融合与业务结果组织。

融合在同一层内进行，因为概览、上下文和原始观察承担不同用途。融合后再按业务对象合并，避免一个对象切出很多 Chunk 后占满结果。对象的排序采用组内最高 Chunk 的 RRF 分数，不把同一个上下文的所有块分数加起来；每个对象最多展示两个匹配块。这样，较长的上下文不会只因为分块多就获得额外的累计分数。

**追问：用咖啡教程举例，两个通道具体怎样配合？**

假设用户查“使用18克咖啡粉的准备步骤”。A 块讲称取18克和装粉，B 块讲布粉和压粉，两者属于 context_02；C 块讲清理使用18克咖啡粉后的残粉，属于 context_04；D 块讲预热，属于 context_01。A、B 是较长上下文拆出的块，这里只概述内容。

稠密检索可能把 B 排第一、A 第二、D 第三、C 第四，因为布粉压粉与准备步骤语义接近。BM25 可能把 A 排第一、C 第二、B 第三，因为 A、C 都直接出现18克等词项。用 k=60、名次从1开始计算 RRF，A 约0.03252，B 约0.03227，C 约0.03175，D 约0.01587。这个演算仅包含两个通道，字面通道有命中时再加入它的排名贡献；这些数字是假设例子，不是实测结果。

融合后按对象分组，context_02 使用 A 的最高分排第一，并同时展示 A、B；context_04 第二，context_01 第三。C 讲的是清理，即使匹配词项也可能不适合剪辑，所以 Agent 还要读原文。后端算排名和分组，Agent 判断内容用途。

**追问：为什么用组内最高分，不把所有 Chunk 的分数相加？**

直接相加会让分块更多的长上下文占优势。用最高分可以保持规则简单，其他匹配块作为补充原文展示，不继续累加分数。代价是没有把多个块的共同支持全部计入对象排名。超过两个匹配块时用 more_matches 提示，但它只表示本次候选里还有未展示的块，不代表已经完整搜索了整个对象。

**追问：metadata 中的 layer 是做什么的？只有 context 和 observation 吗？**

最终方案有 OVERVIEW、CONTEXT、OBSERVATION 三层，分别表示全片概览、内容上下文和原始观察。Agent 通过工具的 layers 参数选择要搜索哪些层，后端把它转换成各检索通道的过滤条件，先限定范围再召回；多个层分别融合排名，不放进同一份语义排序。大素材库可以先查 OVERVIEW，已知素材可以直接查 CONTEXT 或 OBSERVATION。

layer 保存在 Qdrant payload 中，用于过滤和解释结果，不参与正文向量化，也不代替权限检查。source_kind 则表示观察来自语音、画面还是可见文字，只在 OBSERVATION 层生效。这里描述的是目标设计，当前代码的 sourceKind 来源过滤不能当作三层 layer 已经实现。

**追问：Qdrant 不是原生支持混合检索吗，为什么还要自己做？**

它原生支持，能够通过 prefetch 分别召回候选，再用 RRF 融合。项目目前仍使用 Qdrant 完成稠密和 BM25 搜索，只把融合放在 Java，因为还有一条来自 PostgreSQL 的字面匹配通道。Java 统一处理三份排名，再保存结果和通道状态。这样接入已有业务流程比较直接，但也需要维护应用侧的排序逻辑。[Qdrant 混合查询文档](https://qdrant.tech/documentation/search/hybrid-queries/)

**追问：哪些能力是你实现的，哪些是数据库提供的？**

稠密向量由外部 Embedding 模型生成，Qdrant 负责向量检索和 BM25 处理，PostgreSQL 执行原文子串查找。项目代码负责内容和 Chunk 组织、范围及索引版本管理、Java 三路 RRF、结果状态和分页；最新设计再增加三层对象合并和展开入口。因此我会把贡献描述为检索流程与业务契约设计，不说自己开发了一套 BM25 或向量检索引擎。

**追问：为什么不先在 Qdrant 融合两路，再跟 PostgreSQL 结果融合？**

因为这样会形成两次 RRF。第一次已经把稠密和 BM25 的名次转成了新的综合名次，第二次只看到这个新名次，与直接累加三条原始通道的贡献不同。当前选择把三路原始排名交给 Java，一次完成融合，规则更清楚。

**追问：如果以后不用 PostgreSQL 字面检索，还需要 Java 做 RRF 吗？**

不一定。如果只剩 Qdrant 中的稠密和 BM25 两路，可以评估直接使用它的原生融合，减少应用代码。Java 继续处理权限、对象分组和分页。这些业务职责并不要求 RRF 一定由 Java 执行，具体放在哪里取决于需要合并哪些通道。

**追问：多路召回现在是并行的吗？使用什么机制？**

当前不是。代码先执行 PostgreSQL 字面查询，再顺序处理 DENSE 和 BM25，HTTP 用同步 send。目标方案使用 Spring 管理的专用受控执行器，把三条通道作为独立任务，可以通过 CompletableFuture 汇总。每个任务内部仍可使用同步 HTTP 或 JDBC，不必为了并发把整个项目改成响应式架构。Java 线程负责发起调用，向量和 BM25 计算仍在 Qdrant 中完成。

**追问：Embedding 还没完成，其他检索能先开始吗？**

可以。只有稠密搜索依赖查询向量，所以它和 Embedding 放在同一个顺序执行的分支。BM25 直接处理查询文本，字面匹配直接查询数据库，两者可以同时进行。例如查询咖啡准备步骤时，生成向量的等待时间可以与另外两条通道重叠，最后才汇总排名。同一次查询和同一 Embedding 配置的向量在不同内容层复用，不重复调用模型。

**追问：为什么不为每次请求直接创建三个线程？**

用户请求增加以后，下游请求数也会成倍增加，必须在服务实例内共享有限线程和有界队列，并结合数据库连接池、HTTP 资源和模型限额设置容量。队列满就明确返回繁忙，不无界排队，也不退回请求线程执行。多个层或配置先在通道任务内部顺序处理，避免继续扩出大量子任务。多实例时还需要按下游总容量分配上限，不能把单实例线程池说成全局限流。

**追问：怎样避免多个线程把结果写乱？**

每个通道构造自己的结果和状态，返回后由一个汇总过程统一处理，不让线程共同修改同一个 Map 或 JSON。RRF 计算规模很小，顺序执行即可。共享的查询范围在启动前固定，业务事务和数据库连接也不会跨线程传递。这样通道完成先后不同，不影响最终排序。

**追问：一个通道超时，是否要一直等它？**

不会无限等。查询有包含排队时间的统一截止时间，HTTP 和 JDBC 也要设置实际调用超时。已知的只读检索故障可以明确标记，例如 BM25 超时而另两路成功，就用成功通道融合，并告诉 Agent 哪个通道不可用。所有通道都失败时返回错误。只给 Future 设置超时并不能停止底层请求，取消和客户端超时需要一起处理，迟到结果不能改写已经返回的排名。

**追问：Embedding 请求超时也直接忽略、重新发一次吗？**

不可以。模型可能已经执行并收费，响应未知时保存 UNKNOWN 回执，本次搜索明确报错并保留其他已完成结果用于恢复，不自动重付。取消本地等待不能保证远端停止。权限和 scope 错误也不能当成普通检索故障继续返回内容。

**追问：怎么证明并发实现正确，而不只是看起来快了？**

可以用受控调用阻塞 Embedding，检查 BM25 和字面分支是否已经开始，再确认 DENSE 没有提前调用。还要验证线程与队列上限、超时、部分失败和迟到结果。把相同结果按不同完成顺序返回，最终 RRF 和分页应该一致。实际延迟另行观察，不能把偶然一次更快当作正确性证明。

**追问：RRF 和 reranker 有什么区别？**

RRF 合并已有排名，不重新理解查询与文本。Reranker 会进一步判断查询和候选是否相关。如果问题主要是候选已经召回但顺序不好，可以考虑增加重排；如果相关内容根本没有召回，首先应该检查分析、切分和召回条件。

<a id="q13"></a>

### Q13 召回后 Agent 看到了什么？为什么还要展开阅读？

**口述回答**

Agent 看到的不只是 ID，而是匹配 Chunk 的完整文本、所属层次、素材身份、时间定位、关联对象和缺口提示。工具还会提供下一步可以读取的对象或范围。

这些信息足以让 Agent 判断候选是否值得继续阅读，但搜索结果不一定包含完整前提。例如搜索“开始萃取”可能只命中一句操作说明，前面的预热要求没有出现在这个 Chunk 中。

因此，Agent 可以先读取对应内容上下文，查看必要前提，再通过时间范围工具读取原始观察。确定片段内容之后，才获取具体切法。

如果用户问“用了多少克咖啡粉”，也可以直接搜索原始观察，然后展开相关范围核查，不必先经过概览检索。

继续用18克咖啡粉的例子，搜索结果把 A、B 放在 context_02 这一条命中下，返回完整匹配文本和读取入口。我接下来按 context_02 调用 read_video_context，读取 PostgreSQL 中的完整陈述和关系。如果它明确关联预热前提，就继续读取 context_01。然后通过 read_video_range 读取对应原始观察，完成所需范围阅读后再调用 get_clip_options 获取可用切法。已经知道对象 ID，就直接读取，不再靠向量搜索猜其他块在哪里。

**追问：预热检索排名第三，是不是也应该在成片中放第三？**

不是。检索排名只决定哪些内容优先查看，原片顺序说明素材如何表达，剪辑顺序则由用户目标和内容关系决定。预热即使排第三，只要它是明确的必要前提，也可能需要放在准备或启动之前。

**追问：搜索命中为什么不能算整个片段已经读完？**

因为命中结果只展示相关内容，可能省略不匹配的相邻语句。剪辑需要知道区间内实际包含什么，所以范围阅读必须独立记录，不能拿一条搜索命中代替整段阅读。

**追问：Agent 怎么决定查概览、上下文还是原始观察？**

我把选择规则放在工具说明和 Agent 指令中，由已有决策节点根据当前缺少的信息选择，不增加一个专门的分类节点。找相关视频时优先查概览，理解完整步骤时查上下文，定位数字和原话时查原始观察。如果已经有有效对象 ID，就直接读取；同一 scope 下已有有效读取结果，就先复用。它不是每次固定从上到下搜索三遍。

例如用户说“从素材库找意式咖啡教程”，Agent 调用 search_video_content，query 是“意式咖啡制作教程”，layers 是 [OVERVIEW]，不指定 asset_ids。后端只在当前允许素材中查找。返回 video_01 的教程概览、其他视频的清洁或探店介绍后，Agent 根据匹配原文选出 video_01，再调用 get_video_overview 读取完整目录。返回的预热、准备、萃取上下文 ID 可以直接用于下一步读取。

**追问：用户只问用了多少克咖啡粉，还需要先读概览吗？**

如果素材已指定，就可以直接搜索原始观察。比如 query 使用“咖啡粉用量 多少克”，asset_ids=[video_01]，layers=[OBSERVATION]，source_kinds=[SPEECH]。不能先猜18克再去搜索支持答案的句子。假设结果返回 speech_05 的“这里称取18克咖啡粉”、时间位置和 context_02 引用，Agent 再调用 read_video_range 核查相邻语句，确认没有“以前18克，这次16克”这样的修正后回答。只有指代或前提不清时，再展开上下文；这个问题不需要剪辑计划。

**追问：用户问开始萃取前需要做什么，又会怎样查？**

这次要理解完整步骤，所以用 layers=[CONTEXT] 搜索“开始萃取之前的准备步骤和必要条件”。命中准备和启动上下文后，按 ID 展开。如果启动上下文明确定义了预热前提，就继续读取预热上下文，再核查相关原始范围。搜索先给入口，已保存关系帮助继续阅读，不要求所有必要前提都进入搜索前几名。

**追问：生成30秒教程，必须把三个层次都搜索一次吗？**

不需要。用户已经选好 video_01 时，先直接读取概览，再沿目录展开步骤，形成暂定内容计划，读取原始范围并获取片段选项即可。只有缺少具体定位时才搜索，例如查找“称量咖啡粉 布粉 压粉”的语音观察。第二轮缩短到25秒时，也先复用有效的原始阅读记录和计划基线，补充需要的切法。三个层次提供不同信息，但获得信息不一定都要通过搜索。

**追问：能不能同时搜索三层？具体返回什么？**

可以。比如用户问“哪些素材里讲过萃取前的准备，能不能做短教程”，入口还不明确，可以这样调用：

```json
{
  "tool_name": "search_video_content",
  "arguments": {
    "query": "咖啡萃取前的准备",
    "layers": ["OVERVIEW", "CONTEXT", "OBSERVATION"]
  }
}
```

后端在每层分别召回和融合，再按对象最高 Chunk 分数排序，跨层按固定层序轮流返回。例如第一条是 OVERVIEW 层的 video_01 概览，第二条是 CONTEXT 层的预热步骤，第三条是 OBSERVATION 层“灯稳定后再启动”的原话；它们都可能是各自层内第一名。每条带 layer、layer_rank、匹配原文、来源定位和读取入口。第一条并不代表在语义上一定比第二条更相关。

Agent 可以根据当前问题选择读全片目录、直接展开步骤，或者先核查原话。跨层结果可能描述同一内容，利用关联 ID 避免重复阅读即可。多层检索带来更多候选和阅读成本，所以简单数字问答不默认查三层。

**追问：第一次选错层或者没有命中怎么办？**

概览里没有用量，不等于视频里没有说，可以转查原始观察。结果太宽泛，可以缩小素材范围或改查完整上下文。已知对象但内容还没读完，应继续分页；工具返回分析缺失或通道故障，则说明限制，不能当成没有内容。这些调整都在同一个 Agent Loop 中完成，并受既有预算约束。

**追问：你的方案包含 Query 改写吗？由哪个模块完成？**

包含查询改写的行为，由现有 Agent 决策节点完成。模型根据用户目标、已经读到的内容和当前缺少的信息，直接生成检索工具的 query 参数。它可以把用户表达改成更适合检索的形式，也可以把制作任务拆成几个具体信息需求，再根据结果调整下一次查询。我没有额外增加改写节点，后端接到 query 后也不会再调用一次大模型改写。Embedding 和 BM25 的编码、分词只是在处理查询表示。

**追问：咖啡教程需求具体怎样改写？**

用户说“用这个视频做一条30秒咖啡教程，准备步骤必须保留”，Agent 可以查询“咖啡制作的准备步骤和必要条件”，选择 CONTEXT 层和 video_01。30秒继续保存在制作需求中，不需要机械放进检索词。展开上下文以后，如果还要定位操作原话，再查询“称量咖啡粉 布粉 压粉”，选择 OBSERVATION 层和 SPEECH 来源。第一步找完整步骤，第二步定位细节；如果目录和已读内容已经足够，就不必重复搜索。

**追问：改写会不会把用户的问题改偏？**

需要约束它只调整检索表达，不改用户目标。用户问“多少克”，不能猜成“18克”再寻找支持；用户寻找明确原句或型号时，要保留关键措辞、数字、单位和否定条件，不能只留下宽泛主题。原始消息和确认过的需求始终保留，query 只是一次检索输入，不会覆盖需求。后端检查结构、长度和范围，不额外调用模型审查每一次改写。

**追问：稠密检索和 BM25 会分别拿到不同的改写吗？**

当前方案不会。后端把接纳后的同一个 query 用于稠密、BM25 和字面通道，各通道再按各自方式处理。没有为每个通道额外生成一份查询。如果 Agent 根据结果提出新查询，就作为新的一次搜索，重新形成排名，从第一页开始，不能沿用旧查询的游标。

**追问：为什么“保留准备步骤”不能改成“保留原来的十秒”？**

前者是内容要求，后者增加了固定区间或时长要求，两者不是同一个意思。查询可以帮助定位准备内容，但不能替用户新增约束。同样，时长没有放进查询，不代表时长要求被删除，它仍然约束后面的选段和草稿校验。

<a id="q14"></a>

### Q14 PostgreSQL 和 Qdrant 怎样保持一致？索引重建时怎么办？

**口述回答**

我的设计把 PostgreSQL 作为业务内容的权威来源，Qdrant 是可以重新构建的检索副本。索引更新不直接覆盖正在使用的内容，而是构建一个新的索引代次。

具体过程是先固定内容版本，生成 Chunk 清单和文本，再生成向量、写入 Qdrant。核对数量、身份、文本和配置后，才在 PostgreSQL 中发布新的索引代次。构建失败时，旧的可用索引继续提供服务。

Agent 执行时会固定允许使用的分析版本和索引代次，因此同一次执行不会前半段读旧内容、后半段突然读到新内容。仍被执行引用的旧代次不能提前清理。

这种方式增加了版本管理和存储成本，但避免了跨数据库分布式事务，也让重建过程可以恢复。

**追问：用户被撤销权限后，旧执行还能继续读取吗？**

不能。固定版本保证内容一致性，不冻结用户权限。每次读取仍然需要经过业务访问控制，权限撤销后就不再返回相关内容。

## 查阅：Agent 循环、多轮修改与输入

<a id="q15"></a>

### Q15你的 Agent 与固定 Workflow 有什么区别？四个节点分别做什么？

**口述回答**

我的 Agent 是在受控流程中进行自主决策。整体有四个主要节点：初始化、Agent 决策、工具执行，以及草稿校验与审查。

初始化负责理解本轮请求与当前制作的关系，加载需求和状态。决策节点根据已有信息选择下一步，例如调用工具、更新计划、提问、回答或者提交草稿。工具执行节点负责检查参数和范围，执行后把结果写回状态。提交草稿后进入校验与审查，必要时把问题返回主循环修订。

自主性体现在模型决定查什么、读哪里、怎样组织内容；程序规定工具范围、权限、预算和提交条件。

简单问答使用同一循环，只是不需要维护剪辑计划，也不进入草稿检查。这样不必为问答和剪辑分别搭两套 Agent。

**追问：为什么没有给 Plan 和 Critic 各建一个 Agent？**

规划可以表现为主循环中的计划更新，审查也可以是一个输入明确、输出受限的模型调用。当前业务不需要多个独立 Agent 协商，拆开反而会增加状态同步和调试成本。

<a id="q16"></a>

### Q1630 秒教程缩短到 25 秒，但保留准备步骤，状态怎样变化？

**口述回答**

系统先识别这是对当前制作的修改，更新时长要求，并保留其他没有被修改的条件。准备步骤必须保留，也会进入明确需求。

随后，Agent 以原计划为基础调整内容。假设原方案包含预热、准备、启动、停止和成品展示，它可以优先缩短重复讲解和成品展示，而不是直接从末尾截掉五秒。

原素材和分析版本没有变化时，之前读取的观察与上下文可以复用。已有片段选项如果仍然适用，也可以继续使用；缺少更短切法时，再调用工具获取。

需求、计划或草稿发生变化后，对应的旧检查就失效。新的草稿必须重新校验和审查，确认缩短以后仍然保留了必要信息。

**追问：“保留准备步骤”是不是必须保留原来的十秒？**

通常表示保留相应信息，不自动等于原区间完全不动。如果用户明确要求“这一段一帧都不要改”，才把原区间作为锁定条件。否则可以寻找更简洁但信息完整的表达。

<a id="q17"></a>

### Q17 工具结果、持久状态和模型输入有什么区别？视频内容怎样进入模型上下文？

**口述回答**

我的设计分成三步：工具返回结果，系统保存状态，程序再为下一次调用组装上下文。工具结果是这一次检索或读取实际返回的数据；持久状态记录业务目标和执行进度；模型输入则是根据当前任务选出来的一部分内容，不会把整个状态每轮全部发送。

Java 保存需求、计划、草稿和检查结果，也保存权威内容与读取回执。Python 的 checkpoint 和调用日志保存正在执行的动作、读取缓存、分页进度和预算。具体模型调用前，由程序选择相关信息，原文不需要重复复制到每张业务表里。

例如用户要求30秒咖啡教程，搜索命中“准备咖啡粉”以后，模型下一次看到当前需求、匹配原文、context_02 的读取入口，以及“仅命中、尚未展开和读取原始范围”的状态。它据此调用 read_video_context，获得完整的称量、整理粉面和压粉陈述。再读原始范围后，输入中才有具体转写和时间，获取片段选项后才有实际切法及入选文本。

不同调用使用不同内容。请求理解主要看当前消息、已有需求和制作摘要；Agent 决策看目标、计划、相关原文、候选、最新工具结果和阅读进度；内容审查看按成片顺序的实际入选内容、需求、计划及必要原始上下文。模型也在决策节点生成检索查询，不额外增加改写节点。

选择哪些内容主要靠程序规则：Agent 通过计划、选段和工具调用表达关注对象，程序沿当前计划、草稿、候选和未解决问题的引用获取原文，不再调用另一个模型给全部历史打相关性分数。必要前提即使没有入选，也要保留或展开。

输入变长时，我先去掉同源重复文本和无关历史，保留引用目录，需要时再读。但精确选段和审查需要的原文、时间、数字和条件不能只剩摘要。这个设计让模型知道自己实际看到了什么，也避免把一条搜索命中当作整段视频已经理解完整。

**追问：搜索结果具体怎样进入下一次调用？**

假设命中 context_02，原文包含“称取18克咖啡粉，放入粉碗并整理表面”。工具执行节点先保存回执和 search_hits，再由程序把完整匹配文本、对象 ID、版本、读取入口和当前30秒需求组装进下一次输入。阅读状态明确写“上下文尚未展开、原始范围未读”，而不是只告诉模型“已经找到合适素材”。

**追问：展开上下文以后，要把之前的搜索结果再发一遍吗？**

不一定。同一来源、同一版本的文本已经被展开结果包含，就可以只呈现一次，但调用记录和搜索身份仍保存着。上下文里的概括和原始观察不是同一份内容，不能因为意思相似就删掉原文。若还有下一页，模型必须看到未读完的状态。

**追问：原始观察和片段选项需要保留哪些内容？**

例如 speech_05 在20.2—23.4秒说“这里我们称取18克咖啡粉”，后面是整理表面和压粉。模型要看到原文、时间和来源，必要时还有词级信息。片段选项再提供 option_id、起止时间、时长、实际入选转写和边界限制，模型才能判断是否保留了准备信息。只给“这是准备步骤”这个摘要，无法支持精确选择。

**追问：上下文长度不够怎么办？**

先减少同源重复内容和当前无关历史，再控制本次比较的候选范围。工具结果长就继续按分页读取，旧内容保留引用目录。输入预算还要考虑工具定义、固定指令和输出空间，具体配额按模型确定。必要原文仍然放不下时，应缩小当前任务范围或说明输入不足，不能截断条件句后当成完整内容，也不需要每轮另调模型总结全部历史。

**追问：系统已经读过，但这次没有放进提示词，算不算模型已经掌握？**

不能这样理解。读取回执说明系统完成过某次读取，不代表当前模型输入包含了那些文字。因此可以在目录里告诉模型哪些内容能够复用，但精确选段需要的原文还要实际加载进来。提示词裁剪也不能反过来修改权威读取记录，或把尚未读完的分页标成已完成。

**追问：为什么内容审查不能复用决策时的所有输入？**

审查目标是检查最终作品，需要按成片顺序读取实际入选内容，再对照需求、计划和必要上下文。搜索探索历史通常没有帮助，全部发送会分散注意力。尤其不能只给剪辑理由：理由写“保留准备步骤”，实际片段仍可能切掉18克或者预热条件。缺少依据时要返回需补读的范围。

**追问：第二轮要求缩短到25秒，模型输入有什么变化？**

输入更新为25秒目标，继续保留准备要求和其他有效条件，再附旧计划、旧草稿作为修改基线，以及仍相关的原文、选项和阅读进度。不需要重放第一轮全部搜索过程，但本轮需要精确选择的原文必须可见。旧校验和审查失效，修改后按新需求重新检查。

**追问：已经有 checkpoint，为什么还需要调用回执？**

Checkpoint 记录程序执行进度，但外部调用可能已经成功，而进度还没保存。调用回执能够帮助恢复时判断原调用是否已完成，避免因为重新进入节点而重复产生外部副作用。

**追问：程序不理解语义，怎样知道哪些内容相关？**

程序依据明确关系，而不是重新理解所有文本。例如当前计划里的准备项指向 context_02，草稿里的准备片段引用 speech_05—speech_07，最新反馈指向某个被切掉的条件，这些都是直接选择依据。哪一步适合缩短、还要寻找什么，由 Agent 判断并通过动作表达。计划还没形成时，就先提供需求和最新工具结果，让模型继续选择。

**追问：以前搜到的清洁内容怎么处理，会不会以后又有用？**

如果当前计划、候选和问题都没有引用它，可以先不发送全文，但保留搜索记录和读取入口。这只是本次输入的选择，不是断言它永远无关。后面 Agent 认为需要清洁画面，还可以重新读取。这样不必每轮把所有曾经找到的东西都塞进模型。

**追问：缩短到25秒时，是否只给模型看需要修改的片段？**

第一次决策还要看到整条作品的计划、片段顺序和时长。短教程的实际入选文本不长时，也直接保留全部原文。模型了解整体后，才能判断从萃取还是成品展示中缩短；程序不能仅凭“缩短”这个词先排除其他内容。模型确定关注对象并获取新选项以后，后续输入再围绕具体候选展开，同时保留整体结构和准备步骤的保留要求。

**追问：去重是不是看到两段话意思相近就删掉一段？**

不是。按同一来源、版本和字段位置去重，例如搜索命中的半句后来已经由完整范围读取覆盖，可以不重复发送。上下文摘要说“称量并压粉”，原始语句说“称取18克”，二者信息不同，摘要不能代替原文。同一句话出现在不同时间，也不能合并成同一条观察。

**追问：怎样让模型分清已读记录和本次看到的内容？**

输入里分别给出读取进度和本次原文目录。例如 context_02 已读完，speech_05—speech_07 的原文这次实际提供；context_01 只列了可读取入口；context_03 仍有下一页。这个清单由程序根据实际输入生成。模型需要精确判断时，要加载相应文字，不能把“已读过”当成仍然拥有全部原文。

**追问：超长时到底先删什么、后删什么？**

先计算包括指令、工具定义和预留输出在内的总预算，再去掉同源重复文本和失效反馈。其次把暂时无关的历史全文换成目录，保留当前目标和作品结构。然后减少同时比较的候选，分批读取，保留剩余入口。如果必要原文仍放不下，就明确说明输入不足或调整当前处理范围，不能直接截断条件句。有效需求、正在判断的原文和必要前提不能被静默删除。

**追问：最终审查放不下，可以每段单独审查后合起来吗？**

局部比较可以分批，但几段各自正确不等于编排在一起也完整。最终审查还需要判断整体顺序、信息重复和跨片段前提，因此必须有足够的整体输入。当前核心方案没有自动分段汇总审查，如果仍然放不下，就返回未完成或请用户调整任务范围，不把局部通过冒充整体通过。

<a id="q18"></a>

### Q18后端校验和模型审查分别检查什么？

**口述回答**

后端校验处理可以明确计算的规则，例如素材是否允许使用、时间是否越界、引用是否存在、是否完整读取范围、是否切断单词、字幕是否来自入选语音，以及总时长是否满足要求。

模型审查处理内容关系。例如剪掉预热条件以后，“直接开始萃取”是否改变了原意；某一步是否缺失；不同片段是否重复；画面描述是否缺乏观察支持。

流程上先执行后端校验，因为时间越界或时长超标这类问题不值得再花一次模型调用审查。通过以后，模型读取实际入选内容，而不是只读剪辑理由。

审查提出具体问题后，由主循环决定怎样修订。修订完成再重新检查，次数受到预算限制。

**追问：模型觉得节奏还不够好，要一直修改吗？**

不会。风格建议和内容错误要区分。缺少必要步骤可以阻止完成，但“还可以更有感染力”不能无限阻止用户确认。第一版只给有限的内容修订机会，仍然无法解决时说明原因。

<a id="q37"></a>

### Q37没有大量效果评测，凭什么加入显式计划和内容审查？

**口述回答**

我加入这两个设计，是因为它们对应明确的问题。

如果只有最终时间线，很难看出每个片段为什么存在，也不容易判断修改后有没有遗漏用户要求。内容计划把需要表达的信息、保留理由和片段对应关系保存下来，让修改有明确对象。

审查则检查最终选中的内容。例如草稿满足 25 秒，但删掉了预热条件，时长校验不会发现这个问题，内容审查可以针对实际转写检查。

这些机制能够增加可检查性，但不能据此直接宣称理解准确率或剪辑质量提升了多少。代表性案例可以验证流程是否发挥预期作用，效果幅度则需要后续数据。

**追问：既然生成模型已经考虑了内容，为什么还要审查？**

生成阶段同时处理检索、选择、时长和编排，审查阶段只围绕明确标准检查最终结果。它提供了第二次有针对性的检查机会，但不会被当作绝对正确的裁判。

<a id="q39"></a>

### Q39检索、阅读、计划、校验、审查这么多步骤，会不会太慢？

**口述回答**

需要先区分任务。简单问答通常只需要检索和相关范围阅读，不需要生成计划和审查草稿。复杂剪辑才会进入完整流程，因为它需要在内容完整、顺序和时长之间做选择。

优化时，我会先减少重复工作。视频分析在上传后完成，同一素材不需要每轮重新分析；同一范围内的阅读结果可以复用；最终计划更新可以随草稿一起提交，减少一次单独调用。

然后检查模型输入，只发送当前需要的内容。确定性的检查由程序执行，硬校验失败时不调用内容审查。

这些优化可以降低调用次数和输入规模，但需求变化后的检查仍然要重新执行。不能为了缩短等待时间，让旧检查代表新的草稿。

**追问：用户还是觉得慢，怎么办？**

先测清楚时间花在哪里，再做针对性处理。同时让用户看到当前阶段和实际结果，例如正在查找素材、已经形成计划、正在检查草稿。对耗时任务保持可恢复和可停止，比只给一个持续旋转的加载状态更有用。

## 可选扩展：有明确追问时再讨论

本节不属于六条核心回答的必备深度，不增加实现承诺。先讲清目前为什么不需要，再说明什么条件出现后值得考虑。

| 扩展方向 | 什么时候值得考虑 | 当前边界 |
| --- | --- | --- |
| 独立的三类 Worker、多实例分析接管 | 实际排队和资源隔离需求出现 | 三类业务职责不等于必须拆成三个服务；当前本机恢复不能直接用于多实例 |
| 通用 DAG、Temporal、Conductor | 流程种类和跨服务等待明显增多 | 当前用固定依赖，不新增工作流引擎 |
| Redis 分布式锁领取 | 有证据表明数据库领取竞争是瓶颈 | 当前保留 PostgreSQL 原子领取，不额外加锁 |
| 迟到结果接收与复用 | 未提交成果损失已经明显影响费用 | 当前及时保存进度，拒绝旧 attempt 的新业务写入 |

| 多 Agent、复杂长期记忆 | 单一循环无法满足明确的新需求 | 当前维持四节点受控循环 |

### Q23 Java 服务怎样处理大量耗时任务？

**口述回答**

我会先把交互请求和耗时执行分开。HTTP 接口完成校验、保存任务后尽快返回，媒体处理和模型调用由后台执行，避免长时间占用请求线程。

后台也不能无限增加并发。FFmpeg 主要消耗 CPU、内存和磁盘，模型调用则受连接、限额和费用约束，需要分别设置执行上限。线程池、任务队列和数据库连接池的容量要配合，否则只是把等待从一个地方转移到另一个地方。

**追问：线程越多，吞吐量越高吗？**

不一定。线程增加会带来内存和调度成本，下游资源也可能先耗尽。线程池的价值之一就是限制并管理并发资源，而不是尽可能创建线程。[Java ThreadPoolExecutor 文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)

<a id="q25"></a>

### Q25 任务表和 Outbox 表怎样建立索引？

**口述回答**

我会从实际查询出发。例如调度器经常查找“处于待执行状态，并且执行时间已经到达的任务”，索引就应该围绕状态、时间和排序条件设计，而不是看到字段就各建一个索引。

如果只有少部分记录处于待处理状态，可以考虑部分索引，避免把大量历史完成任务都放进相同索引。但是否采用，需要结合 SQL、数据分布和执行计划判断。

**追问：为什么索引不是越多越好？**

每次写入和状态更新都要维护相关索引，会增加存储和写入成本。任务状态变化频繁，所以要优先服务高频、关键的查询。

<a id="q31"></a>

### Q31 当前方案需要增加 rerank 精排吗？它与 RRF、Agent 阅读和内容审查有什么区别？

**口述回答**

我考虑过增加 rerank，但当前核心方案不把它作为必需步骤。先通过素材和层次过滤、三路 RRF 和同对象合并控制候选，再让 Agent 展开完整上下文和原始范围。已知对象可以直接读取，不需要每次重新检索。

RRF 根据多个通道的名次融合，不重新阅读文本。比如查询“使用18克咖啡粉的准备步骤”，称量、布粉和压粉是相关内容，但“清理使用18克咖啡粉后的残粉”也可能因词项重合排得靠前。Reranker 可以把查询和候选一起理解，尝试区分准备和清理，因此适合解决“内容已经召回，但顺序不够好”的问题。

如果后续需要，我会放在对象合并之后，对有限对象的标题和匹配原文进行重排，避免同一个长上下文占用很多名额。当前按最高 Chunk RRF 分数确定对象最终顺序；增加精排以后，这个分数用于选出待重排对象，重排范围内的最终顺序由 reranker 决定。

它会增加一次推理和结果管理成本，而且仍然不能替代完整阅读。Agent 还需要根据用户目标选择内容，内容审查还需要检查实际草稿是否遗漏前提或改变原意。因此我把它留作后续增强，先观察真实查询里是否经常出现排序导致的无效阅读，再决定是否加入。

**追问：已经有 Agent 阅读结果，为什么还可能需要 rerank？**

两者有部分重叠，但目标不同。Rerank 比较候选与当前查询的相关性，可能让 Agent 少读几条无关内容。Agent 还要结合整个制作目标决定后续操作，比如成品展示对准备步骤查询不相关，却可能是完整教程需要的内容。不能让重排模型代替整个规划过程。

**追问：什么情况下值得加，什么情况下加了也没用？**

如果正确内容已经在候选中但经常排得很低，或者 Agent 连续展开清理、保养等无关上下文才找到准备步骤，就值得考虑。若视频分析漏掉了动作，或者正确内容没有进入候选，应先检查分析、查询、过滤和召回规模；rerank 只能重新排列交给它的候选。剪掉预热前提则属于完整阅读和内容审查的问题。

**追问：为什么放在对象合并之后？给模型看完整上下文吗？**

Agent 最后展开的是完整对象，所以先把同一上下文的多个 Chunk 合并，避免一个对象重复占用重排名额。第一步可以给重排模型查询、对象标题和有限匹配原文，不为排序提前加载全部长上下文。这样成本可控，但模型看到的信息也有限，所以排序之后仍然要展开核查。

**追问：增加 rerank 后，还能说按最高 Chunk 分数排序吗？**

只能说它负责候选初排。核心版本的最终顺序由最高 Chunk RRF 分数确定；如果启用增强，重排窗口里的对象最终按 rerank 排序。未进入窗口的对象如何继续展示、同分和失败怎样处理，都要在实施时明确，并保存整次查询的排名，翻页不能重新排序。

**追问：rerank 和内容审查是不是都让模型再看一遍？**

输入和目标不同。Rerank 看查询与候选，决定优先展示哪些内容；审查看需求、计划和实际选中的片段，判断成片是否缺步骤或改变原意。准备片段与查询非常相关，也可能在剪辑时被切掉关键条件，这需要草稿审查才能发现。

**追问：不做大规模评测，怎样决定是否值得加入？**

可以先保留几个真实查询，观察相关内容是否已经召回、是否排名靠后，以及 Agent 展开了多少无关对象。这样能够判断主要问题是不是排序。增加模型调用可能减少后续阅读，但不保证总成本更低或速度更快；程序流程验证和真实效果要分开看。

**追问：能不能让重排模型直接从整个素材库找答案？**

通常不合适，输入规模和成本都太大。召回负责缩小范围，重排负责在有限候选中比较，最后 Agent 再读取和使用内容。

<a id="q32"></a>

### Q32 Skill、工具、Workflow 和 Agent Loop 有什么区别？

**口述回答**

工具提供具体能力，例如搜索内容、读取时间范围。Skill 提供完成某类工作的指引和方法。Workflow 规定步骤及其依赖，适合过程比较确定的任务。

Agent Loop 则在当前状态下反复决定下一步，调用工具后再根据结果继续判断。在我的项目中，上传后的分析是 Workflow，用户问答和剪辑采用 Agent Loop，底层读取能力通过工具提供。

**追问：有工具调用是不是就一定是 Agent？**

不一定。如果调用顺序完全由程序固定，模型只负责填一个字段，也可以只是工作流中的模型步骤。需要看它是否根据中间结果决定后续行为。

<a id="q33"></a>

### Q33 接触 OpenClaw、Hermes 这样的 Agent 系统，你会先看什么？

**口述回答**

我会先沿着一次请求阅读：消息怎样进入，运行循环怎样决策，工具怎样注册和执行，状态保存在哪里，失败后如何恢复。

之后再看权限和外部操作的边界，因为 Agent 能调用工具以后，错误就不只是回答不准确，也可能产生真实操作。最后把这些机制与自己的系统比较，判断哪些设计可以复用，哪些服务于不同业务。

**追问：你能直接介绍它们的具体内部实现吗？**

只介绍实际阅读过的版本和模块。没有读过的部分，可以说明自己的分析方法，不把一般 Agent 原理冒充某个框架的具体实现。

<a id="q34"></a>

### Q34用了这么多组件，如果只有两周，你会删掉什么？

**口述回答**

我会先把范围收敛到单素材、单条成片和一种明确用途，例如保留原声的教程剪辑。优先完成上传、分析、内容定位、草稿检查和确认渲染这条完整链路。

短序列理解、CLIP、复杂重排、多 Agent、动态预览审查都可以推迟。基础设施也要看是否已经具备：如果从零开始且规模很小，可以先用数据库持久任务配合后台执行，不必为了技术栈完整立即引入所有组件。

我会保留任务状态、结果幂等和时间校验，因为这些直接关系到结果能否正确交付。

**追问：三层内容还保留吗？**

可以保留简单版本：原始观察、少量步骤上下文和一个概览。先限制素材规模和输出复杂度，不急着建设复杂的跨窗口关系与高级索引能力。

<a id="q35"></a>

### Q35素材数量增长一百倍，最先出现的瓶颈在哪里？

**口述回答**

我不会仅凭素材数量直接判断。长视频多，瓶颈可能在媒体解码和视觉分析；并发用户多，可能先遇到模型限额；历史素材多但上传少，压力可能主要在索引存储和检索。

我会先区分排队时间和实际处理时间，再看各阶段吞吐、错误率和资源使用。比如排队持续增长，但 CPU 很空闲，就要检查模型额度、连接或调度，而不是直接增加媒体 Worker。

项目当前的本机媒体执行还有单实例假设，扩容前需要先梳理共享执行资格，不能简单增加 Java 实例。

**追问：你会优先缓存什么？**

优先复用输入和配置相同的分析结果、成功向量，以及同一执行中的已读内容。用户目标变化后的计划和检查结果不能因为看起来相似就直接复用。
