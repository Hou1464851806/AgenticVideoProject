# Agent 定向修正与预算治理 Spec

日期：2026-10-30。状态：设计已整理，尚未实施。测试边界已由用户确认；仅保存本地文档，不发布 GitHub Issue。

## Problem Statement

用户要求从素材中选取约 12–20 秒亮点，并明确提出“我确认要剪辑，请你给我方案。”，却只收到“有限修正额度已用尽”。该回复既没有提供可用剪辑草稿，也没有解释真正失败的条件。随后用户说“请你就做第一段”，系统又生成了合法草稿，说明需求与素材本身可以满足。

已核实的失败链条：

| 步骤 | 结果 | 累计修正消耗 |
| --- | --- | --- |
| 首次理解 | output_durations 返回 null，而类型要求列表 | 1 |
| 再次理解 | 改成空列表，识别 DRAFT，并保存 12–20 秒约束 | 1 |
| 第一版草稿 | 32.02 秒，只有 OUTPUT_DURATION 错误 | 2 |
| 第二版草稿 | 开场变长，总长 38.74 秒，仍超时 | 3 |
| 两次补读后第三版草稿 | 回到 32.02 秒，修正额度耗尽 | 3，停止 |

本轮共 11 次模型调用、9 次工具调用，活动耗时约 22.26 秒；没有触发调用总量或活动时间上限。格式错误与业务修正共享 3 次额度。程序的修正建议只尝试改变一个片段边界，三版草稿的所有候选均为空。补读还会清除通用无进展计数，无法体现草稿问题持续存在。

第一版三段长度分别为 13.46、12.64、5.92 秒。删除中间“历史回顾”后为 19.38 秒；后续成功轮次使用了这一组合并通过完整校验，但也消耗了两次修正。不能把换一句话当作解决方案。

## Solution

用户仍通过原有制作会话提出需求。系统按保存的制作条件生成剪辑草稿，遇到可修复问题时提供具体的调整选项，在有限调用内完成修正；不能完成时说明实际违反的条件。

本次保持 Java 与 Python 的分工、任务调度、校验、草稿接受及渲染链路。改造 Agent 内部的输出协议、候选生成、错误反馈、预算和进展判断。程序计算可核对的机械约束，模型判断内容取舍与语义完整性，Java 继续承担完整草稿校验。

## User Stories

1. As a 视频创作者, I want 系统理解我已明确表达的剪辑意图, so that 我不必反复更换指令才能开始制作。
2. As a 视频创作者, I want 本轮确认沿用已明确的 12–20 秒条件, so that 草稿不会擅自变成长视频。
3. As a 视频创作者, I want 未修改的条件保持原值, so that 自动修正不会放宽我的要求。
4. As a 视频创作者, I want 空列表等协议细节由系统处理, so that 我不必为模型字段格式重新发消息。
5. As a 视频创作者, I want 超时草稿获得具体缩短建议, so that 系统能有效推进制作。
6. As a 视频创作者, I want 系统能考虑删除完整片段, so that 不必为凑时长切断句子。
7. As a 视频创作者, I want 删除片段前判断上下文是否连贯, so that 时长合格的草稿仍能表达完整意思。
8. As a 视频创作者, I want 修正后仍核对原始观察证据, so that 选段与内容依据一致。
9. As a 视频创作者, I want 多个成片定义中已合格的输出保持不变, so that 修正一条不会损坏其他条。
10. As a 视频创作者, I want 缺少上下文时只补读必要范围, so that 调用用于解决实际问题。
11. As a 视频创作者, I want 系统识别持续无效的修改, so that 不会为同一个失败方案无限等待。
12. As a 视频创作者, I want 格式错误与剪辑错误各自有有限修正机会, so that 一次字段错误不会挤占全部剪辑机会。
13. As a 视频创作者, I want 总调用量和活动时间仍然有上限, so that 自动修正的成本可控。
14. As a 视频创作者, I want 失败回复说明要求、当前值和未满足条件, so that 我知道下一步是否需要调整需求。
15. As a 视频创作者, I want 系统区分执行未完成和条件确实无解, so that 我不会被误导去放宽可满足的要求。
16. As a 视频创作者, I want 未通过校验的草稿不能成为可确认方案, so that 不会保存不合法结果。
17. As a 视频创作者, I want 已通过校验的草稿仍由我明确接受后保存版本, so that 自动修正不会替我确认方案。
18. As a 视频创作者, I want 补答与重启恢复保留本次执行消耗, so that 恢复不会偷偷增加调用额度。
19. As a 系统维护者, I want 结果未知的付费请求保持原有停止规则, so that 修正逻辑不会引发重复费用。
20. As a 系统维护者, I want 从执行记录看到错误类别、候选和改善情况, so that 可以定位失败原因。
21. As a 开发者, I want 用已有执行入口重放此次故障, so that 不依赖真实模型随机性也能验证修正机制。
22. As a 开发者, I want 区分确定性回归与真实模型验收, so that 不会把脚本模型成功误报为线上成功率。

## Implementation Decisions

### 1. 业务边界与执行链路

- 遵守现有“用户接受剪辑草稿后才保存方案版本”和“通过单实例 Python Worker 调度 Agent”的架构决定。
- 保持用户消息 → Java 接纳与固定上下文 → Python 理解 → Java 绑定制作需求与范围 → Python 读取并编排 → Java 校验 → Python 结果核对 → Java 发布的主链路。
- 在现有 observe_tool → decide_next → check_action 循环内实现定向修正，不新增图节点、服务、队列或第二个 Agent。
- 沿用 DRAFT、ASK、ANSWER 动作与 INCOMPLETE、DRAFT_READY 等结果。只有缺少关键条件或确有条件冲突时才澄清；候选为空不证明需求无解。
- Java 校验通过不证明语义正确。Python 候选满足机械条件也不等于完整校验通过。

### 2. 模型输出契约

- 请求理解提示词、Understanding 字段说明与解析行为一致：可空标量未修改时为 null，output_durations 未指定逐条时长修改时为 []。
- 对 output_durations 显式 null 在模型输出接纳边界规范化为 []，仅适用于已确定等价的“没有逐条修改”语义。其他非法类型继续暴露具体字段错误。
- 逐个核对其他列表字段的未修改与清空语义；不实施通用 null 转空列表。
- 已保存条件仍由现有合并逻辑维护，不因规范化而丢失、清空或扩大。
- 本次保持现有模型适配方式，不将 strict 模式或更换模型列为依赖。

### 3. 输出级定向候选

- 扩展现有草稿修正模块，保留单片段边界候选，增加“删除一个完整片段”的输出级候选。
- 删除候选只面向超长输出；保留至少一个片段，保留其他片段原有顺序、时间和引用，删除后总时长须满足该 output_key 的上下限。
- 候选包含当前草稿哈希、output_key、被删除片段位置、删除前后时长、删除内容与相邻保留内容的可读摘要。摘要来自已有证据或当前草稿，不增加模型调用。
- 绑定草稿哈希避免旧候选用于新稿；沿用已有候选计算的证据身份、范围与边界核对，仍对最终完整草稿执行 Java 校验。
- 删除候选按剩余时长接近允许区间中点、片段位置排序，最多提供 3 个；仅用于稳定展示，不代表语义优先级。
- 模型评估语义后提交完整 DRAFT；程序不自动采纳、不直接删段、不把候选写成合法结果。已合格输出继续受原有保护逻辑约束。
- 首版不枚举多片段子集、不引入组合求解器。没有候选时允许模型重新编排或读取真正需要的新素材。

### 4. 错误类别与反馈

| 问题 | 定向反馈与下一步 |
| --- | --- |
| 请求理解或 Action 结构解析失败 | 给出字段与期望类型，使用格式修正预算 |
| 已解析动作的业务参数、范围、引用不合法 | 给出具体业务问题，使用业务修正预算 |
| 仅 OUTPUT_DURATION | 展示要求、总时长、差额及候选，优先调边界或删段 |
| 缺少上下文或证据读取 | 给出必要范围及分页参数，补读后重新校验 |
| 多类校验错误 | 保留完整问题，优先解决阻碍验证的读取或引用问题，不能忽略其他硬条件 |
| 基础设施失败、取消或付费提交结果未知 | 沿用现有停止与恢复规则，不进入模型修正 |

一次失败只归入一个预算类别。只读调用的安全尝试仍使用原有工具尝试规则，不计作模型修正。定向反馈不禁止有理由的新素材读取，但读取不会抵消草稿停滞。

### 5. 预算契约

| 计数或限制 | 新规则 |
| --- | --- |
| format_repairs | 默认最多 2 次，覆盖理解与动作结构错误 |
| business_repairs | 默认最多 3 次，覆盖业务准入、引用、草稿约束等问题 |
| repairs | 仅作为两类消耗之和展示，不再是独立的共享限额 |
| model_calls / tool_calls | 保持 16 / 20 的整体上限 |
| active_seconds | 保持 300 秒；等待的时间语义不变 |

- 初始尝试不扣修正机会。失败需要再次进入修正时，检查所属类别，未耗尽则扣一次；已经耗尽则停止，计数不继续增长。
- 同一次失败仅在一个节点负责扣额；停止后结果核对不重复扣额。首次草稿校验失败建立进展基线，但允许继续修正仍需扣业务机会。
- 请求理解到正式执行、补答、重启和任务重投继承同一逻辑执行的分类消耗与总调用消耗；明确新请求沿用当前的新执行语义。
- 剩余分类机会和整体调用余量提供给模型。存在剩余修正机会不代表一定能继续，整体调用、时间和停滞上限均可终止执行。

### 6. 独立判断草稿改善

- 保留读取进展统计；新增独立草稿连续无改善统计，默认连续 2 次无改善的后续失败校验后停止。首版失败只建立基线，不计一次停滞。
- 读取新范围、新分页、新证据均不能重置草稿停滞。只有可核对的改善或校验成功可以清零。
- 同一 requirements_hash 下比较。问题身份使用错误码、字段、output_key，实际数值不放入身份。
- 改善定义：没有引入新问题；所有仍存在且可量化的问题均未恶化；至少消除一个问题或减少一个时长违反量。时长违反量为低于下限或高于上限的毫秒数。
- 非时长问题不引入通用评分；消除问题才计为改善。问题截断或需求不同不能据不完整信息宣称改善；新用户请求建立新基线。
- 相同草稿在补齐读取缺口后可重新校验；不能仅按草稿哈希相同就禁止合法补读恢复。
- 保留每次失败的要求、实际时长、问题类别、改善结论与候选数量。利用现有 checkpoint 和执行记录，不建设新观测平台。

### 7. 用户结果与公开契约

- 继续使用现有 RunResult 与 Failure 契约，不增加数据库表、公开状态或必需前端字段。
- INCOMPLETE 的 content 由确定性逻辑根据停止原因与适用的最新校验结果生成，包括要求、实际值、差额以及未完成状态。若校验已失效，不引用旧数值作为当前事实。
- failure.code 区分格式机会耗尽、业务机会耗尽、草稿持续无改善等原因；message 与用户内容一致。错误码遵循现有字段长度限制。
- 不为错误解释再调用模型；不把“未完成”写成“不可满足”，不把未验证候选宣称为可用方案。
- recoverable 继续表达既有任务恢复语义，不因为存在其他剪辑候选就设置为可自动恢复。
- Worker 核对透传即可；Java 与前端预计无需实现变更，以契约及页面验证确认。

### 8. 模块责任

| 模块 | 变更责任 |
| --- | --- |
| 提示词与 Understanding | 统一字段语义与定向修正规则 |
| 状态与运行策略 | 分类预算、草稿进展基线和停止条件 |
| 草稿修正 | 输出级删除候选，保留边界候选与合格输出保护 |
| 模型上下文投影 | 提供候选、分类余量与错误方向 |
| 请求理解和决策准入 | 在唯一处理点分类扣额 |
| 工具观察 | 处理完整校验结果，计算独立草稿改善 |
| 结果核对 | 生成具体错误说明及 Failure |
| 制作会话交接与运行视图 | 继承、显示新状态和消耗 |
| Worker、Java 接收与前端会话 | 验证已有结果契约可承载新信息 |

### 9. 开发阶段数据约定

用户明确项目尚未上线、现有数据均为测试数据。本次直接更新新结构，不处理旧任务、旧数据或旧 checkpoint，不做迁移、兼容层、旧计数推断或 Agent 状态备份。只有需要时清理阻碍验证的测试状态，不默认清空整个项目。

新结构自身的持久化、重启、补答、重投和付费回执正确性仍属范围内。

## Testing Decisions

- 用户已确认：以现有 Agent 公共执行入口为主要测试边界，使用固定记录与脚本模型驱动完整修正循环；补充候选生成、Java 校验及浏览器结果展示验证。
- 好的测试检查外部行为：是否合法、是否继续或停止、实际调用次数、恢复后是否重复调用、用户收到什么结果。不以私有函数调用顺序或内部状态形状代替行为验收。
- 复用现有草稿修正、真实制作适配、额度恢复、制作会话运行、Worker 公共结果和 Java AgentRun 集成测试的组织方式，不新增测试框架或生产测试入口。
- 候选模块只补充必要的数值与保护规则测试；完整场景主要经 Agent 入口完成，Java 完整校验另用已有接口集成边界验证。
- 必测场景：协议 null 规范化；非法输入仍失败；32.02 秒草稿产生 19.38 秒删段候选；没有合法单删候选；多输出保护；补读引用缺口后可重交相同草稿；格式与业务预算独立且总量有界；时长改善、恶化、引入新问题；补读不清空停滞；新任务重启与补答不重置预算；未知付费提交不重试；具体失败消息正常发布。
- 真实模型验收复用已分析素材，分别运行原始请求与明确选段请求，记录每次结果、候选使用、调用量和修正次数。真实调用属于单独验收，不由日常非付费测试隐式触发。
- 本轮原始故障是诊断证据，不把生产数据库作为测试依赖。所需最小样本固定为测试输入；不复制无关对话、凭据或全量数据。
- 文档阶段只检查内容、链接和差异。实施阶段按计划运行模块回归、Python 非付费完整回归、相关 Java 集成验证与当前浏览器入口验收，分别报告通过、失败、跳过和未运行。

## Out of Scope

- 旧任务、旧数据、旧 checkpoint 的迁移、兼容与状态备份。
- 多 Agent、图节点重构、新队列、新服务、新模型供应商或严格结构化模式切换。
- 多片段组合优化器、自动删除内容、自动放宽硬条件。
- 修改方案接受、保存版本、预览、导出流程或绕过 Java 校验。
- 新的前端诊断面板、重试按钮、监控平台及大规模评测系统。
- 将此前“选一段亮点”被识别为 QUERY 的问题扩展为全面意图识别重构。
- 吸收其他尚未实施的视频分析或 Agent 整体重构方案。
