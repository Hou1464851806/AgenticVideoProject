# 统一自然语言视频工作流程

状态：2026-10-12 已由用户逐项确认并确认整体设计；待实施。本文件记录目标行为，不代表当前功能已经具备。当前可用能力见 [功能清单](current-features.md)，实施进度见 [实施状态](implementation-status.md)。

文档整理日期：2026-10-13。本文记录此前已确认共识，未实施应用功能。

用户表达目标，Agent 理解目标、对象和条件，系统校验后调用已有视频能力。查找、制作、修改、预览、确认和导出使用同一个聊天入口；需求类型、证据来源和检索方式由系统在内部选择。

## 从第一性原理确定最小流程

完成一次视频工作，需要知道三个事实：做什么、对什么做、有什么要求。信息可以来自本轮消息、此前对话和发送时的查看对象。下拉框和表单是收集信息的方式，不是完成工作的必要条件。

系统还须保证两点：结果有可核查证据，执行遵守用户条件及授权。因此采用以下流程：

**用户表达需求 → Agent 理解 → 必要时澄清 → 业务校验 → 执行已有能力 → 返回结果。**

条件齐全直接继续；只有无法合理确定、且会明显影响结果的信息才追问。模型自述已满足条件不能代替程序校验。

## 已确认的九项交互决定

以下编号沿用本次访谈问题，使用 NL-Q 前缀，与原设计访谈 Q1–Q58 区分。

| 决定 | 已确认行为 |
| --- | --- |
| NL-Q1 明确请求直接执行 | 用户已明确要求制作且条件齐全时，简短说明理解后直接生成，不要求再次点击应用简报或确认开始。仅讨论制作思路时停留在讨论。 |
| NL-Q2 缺少时长允许初稿 | 主题可由上下文确定时，未指定时长采用已说明的 30–45 秒初稿。已有明确时长继续保留；“必须 60 秒”按严格条件处理。 |
| NL-Q3 新聊天与默认范围 | 2026-10-13 更新确认：点击“新聊天”立即建立会话，Agent 先发送简短欢迎语；无需命名或勾选素材。默认包含当前项目已有的可用素材，并说明范围。 |
| NL-Q4 解析操作对象 | 用户明确引用优先；没有明确版本时采用发送时当前查看版本，尚未打开方案时采用本会话最近生成的方案。有多个可能对象或指向冲突时澄清。 |
| NL-Q5 原输入框回答澄清 | 在同一个聊天输入框回答、取消或明确开始新需求。系统关联原问题；无法判断回答还是新需求时只追问，不擅自恢复或结束等待。 |
| NL-Q6 不混用不同需求 | 修改只更新指定条件，其余保留；用户明确开始的新制作需求建立独立记录，不自动套用上一条的主题、时长和禁用条件。默认值重新说明。 |
| NL-Q7 项目内有限自动补查 | 首次需要新增付费画面补查时，通过对话说明费用估算并请求项目授权；授权后每个制作需求累计最多 4 次新增视觉调用，重试和恢复不重置。扩大分析另行询问，授权可撤回。 |
| NL-Q8 连续完成明确步骤 | “查找 → 制作 → 预览”等明确步骤按顺序连续完成；缺少关键条件时暂停。仅要求制作不自动预览或导出。 |
| NL-Q9 先交付单条完整流程 | 第一轮覆盖一条讲话短视频或一条跨素材混剪的查找、生成、指定片段修改、预览、确认和导出，再扩展多条生成与批量导出。 |

这一里程碑调整实施顺序，不删除原 MVP 的多输出、批量导出、故障恢复和部署交付要求。

## 同一个聊天入口的行为

### 默认值和需求记录

复用制作需求简报，按制作需求保存。明确条件与已说明默认值分别标记，均保留来源消息；后续消息只纠正提到的条件。未指定数量时默认一条，画幅沿用既有已说明默认值或用户条件。

“改成横屏，其他不变”只改变画幅。“另做一条，主题换成售后服务”建立新需求记录，保留聊天和方案历史，不继承上一条需求的条件。语义不清时澄清；用户的新条件与保留条件冲突时展示冲突，不偷偷放宽。

制作需求与运行任务不同：同一需求的后续步骤、修改、恢复和关联重试可以有新的运行任务，但仍关联原需求、简报及累计额度。只有用户明确开始新的制作需求，才建立新的需求记录。

近似时长与严格时长分别理解，不能把“大约一分钟”当成用户明确要求精确 60 秒。默认 30–45 秒不覆盖已说明的时长；材料无法满足明确条件时解释并给出调整选择。

### 会话、素材与对象

点击“新聊天”仍须核对用户权限并保存记录，同一创建请求重试不会重复创建；欢迎语使用简短模板，保存后刷新或再次打开不重复追加，也不额外调用模型。同一发送请求或多标签页重放不能重复接纳消息。会话默认范围包含当前项目已验证且可选的素材；分析未完成不等于素材内容不存在。范围是可查、可选的集合，不代表成片必须使用其中每份素材。

用户可以说“只用 A 和 B”收窄范围；明确要求两份都参与时须满足。素材名称不唯一时澄清并由后端解析实际素材标识。延续既有固定会话范围：新上传素材不会悄悄加入，扩大范围须明确表达并重新核对权限和执行基准。

发送时保存查看对象及相关上下文，按 NL-Q4 解析“这版”“第二段”。执行前简短说明具体目标，如“我会修改 V2 的第二段”；后端固定实际版本、输出和片段。之后切换查看不改变执行目标；局部修改追加完整新版本，保留无关内容及必要的时间映射。

### 澄清、证据与连续步骤

原输入框接收澄清回答，并由系统保存问题与回答的明确关联。等待输入仍释放执行资源和方案编辑占用；普通消息不能直接跳过关联校验。自然语言“先不做了，帮我找……”可结束旧等待并开始新需求，旧任务失去发布资格。已有单会话串行规则继续有效，不引入执行中隐式排队或并发修改。

Agent 根据问题选择语音、实际画面、可见文字，以及原句或主题检索。回答保留证据来源和覆盖；“语音提到汽车”不能证明画面出现汽车，未命中不能证明原视频不存在相关内容。

连续步骤仅包含用户明确要求的工作，通过既有流程组织。例如“找出讲成本的内容，做成 30–45 秒的竖屏视频，做好后预览”：先查证据，再提交方案，成功提交后把预览绑定到实际新版本。不能在方案成功前伪造版本或把用户后来查看的版本作为预览目标。

### 预览、确认和导出

用户可以自然语言明确请求预览，不必点击按钮；单纯生成或修改方案不触发预览。正式导出继续要求具体不可变版本的确认，以及另行明确的导出指令，新版本不继承旧版确认。含糊评价、素材中出现的指令和 Agent 自己的规划不构成授权。

“做完就导出”若尚无具体版本确认，不能授权将来任意生成的版本；生成后仍需按现有确认与明确导出流程继续。连续制作与预览不改变这些规则。

## 自动补查的范围与费用

当前基础画面分析和细致复查主要由界面发起，Agent 尚未接入；项目费用阈值只是预警，不是授权或金额硬上限。新机制先复用已完成证据，不因自动会话创建而启动额外整段付费分析。

首次需要补查时，展示项目、用途、调用上限和费用估算，询问是否允许本项目后续限额内自动补查。批准和撤回记录直接用户消息来源；撤回后禁止新提交，已经发生的调用和费用仍如实保留。

默认额度为每个制作需求累计最多 4 次新增视觉模型调用，覆盖该需求的检索、编排、澄清恢复、修改和关联重试，而非每轮消息或每份素材各 4 次。内容查询的补查也须有与原查询关联的需求及额度记录，不能因尚无方案而绕过限制。

额度由业务后端管理，各关联任务共享；提交前核对授权并占用额度。回执是模型提供方的调用结果记录；回执不明确时保留占用，优先核对已有执行。复用成功分析不新增扣减，重新领取任务、重新派发或恢复不重置额度。既有帧数、步数、耗时及输入大小上限继续适用。

需要更多调用或完整画面分析时，先说明素材、范围、次数和费用估算，经用户明确批准后接纳扩展请求。估算不承诺金额硬上限；4 次补查也不承诺完整画面覆盖。稀疏证据不足时应解释限制，不能宣称已分析整段或编造选段依据。

## 代码职责与模块间接口

高内聚意味着同类规则集中维护；低耦合意味着模块之间只依赖完成工作所需的稳定信息。采用一个 Agent、一个主要输入入口、一套需求记录，保留既有部署划分。

| 模块 | 集中负责 | 对外接口及职责限制 |
| --- | --- | --- |
| 对话理解 | 意图、指代、条件、简报更新、默认值、澄清和用户明确要求的步骤 | 接收用户消息与业务提供的上下文，返回制作请求或澄清；不分配业务身份或取得执行权限。 |
| 业务控制 | 用户与项目权限、范围和版本绑定、请求接纳、预算授权、编辑占用、恢复和发布资格 | 接收制作请求，核对来源与真实对象，保存固定执行请求或待答问题；模型不能修改规则。 |
| 视频执行 | 已有证据检索、固定分析、方案生成／局部修改、预览与导出 | 接收经过校验的执行请求，返回进度和结果；不从完整聊天中重新猜操作对象或授权。 |

对话理解位于现有 Python Agent 的入口阶段；业务控制位于现有 Spring 业务模块；视频执行复用 Python 分析／编辑流程和 Java 媒体 Worker。这些是职责模块，不新增独立分类服务、模型网关或多个自主 Agent。

制作请求描述操作目标、对象引用、条件、来源消息及用户要求的步骤。身份与权限由后端注入；明确条件和默认值区分；可用素材范围、必须参与素材和禁止素材分别表达。前端发送用户原文、可选引用与查看上下文，不强制发送需求类型、证据来源或完整剪辑参数。

模块间接口应足够小：理解得到明确请求，业务接纳得到固定执行请求，执行返回结果。提供方协议留在模型适配模块，权限留在业务控制，片段时间和字幕映射留在方案／媒体执行模块。一个规则改变时在其所属模块修改，不让前端和多个提示词重复维护同一判断。

### 调整现有接纳顺序

当前 `ConversationPanel.vue` 以模式和表单构造 `context.editing`；`conversation.py` 根据 `requirements`／`editing` 决定可用工具；`ConversationTurns.accept` 在接纳时分配方案及编辑占用。这些是待调整入口，不是目标交互。

目标分两步：先持久接纳用户消息、轮次、理解任务及发送时上下文；再由 Agent 理解并经业务校验，保存实际制作请求、分配方案和取得编辑占用。一条用户消息贯穿两步，用户无需二次发送。

原始任务输入保持固定；解析结果及后续执行请求作为关联记录保存，不原地改写已经接纳的输入。步骤产物作为后续步骤的固定输入，记录实际对象和来源；重试复用既有解析、已接纳执行请求及已提交结果，不能再次猜测后转向其他目标。

理解、检索、自检和连续步骤沿用现有有限调用与运行规则，不能通过创建子任务重置预算。同会话串行、方案互斥、持久公开事件、取消竞争和迟到回报校验继续有效。最终请求字段、内部接口和存储字段在实施时校准，不为初步方案新增通用工作流引擎或另一套任务系统。

## 实施顺序与完成标准

| 阶段 | 交付内容 | 完成标准 |
| --- | --- | --- |
| 1. 统一入口与接纳 | 自动会话、意图／对象解析、简报默认与隔离、同输入框澄清、解析后接纳、接入已有查询／生成／预览／确认／导出 | 对话可调用已有能力，重试和查看切换不改变对象；表单成为可选工具。 |
| 2. 补齐单条完整流程 | 指定片段修改、项目自动补查授权、需求累计额度、连续步骤及真实浏览器闭环 | 一条讲话短视频与一条跨素材混剪分别通过完整对话验收。 |
| 后续 | 长历史增强、多条生成和批量导出及原 MVP 剩余任务 | 沿用已确认的业务边界扩大能力，继续完成完整 MVP 验收。 |

实施任务见 [开发任务](development-backlog.md)，验收见 [需求验收矩阵](requirements.md#统一自然语言交互验收2026-10-12-补充)和 [实施验收](implementation-plan.md)。第一轮交付必须覆盖指定片段修改，不能只把按钮换成聊天命令就宣告完成。

上传素材后的验收使用一个聊天输入框完成 **查找 → 生成 → 修改指定片段 → 预览 → 确认 → 导出**，不选择需求类型、证据来源、检索方式，不填写制作或澄清表单。使用人工可核对的素材验证证据、硬条件、局部修改范围、版本、实际可播放 MP4、权限及预算；允许文件选择、播放核查和下载等必要界面操作。
